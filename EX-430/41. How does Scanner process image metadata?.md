# How Does RHACS Scanner Process Image Metadata?

## 1. Overview

RHACS Scanner analyzes container images to identify vulnerabilities in the software packages contained within those images.

A simplified flow is:

```text
Container Registry
       |
       v
Image Metadata
       |
       v
RHACS Scanner
       |
       +---- Image configuration
       +---- OS information
       +---- Package information
       +---- Application dependencies
       |
       v
Package / Component Identification
       |
       v
Vulnerability Matching
       |
       v
RHACS Central
       |
       v
Security Findings
```

The important concept is:

> **Scanner first understands what an image contains and then maps the identified components to known vulnerability information.**

---

# 2. What Is Image Metadata?

Container image metadata describes how an image is constructed and executed.

Depending on the image format and scanner capabilities, relevant information can include:

* Image manifest
* Image configuration
* Image layers
* Operating-system information
* Installed packages
* Package versions
* Application dependencies
* Image architecture
* Environment information
* Entrypoint
* Command
* Labels
* Image digest

Example:

```text
Image:
registry.example.com/app/payment:1.5

Digest:
sha256:abcd...

OS:
Red Hat Enterprise Linux

Packages:
openssl       3.x
curl          8.x
glibc         2.x
python        3.x

Application dependencies:
requests
urllib3
```

Scanner uses this information to determine the software components that need vulnerability analysis.

---

# 3. Image Digest

The image digest is an important identifier.

Example:

```text
registry.example.com/app/payment@sha256:abcd1234...
```

A tag such as:

```text
payment:latest
```

can change over time.

A digest identifies a specific image content.

Conceptually:

```text
Image Tag
   |
   v
latest
   |
   +---- Image A
   |
   +---- Image B
   |
   +---- Image C
```

The digest instead identifies a specific image version.

For enterprise vulnerability tracking, the digest is therefore important for correlating findings with the exact image content.

---

# 4. Scanner Does Not Simply Scan the Image as a Binary File

A common misunderstanding is:

> "Scanner looks at the image and searches for CVE strings."

That is not how vulnerability scanning should be understood.

Scanner needs to determine the software components installed inside the image.

For example:

```text
Container Image
      |
      v
Filesystem
      |
      +-- /usr/bin
      +-- /usr/lib
      +-- /etc
      +-- Package databases
      |
      v
Installed Software
```

The scanner then identifies packages and versions.

---

# 5. Image Retrieval

The scanning process starts with access to the image.

For example:

```text
registry.example.com/project/web:1.2
```

The scanner may need to access the appropriate registry using configured credentials and connectivity.

Typical flow:

```text
RHACS
  |
  v
Image Reference
  |
  v
Registry
  |
  v
Manifest
  |
  v
Image Configuration / Layers
```

If the registry cannot be reached, image scanning can fail or produce incomplete results.

---

# 6. Image Manifest

The image manifest provides information about the image structure.

Conceptually:

```json
{
  "schemaVersion": 2,
  "config": "...",
  "layers": [
    "...",
    "...",
    "..."
  ]
}
```

The manifest helps identify:

* Image configuration
* Layer references
* Architecture
* Image content
* Image digest

Scanner uses this information to understand how to inspect the image.

---

# 7. Image Configuration

The image configuration contains metadata describing how the container should run.

Examples include:

```text
Entrypoint
Command
Environment variables
Working directory
User
Labels
Architecture
OS
```

For example:

```text
OS: linux
Architecture: amd64
User: 1001
WorkingDir: /app
Entrypoint: /app/start.sh
```

This information is useful for understanding image characteristics, although vulnerability identification primarily depends on identifying software components.

---

# 8. Image Layers

Container images are normally composed of multiple filesystem layers.

Example:

```text
Application Layer
-----------------
Python packages
Application files

Layer 3
-----------------
curl
openssl

Layer 2
-----------------
glibc
system libraries

Layer 1
-----------------
Base operating system
```

Scanner processes the image contents rather than treating each layer as an independent application.

The resulting package inventory represents the software available in the resulting image filesystem.

---

# 9. Operating System Detection

One of the first important tasks is determining the operating system represented by the image.

Examples include:

```text
Red Hat Enterprise Linux
CentOS Stream
Ubuntu
Debian
Alpine
Fedora
```

This matters because vulnerability applicability depends heavily on the operating-system distribution.

For example:

```text
Package:
openssl

Version:
3.x
```

The vulnerability status can differ depending on the operating-system vendor and package build.

Therefore:

```text
Package Name
      +
Package Version
      +
Operating System
      |
      v
Vulnerability Matching
```

---

# 10. Package Identification

Scanner identifies installed software packages.

For an RPM-based image, conceptual package information might look like:

```text
openssl
3.x
x86_64

glibc
2.x
x86_64

curl
8.x
x86_64
```

For Debian-based images:

```text
openssl
curl
libc6
python3
```

The scanner uses package-management metadata and filesystem information to identify installed components.

---

# 11. Package Version

The version of a package is critical.

Consider:

```text
openssl-3.x
```

Scanner needs more information than simply the package name.

It may need to identify:

```text
Name
Version
Release
Architecture
Distribution
```

Conceptually:

```text
Component Identity
       |
       +-- Name
       +-- Version
       +-- Release
       +-- Architecture
       +-- OS Distribution
```

This allows vulnerability matching to be more accurate.

---

# 12. Vendor Package Information

Enterprise Linux distributions frequently backport security fixes without changing the upstream software version in the way users might expect.

For example:

```text
Upstream Version:
1.2.x

Vendor Package:
1.2.x-release.el9
```

A package may therefore contain a vendor security fix even though the upstream version appears unchanged.

This is why vulnerability scanners must understand vendor package metadata rather than simply comparing upstream version numbers.

---

# 13. Application Dependency Detection

Modern container images can also contain application-level dependencies.

Examples:

```text
Python
Java
Node.js
Go
Ruby
PHP
```

Example:

```text
Python application
       |
       +-- requests
       +-- urllib3
       +-- flask
```

Scanner can use available package/dependency information to identify components that may have known vulnerabilities.

---

# 14. Software Component Inventory

After processing the image, Scanner builds an inventory.

Example:

```text
Image
 |
 +-- OS: RHEL
 |
 +-- RPM
 |    +-- openssl
 |    +-- curl
 |    +-- glibc
 |
 +-- Python
      +-- requests
      +-- urllib3
```

This inventory is the foundation for vulnerability analysis.

---

# 15. Vulnerability Matching

Once components have been identified, Scanner compares them with vulnerability intelligence.

Conceptually:

```text
Image Component
      |
      v
Component Identity
      |
      v
Vulnerability Database
      |
      v
Matching
      |
      v
CVE / Vulnerability Finding
```

A finding may contain information such as:

```text
CVE
Severity
Affected component
Installed version
Fixed version
Image
Cluster
Workload
```

---

# 16. Severity

Vulnerabilities are commonly categorized by severity.

For example:

```text
Critical
High
Medium
Low
```

RHACS can use vulnerability severity as one of the factors in:

* Risk analysis
* Policy evaluation
* Alerting
* Reporting
* Admission decisions

---

# 17. Fixed Version

Where vulnerability intelligence provides remediation information, RHACS can identify a version containing a fix.

Conceptually:

```text
Installed:
openssl 3.x-old

Vulnerability:
CVE-XXXX-XXXXX

Fixed:
openssl 3.x-new
```

This gives application teams actionable remediation information.

---

# 18. Scanner and Central

Scanner and Central have different responsibilities.

A simplified architecture is:

```text
             RHACS Central
                  |
        +---------+---------+
        |                   |
        v                   v
   Scanner              Scanner DB /
                        Vulnerability
                         Intelligence
```

Central provides the management and security-visibility layer.

Scanner performs image analysis and component identification.

The exact Scanner deployment architecture can vary by RHACS version.


# 22. Image Metadata and Risk

Image metadata alone does not necessarily determine the final application risk.

RHACS can correlate image information with additional security information.

For example:

```text
Image Vulnerability
        |
        +-- Running in Production?
        |
        +-- Internet exposed?
        |
        +-- Runtime activity?
        |
        +-- Policy violation?
        |
        v
      Risk
```

Therefore, an image containing a vulnerability may have different operational significance depending on where and how it is deployed.

---

# 23. Scanner and Admission Control

Scanner results can participate in admission-control decisions when RHACS policies are configured for this purpose.

Example:

```text
Developer
    |
    v
Deploy Image
    |
    v
Admission Controller
    |
    v
RHACS Security Policy
    |
    v
Image Vulnerability Evaluation
    |
    +---- Allowed
    |
    +---- Denied
```

For example, an enterprise might define a policy that prevents deployment of images containing critical vulnerabilities.

Admission enforcement should be introduced carefully to avoid blocking legitimate workloads unexpectedly.

# 25. Metadata Is Not the Same as Vulnerability Intelligence

It is important to distinguish:

```text
Image Metadata
       |
       v
What is inside the image?
```

from:

```text
Vulnerability Intelligence
       |
       v
Which known security issues affect those components?
```

The scanner combines these two areas:

```text
Image Component Inventory
          +
Vulnerability Intelligence
          |
          v
Security Findings
```

---

# 26. Why Accurate Metadata Matters

Incorrect or incomplete metadata can affect vulnerability results.

For example:

```text
Incorrect OS detection
        |
        v
Incorrect package mapping
        |
        v
Incorrect vulnerability applicability
```

Similarly:

```text
Incomplete package inventory
        |
        v
Potentially incomplete vulnerability results
```

Therefore, image construction and package metadata quality are important to reliable scanning.

# 27. Common Image Scanning Problems

## Registry inaccessible

Symptoms:

```text
Image scan unavailable
Registry authentication errors
Timeouts
Connection failures
```

Check:

```bash
oc get secret -n stackrox
oc get pods -n stackrox
```

Also verify registry connectivity and credentials.

---

## Unsupported or unusual image

Some images may provide insufficient package metadata.

Examples include:

* Minimal images
* Distroless images
* Custom-built images
* Scratch-based images
* Unusual package layouts

The resulting scan may have limited component information.

---

## Scanner pod failure

Check:

```bash
oc get pods -n stackrox
```

Then:

```bash
oc describe pod <scanner-pod> -n stackrox
oc logs <scanner-pod> -n stackrox
```

Investigate:

* Image pull errors
* Resource exhaustion
* Storage problems
* Network connectivity
* Configuration errors
* Certificate problems

# 31. Important Interview Explanation

If asked:

> **How does RHACS Scanner process image metadata?**

A strong answer is:

> RHACS Scanner first obtains the image manifest and configuration and analyzes the image filesystem and layers. It identifies the operating system, installed packages, package versions, and applicable application dependencies. It builds a software-component inventory and correlates those components with vulnerability intelligence to identify applicable CVEs and severity information. The resulting vulnerability data is made available through RHACS Central and can be associated with workloads, clusters, risk analysis, policies, and admission controls.

---

RHACS Scanner's core workflow is:

```text
Image
  |
  v
Metadata
  |
  v
Manifest + Configuration + Layers
  |
  v
OS / Package / Dependency Identification
  |
  v
Component Inventory
  |
  v
Vulnerability Matching
  |
  v
Security Findings
  |
  v

```

The key principle is:

> **Scanner converts container image contents and metadata into a software-component inventory, then uses vulnerability intelligence to determine which known vulnerabilities apply to those components.**
