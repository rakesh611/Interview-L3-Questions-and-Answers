# How to Configure Central Database Storage in RHACS

## 1. Overview

RHACS Central requires persistent storage for its database and other persistent data.

When Central is deployed by the RHACS Operator, storage is configured through the `Central` custom resource rather than manually managing the database Deployment or PVC.

The general architecture is:

```text
Central Custom Resource
        |
        v
RHACS Operator
        |
        v
Central Database
        |
        v
Persistent Volume Claim (PVC)
        |
        v
StorageClass
        |
        v
Persistent Volume (PV)
        |
        v
Storage Backend
```

The storage backend may be based on technologies such as:

* OpenShift Data Foundation/Ceph
* LVM Storage
* Cloud block storage
* Other supported CSI storage

---

# 2. Why Persistent Database Storage Is Required

Central stores persistent RHACS data.

If the database were stored only on the container filesystem:

```text
Central Pod
    |
    v
Container filesystem
```

data could be lost when the pod is deleted or recreated.

Persistent storage changes the architecture to:

```text
Central Pod
    |
    v
PVC
    |
    v
PV
    |
    v
Persistent Storage
```

The pod can therefore be recreated while the persistent storage remains available.

---

# 3. Prerequisites

Before configuring Central database storage, verify:

* RHACS Operator is installed.
* The `stackrox` namespace exists.
* A supported StorageClass is available.
* The StorageClass can dynamically provision persistent volumes.
* The storage backend has sufficient capacity.
* The Central CR exists or is ready to be created.

Check the namespace:

```bash
oc get namespace stackrox
```

Check StorageClasses:

```bash
oc get storageclass
```

Example:

```text
NAME                 PROVISIONER
lvms-vg1             topolvm.io
ocs-storagecluster   openshift-storage.rbd.csi.ceph.com
```

---

# 4. Identify the StorageClass

Before configuring Central storage, identify the StorageClass that should provide the database storage.

For example:

```bash
oc get storageclass
```

Inspect a StorageClass:

```bash
oc describe storageclass lvms-vg1
```

Important information includes:

* Provisioner
* Reclaim policy
* Volume binding mode
* Allowed topologies
* Expansion support

Example:

```text
Provisioner: topolvm.io
Reclaim Policy: Delete
VolumeBindingMode: WaitForFirstConsumer
```

The exact values depend on your storage platform.

---

# 5. Configure Storage in the Central CR

The RHACS Operator exposes Central storage configuration through the `Central` custom resource.

The exact storage fields are **version-dependent**, so first inspect the CRD installed in your cluster:

```bash
oc explain central.spec
```

You can also inspect the CRD:

```bash
oc get crd centrals.platform.stackrox.io -o yaml
```

For the installed RHACS release, use the storage configuration supported by that CRD.

A conceptual configuration looks like:

```yaml
apiVersion: platform.stackrox.io/v1alpha1
kind: Central
metadata:
  name: stackrox-central-services
  namespace: stackrox
spec:
  central:
    persistence:
      persistentVolumeClaim:
        claimName: central-db
```

**Important:** Do not copy storage fields blindly between RHACS releases. The exact `Central` CR schema can change between versions.

---

# 6. Recommended Approach

For a production deployment, use a supported RHACS storage configuration and an appropriate StorageClass.

Conceptually:

```text
Central CR
    |
    | storage configuration
    v
RHACS Operator
    |
    v
PVC
    |
    | storageClassName
    v
StorageClass
    |
    v
CSI Provisioner
    |
    v
PV
```

The Operator reconciles the required RHACS resources.

# 7. Verify the Central CR

After applying the Central configuration:

```bash
oc apply -f central.yaml
```

Check:

```bash
oc get central -n stackrox
```

Then:

```bash
oc describe central stackrox-central-services -n stackrox
```

Check the Central status for conditions indicating whether the deployment is progressing normally.

---

# 8. Verify the Database PVC

After the Operator reconciles the configuration:

```bash
oc get pvc -n stackrox
```

Example:

```text
NAME         STATUS   VOLUME       CAPACITY
central-db   Bound    pvc-xxxxx    100Gi
```

The important state is:

```text
STATUS: Bound
```

If the PVC remains:

```text
Pending
```

the storage provisioning path must be investigated.

---

# 9. Inspect the PVC

Use:

```bash
oc describe pvc central-db -n stackrox
```

Check:

* StorageClass
* Requested capacity
* Access mode
* Volume
* Events
* Provisioning errors

Example:

```text
Name:          central-db
Namespace:     stackrox
StorageClass:  lvms-vg1
Status:        Bound
Volume:        pvc-xxxxxxxx
Capacity:      100Gi
```

---

# 10. Verify the PV

Once the PVC is bound:

```bash
oc get pv
```

Find the PV associated with the Central PVC.

Then:

```bash
oc describe pv <pv-name>
```

Verify:

```text
Status: Bound
Claim: stackrox/central-db
StorageClass: lvms-vg1
Capacity: 100Gi
```

The relationship is:

```text
PVC central-db
      |
      v
PV pvc-xxxx
      |
      v
StorageClass lvms-vg1
      |
      v
LVM/CSI Storage
```

# 12. Storage Size

The database storage capacity should be selected based on:

* Number of secured clusters
* Number of workloads
* Number of images
* Vulnerability data
* Compliance data
* Retention requirements
* RHACS deployment scale
* Expected growth

Do not select storage capacity solely based on the current database size.

For production, plan for growth and monitor utilization.

Check PVC capacity:

```bash
oc get pvc -n stackrox
```

---

# 13. Storage Expansion

If the StorageClass supports volume expansion, storage can potentially be increased without recreating the application.

Check whether expansion is supported:

```bash
oc describe storageclass <storage-class>
```

Look for:

```text
AllowVolumeExpansion: true
```

The exact RHACS procedure for resizing its database storage should follow the supported RHACS documentation for the installed version.

Do not manually resize the underlying database filesystem without understanding the RHACS and storage-layer requirements.

---

# 14. Do Not Manually Delete the Database PVC

Avoid commands such as:

```bash
oc delete pvc central-db -n stackrox
```

unless you are deliberately performing a supported recovery, migration, or reinstallation procedure.

Deleting the PVC can result in loss of persistent RHACS data depending on:

* Storage backend
* Reclaim policy
* Backup configuration
* Database architecture
* RHACS version

The PVC should be treated as critical persistent application data.

---

# 15. StorageClass Reclaim Policy

Check:

```bash
oc get storageclass <storage-class> -o yaml
```

Look for:

```yaml
reclaimPolicy: Delete
```

or:

```yaml
reclaimPolicy: Retain
```

### Delete

When the associated PV is released, the storage backend may be deleted according to the provisioner's behavior.

### Retain

The underlying volume is retained for administrative recovery.

For critical production systems, understand the organization's storage and backup policy before selecting the StorageClass.

---

# 16. Database Storage and Backup

Persistent storage is **not the same thing as backup**.

This is important.

```text
PVC
 |
 v
Persistent Database Storage
```

protects against certain pod/container failures.

It does not automatically protect against:

* Accidental deletion
* Database corruption
* Storage failure
* Operator/configuration mistakes
* Cluster-wide disaster
* Ransomware
* Site failure

A production RHACS environment should have an appropriate RHACS backup/recovery strategy.

The architecture should therefore be:

```text
                  RHACS Central
                       |
                       v
                Persistent Storage
                       |
                       v
                 Backup Strategy
                       |
             +---------+---------+
             |                   |
             v                   v
          Local                 Remote
         Backup                Backup
```

# 19. Troubleshooting PVC Pending

If the PVC remains Pending:

```bash
oc get pvc -n stackrox
```

Then:

```bash
oc describe pvc <pvc-name> -n stackrox
```

Look at the Events section.

Common causes include:

* StorageClass does not exist.
* CSI provisioner is unavailable.
* No storage capacity.
* Topology constraints.
* LVM volume group has insufficient space.
* Ceph cluster is unhealthy.
* Incorrect storage configuration.
* Storage backend permissions/configuration problems.

---

# 23. Production Design

A production RHACS database-storage design should consider:

### Capacity

Provide enough capacity for current and future RHACS data.

### Performance

Use storage with suitable IOPS and latency.

### Availability

Understand the storage platform's availability characteristics.

### Backup

Implement regular backups appropriate to the RHACS deployment.

### Recovery

Test restoration procedures rather than assuming backups are usable.

### Monitoring

Monitor:

* PVC capacity
* Storage latency
* Storage backend health
* Database health
* Central pod health

---

# 24. Important Operator Principle

The RHACS Operator follows the Kubernetes Operator model.

The administrator defines desired state:

```text
Central CR
    |
    v
Desired RHACS configuration
```

The Operator creates and reconciles resources:

```text
RHACS Operator
    |
    +--> Central
    +--> Database
    +--> Services
    +--> PVC
    +--> Other supporting resources
```

The storage platform handles the actual persistent volume:

```text
PVC
 |
 v
CSI
 |
 v
PV
 |
 v
Storage Backend
```

Therefore, RHACS and OpenShift storage have different responsibilities.

---

# 25. RHACS vs OpenShift Storage Responsibilities

| Component              | Responsibility                            |
| ---------------------- | ----------------------------------------- |
| RHACS Central CR       | Defines RHACS desired configuration       |
| RHACS Operator         | Creates/reconciles RHACS resources        |
| Central                | Uses persistent database storage          |
| PVC                    | Requests persistent storage               |
| StorageClass           | Defines how storage is provisioned        |
| CSI Driver             | Performs storage provisioning/attachment  |
| PV                     | Represents provisioned persistent storage |
| Ceph/LVM/Cloud storage | Provides actual storage capacity          |

## Key Takeaways

1. **Configure Central storage through the supported RHACS `Central` CR schema.**
2. **Do not assume storage field names are identical across RHACS versions.**
3. **Use a supported OpenShift StorageClass for persistent storage.**
4. **Verify that the Central database PVC becomes `Bound`.**
5. **A PVC is persistent storage, not a backup.**
6. **Do not delete or manually modify the database PVC without a supported recovery/migration plan.**
7. **Monitor both RHACS and the underlying storage platform.**
8. **For production, plan capacity, performance, availability, backup, and disaster recovery.**

The key relationship to remember is:

```text
Central CR
    |
    v
RHACS Operator
    |
    v
PVC
    |
    v
StorageClass
    |
    v
CSI
    |
    v
PV
    |
    v
Persistent Storage
```
