# How Do Declarative Resources and RHACS API Objects Differ?

## Overview

In an RHACS environment, you may encounter two different concepts:

1. **Declarative resources** — Kubernetes/OpenShift resources that describe the desired state of the cluster.
2. **RHACS API objects** — objects exposed by the RHACS API that represent security configuration, policies, deployments, findings, and other RHACS-managed information.

The most important distinction is:

```text
Kubernetes/OpenShift Declarative Resource
        =
"Desired state of the cluster"

RHACS API Object
        =
"Security data/configuration exposed through RHACS APIs"
```

RHACS also provides Kubernetes-native integration for some configuration through resources such as **RHACS custom resources**, depending on the RHACS version and feature being used. Therefore, "declarative" and "API object" are not mutually exclusive concepts.

---

# 1. What Is a Declarative Resource?

Kubernetes uses a **declarative model**.

You describe what you want:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
spec:
  replicas: 3
```

You are telling Kubernetes:

> "I want three replicas of this Deployment."

Kubernetes controllers continuously work toward that desired state.

The model is:

```text
              YAML
               │
               ▼
        Desired State
               │
               ▼
        Kubernetes API
               │
               ▼
          Controllers
               │
               ▼
         Actual State
               │
               ▼
       Reconciliation
```

# 2. Examples of Declarative Resources

Common OpenShift/Kubernetes resources include:

```text
Deployment
StatefulSet
DaemonSet
Service
ConfigMap
Secret
Route
Ingress
NetworkPolicy
Role
RoleBinding
ServiceAccount
PersistentVolumeClaim
Namespace
Custom Resource
```

Example:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: payment-api
spec:
  selector:
    app: payment
  ports:
  - port: 8080
```

This is a declarative resource.

---

# 3. Declarative Means Desired State

Consider:

```yaml
spec:
  replicas: 5
```

This means:

```text
Desired replicas = 5
```

If only three pods are running:

```text
Desired = 5
Actual  = 3
```

Kubernetes controllers attempt to reconcile the difference:

```text
Desired = 5
Actual  = 3
        │
        ▼
Controller
        │
        ▼
Create 2 additional Pods
        │
        ▼
Actual = 5
```

This reconciliation model is fundamental to Kubernetes.

# 4. What Is an RHACS API Object?

RHACS exposes APIs for interacting with its security platform.

An RHACS API object can represent information such as:

```text
Security Policies
Clusters
Deployments
Images
Vulnerabilities
Nodes
Namespaces
Alerts
Compliance information
Security configuration
```

These objects are primarily exposed through RHACS APIs and are consumed by clients, automation, integrations, and applications.

Conceptually:

```text
Client
   │
   ▼
RHACS API
   │
   ▼
RHACS Central
   │
   ├── Security Policies
   ├── Alerts
   ├── Vulnerabilities
   ├── Cluster information
   └── Workload information
```

# 5. Kubernetes API vs RHACS API

There are therefore two important API domains.

```text
┌──────────────────────────────┐
│ Kubernetes / OpenShift API   │
├──────────────────────────────┤
│ Deployment                   │
│ Service                      │
│ Pod                          │
│ ConfigMap                    │
│ Secret                       │
│ NetworkPolicy                │
│ Route                        │
│ RBAC                         │
│ Custom Resources             │
└──────────────────────────────┘


┌──────────────────────────────┐
│ RHACS API                    │
├──────────────────────────────┤
│ Security Policies            │
│ Alerts                       │

│ Images                       │
```

The APIs serve different purposes.

# 6. Important: RHACS API Objects Are Not the Same as Kubernetes Objects

Suppose you have:

```text
Deployment:
payment-api
```

The Deployment is a Kubernetes/OpenShift resource.

RHACS can analyze that deployment and expose security information about it through its API.

For example:

```text
Kubernetes:

Deployment
payment-api
```

RHACS might provide:

```text
RHACS:

Deployment security information
Image vulnerabilities
Policy violations
Risk
Runtime information
```

The RHACS representation does not replace the original Kubernetes Deployment.

RHACS analyzes the resulting workload.

Conceptually:

```text

    │
    ▼

    │
    ├── Image vulnerabilities
    ├── Security policies
    ├── Risk
```

# 8. Declarative Resource Lifecycle

A Kubernetes declarative resource normally follows:

```text
YAML
 │
 ▼
kubectl / oc apply
 │
 ▼
Kubernetes API Server
 │
 ▼
etcd
 │
 ▼
Controller
 │
 ▼
Actual cluster state
```

Example:

```bash
oc apply -f deployment.yaml
```

The desired state is stored in Kubernetes.

---

# 9. RHACS API Object Lifecycle

An RHACS API operation follows a different path.

Conceptually:

```text
Client
  │
  ▼
RHACS API
  │
  ▼
RHACS Central
  │
  ▼
RHACS Data / Configuration
```

For example, an automation tool may use the RHACS API to:

```text
Create security policy
Update policy
Retrieve alerts
Retrieve vulnerability information
Query cluster information
Retrieve security data
```

The RHACS API is therefore primarily an interface to RHACS functionality and data.

---

# 10. Declarative Resource vs API Object

| Feature          | Kubernetes/OpenShift Declarative Resource | RHACS API Object                     |
| ---------------- | ----------------------------------------- | ------------------------------------ |
| Primary platform | Kubernetes/OpenShift                      | RHACS                                |
| Main purpose     | Desired cluster state                     | Security platform data/configuration |
| Typical format   | YAML/JSON                                 | JSON/API payloads                    |
| Managed by       | Kubernetes API/controllers                | RHACS Central/API                    |
| Reconciliation   | Core Kubernetes concept                   | Depends on RHACS feature             |
| Stored in        | Kubernetes API data store                 | RHACS Central's data/configuration   |
| Example          | Deployment                                | Security Policy                      |
| Example          | Service                                   | Alert                                |
| Example          | NetworkPolicy                             | Vulnerability                        |
| Example          | ConfigMap                                 | RHACS cluster information            |
| Main interface   | `kubectl` / `oc`                          | RHACS REST/gRPC APIs and clients     |
| Cluster state    | Yes                                       | Security view of cluster state       |

# 13. Declarative Resources Are Usually Desired State

A key word is:

> **Desired state**

Example:

```yaml
spec:
  replicas: 5
```

This is an instruction describing the state you want.

Kubernetes controllers continuously reconcile:

```text
Desired State
      │
      ▼
Controller
      │
      ▼
Actual State
```

---

# 14. RHACS API Objects Can Represent Observed State

Many RHACS API responses represent information that RHACS has observed or calculated.

For example:

```text
Cluster
    │
    ├── Cluster name
    ├── OpenShift version
    ├── Nodes
    ├── Workloads
    ├── Vulnerabilities
    └── Security findings
```

This is not necessarily something you declare as the desired state of the Kubernetes cluster.

Instead, RHACS is telling you:

> "This is the security information I know about this environment."

---

# 15. Example: Vulnerability

Suppose an application is running:

```text
image:
payment:v10
```

RHACS discovers:

```text
CVE:
CVE-XXXX

Severity:
CRITICAL

Fix available:
Yes
```

This information is an RHACS security finding.

You would not normally create a Kubernetes Deployment like:

```yaml
kind: Vulnerability
```

and expect Kubernetes to manage it.

Instead, RHACS exposes vulnerability information through its security APIs and UI.

---

# 16. Example: Security Policy

Security policies are an important RHACS object.

Conceptually:

```text
RHACS Policy
     │
     ├── Name
     ├── Severity
     ├── Lifecycle stages
     ├── Categories
     ├── Conditions
     └── Enforcement behavior
```

For example:

```text
Policy:
Prevent privileged containers

Severity:
HIGH

Stage:
Deploy

Condition:
privileged = true
```

This policy belongs to the RHACS security domain.

It is not the same thing as a Kubernetes `Deployment`, `Service`, or `NetworkPolicy`.

---

# 17. RHACS Security Policy vs Kubernetes NetworkPolicy

These two names can be confusing.

### Kubernetes NetworkPolicy

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
```

It controls network traffic between workloads.

```text
Pod A ───── allowed ─────► Pod B
```

### RHACS Security Policy

RHACS security policies describe security conditions that should generate violations or be enforced at appropriate lifecycle stages.

```text
Security condition
       │
       ▼
RHACS Policy
       │
       ├── Alert
       └── Enforcement
```

They are completely different concepts.

---

# 18. RHACS Custom Resources

RHACS also provides Kubernetes-native integration for certain configuration and lifecycle operations through custom resources in supported versions/features.

This is an important nuance.

A Custom Resource is itself a Kubernetes API object:

```text
apiVersion
kind
metadata
spec
status
```

For example, conceptually:

```yaml
apiVersion: example.security.redhat.com/v1
kind: SecurityConfiguration
metadata:
  name: example
spec:
  ...
```

If RHACS provides a supported CRD for a particular feature, then that RHACS configuration can be managed declaratively through Kubernetes.

Therefore:

```text
RHACS API object
```

and

```textDeclarative resource
```

are not always mutually exclusive.

A RHACS custom resource can be:

```text
Kubernetes API Object
        +
Declarative Resource
        +
RHACS-specific configuration
```

The exact CRDs and supported fields depend on the RHACS version and feature.

# 19. Three Concepts You Should Not Mix Up

There are actually three useful categories to understand.

```text
                    API Objects
                        │
             ┌──────────┴──────────┐
             ▼                     ▼
       Kubernetes Objects      RHACS API Objects
             │                     │
             │                     │
       Deployment              Security Policy
       Service                 Vulnerability
       ConfigMap               Alert
       Secret                  Cluster data
       NetworkPolicy           Risk information
             │
             ▼
      Declarative model
```

And RHACS may also expose:

```text
RHACS Custom Resources
        │
        ▼
Kubernetes API
        │
        ▼

```

# 24. Why This Difference Matters

If you confuse these concepts, you may attempt something like:

```bash
oc apply -f rhacs-alert.yaml
```

assuming an RHACS API response is a Kubernetes resource.

That normally does not work because an API response is not automatically a Kubernetes CRD.

The correct approach depends on what you are trying to do:

```text
Want to create Kubernetes state?
        │
        ▼
Use Kubernetes/OpenShift resource
        │
        ▼
oc apply / GitOps


Want to query RHACS security data?
        │
        ▼
Use RHACS API


Want declarative RHACS configuration?
        │
        ▼
Use a supported RHACS CRD/GitOps mechanism,
when available
```

# 27. Important Interview Point

Do not say:

> "RHACS API objects are not declarative."

That statement is too broad.

A better answer is:

> "Kubernetes declarative resources describe desired state and are reconciled by Kubernetes controllers. RHACS API objects represent RHACS-specific security data and configuration exposed through RHACS APIs. Some RHACS configuration can also be represented as Kubernetes custom resources and managed declaratively, depending on the supported RHACS feature and version."

This is the technically safer answer.

---

# 28. Interview Question

### How do declarative resources and RHACS API objects differ?

### Answer

Kubernetes/OpenShift declarative resources describe the **desired state of the cluster**, such as Deployments, Services, NetworkPolicies, ConfigMaps, and Secrets. They are submitted to the Kubernetes API and reconciled by controllers.

RHACS API objects represent **RHACS-specific security information and configuration**, such as security policies, alerts, vulnerabilities, cluster information, and other security data. They are exposed through the RHACS API and are primarily consumed by RHACS clients and automation.

However, RHACS also supports Kubernetes-native custom resources for certain features. When such a CRD is available, RHACS configuration can be managed declaratively through Kubernetes and GitOps.

Therefore:

```text
Kubernetes Declarative Resource
    =
Desired cluster state

RHACS API Object
    =
RHACS security data/configuration

RHACS Custom Resource
    =
RHACS-specific Kubernetes object
    that may provide declarative management
```

---

# 29. One-Line Interview Answer

> **Kubernetes declarative resources describe desired cluster state and are reconciled by Kubernetes controllers, while RHACS API objects expose RHACS-specific security data and configuration; supported RHACS custom resources can bridge the two by allowing certain RHACS configuration to be managed declaratively through Kubernetes/GitOps.**
