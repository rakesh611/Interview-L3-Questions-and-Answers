# How Do Disconnected Clusters Affect RHACS Architecture?

## Overview

A **disconnected cluster** is a Kubernetes/OpenShift cluster that does not have normal direct access to the Internet or to external services.

In an RHACS environment, this changes the architecture because RHACS components must operate within controlled network boundaries, and security data must be exchanged through an approved connectivity path.

A connected architecture may look like:

```text
Internet / Corporate Network
           |
           v
      RHACS Central
           |
     +-----+-----+
     |     |     |
     v     v     v
   OCP1  OCP2  OCP3
```

A disconnected architecture may look like:

```text
                  Corporate Security Network
                           |
                           v
                     RHACS Central
                           |
                     Approved Path
                           |
                  +--------+--------+
                  |                 |
                  v                 v
             Disconnected       Disconnected
              Cluster A          Cluster B
                  |                 |
               Sensor            Sensor
                  |                 |
              Collector         Collector
                  |                 |
             Applications      Applications
```

The important point is:

> **Disconnected operation changes network connectivity, image delivery, update strategy, certificate management, vulnerability data availability, and RHACS deployment design.**

---

# 1. What Does "Disconnected" Mean?

Disconnected does not always mean that a cluster has absolutely no network connectivity.

There are several common models.

## Fully Air-Gapped

```text
Internet
   X
   |
   X
Cluster
```

The cluster has no external network access.

## Restricted Network

```text
Internet
   |
 Firewall
   |
 Proxy / Gateway
   |
 Cluster
```

The cluster has controlled access to specific services.

## Connected to Central but Not Internet

```text
Internet
    X
    |
Corporate Network
    |
    v
RHACS Central
    |
    v
Secured Cluster
```

This is particularly important for RHACS.

A cluster may be **disconnected from the Internet but still connected to RHACS Central** through an internal corporate network.

---

# 2. The First Architectural Question

Before designing RHACS for disconnected clusters, determine:

> **Where will RHACS Central run, and how will the secured cluster communicate with it?**

Possible architectures include:

### Model A — Central Outside the Disconnected Zone

```text
             Corporate Network
                    |
              RHACS Central
                    |
              Firewall / DMZ
                    |
                    v
          Disconnected Network
                    |
                    v
             Secured Cluster
```

### Model B — Central Inside the Restricted Network

```text
Restricted Security Network
|
+-- RHACS Central
|
+-- Cluster A
+-- Cluster B
+-- Cluster C
```

### Model C — Separate RHACS Environment

```text
Connected Environment
|
+-- RHACS Central
+-- Connected Clusters


Disconnected Environment
|
+-- Separate RHACS Central
+-- Disconnected Clusters
```

The correct model depends on security boundaries, network connectivity, operational requirements, and RHACS support for the selected deployment/version.

---

# 3. Connected vs Disconnected Architecture

## Connected

```text
                  Internet
                     |
                     v
              RHACS Central
                     |
        +------------+------------+
        |            |            |
     Cluster A    Cluster B    Cluster C
```

The platform can normally access external registries and update sources according to organizational controls.

## Disconnected

```text
                  Internet
                     X
                     |
              Air-Gapped Zone
                     |
              RHACS Central
                     |
        +------------+------------+
        |                         |
     Cluster A                 Cluster B
```

Required artifacts must be brought into the environment through an approved process.

---

# 4. RHACS Central Placement Becomes Critical

In a disconnected environment, RHACS Central should generally be placed where all required secured clusters can reach it over the organization's approved network.

For example:

```text
                   Security Network
                          |
                    RHACS Central
                     /          \
                    /            \
                   v              v
            Production A     Production B
            Disconnected     Disconnected
                Cluster          Cluster
```

If Sensor cannot reach Central, the secured cluster cannot provide normal communication with Central.

Therefore, network architecture must be designed before RHACS installation.

---

# 5. Sensor Connectivity

The RHACS Sensor runs inside each secured cluster.

A simplified architecture is:

```text
Disconnected Cluster
|
+-- Sensor
|     |
|     | Secure connection
|     v
|   RHACS Central
|
+-- Collector
|
+-- Admission Controller
|
+-- Applications
```

The disconnected cluster does **not necessarily need direct Internet access** for Sensor-to-Central communication.

It needs the required connectivity to the RHACS Central endpoint.

---

# 6. Internet Disconnected Does Not Mean RHACS Disconnected

This distinction is extremely important.

Consider:

```text
Internet
   X
   |
Corporate Network
   |
   v
RHACS Central
   |
   v
OpenShift Cluster
```

The OpenShift cluster has no Internet access.

However, Sensor can still communicate with RHACS Central.

Therefore:

> **Internet isolation and RHACS Central isolation are two different architectural problems.**

---

# 7. If the Cluster Cannot Reach Central

If the disconnected cluster cannot communicate with Central:

```text
Disconnected Cluster
        |
      Sensor
        |
        X
        |
RHACS Central
```

Central cannot receive normal information from that secured cluster.

This affects centralized:

* Visibility
* Monitoring
* Policy management
* Findings
* Runtime information
* Cluster status

The exact behavior during connectivity loss depends on the RHACS components and configuration involved.

Therefore, a completely isolated cluster may require a different RHACS architecture rather than simply deploying the normal connected-cluster model.

---

# 8. Multiple Disconnected Clusters

Suppose an organization has:

```text
                    RHACS Central
                         |
             +-----------+-----------+
             |                       |
             v                       v
       Restricted Zone A       Restricted Zone B
             |                       |
       +-----+-----+             +---+---+
       |           |             |       |
      OCP1        OCP2          OCP3    OCP4
```

Each secured cluster requires the necessary RHACS components and network path.

The security architecture must consider:

* Network segmentation
* Firewall rules
* DNS
* TLS
* Certificates
* Routing
* Proxies
* Load balancing
* Central availability

---

# 9. Air-Gapped Architecture

A fully air-gapped environment may look like:

```text
                         Internet
                            X
                            |
                     Physical / Logical
                     Security Boundary
                            |
                            v
                  Air-Gapped Network
                            |
                  +---------+---------+
                  |                   |
                  v                   v
             RHACS Central       Image Registry
                  |                   |
          +-------+-------+           |
          |               |           |
          v               v           |
       OCP-1           OCP-2 <--------+
```

The organization must provide internal sources for artifacts that would otherwise come from the Internet.

---

# 10. Image Registry Becomes More Important

Disconnected OpenShift environments generally cannot pull container images directly from public registries.

For example:

```text
Public Registry
      |
      X
      |
Internet
      X
      |
Disconnected Cluster
```

Instead, organizations commonly use an internal registry:

```text
External Registry
       |
 Approved Transfer
       |
       v
Internal Registry
       |
       v
Disconnected Cluster
```

For RHACS, the required RHACS-related images must also be available through the supported disconnected installation process.

---

# 11. Image Mirroring

A disconnected architecture commonly requires image mirroring.

Conceptually:

```text
Connected Environment
|
+-- Red Hat Registry
+-- RHACS Images
+-- OpenShift Images
|
v
Mirror / Transfer Process
|
v
Disconnected Registry
|
v
Disconnected OpenShift
```

The transfer process must follow organizational security controls.

---

# 12. RHACS Image Availability

RHACS itself consists of container images.

A disconnected deployment therefore needs access to the required RHACS images.

Conceptually:

```text
Connected Registry
       |
       v
Image Mirror
       |
       v
Disconnected Registry
       |
       +--> Central
       +--> Sensor
       +--> Collector
       +--> Admission Controller
```

The exact image mirroring procedure depends on the RHACS release and supported Red Hat disconnected-installation process.

---

# 13. Collector Considerations

Collector runs inside the secured cluster.

Therefore:

```text
Disconnected Cluster
|
+-- Collector
|
+-- Sensor
|
+-- Applications
```

Collector's local operation should be considered independently from external Internet connectivity.

However, the overall security architecture must account for how collected information reaches Central and how required software updates are delivered.

---

# 14. Admission Controller in Disconnected Clusters

Admission Controller operates close to the Kubernetes/OpenShift API.

For example:

```text
Developer
    |
    v
OpenShift API
    |
    v
RHACS Admission Controller
    |
    v
Security Policy
    |
 +--+--+
 |     |
Allow  Deny
```

This is useful in disconnected environments because deployment-time security enforcement can occur locally.

The workload does not need to contact the public Internet simply to be evaluated by the admission control path.

---

# 15. Local Enforcement Is Important

Disconnected environments often have strict security requirements.

Therefore, security controls should not depend unnecessarily on external services.

A desirable architecture is:

```text
                    Disconnected Cluster
                           |
                +----------+----------+
                |          |          |
                v          v          v
             Sensor    Collector   Admission
                                      |
                                      v
                              Local Enforcement
```

Central provides centralized management where connectivity exists, while enforcement components operate within the secured environment.

---

# 16. Vulnerability Data Becomes a Major Concern

RHACS vulnerability management depends on vulnerability information.

In a connected environment:

```text
RHACS
  |
  v
Current vulnerability information
```

In a disconnected environment:

```text
Internet
   X
   |
Disconnected RHACS
```

The organization must have a supported mechanism for keeping vulnerability data current.

This is a major operational consideration.

---

# 17. Vulnerability Feed Updates

A simplified disconnected workflow is:

```text
External Environment
       |
       v
Updated Vulnerability Data
       |
       v
Approved Transfer
       |
       v
Disconnected Security Environment
       |
       v
RHACS
       |
       v
Updated Vulnerability Analysis
```

The exact mechanism depends on the RHACS version and supported disconnected deployment architecture.

Do not assume that a disconnected RHACS deployment can automatically retrieve Internet-based vulnerability information.

---

# 18. Update and Upgrade Strategy

Connected environments may use normal update mechanisms.

Disconnected environments require an artifact-transfer process.

For example:

```text
RHACS Release
      |
      v
Connected Staging
      |
      +--> Validate
      +--> Security Scan
      +--> Approve
      |
      v
Transfer
      |
      v
Disconnected Registry
      |
      v
Disconnected RHACS
```

The same principle applies to required OpenShift and supporting images.

---

# 19. Certificate Management

Disconnected networks make certificate management especially important.

The architecture may include:

```text
Internal CA
   |
   +--> RHACS Central
   |
   +--> Sensor
   |
   +--> Collector-related endpoints
   |
   +--> Admission Controller
```

You must plan:

* Certificate issuance
* CA trust
* Certificate rotation
* DNS names
* Internal endpoints
* Expiration monitoring

A certificate expiration can break communication even when the network itself is healthy.

---

# 20. DNS Architecture

Disconnected environments often use internal DNS.

Example:

```text
Internal DNS
|
+-- rhacs-central.security.example
+-- registry.security.example
+-- api.cluster1.example
+-- apps.cluster1.example
```

The RHACS components must resolve the required internal names.

A common troubleshooting path is:

```bash id="9i5c3r"
nslookup rhacs-central.example.com
```

or:

```bash id="4a8mtc"
dig rhacs-central.example.com
```

DNS must work from the relevant network location.

---

# 21. Firewall Architecture

Only required connections should be allowed.

Conceptually:

```text
Disconnected Cluster
        |
        | Required RHACS traffic
        v
     Firewall
        |
        v
 RHACS Central
```

Do not simply allow unrestricted traffic between networks.

The exact ports and protocols should be taken from the RHACS documentation for the installed release.

---

# 22. Proxy Architecture

Some organizations use an internal proxy instead of completely removing outbound connectivity.

Example:

```text
Disconnected/Restricted Cluster
          |
          v
       Proxy
          |
          v
 Approved External Services
```

This is different from a fully air-gapped architecture.

A proxy-based design can simplify some external access requirements but must comply with organizational security controls.

---

# 23. Central Inside the Air-Gapped Zone

One common design is:

```text
              Corporate Security Boundary
                         |
                +--------+--------+
                |                 |
                v                 v
           RHACS Central     Internal Registry
                |
        +-------+-------+
        |               |
        v               v
      OCP-1           OCP-2
```

Advantages:

* Low latency
* Simple internal communication
* Central remains close to secured clusters
* No direct Internet requirement

The organization still needs an approved mechanism for bringing software and security data into the environment.

---

# 24. Separate RHACS Central for Highly Isolated Zones

In some organizations, the security boundary may be so strong that a disconnected environment cannot communicate with the primary RHACS Central.

For example:

```text
Connected Environment
|
+-- RHACS Central A
+-- Production Clusters


Highly Restricted Environment
|
+-- RHACS Central B
+-- Restricted Clusters
```

This creates separate security-management domains.

The trade-off is that security teams no longer have the same single-Central view across both environments.

Whether this is appropriate depends on organizational requirements and RHACS support for the desired architecture.

---

# 25. Centralized vs Separate Central

### Single Central

```text
              Central
             /   |   \
            /    |    \
        OCP1   OCP2   OCP3
```

Advantages:

* Centralized security management
* Single security view
* Centralized policies
* Easier cross-cluster comparison

Requirement:

* All clusters need an appropriate supported communication path to Central.

### Separate Central

```text
Central A              Central B
   |                       |
OCP1 OCP2               OCP3 OCP4
```

Advantages:

* Strong network isolation
* Independent security domains
* Local management

Disadvantages:

* Multiple Central environments
* Separate administration
* More operational overhead
* More complex reporting
* Cross-environment visibility is reduced

---

# 26. Data Transfer Across Security Boundaries

If security policy requires an air gap, data may need to cross the boundary through controlled processes.

For example:

```text
Disconnected Zone
       |
       v
Security Export
       |
       v
Inspection / Approval
       |
       v
Controlled Transfer
       |
       v
Connected Security Zone
```

This should be designed according to the organization's security classification and approved transfer mechanisms.

---

# 27. Multi-Cluster Disconnected Architecture

A large organization may have several isolated environments:

```text
                         Security Operations
                               |
                 +-------------+-------------+
                 |                           |
                 v                           v
           RHACS Central A             RHACS Central B
             Connected                  Restricted
                 |                           |
          +------+------+              +-----+-----+
          |             |              |           |
         OCP1          OCP2           OCP3        OCP4
       Connected      Connected     Air-Gapped   Air-Gapped
```

This creates **multiple RHACS security domains**.

# 28. Security Team Impact

Disconnected clusters affect security operations.

Security teams must understand:

* Which clusters are connected?
* Which clusters are isolated?
* Which RHACS Central manages each cluster?
* How quickly security data reaches Central?
* How vulnerability information is updated?
* How security incidents are investigated?
* How reports are generated?
* How exceptions are managed?

Documentation becomes especially important.

# 29. Platform Team Impact

Platform teams have additional responsibilities:

```text
Platform Team

+-- RHACS deployment
+-- Internal registry
+-- Image mirroring
+-- DNS
+-- Certificates
+-- Firewall
+-- Routing
+-- Proxy
+-- RHACS upgrades
+-- Vulnerability-data update process

```

Disconnected deployments require more operational planning than normal connected deployments.

---

# 30. Application Team Impact

Application teams also need to understand that external images may not be available.

Instead of:

```text
FROM docker.io/library/nginx
```

the organization may require:

```text
FROM registry.internal.example/nginx
```

The exact registry naming depends on the organization's image-mirroring architecture.

Application teams should use approved internal registries and approved base images.

---

# 31. CI/CD in Disconnected Environments

CI/CD must also work inside the disconnected boundary.

Example:

```text
Git
 |
 v
Internal Jenkins
 |
 v
Build
 |
 v
Internal Registry
 |
 v
Security Validation
 |
 v
OpenShift
```

No Internet dependency should be introduced accidentally.

For example, a build should not unexpectedly attempt:

```text
Jenkins
   |
   v
Internet
   X
```

Instead, dependencies and images should be available from approved internal repositories.

# 33. Monitoring and Logging

RHACS itself should be integrated with the organization's monitoring and logging architecture.

For example:

```text
Disconnected Environment
|
+-- RHACS
+-- Prometheus
+-- Grafana
+-- Logging

```

If the SIEM is outside the disconnected network, an approved data-transfer architecture may be required.

# 34. Backup and Recovery

Disconnected RHACS environments still require backups.

Consider:

```text
RHACS Central
     |
     v
Backup
     |
     v
Internal Backup Storage
```

For highly isolated environments:

```text
RHACS Central
     |
     v
Local Backup
     |
     v
Offline / Protected Backup
```

The organization should document how backups are protected, transported, and restored.

# 35. Disaster Recovery

A disconnected environment needs a clear DR strategy.

For example:

```text
Primary Restricted Zone
        |
        v
RHACS Central
        |
        X
        |
DR Restricted Zone
        |
        v
RHACS Recovery Environment
```

The DR architecture must account for:

* RHACS configuration
* Persistent data
* Certificates
* DNS
* Internal registry
* Network connectivity
* Cluster registration
* Required RHACS images
* Vulnerability-data availability

---

# 36. What Happens During a Network Partition?

Suppose:

```text
Cluster
   |
 Sensor
   |
   X
   |
Central
```

The platform team should investigate:

```text
1. Is Central healthy?
2. Is DNS working?
3. Is routing working?
4. Is firewall traffic allowed?
5. Are certificates valid?
6. Is Sensor healthy?
7. Is the endpoint reachable?
```

Do not immediately assume that the cluster itself is broken.

```text
  |
  X
  |
Central
```

Possible causes:

* Firewall

```text

    |
    v

    |

  |
```

```text
  |
```

# 39. Important Architectural Principle

A disconnected RHACS design should avoid hidden dependencies on the public Internet.

Ask these questions:

```text
Does RHACS need Internet access?

Does Sensor need Internet access?

Where are RHACS images stored?

Where are application images stored?

How are vulnerability updates delivered?

How are RHACS upgrades delivered?

How are certificates issued?

How does DNS work?

How does Central communicate with each cluster?

How does security data reach the SIEM?

How are backups transferred?
```

Every external dependency should have an explicit answer.

# 40. Recommended Enterprise Design

For a restricted OpenShift environment, a practical architecture may be:

```text
                    Corporate Security Network
                             |
                    +--------+--------+
                    |                 |
                    v                 v
              RHACS Central     Internal Registry
                    |                 |
             +------+-------+         |
             |              |         |
             v              v         |
       Production OCP   DR OCP <------+
             |              |
          Sensor         Sensor
             |              |
         Collector      Collector
             |              |
       Admission       Admission
       Controller      Controller
             |              |
        Applications   Applications
```

The environment additionally contains:

```text
Internal DNS
Internal CA
Internal Git
CI/CD
Monitoring
Logging
Backup
```

This creates a self-contained security and application platform.

Before deploying RHACS, verify:

* [ ] RHACS Central placement is defined.
* [ ] Network path from each secured cluster to Central is defined.
* [ ] Firewall rules are approved.
* [ ] DNS resolution works.
* [ ] TLS certificates and trust are defined.
* [ ] Required RHACS images are available.
* [ ] Internal registry is available.
* [ ] OpenShift images are mirrored.
* [ ] Application base images are mirrored.
* [ ] Vulnerability-data update process is defined.
* [ ] RHACS upgrade process is defined.
* [ ] Backup process is defined.
* [ ] Disaster recovery process is defined.
* [ ] Monitoring is available.
* [ ] Logging/SIEM integration is defined.
* [ ] CI/CD does not require unintended Internet access.
* [ ] GitOps repositories are accessible.
* [ ] Security ownership is documented.
* [ ] Platform ownership is documented.

# 42. Connected vs Disconnected Comparison

| Area               | Connected                     | Disconnected                            |
| ------------------ | ----------------------------- | --------------------------------------- |
| Internet           | Usually available             | Restricted/unavailable                  |
| RHACS Central      | Standard connectivity         | Must be reachable through approved path |
| Image registry     | Public/private                | Usually internal mirror                 |
| RHACS images       | Pulled normally               | Must be mirrored                        |
| OpenShift images   | Normal registry access        | Mirrored internally                     |
| Vulnerability data | Easier to update              | Requires controlled update process      |
| Upgrades           | Simpler                       | Requires artifact transfer              |
| DNS                | Corporate/public              | Usually internal                        |
| Certificates       | Standard PKI                  | Internal PKI often required             |
| Firewall           | Less restrictive              | Strictly controlled                     |
| CI/CD              | May use external dependencies | Must use internal dependencies          |
| GitOps             | External/internal             | Usually internal                        |
| Monitoring         | Standard                      | Must work inside security boundary      |
| DR                 | Standard                      | Requires additional planning            |
| Operations         | Simpler                       | More operational complexity             |

# 43. Interview Answer

A strong interview answer is:

> "Disconnected clusters significantly affect RHACS architecture because the cluster may not have Internet access and may also have restricted connectivity to external services. The first design decision is whether the disconnected cluster can still communicate with RHACS Central through an approved internal network path. If it can, RHACS Central can remain centralized while Sensor, Collector, and Admission Controller operate inside the secured cluster. If the security boundary prevents communication with the primary Central, a separate RHACS security domain may be required depending on the supported RHACS architecture. Disconnected environments also require internal image registries, image mirroring, controlled vulnerability-data updates, certificate and DNS management, controlled upgrades, backups, and disaster recovery. The key is to eliminate hidden Internet dependencies while maintaining centralized security visibility and local enforcement where possible."

# 44. Final Mental Model

Remember the architecture this way:

```text
                    INTERNET
                       X
                       |
              SECURITY BOUNDARY
                       |
             +---------+---------+
             |                   |
             v                   v
       RHACS CENTRAL       INTERNAL REGISTRY
             |                   |
       Secure Network            |
             |                   |
       +-----+------+            |
       |            |            |
       v            v            |
    OCP PROD      OCP DR <-------+
       |            |
    Sensor       Sensor
       |            |
  Collector     Collector
       |            |
 Admission     Admission
 Controller    Controller
       |            |
 Applications  Applications
```

The key principle is:

> **A disconnected RHACS deployment must bring the security platform, required container images, vulnerability information, certificates, updates, and supporting services inside the security boundary—or provide an explicitly approved controlled path for them.**

And the most important distinction is:

```text
Disconnected from Internet
          ≠
Disconnected from RHACS Central
```

A cluster can be **Internet-isolated but still centrally managed by RHACS** if an approved network path exists between the secured cluster and RHACS Central.
