# RHACS Central Responsibilities

## 1. Overview

**RHACS Central** is the central management and control-plane component of Red Hat Advanced Cluster Security for Kubernetes (RHACS).

Central provides the primary location for managing RHACS security information across one or more secured Kubernetes/OpenShift clusters.

A simplified architecture is:

```text
                         RHACS Central
                              |
        +---------------------+---------------------+
        |                     |                     |
        v                     v                     v
   Cluster A              Cluster B             Cluster C
     Sensor                 Sensor                Sensor
        |                     |                     |
   Collector              Collector             Collector
```

Central does **not** replace the Kubernetes/OpenShift control plane. Instead, it provides centralized security management, analysis, policy management, vulnerability information, and visibility across secured clusters.

---

# 2. Main Responsibilities of Central

Central is responsible for the following major areas:

1. Security management
2. Cluster management
3. Policy management
4. Vulnerability management
5. Risk analysis
6. Security findings
7. Compliance information
8. Authentication and authorization
9. RHACS API and UI
10. Integration management
11. Configuration management
12. Centralized security visibility

---

# 3. Central as the RHACS Management Plane

Central acts as the primary management plane for RHACS.

It receives security information from RHACS components running on secured clusters and makes that information available through the RHACS UI and API.

```text
Secured Cluster
      |
      | Security telemetry
      v
    Sensor
      |
      v
   Central
      |
      +---- RHACS UI
      |
      +---- RHACS API
      |
      +---- Security Policies
      |
      +---- Vulnerability Information
      |
      +---- Risk Information
```

Central therefore provides a centralized view instead of requiring administrators to inspect each Kubernetes cluster independently.

---

# 4. Cluster Management

Central maintains information about clusters secured by RHACS.

For example:

```text
RHACS Central
   |
   +-- Production OpenShift
   |
   +-- Development OpenShift
   |
   +-- QA OpenShift
   |
   +-- Production Kubernetes
```

Central provides information such as:

* Cluster identity
* Cluster status
* Connected Sensor
* Security information
* Policy violations
* Vulnerability information
* Runtime activity
* Cluster metadata

This is particularly important in enterprise environments with many Kubernetes clusters.

---

# 5. Policy Management

One of Central's most important responsibilities is managing RHACS security policies.

Examples include:

* Privileged containers
* Critical vulnerabilities
* Host namespace usage
* Dangerous Linux capabilities
* Insecure images
* Root containers
* HostPath usage
* Image registry restrictions
* Runtime behavior
* Kubernetes configuration risks

A policy can be represented conceptually as:

```text
Policy
 |
 +-- Policy Name
 +-- Severity
 +-- Conditions
 +-- Categories
 +-- Enforcement
 +-- Exceptions
```

Central stores and manages these policies.

---

# 6. Policy Evaluation

Central participates in evaluating security information against RHACS policies.

The exact processing path depends on the RHACS feature involved.

A simplified model is:

```text
Security Event
      |
      v
RHACS Components
      |
      v
Central
      |
      v
Policy Evaluation
      |
      +---- Pass
      |
      +---- Violation
```

Policy violations can then be displayed to security and platform teams.

* Affected workloads

* Risk

# 9. Risk Management

Central provides an aggregated security-risk view.

Risk information can consider multiple factors, such as:

* Vulnerabilities
* Exposure
* Policy violations
* Runtime activity
* Deployment configuration
* Image security

A simplified model is:

```text
Application
     |
     +-- Vulnerabilities
     +-- Policy violations
     +-- Runtime findings
     +-- Configuration risks
     |
     v
   Risk
```

This helps security teams prioritize remediation instead of treating every finding equally.

The typical architecture is:

```text

     |
     v

     |
     v
Collector
     |
     v
Sensor
     |
     v

```

Central can then provide centralized visibility into relevant runtime security events.

Examples include:

* Suspicious process activity
* Runtime policy violations
* Container behavior
* Security alerts
* Network-related security observations

Central is therefore a key part of the runtime-security management architecture.

# 13. Authorization and RBAC

Authentication answers:

> Who are you?

Authorization answers:

> What are you allowed to do?

Central manages RHACS role-based access control.

Example:

```text
RHACS Administrator
   |
   +-- Full administration

Security Analyst
   |
   +-- Investigate findings
   +-- View vulnerabilities

Application Team
   |
   +-- View application findings

Auditor
   |
   +-- Read-only access
```

The objective is to apply least privilege.

# 18. Central Database

Central uses persistent storage for RHACS data.

Conceptually:

```text
              Central
                 |
                 v
          Central Database
                 |
        +--------+--------+
        |        |        |
     Policies  Findings  Config
```

Therefore, production Central requires appropriate storage planning.

Important considerations include:

* Persistent storage
* Capacity
* Performance
* Availability
* Backup
* Restore
* Encryption
* Retention

A Central pod restart should not result in loss of required persistent RHACS data.

---

# 19. Central and Sensor Relationship

Central does not directly replace Sensor.

Sensor runs on each secured cluster and communicates with Central.

```text
                 Central
                    |
       +------------+------------+
       |            |            |
    Sensor A     Sensor B     Sensor C
       |            |            |
   Cluster A    Cluster B    Cluster C
```

Sensor is responsible for cluster-level communication and security data collection.

Central provides centralized management and analysis.

---

# 20. Central and Collector Relationship

Collector operates closer to the workload/node level.

A simplified relationship is:

```text
Workload
   |
   v
Collector
   |
   v
Sensor
   |
   v
Central
```

Therefore:

* Collector observes relevant runtime information.
* Sensor communicates cluster information.
* Central provides centralized management and visibility.

---

# 21. Central and Admission Controller

The Admission Controller participates in admission-time security enforcement.

Conceptually:

```text
Developer
    |
    v
Kubernetes API
    |
    v
Admission Controller
    |
    +---- Allow
    |
    +---- Deny
```

Central is responsible for the centralized policy and management side of this architecture.

The Admission Controller performs enforcement close to the Kubernetes API admission process.

---

# 22. Central Does Not Manage Kubernetes Workloads

A critical distinction is:

> RHACS Central is not the Kubernetes control plane.

Central does **not** replace:

* Kubernetes API server
* OpenShift API server
* etcd
* Kubernetes scheduler
* Kubernetes controller manager
* OpenShift Machine Config Operator
* OpenShift Cluster Version Operator

For example:

```text
OpenShift Control Plane
        |
        +-- API Server
        +-- etcd
        +-- Scheduler
        +-- Controllers

RHACS
        |
        +-- Central
        +-- Sensor
        +-- Collector
        +-- Admission Controller
```

RHACS provides security management on top of Kubernetes/OpenShift.

# 23. Central in a Multi-Cluster Enterprise

Central becomes particularly valuable when an organization has multiple clusters.

Example:

```text
                    RHACS Central
                         |
       +-----------------+-----------------+
       |                 |                 |
       v                 v                 v
   Production          QA              Development
   OpenShift         OpenShift          Kubernetes
```

Security teams can use one Central deployment to obtain centralized security visibility across secured clusters.

This reduces the need to independently configure and monitor security controls in every cluster.

---

# 24. Central Availability

Central is a critical RHACS component.

If Central becomes unavailable:

* RHACS management access may be affected.
* Central UI/API access may be unavailable.
* Centralized security analysis may be affected.
* Sensor-to-Central communication may be interrupted.
* Security teams may lose centralized visibility.

Therefore, production deployments should consider:

* Multiple Central replicas where supported
* Appropriate node placement
* Persistent storage
* Anti-affinity
* Failure domains
* Backup
* Disaster recovery
* Monitoring

---

# 25. Central Failure Domain

A useful enterprise design principle is:

```text
Central Failure
      |
      +-- RHACS Management Impact
      +-- Centralized Visibility Impact
      +-- API/UI Impact
      +-- Sensor Communication Impact
```

However, this should not be interpreted as:

```text
Central Failure = Kubernetes Cluster Failure
```

Kubernetes/OpenShift workloads are managed by the Kubernetes control plane, not by RHACS Central.

# 28. Central Upgrade Responsibility

Central is managed through the RHACS Operator.

A simplified upgrade flow is:

```text
RHACS Operator
      |
      v
Central CR
      |
      v
Central Components
      |
      v
New RHACS Version
```

Before upgrades:

* Verify compatibility.
* Review release notes.
* Back up required data.
* Test in a non-production environment.
* Validate the Operator.
* Plan rollback/recovery.
* Monitor Central after upgrade.

---

# 29. Central Backup Responsibility

Central data should be included in the enterprise backup and recovery strategy.

Important considerations:

```text
Central
  |
  +-- Configuration
  +-- Policies
  +-- Security data
  +-- Database
  +-- Integrations
  +-- RBAC
```

The backup strategy must include restore testing.

A backup that has never been restored successfully should not be considered a fully validated recovery solution.

# 32. What Central Should Not Be Used For

Central should not be treated as:

* A replacement for OpenShift monitoring
* A replacement for etcd
* A replacement for Kubernetes RBAC
* A replacement for the OpenShift API server
* A general-purpose SIEM
* A general-purpose vulnerability-management platform for arbitrary infrastructure
* A replacement for network firewalls
* A replacement for Kubernetes storage
* A replacement for enterprise backup infrastructure

RHACS complements these technologies rather than replacing them.

# 35. Summary

RHACS Central is the **central management and security-analysis component** of RHACS.

Its primary responsibilities are:

```text
                    RHACS CENTRAL
                         |
       +-----------------+-----------------+
       |                 |                 |
       v                 v                 v
  Management          Analysis         Visibility
       |                 |                 |
       v                 v                 v
 Policies          Vulnerabilities      Clusters
 RBAC              Risk                 Workloads
 Integrations      Compliance           Violations
 API/UI             Security Events      Runtime Data
```

The most important architectural concept is:

> **Central provides centralized RHACS management and security visibility, while Sensor, Collector, and Admission Controller perform security functions closer to the secured Kubernetes/OpenShift clusters.**

For an enterprise RHACS deployment, Central should therefore be treated as a **critical security management service** with appropriate availability, persistent storage, authentication, RBAC, monitoring, backup, disaster recovery, and upgrade procedures.
