# RHACS Central Diagnostics Collection and Enterprise Component-Operations Standard

## 1. Purpose

This document defines:

1. A standardized procedure for collecting **Red Hat Advanced Cluster Security for Kubernetes (RHACS) Central diagnostics**.
2. An enterprise operations standard for managing RHACS components consistently across development, staging, and production environments.
3. Evidence, escalation, health-check, change-management, backup, monitoring, and troubleshooting requirements.

The goal is to ensure that RHACS incidents can be investigated using repeatable, supportable, and auditable procedures.

---

# Part I — Collecting RHACS Central Diagnostics

## 2. Central Diagnostic Scope

RHACS Central is responsible for the central management plane, including:

* RHACS API/UI
* Authentication and authorization
* Security policies
* Cluster metadata
* Vulnerability information
* Compliance information
* Alert and violation data
* Integration configuration
* Central database communication
* Scanner/Scanner V4 integration
* Secured-cluster communication

When collecting diagnostics, gather evidence from the **Central namespace**, Central pods, database, Operator, and relevant cluster resources.

Typical RHACS namespace:

```bash
stackrox
```

Always verify the namespace before collecting diagnostics.

```bash
oc get ns
```

or:

```bash
oc get ns | grep -i stackrox
```

# 3. Initial Central Health Assessment

Start with a high-level health snapshot.

```bash
oc get pods -n stackrox -o wide
```

Check:

```bash
oc get deploy -n stackrox
oc get svc -n stackrox
oc get secret -n stackrox
oc get configmap -n stackrox
```

Check recent events:

```bash
oc get events -n stackrox --sort-by='.lastTimestamp'
```

For a Kubernetes cluster:

```bash
kubectl get pods -n stackrox -o wide
kubectl get events -n stackrox --sort-by='.lastTimestamp'
```

Record:

* Pod status
* Restart count
* Node placement
* Pod IP
* Readiness status
* Liveness status
* Recent events
* Deployment availability

# 4. Identify Central Components

List all RHACS workloads:

```bash
oc get pods -n stackrox
```

Typical components may include:

```text

scanner
scanner-db
sensor

```

The exact component set depends on the RHACS version and deployment architecture.

Determine the Central pod:

```bash
oc get pods -n stackrox | grep central
```

Determine the Central DB pod:

```bash
oc get pods -n stackrox | grep central-db
```

# 5. Collect Central Pod Information

Describe the Central pod:

```bash
oc describe pod <central-pod> -n stackrox
```

Capture:

* Container state
* Restart count
* Environment configuration
* Volume mounts
* Probes
* Resource requests/limits
* Node placement
* Events
* Image version

Save the output:

```bash
oc describe pod <central-pod> -n stackrox > central-pod-describe.txt
```

---

# 6. Collect Central Logs

First identify containers:

```bash
oc get pod <central-pod> -n stackrox \
  -o jsonpath='{.spec.containers[*].name}'
```

Collect current logs:

```bash
oc logs <central-pod> -n stackrox > central.log
```

For a specific container:

```bash
oc logs <central-pod> -n stackrox -c central > central-container.log
```

Collect previous-container logs when a container has restarted:

```bash
oc logs <central-pod> -n stackrox \
  -c central --previous > central-previous.log
```

Collect a recent time window:

```bash
oc logs <central-pod> -n stackrox \
  --since=2h > central-last-2h.log
```

Follow logs during active troubleshooting:

```bash
oc logs -f <central-pod> -n stackrox
```

Avoid collecting unrestricted, extremely large logs in production unless specifically required.


```bash

```

# 8. Collect Central Database Diagnostics

Identify the database pod:

```bash
oc get pods -n stackrox | grep central-db
```

Describe it:

```bash
oc describe pod <central-db-pod> -n stackrox \
  > central-db-describe.txt
```

Collect logs:

```bash
oc logs <central-db-pod> -n stackrox \
  > central-db.log
```

If the container restarted:

```bash
oc logs <central-db-pod> -n stackrox \
  --previous > central-db-previous.log
```

Check storage:

```bash
oc get pvc -n stackrox
```

Describe the relevant PVC:

```bash
oc describe pvc <central-db-pvc> -n stackrox
```

Check the underlying volume:

```bash
oc get pv
```

Look for:

* PVC Pending
* Mount failures
* Storage capacity problems
* Filesystem errors
* Read-only filesystem
* Volume attachment problems
* Database startup failures

---

# 9. Collect Operator Diagnostics

RHACS deployments managed by the Operator should also be investigated from the Operator side.

Find the RHACS Operator:

```bash
oc get pods -A | grep -i rhacs
```

Check Operator subscriptions:

```bash
oc get subscription -A | grep -i rhacs
```

Check CSV:

```bash
oc get csv -A | grep -i rhacs
```

Describe the CSV:

```bash
oc describe csv <csv-name> -n <operator-namespace>
```

Collect Operator logs:

```bash
oc logs <operator-pod> -n <operator-namespace> \
  > rhacs-operator.log
```

Check Operator events:

```bash
oc get events -n <operator-namespace> \
  --sort-by='.lastTimestamp'
```

# 10. Collect Central Custom Resource Information

If the RHACS Operator exposes a Central custom resource in the deployed version, collect it using the appropriate CRD/resource name.

First inspect available resources:

```bash
oc api-resources | grep -i central
```

Then:

```bash
oc get <central-resource> -A
```

Export the relevant resource:

```bash
oc get <central-resource> <name> \
  -n <namespace> -o yaml > central-cr.yaml
```

Review:

* Desired configuration
* Status conditions
* Operator reconciliation state
* Storage configuration
* Exposure configuration
* Resource configuration
* Proxy configuration
* Tolerations
* Node selectors
* Certificates

# 12. Collect Route Information

For OpenShift:

```bash
oc get route -n stackrox
```

Describe the route:

```bash
oc describe route <route-name> -n stackrox
```

Export it:

```bash
oc get route <route-name> -n stackrox -o yaml \
  > central-route.yaml
```

Check:

* Hostname
* TLS termination
* Certificate
* Service target
* Backend port
* Route conditions

For an HTTPS route:

```bash
curl -vk https://<central-hostname>
```

Use `-k` only for diagnostic testing where certificate validation is intentionally bypassed.

# 13. Collect Node and Resource Information

Identify where Central is running:


```bash

```


Check node utilization:

```bash

```

Look for:

* CPU pressure
* Memory pressure
* Disk pressure
* PID pressure
* Scheduling problems
* Evictions
* Insufficient resources

---

# 14. Collect Network Diagnostics

Check NetworkPolicies:

```bash
oc get networkpolicy -n stackrox
```

Describe relevant policies:

```bash
oc describe networkpolicy <policy> -n stackrox
```

Check services:

```bash
oc get svc -n stackrox
```

Test DNS from a suitable troubleshooting pod:

```bash
oc exec -n stackrox <pod> -- \
  getent hosts <service-name>
```

Check connectivity where appropriate:

```bash
oc exec -n stackrox <pod> -- \
  curl -vk https://<service>:<port>
```

Investigate:

* DNS failures
* NetworkPolicy blocks
* Service selector problems
* TLS failures
* Proxy configuration
* Firewall restrictions
* Load-balancer/route problems

---

# 15. Collect Certificate Information

List secrets:

```bash
oc get secret -n stackrox
```

Inspect certificate-related secrets without exposing private-key contents:

```bash
oc describe secret <secret-name> -n stackrox
```

Check certificate expiration where appropriate:

```bash
oc get secret <secret-name> -n stackrox \
  -o jsonpath='{.data.tls\.crt}' | base64 -d | \
  openssl x509 -noout -dates -subject -issuer
```

Do not place private keys or credentials into support bundles or ticket comments.

# 18. Collect Diagnostics During CrashLoopBackOff

When Central is restarting:

```bash
oc get pod <central-pod> -n stackrox
```

Check restart count:

```bash
oc get pod <central-pod> -n stackrox \
  -o jsonpath='{.status.containerStatuses[*].restartCount}'
```

Check termination reason:

```bash
oc get pod <central-pod> -n stackrox \
  -o jsonpath='{.status.containerStatuses[*].lastState}'
```

Collect:

```bash
oc logs <central-pod> -n stackrox --previous
```

Then:

```bash
oc describe pod <central-pod> -n stackrox
```

Common causes include:

* Configuration errors
* Database connectivity problems
* Certificate problems
* Insufficient memory
* Persistent-storage failures
* Corrupt or unavailable data
* Network connectivity failures
* Version incompatibility

---

# 19. Collect Diagnostics During Central DB Startup Failure

Check:

```bash
oc get pod -n stackrox
oc describe pod <central-db-pod> -n stackrox
oc logs <central-db-pod> -n stackrox
oc logs <central-db-pod> -n stackrox --previous
```

Then:

```bash
oc get pvc -n stackrox
oc describe pvc <central-db-pvc> -n stackrox
```

Check node conditions:

```bash
oc describe node <node-name>
```

Check recent events:

```bash
oc get events -n stackrox --sort-by='.lastTimestamp'
```

Do not manually delete database files or PVCs as a first troubleshooting step.

# 21. Sensitive Data Handling

Before sharing diagnostics externally:

* Remove passwords.
* Remove API tokens.
* Remove bearer tokens.
* Remove private keys.
* Remove LDAP bind passwords.
* Remove cloud credentials.
* Remove registry credentials.
* Remove unnecessary personal information.
* Review certificates containing sensitive material.
* Review configuration files for secrets.

Do not run:

```bash
oc get secret -A -o yaml
```

and upload the raw output to a support ticket without reviewing and redacting it.

# Part II — Enterprise Component-Operations Standard

# 22. Objective

An enterprise RHACS operating model should define ownership and operational expectations for every RHACS component.

The standard should cover:

```text
Component
    ↓
Owner
    ↓
Purpose
    ↓
Dependencies
    ↓
Health checks
    ↓
Monitoring
    ↓
Backup/recovery
    ↓
Change procedure
    ↓
Troubleshooting
    ↓
Escalation
```

---

# 23. Component Ownership Model

Define a RACI-style ownership model.

| Component             | Primary Owner          | Secondary Owner         |
| --------------------- | ---------------------- | ----------------------- |
| RHACS Central         | Security Platform Team | OpenShift Platform Team |
| Central DB            | Security Platform Team | Storage Team            |
| Scanner               | Security Platform Team | Platform Team           |
| Scanner DB            | Security Platform Team | Platform Team           |
| Sensor                | Cluster Platform Team  | Security Team           |
| Admission Control     | Security Team          | Platform Team           |
| Collector             | Platform Team          | Security Team           |
| RHACS Operator        | Platform Team          | Security Team           |
| OpenShift cluster     | Platform Team          | Infrastructure Team     |
| Storage               | Storage Team           | Platform Team           |
| DNS                   | Network Team           | Platform Team           |
| Load Balancer/Ingress | Network Team           | Platform Team           |
| Identity Provider     | IAM Team               | Security Team           |

Organizations should adapt this model to their internal support structure.

# 24. Central Operational Standard

## Daily Checks

```bash
oc get pods -n stackrox
oc get deploy -n stackrox
oc get events -n stackrox --sort-by='.lastTimestamp'
```

Verify:

* Central is Ready.
* Central DB is Ready.
* No abnormal restarts.
* No persistent Warning events.
* PVCs are Bound.
* Central endpoint is reachable.
* Authentication works.
* Secured clusters are connected.

# 25. Scanner Operational Standard

Check:

```bash
oc get pods -n stackrox | grep scanner
```

Verify:

* Scanner pod availability
* Scanner DB availability
* Vulnerability data freshness
* Registry connectivity
* Image scanning functionality
* Scanner resource consumption

For Scanner V4 environments, separately monitor the V4 indexer/matcher architecture according to the RHACS version deployed.

# 26. Sensor Operational Standard

For each secured cluster:

```bash
oc get pods -n stackrox
```

Verify:

* Sensor is Running.
* Sensor is Ready.
* Sensor can communicate with Central.
* Cluster appears healthy in RHACS.
* No repeated connection failures exist.

Sensor troubleshooting should include both the secured cluster and Central.

---

# 27. Admission Control Operational Standard

Verify:

```bash
oc get pods -n stackrox
```

Check:

* Admission-control pod
* Service
* Webhook configuration
* TLS certificate
* Webhook endpoints
* API-server communication

Admission-control failures can affect workload deployment, so production changes should follow the enterprise change-management process.

# 28. Collector Operational Standard

Collector is involved in runtime/container telemetry.

Check:

```bash
oc get pods -n stackrox
```

Monitor:

* Collector availability
* Node coverage
* Kernel compatibility
* Runtime compatibility
* Resource consumption
* Repeated crashes

Do not treat Collector failures as Central failures automatically. Determine the actual failure domain first.

# 29. Central Database Operational Standard

The Central database is a critical stateful component.

Enterprise requirements should include:

* Persistent storage
* Storage monitoring
* Capacity alerts
* Backup strategy

* Change control

* Disaster-recovery procedures

Monitor:

```text

PV
Storage backend
Filesystem capacity
I/O latency

Central-to-database connectivity
```

Never perform destructive database operations without an approved recovery procedure.

# 32. Alert Severity Standard

| Severity | Example                                          | Response                    |
| -------- | ------------------------------------------------ | --------------------------- |
| P1       | Central completely unavailable                   | Immediate incident response |
| P1       | Security enforcement unavailable enterprise-wide | Immediate response          |
| P2       | Central degraded but accessible                  | Priority investigation      |
| P2       | Multiple secured clusters disconnected           | Priority investigation      |
| P3       | Scanner degraded                                 | Normal incident             |
| P3       | Individual Sensor unavailable                    | Cluster-level investigation |
| P4       | Non-critical warning                             | Planned remediation         |

The exact SLA should be defined by the enterprise service-management organization.

# 38. Escalation Standard

Escalate to the next support level when:

* Central repeatedly crashes.
* Central DB cannot start.
* Data integrity is suspected.
* RHACS upgrade fails.
* Operator reconciliation remains failed.
* Multiple secured clusters lose connectivity.
* Scanner remains unavailable after standard troubleshooting.
* Vulnerability-feed updates remain broken.
* Admission control causes widespread deployment impact.
* Recovery requires potentially destructive operations.
* Product-level defects are suspected.

Before escalation, provide:

```text
Problem statement
Environment details
Timeline
Exact error
Commands executed
Relevant outputs
Logs
Recent changes
Diagnostics bundle
Business impact
Actions already attempted
```

# 43. What Not to Do

Avoid the following during an incident:

```text
Do not delete Central DB PVCs as a first step.
Do not delete RHACS resources without understanding ownership.
Do not expose secrets in support tickets.
Do not restart every RHACS component simultaneously.
Do not change multiple variables at once during troubleshooting.
Do not disable security enforcement without approval.
Do not modify production configuration manually without change control.
Do not assume a Central error is always a Central problem.
Do not ignore recent Operator or cluster changes.
```

# 44. Final Enterprise Operating Model

A mature RHACS operation should follow this model:

```text
                 Enterprise RHACS
                       |
        +--------------+--------------+
        |              |              |
     Platform        Security       IAM/Network
        |              |              |
     Operator        Policies       Identity
     Central         Violations      DNS/TLS
     Storage         Compliance      Proxy/LB
        |
   Secured Clusters
        |
 +------+------+------+
 |      |      |      |
Sensor Collector Admission Runtime
```

The operating principle is:

```text
Standardize
    ↓
Monitor
    ↓
Detect
    ↓
Collect Evidence
    ↓
Troubleshoot
    ↓
Recover
    ↓
Validate
    ↓
Document
    ↓
Improve
```

A production RHACS environment should therefore have **repeatable diagnostics, clearly assigned ownership, centralized monitoring, controlled changes, tested recovery procedures, and documented escalation paths**.

This approach makes RHACS operations predictable and reduces the risk of ad-hoc troubleshooting in enterprise environments.
