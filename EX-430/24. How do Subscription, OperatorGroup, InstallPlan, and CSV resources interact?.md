# How do Subscription, OperatorGroup, InstallPlan, and CSV Resources Interact?

## 1. Overview

In OpenShift, **Operator Lifecycle Manager (OLM)** uses several Kubernetes resources to install and manage Operators.

The four resources most commonly encountered during an Operator installation are:

```text
Subscription
OperatorGroup
InstallPlan
CSV
```

They have different responsibilities:

```text
OperatorGroup
      │
      │ defines installation scope
      ▼
Subscription
      │
      │ requests an Operator/channel
      ▼
InstallPlan
      │
      │ describes installation actions
      ▼
CSV
      │
      │ represents installed Operator version
      ▼
Operator Deployment
```

A simplified relationship is:

```text
                 OperatorHub
                     │
                     ▼
              ┌──────────────┐
              │ Subscription │
              └──────┬───────┘
                     │
                     ▼
              ┌──────────────┐
              │ InstallPlan  │
              └──────┬───────┘
                     │
                     ▼
              ┌──────────────┐
              │     CSV      │
              └──────┬───────┘
                     │
                     ▼
             Operator Deployment
```

The **OperatorGroup** determines the namespace scope in which the Operator is intended to operate.

---

# 2. What Is an OperatorGroup?

An **OperatorGroup** defines the target namespace scope for Operators installed through OLM.

It answers the question:

> **Which namespaces can this Operator watch/manage?**

For example:

```text
OperatorGroup
    │
    └── Target namespaces
```

An OperatorGroup can be configured for:

* A single namespace.
* Multiple namespaces.
* All namespaces on the cluster.

The exact behavior depends on the Operator's supported installation modes.

---

# 3. Example OperatorGroup

Check OperatorGroups:

```bash
oc get operatorgroup -A
```

Example:

```text
NAMESPACE          NAME                         AGE
rhacs-operator     rhacs-operator-group         10m
```

Inspect it:

```bash
oc get operatorgroup \
  -n rhacs-operator \
  -o yaml
```

You may see information such as:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: rhacs-operator-group
  namespace: rhacs-operator
spec:
  targetNamespaces:
    - rhacs-operator
```

The exact generated configuration depends on the selected installation mode.

---

# 4. What Is a Subscription?

A **Subscription** tells OLM:

> **I want this Operator package from this catalog, using this update channel.**

It establishes the desired Operator subscription.

A Subscription typically specifies:

```text
Package name
Catalog source
Catalog namespace
Channel
Approval strategy
```

For example:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: rhacs-operator
  namespace: rhacs-operator
spec:
  channel: stable
  name: rhacs-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
```

The exact package name and channel depend on the RHACS version and catalog available in your environment.

---

# 5. What Does the Subscription Do?

The Subscription establishes the desired state:

```text
Install this Operator
        │
        ▼
From this catalog
        │
        ▼
Using this channel
        │
        ▼
Keep it updated according to
the approval strategy
```

For example:

```text
Subscription
     │
     ├── Package: RHACS Operator
     ├── Channel: selected channel
     ├── Source: redhat-operators
     └── Approval: Automatic/Manual
```

OLM continuously evaluates the Subscription and determines what Operator version should be installed.

---

# 6. What Is an InstallPlan?

An **InstallPlan** describes the resources and actions required to install or update an Operator.

It answers:

> **What exactly needs to be installed or changed?**

The InstallPlan can contain information about:

* The target CSV.
* Required CRDs.
* Required APIs.
* Required permissions.
* Operator resources.
* Dependencies.
* Other resources required for installation.

Check InstallPlans:

```bash
oc get installplan -A
```

Example:

```text
NAMESPACE         NAME            CSV                         APPROVAL   APPROVED
rhacs-operator    install-xxxxx   rhacs-operator.v4.x.x      Manual     false
```

---

# 7. Automatic vs Manual InstallPlan Approval

An important part of the Subscription is its approval strategy.

## Automatic

With automatic approval:

```text
Subscription
      │
      ▼
OLM creates InstallPlan
      │
      ▼
InstallPlan automatically approved
      │
      ▼
CSV installed
```

The Operator can be installed or upgraded without an administrator manually approving each InstallPlan.

---

## Manual

With manual approval:

```text
Subscription
      │
      ▼
OLM creates InstallPlan
      │
      ▼
Waiting for approval
      │
      ▼
Administrator reviews
      │
      ▼
Administrator approves
      │
      ▼
CSV installed
```

This is commonly useful in controlled enterprise production environments.

---

# 8. Approving an InstallPlan

First identify the InstallPlan:

```bash
oc get installplan -n rhacs-operator
```

Inspect it:

```bash
oc describe installplan <installplan-name> \
  -n rhacs-operator
```

If manual approval is required and the change has been reviewed:

```bash
oc patch installplan <installplan-name> \
  -n rhacs-operator \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

Then monitor:

```bash
oc get installplan -n rhacs-operator
```

---

# 9. What Is a CSV?

**CSV** means:

> **ClusterServiceVersion**

The CSV represents a specific installed version of an Operator.

It answers:

> **Which version of the Operator is installed, and what does OLM know about it?**

A CSV contains information such as:

* Operator version.
* Deployment definition.
* Required permissions.
* Owned CRDs.
* Required CRDs.
* Install modes.
* Operator metadata.
* Installation status.

Check CSVs:

```bash
oc get csv -A
```

Example:

```text
NAMESPACE         NAME                         DISPLAY
rhacs-operator    rhacs-operator.v4.x.x       RHACS Operator
```

Check status:

```bash
oc get csv -n rhacs-operator
```

A healthy CSV should eventually show:

```text
PHASE
Succeeded
```

---

# 10. CSV Lifecycle

A CSV can move through different phases during installation.

Conceptually:

```text
Pending
   │
   ▼
Installing
   │
   ▼
Succeeded
```

If something goes wrong, the CSV may enter a failed state.

Check:

```bash
oc describe csv <csv-name> \
  -n rhacs-operator
```

Pay particular attention to:

```text
Conditions
Events
Requirements
InstallModes
```

# 13. What Happens During Installation?

Suppose an administrator selects the RHACS Operator from OperatorHub.

### Step 1 — OperatorGroup

OpenShift/OLM establishes the Operator's installation scope.

```text
OperatorGroup
      │
      ▼
Target namespace scope
```

---

### Step 2 — Subscription

The administrator selects:

```text
Operator
Channel
Approval strategy
```

OLM creates a Subscription.

```text
Subscription
      │
      └── "Install this Operator from this channel"
```

---

### Step 3 — OLM Resolves Dependencies

OLM evaluates:

* Operator version.
* Dependencies.
* CRDs.
* API requirements.
* Installation mode.
* Existing Operators.

---

### Step 4 — InstallPlan

OLM creates an InstallPlan describing the required installation actions.

```text
InstallPlan
      │
      ├── CSV
      ├── CRDs
      ├── RBAC
      └── Other required resources
```

---

### Step 5 — Approval

If automatic:

```text
InstallPlan → automatically approved
```

If manual:

```text
InstallPlan → waits for administrator
```

---

### Step 6 — CSV Installation

After approval, OLM installs the CSV.

```text
InstallPlan
      │
      ▼
CSV
      │
      ▼
Operator Deployment
```

---

### Step 7 — Operator Starts

The Operator deployment creates its pod:

```bash
oc get pods -n rhacs-operator
```

Example:

```text
NAME                                             READY   STATUS
rhacs-operator-controller-manager-xxxxx-xxxxx   1/1     Running
```

---

### Step 8 — CSV Becomes Succeeded

Finally:

```bash
oc get csv -n rhacs-operator
```

Expected:

```text
PHASE
Succeeded
```

At this point, the Operator installation is successfully completed.

---

# 14. How to Troubleshoot the Chain

When an Operator does not install, troubleshoot from the beginning of the chain.

## Check OperatorGroup

```bash
oc get operatorgroup -n rhacs-operator
```

Then:

```bash
oc describe operatorgroup \
  -n rhacs-operator
```

---

## Check Subscription

```bash
oc get subscription -n rhacs-operator
```

Then:

```bash
oc describe subscription \
  -n rhacs-operator
```

Look for:

```text
CurrentCSV
InstallPlan
Conditions
Events
```

---

## Check InstallPlan

```bash
oc get installplan -n rhacs-operator
```

Then:

```bash
oc describe installplan <name> \
  -n rhacs-operator
```

Check whether:

```text
Approved
```

is required.

---

## Check CSV

```bash
oc get csv -n rhacs-operator
```

Then:

```bash
oc describe csv <csv-name> \
  -n rhacs-operator
```

Look for:

```text
Phase
Conditions
Events
Requirements
```

---

## Check Operator Pod

```bash
oc get pods -n rhacs-operator
```

Then:

```bash
oc describe pod <pod-name> \
  -n rhacs-operator
```

Check logs:

```bash
oc logs <pod-name> \
  -n rhacs-operator
```

# 15. Troubleshooting Decision Tree

Use this sequence:

```text
Operator not working
       │
       ▼
Is OperatorGroup correct?
       │
       ├── No → Fix OperatorGroup
       │
       └── Yes
             │
             ▼
       Is Subscription healthy?
             │
             ├── No → Check catalog/channel
             │
             └── Yes
                   │
                   ▼
             Is InstallPlan created?
                   │
                   ├── No → Check Subscription/dependencies
                   │
                   └── Yes
                         │
                         ▼
                   Is InstallPlan approved?
                         │
                         ├── No → Approve if manual
                         │
                         └── Yes
                               │
                               ▼
                         Is CSV Succeeded?
                               │
                               ├── No → Describe CSV
                               │
                               └── Yes
                                     │
                                     ▼
                               Is Operator Pod Running?
                                     │
                                     ├── No → Check pod/events/logs
                                     │
                                     └── Yes
                                           │
                                           ▼
                                    Operator installed
```

# 16. Common Interview Questions

## Q1. What is a Subscription?

A Subscription tells OLM which Operator package and channel should be installed and maintained.

```text
Subscription = What Operator do I want?
```

---

## Q2. What is an OperatorGroup?

An OperatorGroup defines the namespace scope in which an Operator operates.

```text
OperatorGroup = Where can the Operator operate?
```

---

## Q3. What is an InstallPlan?

An InstallPlan describes the resources and actions required to install or update an Operator.

```text
InstallPlan = What needs to be installed?
```

---

## Q4. What is a CSV?

A ClusterServiceVersion represents a specific version of an installed Operator and describes how OLM should deploy and manage it.

```text
CSV = Which Operator version is installed?
```

# 17. Easy Way to Remember

Use this mnemonic:

```text
OperatorGroup → WHERE
Subscription  → WHAT
InstallPlan   → HOW
CSV           → VERSION
```

More precisely:

```text
OperatorGroup
    = Installation scope

Subscription
    = Desired Operator/channel

InstallPlan
    = Installation/update plan

CSV
    = Installed Operator version + metadata
```

---

# 18. Important Distinction

These resources should not be thought of as four independent objects.

They form an OLM lifecycle chain:

```text
OperatorGroup
      │
      ▼
Subscription
      │
      ▼
InstallPlan
      │
      ▼
CSV
      │
      ▼
Operator Deployment
```

The OperatorGroup establishes scope, the Subscription expresses the desired Operator, OLM generates an InstallPlan, and the CSV represents the Operator version being installed and managed.

## Final Takeaway

The four OLM resources have distinct roles:

| Resource          | Main Question  | Purpose                                                   |
| ----------------- | -------------- | --------------------------------------------------------- |
| **OperatorGroup** | Where?         | Defines the Operator's target namespace scope             |
| **Subscription**  | What?          | Requests an Operator package and channel                  |
| **InstallPlan**   | How?           | Defines the installation/update actions                   |
| **CSV**           | Which version? | Represents the Operator version and installation metadata |

The most important operational flow to remember is:

```text
OperatorGroup
      ↓
Subscription
      ↓
InstallPlan
      ↓
CSV
      ↓
Operator Pod
      ↓
Custom Resources
      ↓
Application/Platform Workload
```

For RHACS:

```text
rhacs-operator
    ├── OperatorGroup
    ├── Subscription
    ├── InstallPlan
    ├── CSV
    └── RHACS Operator

stackrox
    └── RHACS Central
```
