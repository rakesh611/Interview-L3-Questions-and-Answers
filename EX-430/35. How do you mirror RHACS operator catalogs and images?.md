# How Do You Mirror RHACS Operator Catalogs and Images?

In a disconnected or air-gapped OpenShift environment, RHACS cannot pull Operator catalogs and container images directly from public Red Hat registries.

The normal approach is to:

1. Select the required RHACS version.
2. Mirror the RHACS Operator catalog.
3. Mirror the RHACS operand images.
4. Push the content into an approved internal registry.
5. Configure OpenShift to use the mirrored catalog and images.
6. Install RHACS from the internal sources.
7. Validate that all RHACS Pods can pull their images.

The architecture is:

```text
Connected Environment
        |
        | oc-mirror
        v
+-------------------------+
| Internal Registry       |
| registry.example.com    |
+-------------------------+
        |
        v
Disconnected OpenShift
        |
        +-- CatalogSource
        |
        +-- RHACS Operator
        |
        +-- Central
        |
        +-- Scanner
        |
        +-- Sensor
        |
        +-- Admission
```

---

## 1. Understand What Must Be Mirrored

There are two major categories.

### Operator catalog content

This provides the RHACS Operator through OLM.

Conceptually:

```text
RHACS Operator Catalog
        |
        +-- Package
        |
        +-- Channel
        |
        +-- Bundle
        |
        +-- Operator images
```

### RHACS operand images

These are the images used by RHACS itself.

Typical components include:

```text
Central
Scanner
Scanner DB
Sensor
Admission Controller
Other RHACS components
```

Therefore:

```text
Operator catalog
        +
Operator images
        +
RHACS operand images
        =
Complete disconnected RHACS installation
```

---

# 2. Recommended Tool: oc-mirror

For current OpenShift disconnected environments, `oc-mirror` is the preferred Red Hat-supported approach for mirroring Operator catalogs and container images.

The high-level workflow is:

```text
OpenShift Catalog
       |
       v
oc-mirror
       |
       v
Internal Registry
       |
       v
ImageContentSourcePolicy /
ImageDigestMirrorSet
       |
       v
Disconnected OpenShift
```

The exact API used for image mirroring depends on the OpenShift version.

For newer OpenShift versions, `ImageDigestMirrorSet` and related mirror configuration are used instead of older `ImageContentSourcePolicy` configurations where supported.

---

# 3. Prepare the Connected Mirror Host

Use a system that has:

* Internet access
* Sufficient disk space
* `oc`
* `oc-mirror`
* Registry authentication
* Access to the destination registry
* Credentials with permission to pull required Red Hat content

Check:

```bash
oc version
```

Check the mirror tool:

```bash
oc mirror --help
```

The `oc-mirror` version should be compatible with the OpenShift version being managed.

---

# 4. Authenticate to Red Hat Registry

Authenticate the mirror host to the registries required by the selected RHACS release.

For example:

```bash
podman login registry.redhat.io
```

Enter the approved Red Hat registry credentials.

Verify:

```bash
podman login --get-login registry.redhat.io
```

For production environments, use the organization's approved registry credentials and secret-management process.

Do not place passwords directly into Git repositories or shell scripts.

---

# 5. Authenticate to the Internal Registry

Assume the corporate mirror registry is:

```text
registry.example.com
```

Authenticate:

```bash
podman login registry.example.com
```

Verify:

```bash
podman login --get-login registry.example.com
```

The mirror account needs permission to create repositories and push images.

---

# 6. Configure the RHACS Operator Catalog

Create an `ImageSetConfiguration` for the content that must be mirrored.

A conceptual example is:

```yaml
apiVersion: mirror.openshift.io/v2alpha1
kind: ImageSetConfiguration
storageConfig:
  registry:
    imageURL: registry.example.com/ocp4/openshift4
mirror:
  operators:
    - catalog: registry.redhat.io/redhat/redhat-operator-index:v4.18
      packages:
        - name: rhacs-operator
```

The exact API version, catalog image, package name, and channel/version must match the OpenShift and RHACS versions being deployed.

Before using a configuration in production, verify it against the Red Hat documentation for the specific OpenShift release.

---

# 7. Select the RHACS Version

Do not mirror an uncontrolled set of RHACS versions.

Decide:

```text
OpenShift version
RHACS version
RHACS Operator channel
RHACS Operator version
```

For example:

```text
OpenShift
    |
    +-- 4.x
          |
          +-- RHACS Operator
                |
                +-- selected supported channel
                |
                +-- selected RHACS release
```

This makes upgrades and rollback planning easier.

---

# 8. Discover Available RHACS Package Information

On a connected OpenShift environment, you can inspect available packages:

```bash
oc get packagemanifest -A | grep -i rhacs
```

Or inspect the catalog directly according to the catalog-management method being used.

You should identify:

```text
Package name
Channel
Current version
Available versions
Bundle image
Related images
```

Do not guess image names.

Use the catalog metadata associated with the exact RHACS release.

---

# 9. Create the Mirror Configuration

A simplified configuration may look like:

```yaml
apiVersion: mirror.openshift.io/v2alpha1
kind: ImageSetConfiguration
mirror:
  operators:
    - catalog: registry.redhat.io/redhat/redhat-operator-index:v4.18
      packages:
        - name: rhacs-operator
          channels:
            - name: stable
```

The exact channel should be selected according to the RHACS release and your organization's support requirements.

You can also control which versions are mirrored.

For example, conceptually:

```yaml
packages:
  - name: rhacs-operator
    channels:
      - name: stable
        minVersion: <version>
        maxVersion: <version>
```

Use the version-selection syntax supported by your installed `oc-mirror` version.

---

# 10. Mirror the Catalog

Run the appropriate `oc mirror` command for your `oc-mirror` version.

A typical workflow looks like:

```bash
oc mirror \
  --config=imageset-config.yaml \
  docker://registry.example.com
```

This downloads the selected catalog and images and pushes them to the internal registry.

The process may take significant time because Operator catalogs can contain many related images.

---

# 11. What Happens During Mirroring?

Conceptually:

```text
Red Hat Registry
      |
      | Pull
      v
oc-mirror
      |
      +-- Operator catalog
      |
      +-- RHACS operator
      |
      +-- RHACS related images
      |
      v
Internal Registry
```

The mirror process also generates configuration/manifests required to configure the disconnected cluster.

---

# 12. Review the Generated Files

After mirroring, inspect the generated directory.

For example:

```bash
find ./oc-mirror-workspace -type f
```

Depending on the `oc-mirror` version, generated files can include:

```text
CatalogSource
ImageDigestMirrorSet
ImageContentSourcePolicy
Other mirror configuration
```

Do not manually modify generated mirror metadata unless you understand the consequences.

# 14. Transfer Content Into the Disconnected Network

If the mirror registry is directly reachable from the disconnected cluster, no additional physical transfer is required.

If there is a true air gap, use the organization's approved transfer process.

Conceptually:

```text
Internet
   |
   v
Connected Mirror Host
   |
   | Export
   v
Portable Storage
   |
   | Security inspection
   v
Disconnected Network
   |
   v
Internal Registry
```

The transfer process must comply with corporate security policies.

---

# 15. Configure the Disconnected OpenShift Cluster

The disconnected cluster needs to know where mirrored content exists.

Depending on the OpenShift version and mirroring method, this may involve generated:

```text
ImageDigestMirrorSet
ImageTagMirrorSet
ImageContentSourcePolicy
CatalogSource
```

For modern OpenShift installations, prefer the mirror configuration generated and supported for your OpenShift version.

---

# 16. Apply the Mirror Configuration

For example, if `oc-mirror` generated an `ImageDigestMirrorSet`:

```bash
oc apply -f image-digest-mirror-set.yaml
```

Verify:

```bash
oc get imagedigestmirrorset
```

If your OpenShift version uses another supported mechanism, apply the generated resources instead.

---

# 17. Create the Disconnected CatalogSource

The mirrored Operator catalog must be exposed to OLM.

Conceptually:

```text
Internal Registry
       |
       v
CatalogSource
       |
       v
OperatorHub / OLM
       |
       v
RHACS Operator
```

Check:

```bash
oc get catalogsource -A
```

For example:

```bash
oc get catalogsource -n openshift-marketplace
```

Check the CatalogSource status:

```bash
oc describe catalogsource <catalog-name> \
  -n openshift-marketplace
```

---

# 18. Verify the RHACS Package

Check:

```bash
oc get packagemanifest \
  -n openshift-marketplace | grep -i rhacs
```

If the mirrored catalog is working correctly, the RHACS Operator package should become visible.

This confirms that:

```text
Registry
   |
   v
CatalogSource
   |
   v
OLM
   |
   v
RHACS package
```

is working.

---

# 19. Create the RHACS Subscription

Once the mirrored catalog is available, create the RHACS Operator subscription.

Example:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: rhacs-operator
  namespace: rhacs-operator
spec:
  channel: stable
  name: rhacs-operator
  source: <mirrored-catalog>
  sourceNamespace: openshift-marketplace
```

The exact namespace, channel, and source name must match your mirrored RHACS catalog.

---

# 20. Verify OLM Installation

Check:

```bash
oc get subscription -n rhacs-operator
```

Check the InstallPlan:

```bash
oc get installplan -n rhacs-operator
```

Check the CSV:

```bash
oc get csv -n rhacs-operator
```

A successful installation should eventually show:

```text
Succeeded
```

For example:

```text
NAME                       PHASE
rhacs-operator.vX.Y.Z      Succeeded
```

---

# 21. Verify Operator Pods

Check:

```bash
oc get pods -n rhacs-operator
```

Expected result:

```text
NAME                                READY   STATUS
rhacs-operator-xxxxxxxxx            1/1     Running
```

If the Operator Pod shows:

```text
ImagePullBackOff
```

investigate the registry configuration before proceeding.

---

# 22. Install Central

After the RHACS Operator is available, create the RHACS `Central` custom resource.

For example:

```yaml
apiVersion: platform.stackrox.io/v1alpha1
kind: Central
metadata:
  name: central
  namespace: stackrox
spec:
  central:
    exposure:
      route:
        enabled: true
```

The exact CR configuration depends on the RHACS version and desired architecture.

The Operator should then create the RHACS components from the mirrored images.

---

# 23. Verify Central Images

Check:

```bash
oc get pods -n stackrox
```

You should see RHACS components becoming ready.

If Central fails:

```bash
oc describe pod <central-pod> -n stackrox
```

Look at Events for:

```text
Failed to pull image
ErrImagePull
ImagePullBackOff
unauthorized

```

# 24. Verify Image References

Inspect the Pod:

```bash
oc get pod <central-pod> \
  -n stackrox \
  -o jsonpath='{.spec.containers[*].image}'
```

This helps verify that the expected mirrored image is being used.

Also inspect:

```bash
oc get deployment -n stackrox
```

and:

```bash
oc get statefulset -n stackrox
```

where applicable.

# 25. Common Failure: Image Not Mirrored

Symptom:

```text
manifest unknown
```

or:

```text
ImagePullBackOff
```

Troubleshooting:

```text
RHACS Pod
   |
   v
Requested image
   |
   v
Internal Registry
   |
   +-- Image exists?
        |
        +-- NO --> Mirror missing image
        |
        +-- YES
              |
              v
         Authentication
```

Find the exact image:

```bash
oc describe pod <pod> -n stackrox
```

Then verify that image exists in the internal registry.

---

# 26. Common Failure: Registry Authentication

Symptom:

```text
unauthorized: authentication required
```

Check:

```bash
oc get secret -n stackrox
```

Verify that the correct registry credentials are available to the ServiceAccount used by the RHACS component.

Also check:

```bash
oc get serviceaccount -n stackrox
```

and inspect image pull secrets:

```bash
oc get serviceaccount <serviceaccount> \
  -n stackrox \
  -o yaml
```

---

# 27. Common Failure: Registry CA

Symptom:

```text
x509: certificate signed by unknown authority
```

Verify the registry certificate:

```bash
openssl s_client \
  -connect registry.example.com:443 \
  -showcerts
```

Confirm that OpenShift trusts the registry's CA.

Do not disable TLS verification as a workaround.

---

# 28. Common Failure: CatalogSource Unavailable

Check:

```bash
oc get catalogsource \
  -n openshift-marketplace
```

Then:

```bash
oc describe catalogsource <catalog-name> \
  -n openshift-marketplace
```

Check CatalogSource Pods:

```bash
oc get pods \
  -n openshift-marketplace
```

Look for:

```text
ImagePullBackOff
ErrImagePull
CrashLoopBackOff
```

The catalog image itself must be accessible from the disconnected registry.

---

# 29. Common Failure: Wrong OpenShift Catalog

The catalog must correspond to the OpenShift release.

For example:

```text
OpenShift 4.x
       |
       +-- matching Red Hat Operator catalog
               |
               +-- RHACS Operator
```

Do not blindly use a catalog intended for another OpenShift release.

Verify:

```bash
oc version
```

before preparing the mirror.

---

# 30. Common Failure: Wrong RHACS Channel

If the Subscription references a channel that is not available in the mirrored catalog, OLM may not find the expected version.

Check:

```bash
oc get subscription -n rhacs-operator
```

and:

```bash
oc describe subscription rhacs-operator \
  -n rhacs-operator
```

Verify the channel against the mirrored package metadata.

---

# 31. Mirror Only What You Need

A disconnected registry can consume significant storage.

Avoid mirroring every available Operator and every RHACS version unless there is a business requirement.

Prefer:

```text
Required OpenShift catalog
        +
Required RHACS package
        +
Required RHACS channel
        +
Required RHACS version(s)
```

This reduces:

* Registry storage
* Mirror time
* Transfer size
* Maintenance effort
* Security review scope

# 33. Upgrade Strategy

Treat RHACS upgrades as another mirroring operation.

For example:

```text
Current RHACS
     |
     v
Select target release
     |
     v
Mirror catalog
     |
     v
Mirror target images
     |
     v
Validate internal registry
     |
     v
Update disconnected catalog
     |
     v
Update Subscription
     |
     v
OLM installs target Operator
     |
     v
RHACS upgrade
```

Before upgrading, verify that the target version is supported with the OpenShift version.

# 36. Interview Answer

**Question:** How do you mirror RHACS Operator catalogs and images for a disconnected OpenShift cluster?

**Answer:**

> I first identify the OpenShift and RHACS versions and verify their compatibility. On a connected mirror host, I authenticate to the required Red Hat registries and the corporate registry, then use the supported `oc-mirror` workflow to mirror the required RHACS Operator catalog, Operator images, and RHACS operand images into the internal registry. I then transfer the content into the disconnected environment if required, configure the appropriate OpenShift image mirror resources and registry CA/authentication, and expose the mirrored catalog through a `CatalogSource`. After verifying the RHACS package through OLM, I create the Subscription, verify the InstallPlan and CSV, and then deploy Central. Finally, I verify that all RHACS Pods pull their images successfully from the internal registry.

# 37. Key Takeaway

The complete disconnected RHACS flow is:

```text
RHACS Release
     |
     v
Red Hat Operator Catalog
     |
     v
oc-mirror
     |
     +-----------------------+
     |                       |
     v                       v
Operator Catalog        RHACS Images
     |                       |
     +-----------+-----------+
                 |
                 v
        Internal Registry
                 |
                 v
       Mirror Configuration
                 |
                 v
          CatalogSource
                 |
                 v
                OLM
                 |
                 v
          RHACS Operator
                 |
                 v
             Central
                 |
                 v
       RHACS Components
```

The most important principle is:

> **Mirror both the Operator catalog and every required RHACS image. A mirrored catalog without operand images, or mirrored images without a usable disconnected catalog, is not a complete RHACS disconnected installation.**

Always use the Red Hat documentation and tooling version appropriate to the specific OpenShift and RHACS releases being deployed, because `oc-mirror` APIs, mirror resources, and supported RHACS channels can change between releases.
