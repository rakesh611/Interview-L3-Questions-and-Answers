# How Do Build-Time and Runtime Evidence Differ?

## 1. Overview

In RHACS, **build-time evidence** and **runtime evidence** answer different security questions.

The simplest distinction is:

```text
Build Time
    |
    | "What is inside this image and how was it built?"
    v
Container Image
    |
    v
Runtime
    |
    | "What is actually happening in the cluster?"
    v
Running Workload
```

Build-time evidence describes the **artifact before or around deployment**.

Runtime evidence describes the **actual behavior of the workload after it is running**.

Both are important because a container image can be secure when built but behave unexpectedly at runtime, and a runtime workload can be exposed to risks because of how it is deployed.

---

# 2. Build-Time Evidence

Build-time evidence is information available before the application is running in production.

Typical sources include:

* Container image
* Image layers
* Package information
* Software components
* Known vulnerabilities
* Image metadata
* Dockerfile or Containerfile
* CI/CD pipeline information
* Image registry information
* Build process
* Image configuration

For example:

```text
Developer
    |
    v
Git Repository
    |
    v
Dockerfile / Containerfile
    |
    v
CI/CD Pipeline
    |
    v
Container Image
    |
    v
RHACS Image Analysis
```

RHACS can use image-related information to identify security risks before the workload is deployed.

---

# 3. Example of Build-Time Evidence

Suppose a developer builds:

```text
payment-api:v10
```

The image contains:

```text
Application
OpenSSL
glibc
Python
curl
Operating-system packages
Application dependencies
```

A vulnerability scanner may identify:

```text
OpenSSL
   |
   +-- CVE
   |
   +-- Severity: Critical
```

This is build-time evidence because the vulnerable component exists **inside the image**.

The security team can identify the issue before deployment.

---

# 4. What Build-Time Evidence Tells You

Build-time evidence can answer questions such as:

### What packages are inside the image?

```text
Image
 |
 +-- Package A
 +-- Package B
 +-- Package C
```

### Does the image contain known vulnerabilities?

```text
Image
 |
 +-- CVE-XXXX
 +-- CVE-YYYY
```

### Which image is being deployed?

```text
Deployment
     |
     v
payment-api:v10
```

### Where did the image come from?

```text
Registry
    |
    v
payment-api:v10
```

### Is the image associated with a risky component?

For example:

```text
Outdated package
Unpatched library
Known vulnerability
Risky configuration
```

---

# 5. Runtime Evidence

Runtime evidence is collected from the workload while it is actually running.

The question changes from:

> What is inside the image?

to:

> What is the workload actually doing?

A simplified flow is:

```text
Kubernetes Cluster
       |
       v
Running Pod
       |
       +-- Process activity
       +-- Network activity
       +-- Container behavior
       +-- Runtime events
       |
       v
RHACS Runtime Security
       |
       v
Security Finding
```

Runtime evidence is therefore based on observed behavior rather than only the static contents of an image.

---

# 6. Example of Runtime Evidence

Suppose:

```text
payment-api
```

is running normally.

Expected behavior:

```text
payment-api
   |
   +-- Listen on TCP/8080
   |
   +-- Connect to payment-db
   |
   +-- Serve application requests
```

Suddenly the container starts:

```text
payment-api
   |
   +-- Start unexpected shell
   |
   +-- Execute unusual command
   |
   +-- Access unexpected resource
   |
   +-- Make unexpected network connection
```

That activity is runtime evidence.

The image itself may not have changed.

---

# 7. Runtime Evidence Can Reveal Behavior

Consider an image:

```text
myapp:v1
```

The image contains:

```text
Java
Application
Libraries
```

The image scan may report:

```text
No critical vulnerabilities
```

However, after deployment:

```text
myapp:v1
     |
     +-- Unexpected process starts
     |
     +-- Unexpected network connection
     |
     +-- Suspicious runtime behavior
```

The image can still be considered clean from a vulnerability perspective while its **runtime behavior is suspicious**.

This demonstrates why image scanning alone is insufficient.

---

# 8. Build-Time vs Runtime Evidence

| Area                     | Build-Time Evidence           | Runtime Evidence                      |
| ------------------------ | ----------------------------- | ------------------------------------- |
| Primary question         | What was built?               | What is happening?                    |
| Main subject             | Image                         | Running workload                      |
| Timing                   | Before deployment             | During execution                      |
| Source                   | Image/registry/build pipeline | Running Kubernetes workload           |
| Vulnerabilities          | Yes                           | Can correlate with running workload   |
| Package information      | Yes                           | Not the primary focus                 |
| Process behavior         | No                            | Yes                                   |
| Network behavior         | Limited/static context        | Yes                                   |
| Container activity       | No                            | Yes                                   |
| Deployment configuration | Some                          | Yes, in actual cluster context        |
| Runtime anomaly          | No                            | Yes                                   |
| Main security goal       | Prevent risky artifacts       | Detect/protect against risky behavior |

---

# 9. Build-Time Evidence Flow

A typical flow is:

```text
Source Code
     |
     v
Dockerfile / Containerfile
     |
     v
Build
     |
     v
Container Image
     |
     +------------------+
     |                  |
     v                  v
Registry           RHACS Scanner
                        |
                        v
                 Vulnerability Data
                        |
                        v
                  Security Finding
```

The evidence exists before the workload starts running.

---

# 10. Runtime Evidence Flow

Runtime evidence follows a different path:

```text
Container Image
       |
       v
Kubernetes Deployment
       |
       v
Running Pod
       |
       v
Container Runtime
       |
       +-- Process Activity
       +-- Network Activity
       +-- Runtime Events
       |
       v
RHACS Components
       |
       v
RHACS Central
       |
       v
Security Finding
```

This evidence represents what is actually happening in the cluster.

---

# 11. Build-Time Evidence Example: Vulnerable Package

Suppose an image contains:

```text
nginx
OpenSSL 1.x
```

The vulnerability database identifies:

```text
OpenSSL
   |
   +-- Known vulnerability
   |
   +-- High severity
```

RHACS can associate the vulnerability with:

```text
Image
   |
   +-- Deployment
          |
          +-- Namespace
                 |
                 +-- Cluster
```

The security team can therefore understand where the vulnerable image is being used.

---

# 12. Runtime Evidence Example: Unexpected Process

Suppose the normal process is:

```text
PID 1
 |
 +-- java
```

But runtime activity shows:

```text
PID 1
 |
 +-- java
      |
      +-- /bin/sh
           |
           +-- curl
```

If this behavior is unexpected for the application, it can become a security signal.

The important difference is:

```text
Image Evidence:
"Does the image contain curl?"

Runtime Evidence:
"Is curl actually being executed?"
```

These are different questions.

---

# 13. Runtime Evidence Example: Network Activity

Suppose the expected architecture is:

```text
frontend
   |
   v
backend
   |
   v
database
```

But the backend suddenly communicates with an unexpected external destination:

```text
backend
   |
   +---------------------> Unknown external destination
```

This is runtime evidence.

It can provide important context that cannot be obtained simply by looking at the container image.

---

# 14. Build-Time Evidence and Admission Control

Build-time evidence can be used to make deployment decisions.

For example:

```text
Image
 |
 v
RHACS Scanner
 |
 v
Critical Vulnerability
 |
 v
RHACS Policy
 |
 +---- Violation ----> Deployment blocked
```

This creates a security gate before the workload enters the cluster.

---

# 15. Runtime Evidence and Detection

Runtime evidence is more relevant after the workload has been admitted and started.

For example:

```text
Deployment
    |
    v
Pod starts
    |
    v
Runtime behavior
    |
    +---- Normal ------> Continue
    |
    +---- Suspicious --> Alert / Policy Action
```

This provides a second security layer.

---

# 16. Why Both Are Required

Consider this example:

```text
Build Time
-----------
Image has no critical vulnerabilities
        |
        v
Deployment allowed
        |
        v
Runtime
-----------
Unexpected process starts
        |
        v
Security alert
```

Now consider the reverse:

```text
Build Time
-----------
Image contains critical vulnerability
        |
        v
Deployment blocked
```

In the first example, runtime security catches something that static image analysis did not identify.

In the second example, build-time security prevents a known-risky artifact from being deployed.

Therefore:

```text
Build-Time Security
        +
Runtime Security
        =
Defense in Depth
```

# 17. Relationship With CI/CD

Build-time evidence is particularly useful in DevSecOps pipelines.

Example:

```text
Git
 |
 v
Jenkins
 |
 v
Build Image
 |
 v
RHACS Scan
 |
 +---- Policy violation ---> FAIL
 |
 +---- Pass ---------------> Registry
                                  |
                                  v
                              Kubernetes
```

This prevents security problems from reaching later stages of the deployment lifecycle.

---

# 18. Relationship With Kubernetes Configuration

Runtime security is not only about processes.

The actual Kubernetes deployment configuration also matters.

For example:

```yaml
securityContext:
  privileged: true
```

or:

```yaml
hostNetwork: true
```

or:

```yaml
allowPrivilegeEscalation: true
```

These configurations can significantly affect the runtime security posture.

Therefore, RHACS evaluates security in the context of:

```text
Image
 +
Deployment
 +
Kubernetes Configuration
 +
Runtime Behavior
```

# 22. Important Distinction

The easiest way to remember the difference is:

```text
BUILD-TIME
"What is this image?"

RUNTIME
"What is this workload doing?"
```

Another useful distinction is:

```text
Build-Time = Artifact Security

Runtime = Behavior Security
```

And in an enterprise environment:

```text
Build-Time
     |
     v
Prevent bad artifacts

Runtime
     |
     v
Detect/respond to bad behavior
```

---

# 23. Comparison With Traditional Image Scanning

A traditional image scanner primarily answers:

```text
Does this image contain known vulnerabilities?
```

RHACS goes further by correlating:

```text
Image
 +
Kubernetes configuration
 +
Deployment
 +
Cluster
 +
Runtime behavior
```

Therefore, the security decision can be more contextual.

For example:

```text
Image has vulnerability
       |
       +-- Is it actually deployed?
       |
       +-- Which cluster?
       |
       +-- Which namespace?
       |
       +-- Which workload?
       |
       +-- Is the vulnerable component actually relevant?
       |
       +-- Is suspicious runtime activity also occurring?
```

---

# 24. Interview Answer

A concise interview answer is:

> **Build-time evidence describes the security characteristics of an artifact before it runs, such as image contents, packages, vulnerabilities, and image metadata. Runtime evidence describes what the deployed workload is actually doing, such as process activity, network behavior, and runtime events. RHACS combines these sources with Kubernetes configuration and deployment context to provide a more complete security assessment. Build-time controls help prevent risky images from being deployed, while runtime security helps detect suspicious behavior after workloads are running.**
