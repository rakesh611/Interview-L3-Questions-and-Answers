# How Do You Validate RHACS Operator and Central Readiness?

After installing RHACS, do not assume that the installation is complete just because the Operator or Central Pod is `Running`.

A proper validation checks:

1. RHACS Operator installation
2. Operator Pod readiness
3. CSV status
4. Subscription status
5. Central Custom Resource
6. Central Deployment/Pods
7. Central Services
8. Central health/readiness
9. Routes or other exposure
10. RHACS application login
11. Logs and events
12. Dependent components such as Scanner

The validation flow is:

```text
RHACS Operator
      |
      v
Subscription
      |
      v
InstallPlan
      |
      v
CSV = Succeeded
      |
      v
Operator Pod = Ready
      |
      v
Central CR
      |
      v
Central Deployment/Pods
      |
      v
Services
      |
      v
Route / Endpoint
      |
      v
RHACS UI/API
      |
      v
Ready
```

---

## 1. Confirm the RHACS Operator Namespace

First identify the namespace where the RHACS Operator was installed.

For example:

```bash
oc get namespace | grep -i rhacs
```

A common namespace is:

```text
rhacs-operator
```

Check:

```bash
oc get pods -n rhacs-operator
```

Expected:

```text
NAME                                READY   STATUS
rhacs-operator-xxxxxxxxxx           1/1     Running
```

A `Running` Pod is useful, but it is not by itself proof that the Operator is fully ready.

---

## 2. Validate the Operator Subscription

Check the Subscription:

```bash
oc get subscription -n rhacs-operator
```

Example:

```text
NAME             PACKAGE          CHANNEL
rhacs-operator   rhacs-operator   stable
```

Inspect it:

```bash
oc describe subscription rhacs-operator \
  -n rhacs-operator
```

Look for:

```text
InstallPlan:
State:
Current CSV:
Installed CSV:
```

The Subscription should reference the expected RHACS channel and version.

---

## 3. Validate the InstallPlan

Check:

```bash
oc get installplan -n rhacs-operator
```

Example:

```text
NAME            CSV                         APPROVAL
install-xxxxx   rhacs-operator.vX.Y.Z      Automatic
```

If approval is manual, verify the InstallPlan is approved.

Check:

```bash
oc describe installplan <installplan-name> \
  -n rhacs-operator
```

A pending manual InstallPlan means the Operator may not have been installed yet.

---

## 4. Validate the CSV

The ClusterServiceVersion (CSV) is one of the most important Operator readiness indicators.

Run:

```bash
oc get csv -n rhacs-operator
```

Expected:

```text
NAME                       DISPLAY          VERSION   PHASE
rhacs-operator.vX.Y.Z      RHACS Operator   X.Y.Z     Succeeded
```

The key value is:

```text
PHASE = Succeeded
```

If you see:

```text
Pending
Installing
Failed
Replacing
```

the Operator installation requires further investigation.

---

## 5. Inspect a Failed CSV

If the CSV is not `Succeeded`:

```bash
oc describe csv rhacs-operator.vX.Y.Z \
  -n rhacs-operator
```

Check:

* Conditions
* Events
* Install status
* Related objects
* Deployment status

Also check namespace events:

```bash
oc get events \
  -n rhacs-operator \
  --sort-by=.lastTimestamp
```

---

## 6. Validate the Operator Deployment

Check Deployments:

```bash
oc get deployment -n rhacs-operator
```

Expected:

```text
NAME             READY   UP-TO-DATE   AVAILABLE
rhacs-operator   1/1     1            1
```

Then inspect:

```bash
oc describe deployment rhacs-operator \
  -n rhacs-operator
```

You want:

```text
Available replicas: 1
Ready replicas:     1
```

---

## 7. Validate the Operator Pod

Run:

```bash
oc get pods \
  -n rhacs-operator \
  -o wide
```

Expected:

```text
READY   STATUS
1/1     Running
```

Check readiness:

```bash
oc get pod <operator-pod> \
  -n rhacs-operator \
  -o jsonpath='{.status.containerStatuses[*].ready}'
```

Expected:

```text
true
```

---

## 8. Check Operator Logs

Operator logs are important even when the Pod is `Running`.

Run:

```bash
oc logs deployment/rhacs-operator \
  -n rhacs-operator
```

Look for:

```text
error
failed
reconcile
timeout
forbidden
unauthorized
x509
ImagePull
```

Normal Operator logs should show successful reconciliation rather than repeated failures.

---

# 9. Validate RHACS Custom Resources

After the Operator is ready, check RHACS resources.

Run:

```bash
oc api-resources | grep -i stackrox
```

You should see RHACS-related resources.

Check Central:

```bash
oc get central -A
```

Example:

```text
NAMESPACE   NAME       STATUS
stackrox    central    ...
```

---

# 10. Validate the Central Custom Resource

Inspect Central:

```bash
oc get central central \
  -n stackrox \
  -o yaml
```

You should inspect:

```text
spec
status
conditions
```

A healthy Central should eventually report a successful/ready status appropriate to the installed RHACS version.

You can also use:

```bash
oc describe central central \
  -n stackrox
```

Check:

* Conditions
* Events
* Central configuration
* Exposure configuration
* Persistence configuration
* TLS configuration
* Reconciliation errors

---

# 11. Validate Central Pods

Check:

```bash
oc get pods -n stackrox
```

Typical RHACS components include:

```text
central
scanner
scanner-db
```

Depending on the RHACS release and configuration, additional components may exist.

The important requirement is that the required Pods become:

```text
Running
```

and containers become:

```text
Ready
```

Do not rely only on Pod phase.

---

# 12. Check Pod Readiness

For Central:

```bash
oc get pod <central-pod> \
  -n stackrox
```

Then:

```bash
oc describe pod <central-pod> \
  -n stackrox
```

Look at:

```text
Conditions
Containers
Readiness
Events
```

A healthy Pod should have:

```text
Ready = True
```

---

# 13. Check Central Deployment

Run:

```bash
oc get deployment -n stackrox
```

Example:

```text
NAME      READY   UP-TO-DATE   AVAILABLE
central   1/1     1            1
```

If Central is not ready:

```bash
oc describe deployment central \
  -n stackrox
```

Check for:

```text
Unavailable replicas
FailedCreate
ImagePullBackOff
MountVolume errors
Probe failures
Scheduling failures
```

---

# 14. Validate Central Services

List services:

```bash
oc get svc -n stackrox
```

You should see the Central service.

For example:

```text
NAME      TYPE       CLUSTER-IP
central   ClusterIP  172.x.x.x
```

Inspect it:

```bash
oc describe svc central \
  -n stackrox
```

Important checks include:

```text
Selector
Endpoints
Ports
TargetPort
```

---

# 15. Check Central Endpoints

Run:

```bash
oc get endpoints -n stackrox
```

or, on newer clusters:

```bash
oc get endpointslice -n stackrox
```

The Central service should have endpoints pointing to ready Central Pods.

If a Service exists but has no endpoints, investigate:

```text
Service selector
       |
       v
Pod labels
       |
       v
Pod readiness
```

---

# 16. Validate the Central Route

If Central is exposed through an OpenShift Route:

```bash
oc get route -n stackrox
```

Example:

```text
NAME      HOST/PORT
central   central-stackrox.apps.example.com
```

Inspect:

```bash
oc describe route central \
  -n stackrox
```

Check:

* Host
* Service
* Target port
* TLS termination
* Certificate
* Ingress status

---

# 17. Test Central DNS

From a client system:

```bash
dig central-stackrox.apps.example.com
```

or:

```bash
nslookup central-stackrox.apps.example.com
```

Verify that DNS resolves to the expected OpenShift ingress/load-balancer address.

---

# 18. Test Central HTTPS

From an appropriate client:

```bash
curl -vk \
  https://central-stackrox.apps.example.com
```

A response from Central indicates that the request reached the RHACS endpoint.

For production validation, use the correct trusted CA instead of relying on `-k`.

For example:

```bash
curl \
  --cacert corporate-ca.crt \
  https://central-stackrox.apps.example.com
```

---

# 19. Validate the Central Certificate

Inspect the certificate:

```bash
openssl s_client \
  -connect central-stackrox.apps.example.com:443 \
  -servername central-stackrox.apps.example.com
```

Check:

* Subject
* Issuer
* SAN
* Expiration
* Certificate chain

The certificate SAN must contain the hostname being accessed.

---

# 20. Validate Central Logs

Check Central logs:

```bash
oc logs deployment/central \
  -n stackrox
```

If there are multiple containers:

```bash
oc get pod <central-pod> \
  -n stackrox \
  -o jsonpath='{.spec.containers[*].name}'
```

Then:

```bash
oc logs <central-pod> \
  -n stackrox \
  -c <container-name>
```

Look for repeated:

```text
ERROR
FATAL
panic
connection refused
timeout
x509
database
certificate
```

---

# 21. Check Central Events

Run:

```bash
oc get events \
  -n stackrox \
  --sort-by=.lastTimestamp
```

Important events include:

```text
FailedScheduling
FailedMount
FailedPull
FailedCreate
Unhealthy
BackOff
FailedProbe
```

A healthy deployment should not have continuously repeating failure events.

---

# 22. Validate Central Storage

If persistent storage is configured, check PVCs:

```bash
oc get pvc -n stackrox
```

Expected:

```text
STATUS = Bound
```

For example:

```text
NAME              STATUS   VOLUME
central-db        Bound    pvc-xxxxxxxx
```

If a PVC is `Pending`, Central may not become ready.

Investigate:

```bash
oc describe pvc <pvc-name> \
  -n stackrox
```

---

# 23. Validate Central Scheduling

Check:

```bash
oc get pod <central-pod> \
  -n stackrox \
  -o wide
```

Confirm:

* Node assignment
* Pod IP
* Container readiness
* Restart count

If the Pod is pending:

```bash
oc describe pod <central-pod> \
  -n stackrox
```

Look for:

```text
Insufficient CPU
Insufficient memory
Node selector mismatch
Taint/toleration problem
Affinity problem
PVC problem
```

---

```text

   |
```

# 29. Common Readiness Problems

| Component    | Status           | Common Cause                            |
| ------------ | ---------------- | --------------------------------------- |
| Subscription | Missing/Pending  | Wrong catalog/channel                   |
| InstallPlan  | Pending          | Manual approval required                |
| CSV          | Failed           | Operator installation problem           |
| Operator Pod | CrashLoopBackOff | Operator configuration/dependency issue |
| Central CR   | Not Ready        | Central reconciliation problem          |
| Central Pod  | Pending          | CPU/memory/storage/scheduling           |
| Central Pod  | ImagePullBackOff | Registry/image problem                  |
| Central Pod  | CrashLoopBackOff | Application/configuration problem       |
| Service      | No endpoints     | Pod selector/readiness issue            |
| Route        | 503              | Backend Pod/service not ready           |
| Route        | TLS error        | Certificate/CA/SAN problem              |
| PVC          | Pending          | Storage problem                         |

# 30. Corporate/L3 Validation Approach

At L3 level, validate the entire dependency chain rather than restarting Pods immediately.

Use this model:

```text
                   RHACS Operator
                         |
              +----------+----------+
              |                     |
        OLM/CSV Status          Operator Logs
              |
              v
          Central CR
              |
        +-----+------+
        |            |
     Storage      Scheduling
        |            |
        +-----+------+
              |
              v
         Central Pod
              |
        +-----+------+
        |            |
     Readiness     Logs
        |
        v
       Service
        |
        v
      Route
        |
        v
      DNS/TLS
        |
        v
    RHACS Console
```

This approach prevents treating every RHACS issue as an Operator problem.

# 31. Interview Answer

**Question:** How do you validate RHACS Operator and Central readiness?

**Answer:**

> I first validate the RHACS Subscription, InstallPlan, and CSV. The CSV should reach `Succeeded`, and the Operator Deployment and Pod should be available and ready. I then validate the Central Custom Resource, Central Deployment and Pods, storage, Services, endpoints, and Route. I check Pod readiness rather than relying only on the `Running` phase. Finally, I test DNS, TLS, the RHACS endpoint, and authentication. If anything is unhealthy, I inspect `oc describe`, events, Operator/Central logs, registry access, storage, scheduling, and certificate configuration to identify the failing dependency.

---

# 32. Final Readiness Criteria

Consider RHACS ready only when the following are true:

```text
[✓] Subscription configured
[✓] InstallPlan completed
[✓] CSV = Succeeded
[✓] Operator Deployment available
[✓] Operator Pod Ready
[✓] Central CR healthy/ready
[✓] Central Pod Ready
[✓] Required storage Bound
[✓] Central Service has endpoints
[✓] Route/endpoint available
[✓] DNS resolves correctly
[✓] TLS certificate is valid
[✓] RHACS UI/API is reachable
[✓] Authentication works
[✓] No persistent critical events/errors
```

The key principle is:

> **Operator readiness means the RHACS Operator is successfully installed and reconciling resources. Central readiness means the Central workload and its dependencies are healthy, reachable, and capable of serving RHACS users and APIs. Validate both levels independently before declaring the RHACS installation successful.**
