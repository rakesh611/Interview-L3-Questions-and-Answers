# How to Configure Central Exposure Through an OpenShift Route

## 1. Overview

RHACS Central can be exposed externally through an OpenShift `Route`.

The basic architecture is:

```text
User Browser
     |
     | HTTPS
     v
OpenShift Router
     |
     v
OpenShift Route
     |
     v
Central Service
     |
     v
Central Pod
```

When RHACS is installed using the RHACS Operator, the preferred approach is to configure Route exposure through the `Central` custom resource rather than manually creating a Route.

---

## 2. Prerequisites

Before configuring Route exposure, verify that:

* RHACS Operator is installed.
* The `Central` custom resource exists.
* Central is running.
* The `stackrox` namespace exists.
* OpenShift ingress/router is healthy.
* A working application domain exists.

Check the namespace:

```bash
oc get namespace stackrox
```

Check the Operator:

```bash
oc get pods -n rhacs-operator
```

Check Central:

```bash
oc get central -n stackrox
```

Check Central pods:

```bash
oc get pods -n stackrox
```

---

## 3. Verify Central Service

Before exposing Central, verify that the Central Service exists.

```bash
oc get svc -n stackrox
```

Inspect the service:

```bash
oc describe svc central -n stackrox
```

Also check that the Service has endpoints:

```bash
oc get endpoints -n stackrox
```

Depending on the RHACS version, the exact Service names can differ.

The important requirement is that the Central Service has healthy endpoints.

---

## 4. Configure Route Exposure in the Central CR

The RHACS Operator can manage the OpenShift Route when Route exposure is enabled in the `Central` custom resource.

A simplified example is:

```yaml
apiVersion: platform.stackrox.io/v1alpha1
kind: Central
metadata:
  name: stackrox-central-services
  namespace: stackrox
spec:
  central:
    exposure:
      route:
        enabled: true
```

Apply the configuration:

```bash
oc apply -f central.yaml
```

The RHACS Operator detects the change and reconciles the required resources.

---

## 5. Check the Central CR

After applying the configuration:

```bash
oc get central -n stackrox
```

For more details:

```bash
oc describe central stackrox-central-services -n stackrox
```

Look for status information indicating that Central is progressing toward a healthy state.

---

## 6. Verify the Route

Check the Route:

```bash
oc get route -n stackrox
```

Example:

```text
NAME      HOST/PORT
central   central-stackrox.apps.example.com
```

The hostname depends on the OpenShift cluster's configured application domain.

To see the complete Route:

```bash
oc get route central -n stackrox -o yaml
```

Or:

```bash
oc describe route central -n stackrox
```

---

## 7. Find the Route URL

You can retrieve the hostname with:

```bash
oc get route central -n stackrox \
  -o jsonpath='{.spec.host}{"\n"}'
```

Example:

```text
central-stackrox.apps.example.com
```

The Central UI URL would normally be:

```text
https://central-stackrox.apps.example.com
```

---

## 8. Verify the OpenShift Router

The Route depends on the OpenShift ingress/router.

Check the router pods:

```bash
oc get pods -n openshift-ingress
```

Check router status:

```bash
oc get deployment -n openshift-ingress
```

Check ingress controllers:

```bash
oc get ingresscontroller -n openshift-ingress-operator
```

A Route can exist while external access still fails if the OpenShift ingress/router is unhealthy.

---

## 9. Verify DNS

The Route hostname must resolve to the OpenShift ingress endpoint.

Get the Route hostname:

```bash
oc get route central -n stackrox \
  -o jsonpath='{.spec.host}{"\n"}'
```

Then test DNS from a client:

```bash
dig central-stackrox.apps.example.com
```

or:

```bash
nslookup central-stackrox.apps.example.com
```

The hostname should resolve to the appropriate OpenShift ingress/load-balancer address.

The traffic path is:

```text
DNS
 |
 v
OpenShift Ingress IP
 |
 v
Router
 |
 v
Route
 |
 v
Central Service
 |
 v
Central Pod
```

---

## 10. TLS Configuration

Central should be accessed securely using HTTPS.

Check the Route:

```bash
oc get route central -n stackrox -o yaml
```

Look at:

```yaml
spec:
  tls:
```

The TLS configuration determines how OpenShift handles encrypted traffic for the Route.

For example, a Route may use TLS termination at the OpenShift router.

Conceptually:

```text
Client
  |
  | HTTPS
  v
OpenShift Router
  |
  | HTTP/HTTPS depending on Route configuration
  v
Central Service
  |
  v
Central
```

The exact TLS mode should match the RHACS version and supported configuration.

---

## 11. Custom Hostname

In environments where a specific hostname is required, Route configuration can be customized according to the RHACS Operator version and supported `Central` CR fields.

For example, the desired corporate URL might be:

```text
https://rhacs.example.com
```

DNS would point:

```text
rhacs.example.com
        |
        v
OpenShift Ingress
```

The Route then forwards the request to Central.

Do not assume that arbitrary Route fields are supported in the RHACS `Central` CR. Always verify the CR schema for the installed RHACS version:

```bash
oc explain central.spec.central.exposure
```

You can also inspect the CRD:

```bash
oc get crd centrals.platform.stackrox.io -o yaml
```

---

## 12. Check Route Details

Use:

```bash
oc describe route central -n stackrox
```

Important fields include:

```text
Host
Path
Service
Port
TLS
Wildcard Policy
```

The critical relationship is:

```text
Route
  |
  +--> Host
  |
  +--> Service
          |
          +--> Central Pod
```

If the Route points to the wrong Service or the Service has no endpoints, the application will not be accessible.

---

## 13. Test HTTPS Connectivity

From a system that can resolve and reach the OpenShift Route:

```bash
curl -k https://central-stackrox.apps.example.com
```

For more detailed troubleshooting:

```bash
curl -vk https://central-stackrox.apps.example.com
```

The `-v` option displays:

* DNS connection
* TCP connection
* TLS handshake
* HTTP request
* HTTP response

---

## 14. Verify Central Directly

If the Route does not work, determine whether Central itself is healthy.

Check:

```bash
oc get pods -n stackrox
```

Check Central logs:

```bash
oc logs deployment/central -n stackrox
```

If the Central deployment name differs:

```bash
oc get deployment -n stackrox
```

Then use the actual deployment name.

---

## 15. Verify Service Endpoints

Check:

```bash
oc get svc -n stackrox
```

Then:

```bash
oc get endpoints -n stackrox
```

For newer Kubernetes/OpenShift environments, EndpointSlices can also be useful:

```bash

```

## 16. Route Troubleshooting Flow

If the RHACS UI cannot be accessed, troubleshoot from the outside inward:

```text
1. DNS
   |
   v
2. Ingress IP / Load Balancer
   |
   v
3. OpenShift Router
   |
   v
4. Route
   |
   v
5. Central Service
   |
   v
6. Endpoint / EndpointSlice
   |
   v
7. Central Pod
```

Commands:




## 17. Common Problems

### Problem 1: Route Does Not Exist

Check the Central configuration:

```bash
oc get central stackrox-central-services -n stackrox -o yaml
```

Check Operator status:

```bash
oc get pods -n rhacs-operator
```

Check Operator logs:

```bash
oc logs deployment/rhacs-operator -n rhacs-operator
```

---

### Problem 2: Route Exists but UI Is Not Accessible

Check:

```bash
oc describe route central -n stackrox
```

Then:

```bash
oc get svc -n stackrox
```

and:

```bash
oc get endpoints -n stackrox
```

If the Service has no endpoints, investigate the Central pod.

---

### Problem 3: DNS Does Not Resolve

Test:

```bash
dig central-stackrox.apps.example.com
```

If DNS fails, fix the DNS record or wildcard DNS configuration for the OpenShift application domain.

---

### Problem 4: TLS Error

Check:

```bash
oc describe route central -n stackrox
```

Inspect:

```yaml
spec:
  tls:
```

Also test:

```bash
curl -vk https://central-stackrox.apps.example.com
```

Look at the certificate presented by the router and verify that the hostname matches the certificate.

---

### Problem 5: HTTP 503

A `503 Service Unavailable` commonly indicates that the router cannot successfully reach a usable backend.

Check:

```bash
oc get route central -n stackrox
```

```bash
oc get svc central -n stackrox
```

```bash
oc get endpoints -n stackrox
```

```bash
oc get pods -n stackrox
```

The most important question is:

```text
Does the Central Service have healthy endpoints?
```

---

## 18. Should You Manually Create the Route?

When Central is managed by the RHACS Operator, prefer configuring Route exposure through the supported `Central` custom resource.

Avoid manually creating a competing Route such as:

```yaml
kind: Route
```

unless there is a specific documented requirement.

Why?

Because the Operator manages the desired RHACS state.

Manual changes to operator-managed resources can:

* Be overwritten during reconciliation.
* Create conflicting configuration.
* Make troubleshooting harder.
* Cause unexpected behavior during upgrades.

The preferred model is:

```text
Administrator
     |
     v
Central CR
     |
     v
RHACS Operator
     |
     v
OpenShift Route
```

## 19. Corporate Example

Suppose the OpenShift cluster has:

```text
Base domain:
apps.corp.example.com
```

The RHACS Central Route could be exposed as:

```text
central-stackrox.apps.corp.example.com
```

The traffic flow would be:

```text
Security Administrator
          |
          | HTTPS
          v
central-stackrox.apps.corp.example.com
          |
          v
Corporate DNS
          |
          v
Load Balancer
          |
          v
OpenShift Router
          |
          v
RHACS Route
          |
          v
Central Service
          |
          v
RHACS Central
```

For production environments, DNS, certificates, load balancing, authentication, network controls, and access policies should all be designed according to corporate security requirements.

# 21. Complete Configuration Flow

The complete RHACS Central Route configuration can be remembered as:

```text
Step 1
Create/modify Central CR
        |
        v
Step 2
Enable supported Route exposure
        |
        v
Step 3
RHACS Operator reconciles Central
        |
        v
Step 4
Central Deployment is available
        |
        v
Step 5
Central Service provides internal access
        |
        v
Step 6
OpenShift Route exposes the Service
        |
        v
Step 7
DNS resolves Route hostname
        |
        v
Step 8
OpenShift Router receives HTTPS request
        |
        v
Step 9
Route forwards traffic to Central Service
        |
        v
Step 10
Central Pod serves RHACS UI/API
```

# 22. Key Takeaways

1. **The RHACS Operator manages Central resources.**
2. **Route exposure should normally be configured through the supported `Central` CR configuration.**
3. **The Route points to a Central Service.**
4. **The Service forwards traffic to Central pod endpoints.**
5. **DNS must resolve the Route hostname to OpenShift ingress.**
6. **TLS must be configured correctly for secure access.**
7. **Do not manually modify operator-managed resources unless required by the RHACS documentation.**
8. **For troubleshooting, follow the path: DNS → Router → Route → Service → Endpoint → Central Pod.**

The most important architecture to remember for an RHACS interview or production troubleshooting scenario is:

```text
Central CR
    |
    v
RHACS Operator
    |
    v
OpenShift Route
    |
    v
Central Service
    |
    v
Central Pod
```
