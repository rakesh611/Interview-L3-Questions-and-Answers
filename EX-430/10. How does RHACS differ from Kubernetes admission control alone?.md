# How Does RHACS Differ From Kubernetes Admission Control Alone?

## Overview

Kubernetes admission control and **RHACS (Red Hat Advanced Cluster Security)** both can participate in preventing insecure workloads from being deployed, but they are **not the same thing**.

The key difference is:

```text
Kubernetes Admission Control
    =
"Should this API request be allowed?"

RHACS
    =
"Is this workload secure across its lifecycle,
and should we prevent, detect, investigate,
and manage the associated risk?"
```

Kubernetes admission control is an **API request control point**.

RHACS is a **broader Kubernetes/OpenShift security platform** that can use admission control as one part of its security architecture.

---

# 1. What Is Kubernetes Admission Control?

Admission control occurs after authentication and authorization, but before an object is persisted in the Kubernetes API server.

Conceptually:

```text
User / ServiceAccount
        │
        ▼
Authentication
        │
        ▼
Authorization / RBAC
        │
        ▼
Admission Control
        │
        ├── Allow
        │
        └── Reject
        │
        ▼
Kubernetes API Server
        │
        ▼
etcd
```

Admission control answers:

> **"Can this API request be accepted?"**

---

# 2. Why Kubernetes Uses Admission Control

Authentication answers:

```text
"Who are you?"
```

Authorization answers:

```text
"Are you allowed to perform this action?"
```

Admission control answers:

```text
"Is this requested object allowed to be created or modified?"
```

For example:

```text
User:
developer

Action:
create deployment

RBAC:
ALLOWED

Admission:
REJECTED

Reason:
Policy violation
```

---

# 3. Types of Kubernetes Admission Control

Modern Kubernetes admission control commonly involves:

```text
Admission
   │
   ├── Built-in admission plugins
   │
   ├── MutatingAdmissionWebhook
   │
   └── ValidatingAdmissionWebhook
```

The exact admission plugins and behavior depend on the Kubernetes/OpenShift version.

A simplified architecture is:

```text
                     API Request
                         │
                         ▼
                  Kubernetes API
                         │
             ┌───────────┴───────────┐
             │                       │
             ▼                       ▼
        Mutating                  Validating
        Admission                 Admission
             │                       │
             ▼                       ▼
        Modify object            Allow/Reject
```

---

# 4. Mutating Admission

A mutating admission controller can modify an incoming object.

For example:

```yaml
spec:
  containers:
  - name: app
    image: nginx
```

A mutating webhook could add:

```yaml
securityContext:
  runAsNonRoot: true
```

Conceptually:

```text
Original object
      │
      ▼
Mutating Admission
      │
      ▼
Modified object
      │
      ▼
Validation
```

---

# 5. Validating Admission

A validating admission controller decides whether an object should be accepted.

Example:

```text
IF

namespace = production
AND
container is privileged

THEN

REJECT
```

Flow:

```text
Deployment
    │
    ▼
Validating Admission
    │
    ├── PASS ──► Create
    │
    └── FAIL ──► Reject
```

This is where admission control becomes an important security enforcement mechanism.

---

# 6. What Is RHACS?

RHACS is a broader security platform for Kubernetes/OpenShift.

It covers:

```text
RHACS
 │
 ├── Vulnerability Management
 ├── Image Security
 ├── Kubernetes Configuration
 ├── Admission Control
 ├── Runtime Security
 ├── Network Security
 ├── Security Policies
 ├── Risk Prioritization
 ├── Compliance
 └── Multi-cluster Security
```

Admission control is therefore **one RHACS capability**, not the entire RHACS platform.

Consider:

```text
Kubernetes Admission Control
```

RHACS:


# 8. Admission Control Alone Is Not a Complete Security Platform

Suppose a developer deploys:

```text
payment-api:v5
```

Admission control might check:

```text
Is privileged=true?
Is hostNetwork=true?
Is this namespace allowed?
Does this object violate policy?
```

If the object passes:

```text
Deployment
    │
    ▼
Admission
    │
    ▼
Allowed
```

The admission controller's primary decision is complete.

But RHACS continues to provide security visibility after deployment.

```text
Deployment
    │
    ▼
RHACS
    │
    ├── Image vulnerability
    ├── Configuration
    ├── Runtime behavior
    ├── Network behavior
    ├── Risk
    └── Policy violations
```

---

# 9. Example: Image Vulnerability

Suppose:

```text
Image:
payment:v5

CRITICAL CVEs:
2
```

A generic Kubernetes admission controller does not inherently provide container vulnerability scanning.

You need an admission policy or external security system that knows about image vulnerability information.

RHACS can integrate vulnerability information into security policies.

Example:

```text
Image:
payment:v5

CRITICAL CVE
     │
     ▼
RHACS Policy
     │
     ├── Production?
     │
     ├── Fix available?
     │
     └── Severity?
            │
            ▼
         Reject
```

This is much more security-aware than basic admission alone.

---

# 10. Example: Runtime Security

Suppose the deployment passes admission:

```text
payment-api
     │
     ▼
Admission
     │
     ▼
PASS
```

After 30 minutes, the container starts executing an unexpected process:

```text
payment-api
     │
     └── unexpected process
```

Generic admission control does not continuously monitor the container's runtime behavior.

RHACS runtime security can detect runtime behavior according to its configured policies and capabilities.

Conceptually:

```text
Container
   │
   ▼
Runtime activity
   │
   ▼
RHACS Collector / Runtime Security
   │
   ▼
Security event
   │
   ▼
Alert / Response
```

This is a major difference.

---

# 11. Admission Is Primarily Preventive

Admission control is mainly used for:

```text
PREVENTION
```

For example:

```text
Don't deploy privileged workloads.
Don't deploy images with unacceptable vulnerabilities.
Don't deploy workloads violating security policy.
```

Flow:

```text
Developer
    │
    ▼
Deploy
    │
    ▼
Admission
    │
    ▼
REJECT
```

---

# 12. RHACS Provides Prevention + Detection

RHACS can support multiple stages:

```text
                   RHACS
                     │
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
   Prevention      Detection    Investigation
       │             │             │
       ▼             ▼             ▼
   Admission       Runtime       Security
   Policies        Alerts        Analysis
```

Therefore:

```text
Admission alone
    =
Prevent bad deployment

RHACS
    =
Prevent + Detect + Analyze + Manage Risk
```

---

# 13. Kubernetes Admission vs RHACS Admission

RHACS can use its own admission-control capability.

Conceptually:

```text
                    OpenShift API
                         │
                         ▼
                RHACS Admission
                    Controller
                         │
                         ▼
                 RHACS Policies
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
       Image          Config          Other
       Security       Security        Conditions
          │              │              │
          └──────────────┼──────────────┘
                         ▼
                    Allow / Reject
```

RHACS admission control is therefore not simply another generic admission mechanism; it is tied to the RHACS security-policy model.

---

# 14. Policy Example

Suppose the organization has the following requirement:

```text
Production workloads must not:

1. Use privileged containers
2. Run as root
3. Use hostNetwork
4. Deploy images with critical vulnerabilities
5. Use prohibited capabilities
```

A simple admission policy may check some Kubernetes object properties.

RHACS can combine multiple security signals.

Conceptually:

```text
                    Deployment
                        │
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
      Image          Kubernetes        Runtime*
      Risk           Configuration     Context
        │               │                │
        └───────────────┼────────────────┘
                        ▼
                  RHACS Policy
                        │
             ┌──────────┴──────────┐
             ▼                     ▼
          PASS                    FAIL
             │                     │
             ▼                     ▼
         Deploy                 Reject
```

`*` Runtime information is relevant to RHACS runtime security but is not necessarily available during admission.

---

# 15. Important Limitation: Admission Happens Before Runtime

This is an important architectural concept.

At admission time:

```text
Container has not started yet.
```

Therefore admission can evaluate things such as:

```text
Image
Pod specification
Namespace
Labels
Security context
Service account
Requested resources
Configuration
```

But it cannot know everything that will happen later.

For example:

```text
Unexpected process
Unexpected outbound connection
Unexpected file access
Runtime behavior
```

These are runtime concerns.

RHACS provides security beyond the admission point.

# 22. Admission Control Is Not the Same as Policy Management

Another important distinction:

```text
Admission Controller
        =
Enforcement point
```

while:

```text
RHACS
        =
Security policy + analysis +
visibility + enforcement + detection
```

Think of the admission controller as a **security gate**.

```text
                 SECURITY GATE
                      │
                      ▼
                 ┌─────────┐
                 │Admission│
                 └────┬────┘
                      │
             ┌────────┴────────┐
             ▼                 ▼
          Allowed           Rejected
```

RHACS is the broader security system deciding what security conditions should be applied and analyzing what happens before and after that gate.

# 23. Example: Privileged Deployment

Consider:

```yaml

  name: test-app
spec:
  template:
    spec:
      containers:
      - name: app
        image: example.com/app:v1

          privileged: true
```

### Admission Control

A validating policy could say:

```text

THEN reject
```

Result:

```text
Deployment
    │
    ▼

    │
    ▼

```

### RHACS

RHACS can also detect the privileged configuration as a security-policy violation and potentially block it at admission, depending on the configured policy and enforcement stage.

After deployment, RHACS can continue to evaluate other security properties and runtime behavior.

# 30. Interview Answer

### Question

**How does RHACS differ from Kubernetes admission control alone?**

### Answer

Kubernetes admission control is a **control point in the Kubernetes API request lifecycle**. It evaluates an object before it is persisted and can allow, reject, or in some cases mutate the request.

RHACS is a much broader **Kubernetes/OpenShift security platform**. It can use admission control to prevent insecure deployments, but it also provides image vulnerability management, Kubernetes configuration analysis, security policies, runtime monitoring, network visibility, risk prioritization, compliance/security posture, and centralized multi-cluster security management.

For example:

```text
Admission Control:

"Is this deployment allowed?"
        │
        ├── YES
        └── NO
```

RHACS:

```text
"Is this workload secure?"

        ├── Image vulnerabilities
        ├── Kubernetes configuration
        ├── RBAC risks
        ├── Network exposure
        ├── Admission policy
        ├── Runtime behavior
        └── Overall workload risk
```

Therefore:

> **Kubernetes admission control is an enforcement point, while RHACS is a complete cloud-native security platform that uses admission control as one part of its prevention strategy and continues security monitoring throughout the workload lifecycle.**

# 31. One-Line Interview Answer

> **Admission control decides whether a Kubernetes API object should be allowed or rejected, while RHACS provides broader Kubernetes/OpenShift security across image, build, deployment, admission, configuration, network, runtime, and risk-management layers.**
