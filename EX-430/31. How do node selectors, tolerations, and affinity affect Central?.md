# How Node Selectors, Tolerations, and Affinity Affect RHACS Central

## 1. Overview

RHACS Central runs as a Kubernetes workload on OpenShift worker nodes.

Kubernetes scheduling determines **which node can run the Central pod**.

Three important scheduling mechanisms are:

* **Node selector**
* **Tolerations**
* **Affinity / Anti-affinity**

They answer different questions:

```text
Node Selector
--------------
"Which nodes may run Central?"

Toleration
----------
"Can Central run on a node that has a matching taint?"

Affinity
--------
"Which nodes or workloads should Central prefer or avoid?"
```

The simplified scheduling flow is:

```text
Central Pod
    |
    v
OpenShift Scheduler
    |
    +--> Node Selector
    |
    +--> Taints / Tolerations
    |
    +--> Node Affinity
    |
    +--> Pod Affinity / Anti-Affinity
    |
    v
Eligible Node
    |
    v
Central Pod
```

---

# 2. Why Scheduling Matters for Central

Central is a critical RHACS component.

If Central is scheduled onto an unsuitable node, you may experience:

* Pod remaining `Pending`
* Resource contention
* Performance problems
* Reduced availability
* Central downtime
* Problems during node maintenance
* Incorrect workload placement

A production environment may therefore use scheduling rules to control where Central runs.

---

# 3. Node Selector

A `nodeSelector` is the simplest way to restrict a pod to nodes with specific labels.

For example, suppose nodes have:

```text
worker-01   rhacs=true
worker-02   rhacs=true
worker-03   rhacs=false
```

A Central pod with:

```yaml
nodeSelector:
  rhacs: "true"
```

can run only on:

```text
worker-01
worker-02
```

It cannot run on:

```text
worker-03
```

---

# 4. Node Selector Example

Conceptual Central configuration:

```yaml
spec:
  central:
    nodeSelector:
      rhacs: "true"
```

The exact location and supported fields depend on the installed RHACS Operator version.

Always verify the CR schema:

```bash
oc explain central.spec
```

and:

```bash
oc explain central.spec.central
```

Do not assume that a Kubernetes PodSpec field can be inserted at an arbitrary location in the RHACS `Central` CR.

---

# 5. Labeling Nodes

Before using a node selector, label the target nodes.

For example:

```bash
oc label node worker-01 rhacs=true
```

and:

```bash
oc label node worker-02 rhacs=true
```

Verify:

```bash
oc get nodes --show-labels
```

Or:

```bash
oc get nodes -l rhacs=true
```

Expected:

```text
NAME
worker-01
worker-02
```

---

# 6. What Happens If No Node Matches?

Suppose Central requires:

```yaml
nodeSelector:
  rhacs: "true"
```

but no node has:

```text
rhacs=true
```

The pod cannot be scheduled.

Check:

```bash
oc get pods -n stackrox
```

You may see:

```text
central-xxxxxxxxxx-xxxxx   0/1   Pending
```

Inspect:

```bash
oc describe pod <central-pod> -n stackrox
```

The Events section will normally show a scheduling reason.

Typical concept:

```text
0/3 nodes are available:
3 node(s) didn't match Pod's node affinity/selector
```

---

# 7. Taints and Tolerations

Node selectors use **labels**.

Taints use a different mechanism.

A taint says:

> Do not schedule ordinary pods onto this node unless the pod has a matching toleration.

For example:

```bash
oc adm taint nodes worker-01 rhacs-only=true:NoSchedule
```

Now the node has a taint:

```text
rhacs-only=true:NoSchedule
```

A normal Central pod cannot be scheduled there unless it tolerates that taint.

---

# 8. Toleration

A toleration allows a pod to be scheduled onto a node with a matching taint.

Conceptual example:

```yaml
tolerations:
  - key: "rhacs-only"
    operator: "Equal"
    value: "true"
    effect: "NoSchedule"
```

This means:

```text
Node:
rhacs-only=true:NoSchedule

Pod:
tolerates rhacs-only=true:NoSchedule

Result:
Pod may be scheduled there
```

Important:

> A toleration does **not** force a pod onto a node.

It only makes the pod eligible for a tainted node.

---

# 9. Taint vs Toleration

Remember the difference:

```text
Taint
------
Applied to NODE

"Keep pods away unless they tolerate me."


Toleration
----------
Applied to POD

"I am allowed to run on that tainted node."
```

Example:

```text
Node
 |
 +-- taint: rhacs-only=true:NoSchedule
 |
 v
Central Pod
 |
 +-- toleration: rhacs-only=true:NoSchedule
 |
 v
Allowed
```

---

# 10. Node Selector + Toleration

These mechanisms can be combined.

Example:

```yaml
nodeSelector:
  rhacs: "true"

tolerations:
  - key: "rhacs-only"
    operator: "Equal"
    value: "true"
    effect: "NoSchedule"
```

Now Central requires both conditions:

```text
Node must have:
rhacs=true

AND

Node must allow:
rhacs-only=true:NoSchedule
```

Conceptually:

```text
                 Candidate Node
                       |
             +---------+---------+
             |                   |
             v                   v
       rhacs=true?       Toleration matches?
             |                   |
             +---------+---------+
                       |
                      YES
                       |
                       v
               Central can run
```

---

# 11. Affinity

Affinity provides more flexible scheduling rules than a simple `nodeSelector`.

There are two major categories:

### Node affinity

Controls relationships between the pod and nodes.

### Pod affinity

Controls relationships between pods.

There is also:

### Pod anti-affinity

Attempts to keep pods away from other matching pods.

---

# 12. Node Affinity

Node affinity allows Central to express preferences or requirements about node labels.

For example:

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: rhacs
              operator: In
              values:
                - "true"
```

This is similar to a node selector but supports more expressive matching.

---

# 13. Required Node Affinity

`requiredDuringSchedulingIgnoredDuringExecution` means the requirement must be satisfied when scheduling.

Example:

```yaml
requiredDuringSchedulingIgnoredDuringExecution:
  nodeSelectorTerms:
    - matchExpressions:
        - key: workload
          operator: In
          values:
            - security
```

Central can only be scheduled on nodes labeled:

```text
workload=security
```

If no matching node exists:

```text
Central -> Pending
```

---

# 14. Preferred Node Affinity

`preferredDuringSchedulingIgnoredDuringExecution` expresses a preference rather than a strict requirement.

Example:

```yaml
preferredDuringSchedulingIgnoredDuringExecution:
  - weight: 100
    preference:
      matchExpressions:
        - key: workload
          operator: In
          values:
            - security
```

This means:

> Prefer security nodes, but use another suitable node if necessary.

This is useful when you want to optimize placement without making Central unschedulable.

---

# 15. Required vs Preferred

The easiest way to remember:

```text
required
--------
MUST satisfy the rule.

preferred
---------
TRY to satisfy the rule.
```

Example:

```text
Required:
Central MUST run on rhacs=true nodes.

Preferred:
Central SHOULD run on rhacs=true nodes.
```

If preferred nodes are unavailable, the scheduler can choose another eligible node.

---

# 16. Pod Affinity

Pod affinity allows a pod to prefer or require placement near other pods.

For example, Central could be configured to prefer nodes running another RHACS-related component.

Conceptually:

```text
Node 1
+-------------------+
| Central           |
| Related RHACS pod |
+-------------------+
```

The exact topology and workload relationship should be designed carefully.

Pod affinity can increase locality, but it can also create scheduling constraints.

---

# 17. Pod Anti-Affinity

Pod anti-affinity is particularly important for high availability.

It can tell Kubernetes:

> Prefer or require matching pods to run on different nodes.

For example:

```text
Node 1
+----------------+
| Central pod A  |
+----------------+

Node 2
+----------------+
| Central pod B  |
+----------------+
```

instead of:

```text
Node 1
+----------------+
| Central pod A  |
| Central pod B  |
+----------------+
```

For components where multiple replicas are deployed, anti-affinity can reduce the impact of a node failure.

The exact RHACS Central replica and HA configuration depends on the RHACS version and deployment architecture.

---

# 18. Topology Spread

Modern Kubernetes/OpenShift environments can also use topology spread constraints.

They help distribute workloads across failure domains such as:

* Nodes
* Zones
* Regions

Conceptually:

```text
Zone A                 Zone B
+----------------+     +----------------+
| Central        |     | Central        |
+----------------+     +----------------+
```

rather than:

```text
Zone A
+------------------------+
| Central                |
| Central                |
+------------------------+

Zone B
+------------------------+
|                        |
+------------------------+
```

Topology distribution is useful when designing highly available applications.

---

# 19. How Scheduling Rules Interact

These mechanisms are evaluated together.

For example:

```text
Central Pod
    |
    +--> nodeSelector
    |
    +--> node affinity
    |
    +--> tolerations
    |
    +--> pod affinity
    |
    +--> pod anti-affinity
    |
    +--> topology constraints
    |
    v
Scheduler
```

A node must satisfy all mandatory constraints.

For example:

```text
Node A
  rhacs=true
  security=true
  taint: rhacs-only=true:NoSchedule

Central
  nodeSelector: rhacs=true
  affinity: security=true
  toleration: rhacs-only=true:NoSchedule

Result:
Eligible
```

# 20. Example Corporate Design

Suppose a company has dedicated security nodes:

```text
worker-sec-01
worker-sec-02
worker-app-01
worker-app-02
```

Security nodes are labeled:

```text
rhacs=true
```

and:

```text
workload=security
```

They are also tainted:

```text
rhacs-only=true:NoSchedule
```

The goal is:

> Run RHACS Central on security nodes and prevent ordinary workloads from consuming those nodes.

Architecture:

```text
                OpenShift Cluster
                       |
          +------------+------------+
          |                         |
          v                         v
   Security Nodes             Application Nodes
   +-----------+              +-----------+
   | sec-01    |              | app-01    |
   | sec-02    |              | app-02    |
   +-----------+              +-----------+
        |
        +-- rhacs=true
        +-- workload=security
        +-- taint rhacs-only=true
```

Central then uses:

```text
Node Selector/Affinity
        +
Toleration
```

to become eligible for the security nodes.

---

# 21. Why Toleration Alone Is Not Enough

Consider:

```text
worker-01:
taint rhacs-only=true:NoSchedule

worker-02:
no taint
```

Central has:

```yaml
tolerations:
  - key: rhacs-only
    operator: Equal
    value: "true"
    effect: NoSchedule
```

Central is allowed on `worker-01`.

But it can also run on `worker-02`.

Therefore:

```text
Toleration = permission
```

not:

```text
Toleration = placement
```

If you want Central to actually prefer or require the security nodes, combine toleration with node selector or affinity.

---

# 22. Why Node Selector Alone Is Not Enough

Suppose:

```text
worker-sec-01:
rhacs=true

worker-sec-02:
rhacs=true
```

Central has:

```yaml
nodeSelector:
  rhacs: "true"
```

This restricts Central to those nodes.

However, it does not automatically:

* Protect the nodes from other workloads.
* Spread replicas across nodes.
* Handle taints.
* Express complex preferences.

Therefore, production designs may combine multiple scheduling mechanisms.

---

# 23. Example Scheduling Strategy

A reasonable conceptual production strategy is:

```text
Central
 |
 +-- Node affinity
 |     |
 |     +-- Require security-labelled nodes
 |
 +-- Toleration
 |     |
 |     +-- Allow dedicated security nodes
 |
 +-- Pod anti-affinity
 |     |
 |     +-- Prefer separation across nodes
 |
 +-- Resource requests/limits
       |
       +-- Reserve appropriate CPU/memory
```

The exact RHACS configuration should use fields supported by your installed RHACS Operator.

---

# 24. Resource Requests Also Matter

Scheduling is not based only on labels and taints.

CPU and memory requests also affect placement.

Check Central resources:

```bash
oc describe pod <central-pod> -n stackrox
```

Look for:

```text
Requests:
  cpu:
  memory:
```

If no eligible node has sufficient available resources, Central can remain Pending even when labels and tolerations are correct.

Conceptually:

```text
Node eligibility
       |
       +-- Labels
       +-- Taints
       +-- Affinity
       +-- Topology
       +-- Resources
       |
       v
Scheduler selects node
```

# 25. Troubleshooting Central Pending

Start with:

```bash
oc get pods -n stackrox
```

If Central is Pending:

```bash
oc describe pod <central-pod> -n stackrox
```

Look at Events.

Then inspect nodes:

```bash
oc get nodes
```

Check labels:

```bash
oc get nodes --show-labels
```

Check specific labels:

```bash
oc get nodes -l rhacs=true
```

Check taints:

```bash
oc describe node <node-name> | grep -i taint
```

Check resources:

```bash
oc describe node <node-name>
```

---

# 26. Troubleshooting Node Selector Problems

If you see:

```text
didn't match Pod's node affinity/selector
```

check:

```bash
oc get nodes --show-labels
```

Compare the required label with the actual node label.

For example, Central requires:

```text
rhacs=true
```

but nodes have:

```text
rhacs=yes
```

These are different values.

```text
rhacs=true
     !=
rhacs=yes
```

Fix the label or scheduling configuration.

---

# 27. Troubleshooting Tolerations

If a node has:

```text
rhacs-only=true:NoSchedule
```

but Central has no matching toleration, the scheduler will reject that node.

Check:

```bash
oc describe node <node-name>
```

Look for:

```text
Taints:
  rhacs-only=true:NoSchedule
```

Then inspect the Central pod specification:

```bash
oc get pod <central-pod> -n stackrox -o yaml
```

Look for:

```yaml
tolerations:
```

---

# 28. Troubleshooting Affinity

If affinity is too restrictive, Central may remain Pending.

Inspect the pod:

```bash
oc get pod <central-pod> -n stackrox -o yaml
```

Look for:

```yaml
affinity:
```

Then check node labels:

```bash
oc get nodes --show-labels
```

For required affinity, every mandatory condition must be satisfied.

If no node satisfies the expression:

```text
Central -> Pending
```

# 29. Operator Ownership

When Central is managed by the RHACS Operator, do not assume that directly editing the generated Central Deployment is the correct solution.

For example, manually running:

```bash
oc edit deployment central -n stackrox
```

may not be appropriate.

The Operator may reconcile the Deployment back to its desired configuration.

The preferred approach is:

```text
Administrator
      |
      v
Central CR
      |
      v
RHACS Operator
      |
      v
Central Deployment
```

Configure scheduling through the supported Central CR fields for your RHACS release.

---

# 30. Version-Specific Configuration

RHACS Operator CR schemas can differ between releases.

Before configuring node scheduling, inspect:

```bash
oc explain central.spec
```

Then inspect the relevant nested fields:

```bash
oc explain central.spec.central
```

You can also inspect the CRD:

```bash
oc get crd centrals.platform.stackrox.io -o yaml
```

This is important because a configuration copied from another RHACS version may not be accepted by your installed Operator.

# 33. Best Practices

### 1. Use labels carefully

Use clear labels such as:

```text
workload=security
rhacs=true
```

Avoid ambiguous labels.

### 2. Do not over-constrain Central

If you require:

```text
rhacs=true
workload=security
zone=zone-a
disk=nvme
```

and only one node satisfies all requirements, a single node failure could make Central unschedulable.

### 3. Use tolerations with placement rules

Remember:

```text
Toleration allows.
Selector/affinity places.
```

### 4. Consider node failure

For HA designs, ensure suitable nodes exist in multiple failure domains.

### 5. Monitor resources

Labels can be correct while the node still lacks enough CPU or memory.

### 6. Configure through the Operator

Use the supported RHACS `Central` CR rather than modifying generated resources directly.

# 35. Interview Questions

## Q1. What is a node selector?

A node selector restricts a pod to nodes having specified labels.

```text
Pod
 |
 +-- nodeSelector: rhacs=true
 |
 v
Only matching nodes
```

---

## Q2. What is a toleration?

A toleration allows a pod to be scheduled onto a node with a matching taint.

It does not force the pod onto that node.

---

## Q3. What is node affinity?

Node affinity provides more expressive rules for selecting or preferring nodes based on node labels.

---

## Q4. What is pod anti-affinity?

Pod anti-affinity allows workloads to avoid being scheduled near other matching pods, which can help distribute replicas across nodes.

---

## Q5. What happens if the node selector matches no nodes?

The Central pod remains `Pending` because the scheduler cannot find an eligible node.

---

## Q6. Can a toleration force Central onto a node?

No.

A toleration only makes the pod eligible for a tainted node.

Use node selector or affinity to control placement.

# 36. Final Architecture

The complete scheduling model can be remembered as:

```text
                         Central Pod
                              |
              +---------------+---------------+
              |               |               |
              v               v               v
        Node Selector     Toleration       Affinity
              |               |               |
              |               |               |
              +---------------+---------------+
                              |
                              v
                     OpenShift Scheduler
                              |
                +-------------+-------------+
                |                           |
                v                           v
          Eligible Nodes              Ineligible Nodes
                |
                v
          Central scheduled
```

## Key Takeaways

1. **Node selector** says which labeled nodes Central can use.
2. **Toleration** allows Central to run on nodes with matching taints.
3. **Toleration alone does not force placement.**
4. **Node affinity** provides more advanced node-selection rules.
5. **Pod affinity** can influence placement relative to other pods.
6. **Pod anti-affinity** can help separate replicas across nodes.
7. **Resource availability also affects scheduling.**
8. **Overly restrictive rules can leave Central Pending.**
9. **For Operator-managed RHACS, configure supported scheduling settings through the `Central` CR.**
10. **Always verify the installed RHACS CRD because scheduling fields can vary by RHACS version.**

The simplest mental model is:

```text
Node Selector = WHERE can Central run?
Toleration    = CAN Central run on a tainted node?
Affinity      = WHICH nodes should Central prefer/require?
Anti-Affinity = WHICH workloads/nodes should Central avoid?
```
