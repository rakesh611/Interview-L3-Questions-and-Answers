# Which Namespace Should Host RHACS Central?

## 1. Short Answer

**RHACS Central should normally be deployed in the `stackrox` namespace.**

The typical RHACS namespace separation is:

```text
rhacs-operator
└── RHACS Operator

stackrox
└── RHACS Central
```

This separation is important because the **RHACS Operator** and the **RHACS Central workload** have different responsibilities.

---

# 2. Typical RHACS Namespace Architecture

A typical OpenShift RHACS deployment looks like:

```text
OpenShift Cluster
│
├── rhacs-operator
│   └── RHACS Operator
│
└── stackrox
    ├── Central
    ├── Scanner
    ├── Scanner V4
    ├── Central DB
    └── Other RHACS Central components
```

The architecture can be summarized as:

```text
                  OpenShift Cluster
                         │
          ┌──────────────┴──────────────┐
          │                             │
          ▼                             ▼
   rhacs-operator                   stackrox
          │                             │
          ▼                             ▼
   RHACS Operator                RHACS Central
                                        │
                              ┌─────────┼─────────┐
                              ▼         ▼         ▼
                           Scanner   Scanner V4  Central DB
```

The exact set of RHACS components depends on the RHACS version and Central configuration.

---

# 3. Why `stackrox`?

The `stackrox` namespace provides a dedicated location for the RHACS Central management plane.

This gives a clean separation:

```text
rhacs-operator
      │
      └── Operator lifecycle

stackrox
      │
      └── RHACS Central workload
```

This makes it easier to:

* Troubleshoot Central.
* Monitor Central resources.
* Manage namespace-specific RBAC.
* Review Central events.
* Apply resource quotas and policies.
* Configure network policies.
* Manage Central-related secrets and configuration.
* Separate Operator lifecycle from application workload lifecycle.

---

# 4. Central Is the RHACS Management Plane

Central is the primary RHACS management component.

It provides functions such as:

```text
RHACS Central
│
├── RHACS API
├── RHACS Web UI
├── Security policy management
├── Vulnerability information
├── Risk information
├── Compliance information
├── Cluster management
├── Alert management
└── Communication with secured clusters
```

Therefore, Central should be treated as a critical management-plane workload.

A simplified architecture is:

```text
                  RHACS Central
                       │
          ┌────────────┼────────────┐
          │            │            │
          ▼            ▼            ▼
       Web UI        API        Database
          │
          │
          ▼
    Secured Clusters
```

---

# 5. `rhacs-operator` vs `stackrox`

This distinction is very important for RHACS administration.

| Namespace        | Main Purpose                                 |
| ---------------- | -------------------------------------------- |
| `rhacs-operator` | RHACS Operator                               |
| `stackrox`       | RHACS Central and related Central components |

Conceptually:

```text
rhacs-operator
       │
       ▼
RHACS Operator
       │
       │ manages
       ▼
stackrox
       │
       ├── Central
       ├── Scanner
       ├── Scanner V4
       └── Central-related resources
```

---

# 6. Create the `stackrox` Namespace

In an installation workflow where the namespace is not created automatically, you can create it with:

```bash
oc create namespace stackrox
```

Verify:

```bash
oc get namespace stackrox
```

Expected:

```text
NAME       STATUS   AGE
stackrox   Active   ...
```

However, when using the RHACS Operator and Central custom resource, follow the RHACS installation workflow for your specific RHACS version. The Operator may create or manage required resources as part of the Central deployment process.

---

# 7. Deploy Central into `stackrox`

After installing the RHACS Operator, you create/configure the RHACS **Central** custom resource.

Conceptually:

```text
OperatorHub
     │
     ▼
RHACS Operator
     │
     ▼
rhacs-operator
     │
     │ watches RHACS resources
     ▼
Central Custom Resource
     │
     ▼
stackrox namespace
     │
     ▼
RHACS Central
```

The Operator reconciles the Central custom resource and creates the required RHACS components.

# 10. Check Central Custom Resource

RHACS uses custom resources managed by the Operator.

First identify the RHACS API resources:

```bash
oc api-resources | grep -i stackrox
```

Depending on the RHACS version, inspect the relevant Central resource:

```bash
oc get central -A
```

or:

```bash
oc get central -n stackrox
```

To inspect a Central resource:

```bash
oc describe central <central-name> -n stackrox
```

This is useful for checking:

* Deployment configuration.
* Conditions.
* Status.
* Component configuration.
* Events.
* Reconciliation problems.

# 11. Central Namespace and Secured Cluster Namespaces

The `stackrox` namespace is primarily associated with the RHACS Central installation.

It should not be confused with the namespaces used by RHACS components on secured clusters.

A typical architecture is:

```text
               RHACS Central Cluster
                       │
                       │
                   stackrox
                       │
                       ▼
                 RHACS Central
                       │
              ┌────────┼────────┐
              │        │        │
              ▼        ▼        ▼
          Cluster-A Cluster-B Cluster-C
              │        │        │
              ▼        ▼        ▼
           RHACS     RHACS     RHACS
           Sensor    Sensor    Sensor
           Collector Collector Collector
```

Therefore, `stackrox` is not necessarily present as the Central workload namespace on every secured cluster in the same way.

---

# 12. Central Namespace Is Different From Operator Namespace

Do not install both components into the same namespace simply because the Operator manages Central.

Recommended separation:

```text
Operator:
    rhacs-operator

Central:
    stackrox
```

Why?

Because:

```text
Operator = lifecycle/controller component

Central = RHACS management-plane application
```

This separation makes operational troubleshooting much easier.

# 13. Troubleshooting Central

## Central Pod Is Not Running

Check:

```bash
oc get pods -n stackrox
```

If a pod is not running:

```bash
oc describe pod <pod-name> -n stackrox
```

Check logs:

```bash
oc logs <pod-name> -n stackrox
```

If the pod restarted:

```bash
oc logs <pod-name> \
  -n stackrox \
  --previous
```

---

# 14. Check Central Events

Run:

```bash
oc get events \
  -n stackrox \
  --sort-by='.lastTimestamp'
```

Look for:

```text
FailedScheduling
FailedMount
FailedAttachVolume
ImagePullBackOff
CrashLoopBackOff
FailedCreate
Unhealthy
```

These events can quickly identify deployment problems.

---

# 15. Check Central Services

Run:

```bash
oc get svc -n stackrox
```

Check the endpoints:

```bash
oc get endpoints -n stackrox
```

For newer Kubernetes/OpenShift environments, also check:

```bash
oc get endpointslice -n stackrox
```

If the Central service exists but has no endpoints, investigate whether the Central pod is:

```text
Running
Ready
```

---

# 16. Check Central Deployment

Run:

```bash
oc get deployment -n stackrox
```

Then:

```bash
oc describe deployment <deployment-name> -n stackrox
```

Check:

```text
Desired replicas
Available replicas
Ready replicas
Events
```

A healthy deployment should have the expected number of replicas available.

---

# 17. Check Central Database

Depending on the RHACS version and configuration, Central may use a separate database component.

Check:

```bash
oc get pods -n stackrox
```

Look for database-related workloads.

For example:

```text
Central
Central DB
```

Do not assume that the database architecture is identical across every RHACS version. Always verify the components deployed by your specific RHACS release.

# 18. Storage Considerations

Central is a stateful management component, so storage planning is important.

Before production deployment, evaluate:

```text
StorageClass
        │
        ▼
PersistentVolume
        │
        ▼
PersistentVolumeClaim
        │
        ▼
RHACS Central / Database
```

Check available StorageClasses:

```bash
oc get storageclass
```

Check PVCs:

```bash
oc get pvc -n stackrox
```

Check PVs:

```bash
oc get pv
```

If a PVC remains `Pending`:

```bash
oc describe pvc <pvc-name> -n stackrox
```

Investigate:

* StorageClass.
* Provisioner.
* Available capacity.
* Access mode.
* Node topology.
* CSI driver.
* Storage policies.

---

# 19. Production Considerations

Because Central is the RHACS management plane, production deployments should consider:

### High Availability

Use an RHACS configuration appropriate for the availability requirements of the environment.

### Storage

Use reliable persistent storage where required.

### Backup

Plan backup and recovery for RHACS configuration and state according to Red Hat's supported RHACS backup/recovery procedures.

### Network

Ensure communication between:

```text
Central
   │
   ├── RHACS Sensors
   ├── RHACS secured clusters
   └── Required external services
```

is permitted.

### Security

Apply organizational:

* RBAC
* NetworkPolicies
* Resource policies
* Pod security controls
* Monitoring
* Audit requirements

according to the RHACS and OpenShift support requirements.

                    │                     │

The Central cluster provides the RHACS management plane, while secured clusters run the RHACS components needed to monitor and enforce security controls.

# 23. Interview Answer

### Question

**Which namespace should host RHACS Central?**

### Answer

RHACS Central should normally be deployed in the dedicated:

```text
stackrox
```

namespace.

The RHACS Operator is normally installed separately in:

```text
rhacs-operator
```

The Operator manages the Central custom resource and reconciles the RHACS Central deployment.

Therefore:

```text
rhacs-operator
    └── RHACS Operator

stackrox
    └── RHACS Central
```

This separation provides cleaner lifecycle management, troubleshooting, RBAC, monitoring, and operational isolation.
