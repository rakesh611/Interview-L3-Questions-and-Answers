# How Scanner V4 Indexer and Matcher Functions Differ

## Overview

RHACS Scanner V4 uses a separated **Indexer** and **Matcher** architecture for vulnerability scanning.

The two components have different responsibilities:

* **Indexer** — analyzes an image and creates a structured representation of its software contents.
* **Matcher** — compares that indexed software information against vulnerability definitions and determines which vulnerabilities apply.

A simple way to remember the difference is:

> **Indexer discovers what is inside the image; Matcher determines what is vulnerable.**

---

## 1. Scanner V4 High-Level Flow

A simplified Scanner V4 workflow looks like this:

```text
Container Image
      |
      v
+------------------+
|      Indexer     |
|------------------|
| Extract image    |
| layers/files     |
| Identify packages|
| Build index      |
+--------+---------+
         |
         v
   Image Index
         |
         v
+------------------+
|      Matcher     |
|------------------|
| Read packages    |
| Compare against  |
| vulnerability DB |
| Apply matching   |
| logic            |
+--------+---------+
         |
         v
 Vulnerability Results
```

The separation allows indexing and vulnerability matching to evolve independently.

---

# 2. What the Indexer Does

The **Indexer** is responsible for understanding the software content of a container image.

Its primary question is:

> **"What software packages and components are present in this image?"**

The Indexer processes the image filesystem and metadata to identify installed software.

Typical information can include:

* Operating-system packages
* Language ecosystem packages
* Package versions
* Package names
* Package relationships
* Distribution information
* Image metadata
* Filesystem information required for package identification

For example, an image might contain:

```text
Operating System: RHEL
Package: openssl
Version: 3.0.x
Package: curl
Version: 8.x
Package: glibc
Version: 2.x
```

The Indexer turns this information into an internal representation that the Matcher can consume.

---

# 3. Indexer Does Not Primarily Decide Vulnerability Status

The Indexer should not be thought of as the component that answers:

> "Is this package vulnerable?"

Instead, it establishes the package inventory.

For example:

```text
Image
 |
 +-- openssl-3.0.x
 +-- curl-8.x
 +-- glibc-2.x
```

The Indexer identifies these packages and their versions.

The vulnerability determination is subsequently performed by the Matcher.

---

# 4. What the Matcher Does

The **Matcher** takes the software inventory produced by the Indexer and compares it with vulnerability definitions.

Its primary question is:

> **"Which known vulnerabilities apply to the software identified in this image?"**

The Matcher uses vulnerability intelligence maintained in the Scanner vulnerability database.

Conceptually:

```text
Indexed Package
       |
       v
Vulnerability Definitions
       |
       v
Matching Logic
       |
       v
Applicable Vulnerability
```

For example:

```text
Package:
openssl 3.0.x

        |
        v

Vulnerability Database

CVE-XXXX-YYYY
Affected versions: ...
Severity: High

        |
        v

Matcher

        |
        v

Vulnerability Result
```

---

# 5. Indexer vs Matcher

| Area                                   | Indexer                            | Matcher                              |
| -------------------------------------- | ---------------------------------- | ------------------------------------ |
| Primary purpose                        | Discover image contents            | Determine applicable vulnerabilities |
| Main question                          | What is installed?                 | What is vulnerable?                  |
| Input                                  | Container image/filesystem         | Indexed package/component data       |
| Uses vulnerability definitions         | Not primarily                      | Yes                                  |
| Identifies packages                    | Yes                                | Consumes package information         |
| Determines CVEs                        | No, not its primary responsibility | Yes                                  |
| Determines vulnerability applicability | No                                 | Yes                                  |
| Produces package inventory             | Yes                                | Consumes it                          |
| Produces vulnerability findings        | No                                 | Yes                                  |

---

# 6. Example

Suppose a container image contains:

```text
RHEL 9
 |
 +-- openssl-3.0.x
 +-- curl-8.x
 +-- glibc-2.x
```

### Step 1 — Indexer

The Indexer examines the image and discovers:

```text
openssl
curl
glibc
```

along with their versions and package metadata.

It creates an index similar conceptually to:

```text
Image Index
-------------------------
openssl  -> 3.0.x
curl     -> 8.x
glibc    -> 2.x
```

### Step 2 — Matcher

The Matcher receives the package information.

It consults vulnerability definitions:

```text
openssl 3.0.x
    |
    +--> CVE-A
    +--> CVE-B

curl 8.x
    |
    +--> CVE-C

glibc 2.x
    |
    +--> No applicable vulnerability
```

The final result could therefore contain:

```text
CVE-A    High
CVE-B    Medium
CVE-C    Critical
```

---

# 7. Why Scanner V4 Separates the Two Functions

Separating indexing from matching provides several operational advantages.

## 7.1 Reuse of Indexed Data

The software inventory can be represented independently from vulnerability matching.

This reduces the need to repeatedly inspect the complete image filesystem when vulnerability definitions change.

---

## 7.2 Faster Vulnerability Database Updates

Vulnerability definitions change frequently.

For example:

```text
Day 1

Image
 |
 v
Indexer
 |
 v
Package Inventory
 |
 v
Matcher
 |
 v
CVE-1
```

Later, a new vulnerability is added:

```text
New vulnerability definition
          |
          v
      Matcher
          |
          v
Existing package inventory
          |
          v
New vulnerability result
```

The conceptual separation means vulnerability intelligence can be updated without treating every image as if it were completely new.

---

## 7.3 Separation of Concerns

The architecture separates two different problems:

```text
Image analysis
      |
      v
"What is installed?"
      |
      v
Indexer
```

from:

```text
Security intelligence
      |
      v
"What is vulnerable?"
      |
      v
Matcher
```

This makes the architecture easier to operate and troubleshoot.

---

# 8. Operational Troubleshooting

The distinction is particularly useful during troubleshooting.

## If Package Detection Is Wrong

Investigate the **Indexer** path.

Typical questions include:

* Was the image accessible?
* Could its layers be retrieved?
* Was the filesystem successfully extracted?
* Was the operating-system distribution detected?
* Was the package manager database available?
* Were packages correctly identified?
* Is the image format supported?

Conceptually:

```text
Image
  |
  X
Indexer
  |
  X
Incorrect/Incomplete Package Inventory
```

---

## If Packages Are Correct but CVEs Are Missing

Investigate the **Matcher** and vulnerability-data path.

Typical questions include:

* Is the package correctly represented in the index?
* Is the vulnerability definition present?
* Is the package/version mapped correctly?
* Is the affected-product information available?
* Is the vulnerability database current?
* Is the matching logic correctly associating the package with the vulnerability?

Conceptually:

```text
Correct Package Inventory
          |
          v
       Matcher
          |
          X
Missing/Incorrect Vulnerability Result
```

---

# 9. Indexer Failure vs Matcher Failure

A useful troubleshooting model is:

```text
                    Image
                      |
                      v
                  Indexer
                 /       \
              Good       Failed
               |           |
               v           v
        Package Index    Investigate
               |
               v
             Matcher
            /       \
         Good       Failed
          |           |
          v           v
 Vulnerability      Investigate
   Results           Matcher/DB
```

This helps prevent troubleshooting the wrong component.

For example, if an expected package is completely absent from the indexed inventory, updating vulnerability definitions will not normally fix the underlying problem. The package-detection/indexing path must be investigated first.

---

# 10. Indexer and Matcher Dependency

The Matcher depends on the information produced by indexing.

Conceptually:

```text
                Container Image
                       |
                       v
                    Indexer
                       |
                       v
              Software Inventory
                       |
                       v
                    Matcher
                       |
          +------------+------------+
          |                         |
          v                         v
 Vulnerability DB            Matching Rules
          |                         |
          +------------+------------+
                       |
                       v
             Vulnerability Results
```

Therefore:

> **No useful package inventory means the Matcher has insufficient information to produce accurate vulnerability results.**

---

# 11. Relationship With Scanner V4 Database

Scanner V4 maintains vulnerability information separately from the image's software inventory.

The database contains vulnerability intelligence such as:

* Vulnerability identifiers
* Affected products
* Version ranges
* Severity information
* Distribution-specific information
* Fixed-version information
* Other metadata used for vulnerability matching

The Indexer primarily establishes:

```text
Image -> Package Inventory
```

The Matcher performs:

```text
Package Inventory + Vulnerability Definitions
                    |
                    v
             Vulnerability Results
```

---

# 12. Important Operational Distinction

When investigating Scanner V4, avoid treating **Indexer** and **Matcher** as interchangeable.

### Indexer

```text
Container image
      |
      v
Filesystem/package analysis
      |
      v
Package inventory
```

### Matcher

```text
Package inventory
      +
Vulnerability definitions
      |
      v
Vulnerability assessment
```

The Indexer is therefore primarily **content discovery**, while the Matcher is primarily **security correlation**.

---

# 13. Corporate Troubleshooting Example

Assume an enterprise team reports:

> "RHACS is scanning the image, but the expected OpenSSL package is not appearing."

The first investigation should focus on the indexing path:

```text
Image
 |
 v
Indexer
 |
 +-- OS detected?
 +-- Filesystem extracted?
 +-- Package database detected?
 +-- OpenSSL package detected?
 +-- Correct package version?
```

If OpenSSL appears correctly but the expected CVE is missing:

```text
Package inventory
       |
       v
Matcher
       |
       +-- Vulnerability definition available?
       +-- Product mapping correct?
       +-- Version matching correct?
       +-- Vulnerability data current?
```

This gives administrators a much clearer troubleshooting boundary.

---

# 14. Key Takeaways

1. **Indexer discovers software inside the image.**
2. **Matcher determines which vulnerabilities apply to that software.**
3. The Indexer primarily produces a **software/package inventory**.
4. The Matcher consumes that inventory and **correlates it with vulnerability definitions**.
5. Indexing problems generally appear as **missing or incorrect package information**.
6. Matching problems generally appear as **incorrect or missing vulnerability findings despite correct package inventory**.
7. Separating the functions improves scalability, maintainability, and operational troubleshooting.
8. Scanner V4's architecture allows image-content analysis and vulnerability intelligence processing to be treated as distinct responsibilities.

## One-Line Interview Answer

> **"In RHACS Scanner V4, the Indexer analyzes the container image and builds an inventory of its software packages and metadata, while the Matcher takes that inventory and correlates it with vulnerability definitions to determine the applicable CVEs, severity, and affected versions."**
