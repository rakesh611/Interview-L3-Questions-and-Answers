# How Does RHACS Handle Multiple Secured Clusters?

## Overview

Red Hat Advanced Cluster Security for Kubernetes (RHACS) is designed to provide **centralized security management and visibility across multiple Kubernetes and OpenShift clusters**.

Instead of installing a completely independent RHACS security platform for every cluster, an organization can use a central RHACS environment and connect multiple secured clusters to it.

The basic architecture is:

```text
                         RHACS Central
                              |
              +---------------+---------------+
              |               |               |
              v               v               v
        Secured Cluster 1 Secured Cluster 2 Secured Cluster 3
              |               |               |
            Sensor          Sensor          Sensor
              |               |               |
          Collector       Collector       Collector
              |               |               |
         OpenShift       OpenShift       Kubernetes
```

This allows security teams to manage security posture across many clusters from a central location.

---

# 1. What Is a Secured Cluster?

A **secured cluster** is a Kubernetes/OpenShift cluster that has RHACS components installed so that RHACS can monitor and secure workloads running on that cluster.

A typical secured cluster contains:

```text
Secured Cluster
|
+-- Sensor
|
+-- Admission Controller
|
+-- Collector
|
+-- Kubernetes/OpenShift API
|
+-- Application workloads
```

The RHACS Central instance provides centralized management and analysis.

---

# 2. Central and Secured Clusters

The most important concept is the separation between:

```text
Central
```

and:

```text
Secured Cluster
```

### RHACS Central

Central is responsible for centralized RHACS functions such as:

* Security management
* Policy management
* Security data
* Vulnerability information
* Cluster management
* RHACS UI
* API access
* Centralized visibility

### Secured Cluster

The secured cluster runs components that interact directly with the cluster.

Typically:

```text
Sensor
Collector
Admission Controller
```

These components provide cluster-level security capabilities.

# 3. Multi-Cluster Architecture

A common enterprise deployment looks like:

```text
                         Security Team
                              |
                              v
                       RHACS Central
                              |
       +----------------------+----------------------+
       |                      |                      |
       v                      v                      v
   Production             Development             DR
   Cluster                  Cluster              Cluster
       |                      |                      |
     Sensor                 Sensor                Sensor
       |                      |                      |
   Collector              Collector             Collector
```

The security team gets centralized visibility while individual clusters retain their own Kubernetes/OpenShift resources.

# 6. Cluster Registration

Before RHACS can secure a cluster, the cluster needs to be registered/configured with RHACS Central.

Conceptually:

```text
New OpenShift Cluster
        |
        v
Install RHACS components
        |
        v
Connect to Central
        |
        v
Cluster registered
        |
        v
Sensor establishes communication
        |
        v
Central receives cluster data
```

The exact installation and registration procedure depends on the RHACS deployment method and RHACS version.

---

# 7. Sensor Per Cluster

One of the most important concepts is:

> **Each secured cluster has its own Sensor.**

For example:

```text
RHACS Central
     |
     +---- Sensor ---> Production Cluster
     |
     +---- Sensor ---> Development Cluster
     |
     +---- Sensor ---> DR Cluster
```

The Sensor is responsible for communicating security-related information between the secured cluster and Central.

---

# 8. Collector Per Cluster

The Collector is deployed in secured clusters to provide runtime and network-related security visibility.

Example:

```text
Production Cluster
|
+-- Sensor
|
+-- Collector
|
+-- Admission Controller
|
+-- Applications
```

Another cluster has its own components:

```text
Development Cluster
|
+-- Sensor
|
+-- Collector
|
+-- Admission Controller
|
+-- Applications
```

The components operate locally within each secured cluster.

---

# 9. Admission Controller Per Cluster

If RHACS admission control is enabled, the Admission Controller is deployed in the secured cluster.

For example:

```text
Developer
   |
   v
Kubernetes API
   |
   v
Admission Controller
   |
   v
RHACS Policy
   |
 +--+--+
 |     |
Allow  Deny
```

This allows admission enforcement to happen at the cluster where the workload is being deployed.

---

# 10. Centralized Policy Management

One of the major advantages of multi-cluster RHACS is centralized security policy management.

For example:

```text
Security Policy:
Do not deploy privileged containers
```

The policy can be applied to appropriate secured clusters.

Conceptually:

```text
                    RHACS Central
                         |
             Privileged Container Policy
                         |
        +----------------+----------------+
        |                |                |
        v                v                v
      PROD              DEV              DR
        |                |                |
      Enforce          Alert            Enforce
```

The exact policy scope and enforcement behavior should be configured according to organizational requirements.

---

# 11. Cluster-Specific Policies

Not every cluster needs identical security requirements.

For example:

```text
Production
-----------
Critical policy
High enforcement
Strict admission control

Development
-----------
More permissive
Testing policies

DR
--
Production-like controls
```

RHACS allows organizations to organize security policies and scopes according to their environments.

# 12. Cluster Identification

When operating multiple clusters, teams need to know **where a finding originated**.

# 20. Network Connectivity

Each secured cluster needs the required network connectivity to RHACS Central.

Conceptually:

```text

       |
       | Secure connection
       |
       v

```

For multiple clusters:

```text
Cluster A ----\
```

Firewall rules, DNS, certificates, routing, proxies, and network security controls must be designed appropriately.

# 28. What Happens If One Cluster Is Down?

Suppose:

```text
Cluster A -> Healthy
Cluster B -> Down
Cluster C -> Healthy
```

RHACS Central can continue managing/monitoring the other connected clusters, subject to the specific functionality and connectivity available.

Conceptually:

```text
                 RHACS Central
                  /          \
                 /            \
          Cluster A          Cluster C
           Healthy            Healthy

                X
                |
           Cluster B
             Down
```

The platform team should investigate the disconnected cluster.

A disconnected Sensor is an operational problem that should be distinguished from a security finding.

---

# 29. Central Failure vs Cluster Failure

These are different scenarios.

## Secured Cluster Failure

```text
Cluster A
    X
    |
Sensor unavailable
```

Other secured clusters may remain connected to Central.

## Central Failure

```text
             RHACS Central
                  X
               /  |  \
              /   |   \
        Cluster A B   C
```

A Central outage can affect centralized RHACS management and visibility.

Therefore, Central should be designed with appropriate availability and recovery architecture for production environments.

# 41. Scaling Considerations

As the number of secured clusters increases, organizations should plan for:

```text
More Clusters
     |
     +--> More Sensors
     |
     +--> More Collectors
     |
     +--> More Workloads
     |
     +--> More Security Data
     |
     v
RHACS Central Capacity
```

Central should be sized according to:

* Number of secured clusters
* Number of nodes
* Number of workloads
* Deployment volume
* Security data volume
* Retention requirements
* HA requirements

Do not size RHACS Central based only on the number of clusters.

# 44. Centralized vs Distributed Responsibility

The architecture can be summarized as:

```text
                CENTRALIZED
                   RHACS
                     |
      +--------------+--------------+
      |              |              |
      v              v              v
   Cluster A      Cluster B      Cluster C
      |              |              |
   DISTRIBUTED    DISTRIBUTED    DISTRIBUTED
   Components     Components     Components
```

### Centralized

* Security visibility
* Policy management
* RHACS management
* Vulnerability information
* Risk information

### Distributed

* Sensor
* Collector
* Admission Controller
* Cluster interaction
* Runtime collection
* Local Kubernetes/OpenShift enforcement

# 45. Interview Answer

A strong interview answer is:

> "RHACS uses a centralized management model for multiple secured clusters. RHACS Central provides centralized security visibility, policy management, vulnerability and risk information, while each OpenShift or Kubernetes cluster runs its own RHACS components such as Sensor, Collector, and optionally Admission Controller. Each Sensor communicates with Central and represents its secured cluster. This allows security teams to monitor many clusters from one RHACS environment while cluster-specific components continue to operate locally. Policies can be scoped according to clusters, namespaces, or workloads, and RBAC can be used to separate security, platform, and application-team access. In an enterprise environment, Central should also be designed for appropriate availability, storage, backup, and disaster recovery."

# 47. Key Takeaways

1. **One RHACS Central can provide centralized security management for multiple secured clusters.**
2. **Each secured cluster has its own RHACS components.**
3. **Sensor provides the primary cluster-to-Central communication path.**
4. **Collector provides cluster-level runtime/network security visibility.**
5. **Admission Controller provides deployment-time enforcement when configured.**
6. **Security policies can be applied according to organizational scope and requirements.**
7. **Cluster identity is important when investigating findings.**
8. **RBAC should separate security, platform, and application responsibilities.**
9. **Central availability is critical because it is the central management point.**
10. **Each secured cluster continues to operate as an independent Kubernetes/OpenShift cluster.**

# 48. Final Mental Model

Remember:

```text
                 RHACS CENTRAL
                      |
        Centralized Security Management
                      |
       +--------------+--------------+
       |              |              |
       v              v              v
   Cluster 1       Cluster 2       Cluster 3
       |              |              |
     Sensor         Sensor         Sensor
       |              |              |
   Collector       Collector       Collector
       |              |              |
 Admission        Admission        Admission
 Controller       Controller       Controller
       |              |              |
   Workloads       Workloads       Workloads
```

The simplest way to remember it is:

> **RHACS Central provides the centralized security brain, while each secured cluster runs local RHACS components that collect security information and enforce security controls close to the workloads.**

This architecture allows an organization to manage security consistently across **development, test, production, DR, regional, and business-unit clusters** without treating every Kubernetes/OpenShift cluster as an isolated security platform.
