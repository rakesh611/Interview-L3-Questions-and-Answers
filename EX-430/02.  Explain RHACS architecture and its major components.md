# RHACS Architecture and Major Components

## 1. Overview

**Red Hat Advanced Cluster Security for Kubernetes (RHACS)** is a Kubernetes/OpenShift security platform designed to provide security across:

```text
Build → Deploy → Runtime
```

RHACS uses a centralized management architecture with a **Central** component and lightweight components deployed into each protected cluster.

A simplified architecture is:

```text
                         RHACS
                           |
                    +------+------+
                    |   Central   |
                    |             |
                    |  API/UI     |
                    |  Policies   |
                    |  Risk       |
                    |  Vulnerability
                    |  Management |
                    +------+------+
                           |
              +------------+-------------+
              |            |             |
              v            v             v
         OpenShift-1  OpenShift-2  OpenShift-3
              |            |             |
        +-----+-----+ +----+----+  +-----+-----+
        |           | |         |  |           |
   Sensor       Collector  Sensor  Collector
        |           |         |
        +-----------+---------+
                    |
                Admission
                Controller
                    |
              Build/Deploy/
               Runtime
```

7. Scanner DB
8. Scanner V4

Not every RHACS deployment or version exposes exactly the same set of components. For example, vulnerability scanning architecture has evolved across RHACS releases. The exact scanner components depend on the RHACS version and configuration.

# 3. Central

## What is Central?

**Central is the main control-plane component of RHACS.**

It provides centralized management and security intelligence for protected Kubernetes/OpenShift clusters.

Think of Central as:

```text
RHACS Brain / Control Plane
```

Central communicates with:

```text
                    Central
                       |
        +--------------+--------------+
        |              |              |
      Sensor        Scanner        UI/API
        |
      Cluster
```

## Major responsibilities

Central is responsible for:

- Centralized security management
- Security policies
- Risk assessment
- Vulnerability information
- Cluster management
- Security events
- API
- RHACS web console
- Integrations
- Authentication/authorization
- Alert management
- Compliance information

## Example

Suppose the organization has:

```text
Cluster-1
Cluster-2
Cluster-3
Cluster-4
```

Central provides a centralized security view:

```text
                 RHACS Central
                       |
       +---------------+---------------+
       |               |               |
   Cluster-1       Cluster-2       Cluster-3
```

Security teams don't need to independently manage security information from every cluster.

---

# 4. Central DB

## What is Central DB?

Central DB is the persistent database used by RHACS to store security-related data.

Depending on the RHACS version and deployment architecture, the database implementation and storage model can differ.

Conceptually:

```text
Central
   |
   v
Central DB
   |
   +-- Configuration
   +-- Security data
   +-- Policies
   +-- Metadata
   +-- Cluster information
```

## Why is it important?

Without persistent storage, Central would lose important security-management information after a restart.

The database provides persistence for RHACS control-plane data.

---

# 5. Sensor

## What is Sensor?

**Sensor is the main RHACS component deployed inside each secured cluster.**

Think of Sensor as:

```text
Cluster Security Manager / Agent
```

Architecture:

```text
                 RHACS Central
                       |
                       |
                    Sensor
                       |
        +--------------+--------------+
        |              |              |
       API          Kubernetes       Workloads
       Server        Objects
```

## Major responsibilities

Sensor:

- Watches Kubernetes/OpenShift resources
- Monitors cluster configuration
- Receives information about deployments
- Collects Kubernetes metadata
- Communicates with Central
- Helps enforce and evaluate security policies
- Coordinates cluster-level RHACS operations

Sensor communicates with the Kubernetes/OpenShift API server to understand cluster state.

## Example

When an administrator creates:

```bash
oc create deployment nginx --image=nginx
```

Sensor observes the deployment and sends relevant security information to Central.

---

# 6. Collector

## What is Collector?

**Collector is responsible for collecting runtime-level information from nodes and containers.**

Collector runs on cluster nodes, normally as a DaemonSet so that the required nodes can be monitored.

Conceptually:

```text
OpenShift Node
|
+-- Pod
+-- Pod
+-- Pod
|
+-- RHACS Collector
```

Multiple nodes:

```text
Node-1                  Node-2                  Node-3
   |                       |                       |
Collector               Collector               Collector
```

## Major responsibilities

Collector provides information about:

- Container processes
- Runtime activity
- Network activity
- Container behavior
- Node-level runtime information

It helps RHACS detect suspicious runtime behavior.

## Example

A normal application might execute:

```text
java
```

But after compromise it starts:

```text
/bin/sh
curl
wget
```

Collector helps provide the runtime information needed for RHACS to detect such unexpected behavior.

# 7. Admission Controller

## What is Admission Controller?

The **Admission Controller** provides deployment-time security enforcement.

It integrates with Kubernetes/OpenShift admission mechanisms.

Conceptually:

```text
Developer
    |
    v
Deployment
    |
    v
Kubernetes API Server
    |
    v
RHACS Admission Controller
    |
    +---- PASS ----> Deployment accepted
    |
    +---- FAIL ----> Deployment rejected
```

## What can it prevent?

Depending on configured RHACS policies, it can help prevent deployments that violate requirements such as:

- Critical vulnerabilities
- Unauthorized images
- Privileged containers
- Dangerous security configurations
- Disallowed deployment characteristics

## Why is it important?

Without deployment-time enforcement:

```text
Bad workload
    |
    v
OpenShift
    |
    v
Production
```

With admission enforcement:

```text
Bad workload
    |
    v
RHACS Policy
    |
    X
Rejected
```

# 8. Scanner

## What is Scanner?

RHACS uses vulnerability scanning components to identify vulnerabilities in container images.

A scanner analyzes:

```text
Container Image
       |
       v
Packages / Libraries
       |
       v
Vulnerability Database
       |
       v
CVE Findings
```

For example:

```text
myapp:v10
 |
 +-- openssl
 |      |
 |      +-- CVE
 |
 +-- log4j
 |      |
 |      +-- CVE
 |
 +-- glibc
        |
        +-- CVE
```

## Purpose

Scanner helps identify:

- CVEs
- Vulnerable packages
- Vulnerable application dependencies
- Vulnerable base images

The exact scanner implementation depends on the RHACS version.

# 12. RHACS Operator

## What is RHACS Operator?

The **RHACS Operator** manages the lifecycle of RHACS components on OpenShift/Kubernetes.

It follows the Kubernetes Operator model.

Instead of manually managing every RHACS component:

```text
Manual installation
   |
   +-- Deployment
   +-- Service
   +-- Secret
   +-- RBAC
   +-- Config
   +-- Upgrade
```

The Operator manages RHACS resources and components.

Conceptually:

```text
OpenShift
   |
   v
RHACS Operator
   |
   +-- Central
   +-- Sensor
   +-- Collector
   +-- Admission Controller
   +-- Scanner
```

## Major responsibilities

The Operator helps with:

- Installation
- Configuration
- Lifecycle management
- Upgrades
- Reconciliation
- Component deployment
- Health management

# 25. Most Important Interview Point

If asked:

> **Explain RHACS architecture.**

A strong L3 answer is:

> RHACS follows a centralized security architecture. **Central** acts as the management and security intelligence plane. **Sensor** runs in each protected OpenShift/Kubernetes cluster and collects cluster-level information through the Kubernetes API. **Collector** provides node and container runtime visibility. **Admission Controller** provides deployment-time policy enforcement. **Scanner/Scanner V4** analyzes container images for vulnerabilities. Central stores and manages security information and exposes the RHACS UI and API. The RHACS Operator manages the lifecycle of the RHACS components on OpenShift. Together, these components provide vulnerability management, configuration security, policy enforcement, network visibility, compliance and runtime threat detection across build, deploy and runtime.
