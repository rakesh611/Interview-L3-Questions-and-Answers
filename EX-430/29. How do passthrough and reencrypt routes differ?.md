# How Passthrough and Reencrypt Routes Differ in OpenShift

## 1. Overview

OpenShift Routes control how external traffic reaches a Service.

Two important TLS termination modes are:

* **Passthrough**
* **Reencrypt**

The main difference is **where TLS is terminated** and whether the connection between the OpenShift Router and the backend remains encrypted.

```text
Passthrough:

Client
  |
  | HTTPS/TLS
  v
OpenShift Router
  |
  | HTTPS/TLS - same connection
  v
Backend Service
  |
  v
Application
```

```text
Reencrypt:

Client
  |
  | HTTPS/TLS
  v
OpenShift Router
  |
  | HTTPS/TLS - new connection
  v
Backend Service
  |
  v
Application
```

---

# 2. What Is TLS Termination?

TLS termination means decrypting HTTPS traffic.

With normal edge termination:

```text
Client
   |
   | HTTPS
   v
Router
   |
   | HTTP
   v
Application
```

The Router decrypts the client connection.

With passthrough:

```text
Client
   |
   | HTTPS
   v
Router
   |
   | HTTPS
   v
Application
```

The Router does **not** decrypt the TLS connection.

With reencrypt:

```text
Client
   |
   | HTTPS
   v
Router
   |
   | HTTPS
   v
Application
```

The Router decrypts the first TLS connection and creates a **new TLS connection** to the backend.

---

# 3. Passthrough Route

A passthrough Route sends the encrypted TLS connection directly to the backend application.

The OpenShift Router does not terminate TLS.

```text
                 TLS connection
Client ==================================> Application
              Router passes through
```

The backend application is responsible for:

* TLS termination
* Server certificate
* Private key
* TLS configuration
* HTTPS protocol

---

## 4. Passthrough Traffic Flow

```text
Client
  |
  | HTTPS
  | TLS session #1
  v
OpenShift Router
  |
  | Encrypted TLS traffic
  | No TLS termination
  v
Service
  |
  v
Application
  |
  | TLS termination
  v
Application process
```

The Router essentially forwards the encrypted connection.

---

# 5. Passthrough Example

Example Route:

```yaml
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: app
  namespace: demo
spec:
  host: app.example.com
  to:
    kind: Service
    name: app
  port:
    targetPort: https
  tls:
    termination: passthrough
```

Apply:

```bash
oc apply -f route.yaml
```

Verify:

```bash
oc get route app -n demo
```

Check details:

```bash
oc describe route app -n demo
```

---

# 6. Important Passthrough Characteristic

The backend must understand TLS.

For example:

```text
Router
   |
   | encrypted HTTPS
   v
Service
   |
   v
Nginx / Apache / RHACS / Application
   |
   v
TLS termination
```

If the backend only speaks HTTP, passthrough will not work correctly.

---

# 7. Reencrypt Route

A reencrypt Route uses TLS on **both sides of the OpenShift Router**.

The Router terminates the external TLS connection and then establishes a new TLS connection to the backend.

```text
Client
   |
   | HTTPS
   v
OpenShift Router
   |
   | decrypt
   |
   | new HTTPS/TLS connection
   v
Backend Service
   |
   v
Application
```

There are therefore two TLS connections:

```text
TLS Connection #1
Client <=================> Router

TLS Connection #2
Router <=================> Backend
```

---

# 8. Reencrypt Traffic Flow

```text
Client
  |
  | HTTPS/TLS
  v
OpenShift Router
  |
  | TLS termination
  |
  | New TLS connection
  v
Service
  |
  | HTTPS/TLS
  v
Application
```

The traffic remains encrypted from the client to the Router and from the Router to the application.

---

# 9. Reencrypt Example

Example:

```yaml
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: app
  namespace: demo
spec:
  host: app.example.com
  to:
    kind: Service
    name: app
  port:
    targetPort: https
  tls:
    termination: reencrypt
    destinationCACertificate: |
      -----BEGIN CERTIFICATE-----
      ...
      -----END CERTIFICATE-----
```

The `destinationCACertificate` allows the Router to validate the backend's certificate.

Apply:

```bash
oc apply -f route.yaml
```

Verify:

```bash
oc describe route app -n demo
```

---

# 10. Why Is destinationCACertificate Important?

With reencrypt, the Router establishes a TLS connection to the backend.

The Router needs to know whether the backend certificate can be trusted.

The `destinationCACertificate` provides the CA certificate used to validate the backend certificate.

Conceptually:

```text
Client
   |
   | TLS
   v
Router
   |
   | validates backend certificate
   | using destination CA
   v
Backend
```

If certificate validation fails, the Router may not be able to establish the backend connection.

---

# 11. Passthrough vs Reencrypt

| Feature                              | Passthrough               | Reencrypt                |
| ------------------------------------ | ------------------------- | ------------------------ |
| Client-to-Router TLS                 | Yes                       | Yes                      |
| Router terminates client TLS         | No                        | Yes                      |
| Router-to-backend encryption         | Yes                       | Yes                      |
| Number of TLS connections            | One end-to-end connection | Two TLS connections      |
| Backend terminates TLS               | Yes                       | Yes                      |
| Router validates backend certificate | Not as a TLS endpoint     | Yes                      |
| Backend must support HTTPS/TLS       | Yes                       | Yes                      |
| Router can inspect HTTP content      | No                        | Yes, after termination   |
| Backend traffic encrypted            | Yes                       | Yes                      |
| Certificate at backend               | Required                  | Required                 |
| Typical use                          | End-to-end TLS            | Secure TLS on both sides |

# 12. Key Difference

The easiest way to remember the difference is:

```text
PASSTHROUGH
============
Router does NOT terminate TLS.

Client ===========================> Backend
             TLS
```

Whereas:

```text
REENCRYPT
=========
Router terminates TLS and creates another TLS session.

Client =====TLS=====> Router =====TLS=====> Backend
```

# 13. Certificate Differences

## Passthrough

The backend owns the certificate used for the client connection.

```text
Client
  |
  | validates backend certificate
  v
Router
  |
  | passes encrypted traffic
  v
Backend
  |
  +-- Certificate
  +-- Private Key
```

The certificate normally needs to match the external hostname.

For example:

```text
central.example.com
```

---

## Reencrypt

There are effectively two certificate relationships.

### External certificate

The Router presents a certificate to the client.

```text
Client
  |
  | validates Router certificate
  v
Router
```

### Backend certificate

The backend presents a certificate to the Router.

```text
Router
  |
  | validates backend certificate
  v
Backend
```

Therefore:

```text
Client
   |
   | External TLS certificate
   v
Router
   |
   | Backend TLS certificate
   v
Application
```

---

# 14. Security Comparison

Both approaches provide encrypted traffic to the backend.

### Passthrough

Advantages:

* End-to-end TLS from client to application
* Router does not decrypt application traffic
* Backend controls TLS completely
* Useful when applications require direct TLS handling

Disadvantages:

* Router cannot inspect decrypted HTTP traffic
* Backend must manage TLS
* Certificate management can be more application-specific

---

### Reencrypt

Advantages:

* Traffic remains encrypted to the backend
* Router can terminate external TLS
* Router can establish a separately trusted TLS connection
* Useful when organizations require encrypted internal traffic

Disadvantages:

* More certificate management
* Two TLS sessions
* Backend certificate validation must be configured correctly

# 15. RHACS Central Example

RHACS Central can be exposed through an OpenShift Route.

For a security-sensitive RHACS environment, understanding the TLS flow is important.

### Passthrough-style architecture

```text
RHACS Administrator
       |
       | HTTPS
       v
OpenShift Router
       |
       | Encrypted TLS
       v
Central Service
       |
       v
RHACS Central
       |
       | TLS termination
       v
Central
```

The Router does not terminate the Central TLS connection.

---

### Reencrypt-style architecture

```text
RHACS Administrator
       |
       | HTTPS
       v
OpenShift Router
       |
       | TLS termination
       |
       | New HTTPS/TLS connection
       v
Central Service
       |
       v
RHACS Central
```

The Router handles the external TLS session and establishes another TLS session toward Central.

The exact RHACS Route/TLS configuration should follow the RHACS version's supported Operator configuration rather than manually modifying operator-managed resources.

---

# 16. When Should You Use Passthrough?

Passthrough is appropriate when:

* The application must control TLS.
* The application needs end-to-end TLS.
* The Router should not terminate TLS.
* The application already has a complete TLS configuration.
* HTTP-level inspection at the Router is not required.

Example applications can include systems where the application itself is responsible for TLS policy and certificate handling.

---

# 17. When Should You Use Reencrypt?

Reencrypt is appropriate when:

* External traffic must use HTTPS.
* Backend traffic must also remain encrypted.
* The Router should terminate the external TLS session.
* The organization wants independent external and internal certificates.
* Backend certificate validation is required.

A common corporate architecture is:

```text
Internet / Corporate User
          |
          | HTTPS
          v
OpenShift Router
          |
          | HTTPS
          v
Application
```

This provides encryption on both network segments.

# 18. Troubleshooting Passthrough

Check the Route:

```bash
oc get route app -n demo -o yaml
```

Verify:

```yaml
tls:
  termination: passthrough
```

Check that the backend listens on HTTPS:

```bash
oc get svc app -n demo
```

Check the application:

```bash
oc get pods -n demo
```

Test:

```bash
curl -vk https://app.example.com
```

If the backend is only serving HTTP, passthrough will fail.

---

# 19. Troubleshooting Reencrypt

Check:

```bash
oc get route app -n demo -o yaml
```

Verify:

```yaml
tls:
  termination: reencrypt
```

Check the destination CA:

```bash
oc describe route app -n demo
```

Verify that the backend supports HTTPS.

Check:

```bash
oc get svc app -n demo
```

Then:

```bash
oc get endpoints app -n demo
```

Test externally:

```bash
curl -vk https://app.example.com
```

If the Router cannot validate or connect to the backend TLS endpoint, investigate:

* Backend certificate
* Destination CA
* Certificate hostname/SAN
* Backend HTTPS port
* Service target port
* Application TLS configuration
* Network connectivity

---

# 20. Common Interview Question

### Question

**What is the difference between passthrough and reencrypt Route?**

### Answer

> In a passthrough Route, the OpenShift Router does not terminate TLS. It forwards the encrypted TLS connection directly to the backend, where TLS is terminated.
>
> In a reencrypt Route, the Router terminates the external TLS connection and then establishes a new TLS connection to the backend. The backend connection therefore remains encrypted, and the Router can validate the backend certificate using the configured destination CA.

# 21. Simple Memory Trick

Remember:

```text
PASSTHROUGH
-----------
TLS passes THROUGH the Router.

Client ===== TLS =====> Backend
```

```text
REENCRYPT
---------
TLS ends at Router,
then TLS starts again.

Client === TLS ===> Router === TLS ===> Backend
```

# 22. Final Summary

| Question                            | Passthrough    | Reencrypt                                     |
| ----------------------------------- | -------------- | --------------------------------------------- |
| Does Router terminate external TLS? | No             | Yes                                           |
| Is backend traffic encrypted?       | Yes            | Yes                                           |
| Does backend terminate TLS?         | Yes            | Yes                                           |
| TLS sessions                        | One            | Two                                           |
| Backend certificate required?       | Yes            | Yes                                           |
| Destination CA required?            | No             | Normally used for backend validation          |
| Router sees decrypted HTTP?         | No             | Yes                                           |
| Best for                            | End-to-end TLS | TLS on both external and internal connections |

The most important architecture to remember is:

```text
Passthrough:

Client
  |
  | TLS
  v
Router
  |
  | TLS - unchanged
  v
Backend


Reencrypt:

Client
  |
  | TLS #1
  v
Router
  |
  | TLS #2
  v
Backend
```

**In short:**

> **Passthrough = one TLS connection that passes through the Router.**

> **Reencrypt = TLS terminates at the Router and a new TLS connection is established to the backend.**
