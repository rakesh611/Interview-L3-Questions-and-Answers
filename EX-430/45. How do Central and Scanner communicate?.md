# How Central and Scanner Communicate in RHACS

## Overview

In Red Hat Advanced Cluster Security for Kubernetes (RHACS), **Central** and **Scanner** work together to provide vulnerability-management capabilities.

At a high level:

```text
                    RHACS Central
                         |
              Vulnerability requests
                         |
                         v
                 +---------------+
                 |    Scanner    |
                 |---------------|
                 | Scanner V4    |
                 | Indexer       |
                 | Matcher       |
                 +-------+-------+
                         |
                         v
                 Scanner database
                         |
                         v
               Vulnerability results
                         |
                         v
                    RHACS Central
                         |
                         v
                 RHACS UI / API
```

The important concept is that **Central is the primary RHACS control-plane component**, while Scanner provides image-analysis and vulnerability-scanning capabilities.

---

# 1. Responsibilities of Central

Central is responsible for the main RHACS control-plane functions.

It maintains and exposes RHACS security information and coordinates activities involving secured clusters and image scanning.

Central is responsible for areas such as:

* RHACS API
* RHACS web UI
* Authentication and authorization
* Security policies
* Vulnerability findings
* Risk information
* Cluster management
* Alert management
* Communication with Secured Cluster components
* Coordination with Scanner components

Central should therefore be viewed as the primary consumer and coordinator of Scanner results.

---

# 2. Responsibilities of Scanner

Scanner is responsible for container-image vulnerability analysis.

In Scanner V4, the major functional responsibilities include:

```text
Scanner
 |
 +-- Indexer
 |     |
 |     +-- Analyzes image contents
 |     +-- Identifies packages
 |     +-- Builds image/package representation
 |
 +-- Matcher
       |
       +-- Uses vulnerability definitions
       +-- Correlates packages with vulnerabilities
       +-- Produces vulnerability matches
```

Scanner therefore focuses on the technical analysis of container images rather than acting as the main RHACS control plane.

---

# 3. Basic Communication Model

A simplified communication sequence is:

```text
Central
   |
   |  Image scan request
   v
Scanner
   |
   |  Analyze image
   v
Indexer
   |
   |  Package/component inventory
   v
Matcher
   |
   |  Vulnerability correlation
   v
Scanner
   |
   |  Scan result
   v
Central
```

Central can then use the resulting information for:

* Risk calculations
* Vulnerability reporting
* Policy evaluation
* UI presentation
* API consumers
* Alerting and security workflows

---

# 4. Central Does Not Perform All Image Analysis Itself

A common misconception is:

> "Central scans every image itself."

That is not the correct architectural model.

Central coordinates and consumes scanning information, while Scanner performs the specialized vulnerability-analysis work.

Conceptually:

```text
Central
  |
  | "Analyze this image"
  v
Scanner
  |
  +-- Index
  |
  +-- Match
  |
  v
Results
  |
  v
Central
```

This separation keeps the RHACS control plane distinct from the image-scanning workload.

---

# 5. Scanner V4 Communication

Scanner V4 introduces a more modular scanning architecture.

The important components include:

```text
                Scanner V4
                    |
          +---------+---------+
          |                   |
          v                   v
       Indexer             Matcher
          |                   |
          |                   |
          +---------+---------+
                    |
                    v
            Vulnerability data
```

Central interacts with Scanner through the Scanner interfaces rather than directly implementing the Indexer and Matcher logic itself.

The exact internal services, endpoints, protocols, and deployment topology can vary by RHACS version and configuration, so administrators should use the deployed RHACS release documentation and inspect the actual services when troubleshooting.

---

# 6. Image Scanning Workflow

Consider an image:

```text
registry.example.com/payments/api:1.5
```

A simplified workflow is:

### Step 1 — Central receives image information

Central receives information about an image from RHACS components.

For example:

```text
Registry:
registry.example.com

Repository:
payments/api

Tag:
1.5
```

---

### Step 2 — Central requests scanning

Central coordinates image analysis through Scanner.

Conceptually:

```text
Central
   |
   | Scan image
   v
Scanner
```

---

### Step 3 — Scanner obtains image content

The Scanner workflow accesses the image or required image metadata/layers through the configured registry-access mechanism.

The Indexer then analyzes the image.

```text
Container Image
       |
       v
     Indexer
       |
       v
Package Inventory
```

---

### Step 4 — Matcher determines vulnerabilities

The Matcher uses the indexed package information and vulnerability definitions.

```text
Package Inventory
       +
Vulnerability Definitions
       |
       v
     Matcher
       |
       v
Vulnerability Matches
```

---

### Step 5 — Results return to Central

The resulting vulnerability information is returned to Central.

```text
Scanner
   |
   | Vulnerability results
   v
Central
```

Central can then associate those findings with the relevant image and RHACS security objects.

---

# 7. Central Uses Scanner Results

Once vulnerability information is available to Central, RHACS can use it in multiple workflows.

For example:

```text
                    Scanner
                       |
                       v
              Vulnerability Results
                       |
                       v
                    Central
                       |
        +--------------+--------------+
        |              |              |
        v              v              v
      Risk           Policy           UI
    Analysis        Evaluation      Reporting
```

This is why a Scanner problem can have a visible impact on vulnerability information in the RHACS UI even though Central itself is healthy.

---

# 8. Scanner Is Not the RHACS Control Plane

Another important distinction is:

```text
Central
  = RHACS control plane

Scanner
  = image vulnerability analysis
```

Central handles the broader RHACS platform functions.

Scanner specializes in container-image analysis and vulnerability matching.

Therefore:

```text
Central failure
    |
    +--> RHACS control-plane functionality affected


Scanner failure
    |
    +--> Image vulnerability scanning affected
```

The exact impact depends on the component and workflow involved.

---

# 9. Scanner Database and Communication

Scanner also depends on vulnerability-definition data.

Conceptually:

```text
                 Scanner
                    |
        +-----------+-----------+
        |                       |
        v                       v
     Indexer                 Matcher
                                |
                                v
                     Vulnerability Database
```

The Matcher uses vulnerability definitions to determine whether packages found by the Indexer correspond to known vulnerabilities.

Therefore, troubleshooting vulnerability results requires distinguishing between:

1. Central communication problems
2. Scanner availability problems
3. Registry/image-access problems
4. Indexing problems
5. Matcher problems
6. Vulnerability-database/data problems

---

# 10. Secured Cluster Relationship

Central also communicates with RHACS Secured Cluster components.

A simplified enterprise architecture is:

```text
                         RHACS Central
                              |
             +----------------+----------------+
             |                                 |
             v                                 v
        Secured Cluster                    Scanner
        Components                         Services
             |                                 |
             |                                 |
             v                                 v
       Runtime/Cluster                   Image Analysis
          Data                              & Matching
```

This distinction is important:

* **Secured Cluster services** provide cluster-level/runtime security capabilities.
* **Scanner** provides image vulnerability-analysis capabilities.
* **Central** coordinates and stores/serves the RHACS security information.

---

# 11. Typical Enterprise Deployment

A conceptual enterprise deployment might look like:

```text
                 OpenShift / Kubernetes
                         |
              +----------+----------+
              |                     |
              v                     v
         RHACS Central         RHACS Scanner
              |                     |
              |                     +-- Indexer
              |                     |
              |                     +-- Matcher
              |
              +--------+
                       |
                       v
                 RHACS Database
```

Depending on the RHACS release and deployment model, Scanner components may be deployed in ways that differ from this simplified diagram.

The key architectural principle remains:

> **Central provides the RHACS control plane, while Scanner provides container-image vulnerability analysis.**

# 12. Troubleshooting Central-to-Scanner Communication

When image scanning is failing, start by determining whether the problem is communication or scanning itself.

## Step 1 — Check Central

Check Central health:

```bash
oc -n stackrox get pods
```

Check Central logs:

```bash
oc -n stackrox logs deploy/central
```

Look for:

```text
scanner
connection
timeout
unavailable
TLS
certificate
RPC
```

---

## Step 2 — Check Scanner

Check Scanner-related pods:

```bash
oc -n stackrox get pods | grep -i scanner
```

Check Scanner logs:

```bash
oc -n stackrox logs <scanner-pod>
```

Look for:

```text
connection refused
timeout
TLS error
certificate error
registry error
authentication failure
matcher error
indexer error
```

---

# 13. Check RHACS Services

Review services:

```bash
oc -n stackrox get svc
```

Identify the relevant Scanner services and verify that they have endpoints.

For example:

```bash
oc -n stackrox get endpoints
```

Depending on the OpenShift version and API behavior, EndpointSlices can also be useful:

```bash
oc -n stackrox get endpointslices
```

A service without healthy endpoints can cause Central-to-Scanner communication failures.

---

# 14. Check Scanner Service Resolution

From an appropriate RHACS pod, verify DNS resolution for the relevant Scanner service.

For example:

```bash
oc -n stackrox exec -it <central-pod> -- \
  getent hosts <scanner-service>
```

If the image contains suitable networking tools, administrators can also test connectivity to the service port.

The important sequence is:

```text
DNS
 |
 v
Service
 |
 v
Endpoint
 |
 v
Pod
```

A failure at any layer can prevent communication.

---

# 15. TLS and Certificate Problems

Central-to-Scanner communication can also be affected by TLS configuration.

Typical symptoms include:

```text
certificate verify failed
unknown authority
x509 error
TLS handshake failure
```

When this happens, investigate:

* Scanner service certificates
* CA configuration
* Central trust configuration
* Certificate expiration
* Service names/SANs
* Network path
* RHACS version compatibility

Do not disable TLS verification as a permanent enterprise solution merely to bypass an error.

---

# 16. NetworkPolicy Considerations

NetworkPolicy can prevent Central from reaching Scanner even when both pods are healthy.

For example:

```text
Central Pod
    |
    | X
    |
NetworkPolicy
    |
    X
    |
Scanner Pod
```

Check policies:

```bash
oc -n stackrox get networkpolicy
```

If policies are present, verify that the required traffic is permitted.

A useful troubleshooting approach is:

```text
Central Pod
    |
    v
DNS resolution
    |
    v
Scanner Service
    |
    v
Scanner Endpoint
    |
    v
Scanner Pod
```

---

# 17. Registry Access Is a Separate Problem

It is important not to confuse **Central-to-Scanner communication** with **Scanner-to-registry access**.

These are different communication paths.

```text
                  +----------------+
                  |     Central    |
                  +-------+--------+
                          |
                          | Scanner communication
                          v
                  +----------------+
                  |    Scanner     |
                  +-------+--------+
                          |
                          | Registry access
                          v
                  +----------------+
                  | Container      |
                  | Registry       |
                  +----------------+
```

Therefore, an image scan can fail because:

* Central cannot communicate with Scanner, or
* Scanner cannot access the registry, or
* Indexing fails, or
* Matching fails, or
* Vulnerability data is unavailable.

These should be investigated separately.

---

# 18. Proxy and Disconnected Environments

In corporate environments, Scanner behavior can also be affected by proxy or disconnected-registry architecture.

A disconnected environment may look like:

```text
                 RHACS Central
                       |
                       v
                    Scanner
                       |
                       v
              Internal Registry
                       |
                       v
                Internal Mirror
```

External vulnerability-data synchronization may require a separate mechanism depending on the RHACS deployment and release.

The key principle is:

> **Central-to-Scanner connectivity and Scanner's access to image/vulnerability data are separate network dependencies.**

---

# 19. Common Failure Scenarios

| Symptom                          | Likely Area                     |
| -------------------------------- | ------------------------------- |
| Scanner pod is not running       | Scanner deployment              |
| Central cannot reach Scanner     | Service/network/TLS             |
| Scanner cannot pull image        | Registry/network/authentication |
| Package missing from scan        | Indexer                         |
| Package detected but CVE missing | Matcher/vulnerability data      |
| TLS handshake failure            | Certificates/trust              |
| Connection timeout               | NetworkPolicy/network path      |
| DNS lookup failure               | Cluster DNS/service discovery   |
| Scanner database/data problem    | Scanner data/update path        |
| Central UI unavailable           | Central/control plane           |

---

# 20. Recommended Troubleshooting Sequence

When investigating Central-to-Scanner problems, use this order:

```text
1. Check Central Pod
       |
       v
2. Check Scanner Pod
       |
       v
3. Check Scanner Service
       |
       v
4. Check Service Endpoints
       |
       v
5. Check DNS
       |
       v
6. Check NetworkPolicy
       |
       v
7. Check TLS/certificates
       |
       v
8. Check Registry Access
       |
       v
9. Check Indexer
       |
       v
10. Check Matcher
       |
       v
11. Check Vulnerability Data
```

This prevents administrators from immediately blaming the vulnerability database when the real problem is basic network connectivity.

---

# 21. Key Interview Answer

> **"Central acts as the RHACS control plane and coordinates image vulnerability scanning through Scanner. Scanner performs the specialized image-analysis work: the Indexer builds the software/package inventory and the Matcher correlates that inventory with vulnerability definitions. Scanner returns vulnerability information to Central, which uses it for risk analysis, policy evaluation, reporting, and presentation through the RHACS UI/API."**

# 22. Final Summary

The Central-to-Scanner relationship can be remembered as:

```text
                 CENTRAL
                    |
             Coordinates Scan
                    |
                    v
                SCANNER
                    |
          +---------+---------+
          |                   |
          v                   v
       INDEXER             MATCHER
          |                   |
          |                   |
          +---------+---------+
                    |
                    v
          Vulnerability Results
                    |
                    v
                 CENTRAL
                    |
          +---------+---------+
          |         |         |
          v         v         v
        Risk      Policy      UI
      Analysis   Evaluation  Reporting
```

### Core distinction

**Central orchestrates and consumes security information.**

**Scanner performs container-image vulnerability analysis.**

**Indexer determines what is inside the image.**

**Matcher determines which known vulnerabilities apply.**

That separation is fundamental to understanding RHACS Scanner V4 architecture and troubleshooting image-scanning failures.
