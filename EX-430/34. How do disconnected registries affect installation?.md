# How Do Disconnected Registries Affect RHACS Installation?

Disconnected or air-gapped environments do not have direct access to the internet or external container registries. RHACS can be deployed in such environments, but the installation process must be planned around a private/disconnected registry.

The major differences are:

* RHACS images must be available in the disconnected registry.
* The RHACS Operator must be installed from a mirrored catalog.
* Image references must point to accessible internal registries.
* Registry authentication must be configured.
* Custom CA certificates may be required.
* OpenShift nodes must be able to pull the required images.
* Updates require an internal mirroring process.

---

## 1. What Is a Disconnected Environment?

A disconnected environment is a cluster where OpenShift nodes cannot directly access external registries such as:

```text
registry.redhat.io
quay.io
docker.io
```

Instead, images are copied into an internal registry:

```text
Internet-connected environment
          |
          | mirror
          v
+-------------------------+
| Corporate Registry      |
| registry.example.com    |
+-------------------------+
          |
          v
+-------------------------+
| Disconnected OpenShift  |
| Cluster                 |
+-------------------------+
```

The disconnected registry becomes the image source for RHACS and other platform components.

---

## 2. Why RHACS Installation Changes

In a normal connected installation:

```text
OpenShift
    |
    +--> Red Hat Catalog
    |
    +--> RHACS Operator
    |
    +--> RHACS Images
```

In a disconnected environment:

```text
Connected Registry
       |
       | mirror
       v
Disconnected Registry
       |
       +--> RHACS Operator Images
       |
       +--> RHACS Operand Images
       |
       +--> Supporting Images
       |
       v
OpenShift Cluster
```

The cluster must be able to obtain everything it needs from the internal sources.

---

## 3. RHACS Operator Images Must Be Available

The RHACS Operator is responsible for managing RHACS resources.

In a connected environment, the Operator can obtain its images from Red Hat's registry infrastructure.

In a disconnected environment, the required Operator images must be mirrored into the approved internal registry.

For example:

```text
registry.example.com/rhacs/operator
```

The exact repository and image locations depend on the RHACS version and mirroring method being used.

---

## 4. RHACS Operand Images Must Also Be Mirrored

Installing the Operator alone is not enough.

RHACS creates components such as:

```text
Central
Scanner
Admission Controller
Sensor
```

Their images must also be available.

Conceptually:

```text
Internal Registry
|
+-- RHACS Operator
|
+-- Central
|
+-- Scanner
|
+-- Admission Controller
|
+-- Sensor
|
+-- Other required RHACS images
```

If even one required image is missing, installation or component startup can fail.

Typical symptoms include:

```text
ImagePullBackOff
ErrImagePull
manifest unknown
unauthorized
x509: certificate signed by unknown authority
```

---

## 5. The Operator Catalog Must Be Available

In disconnected OpenShift environments, Operator installation itself may need a mirrored catalog.

Instead of:

```text
OperatorHub
    |
    v
Internet
```

the architecture becomes:

```text
Disconnected Operator Catalog
            |
            v
       OLM
            |
            v
     RHACS Operator
```

A common approach is to mirror the required Red Hat Operator catalog into an internal registry and expose it to the disconnected cluster.

---

## 6. CatalogSource and OLM

The RHACS Operator is installed through OpenShift's Operator Lifecycle Manager (OLM).

In a disconnected environment, OLM may consume a custom `CatalogSource`.

Conceptually:

```text
CatalogSource
      |
      v
PackageManifest
      |
      v
Subscription
      |
      v
InstallPlan
      |
      v
ClusterServiceVersion
      |
      v
RHACS Operator
```

The CatalogSource must reference an image that the disconnected cluster can access.

Check:

```bash
oc get catalogsource -A
```

Check RHACS-related packages:

```bash
oc get packagemanifest -A | grep -i rhacs
```

Check subscriptions:

```bash
oc get subscription -A
```

---

## 7. ImageContentSourcePolicy and ImageDigestMirrorSet

OpenShift can redirect image pulls from external registries to internal mirrors.

Depending on the OpenShift version and disconnected architecture, organizations may use:

* `ImageDigestMirrorSet`
* `ImageTagMirrorSet`
* Older `ImageContentSourcePolicy` configurations

For modern OpenShift environments, `ImageDigestMirrorSet` is generally preferred where applicable.

Conceptually:

```text
Original registry
       |
       | mirror rule
       v
Internal registry
```

For example:

```text
registry.redhat.io
        |
        v
mirror-registry.example.com
```

The exact mirror configuration must match the organization's OpenShift version and supported disconnected-installation procedure.

---

## 8. Image Pull Secrets Become Important

The internal registry may require authentication.

For example:

```text
registry.example.com
        |
        +-- username
        +-- password/token
```

OpenShift can use an image pull secret to authenticate.

Example:

```bash
oc create secret docker-registry internal-registry \
  --docker-server=registry.example.com \
  --docker-username=<username> \
  --docker-password=<password> \
  --docker-email=<email> \
  -n stackrox
```

However, do not blindly create a namespace-specific secret if the RHACS installation method already manages image pull authentication.

Determine which ServiceAccounts and namespaces require access to the internal registry.

---

## 9. Registry CA Trust

Corporate disconnected registries commonly use internal PKI.

Example:

```text
https://registry.example.com
          |
          v
Corporate Registry CA
```

The OpenShift cluster must trust the registry certificate.

If the registry uses a private CA and the CA is not trusted, nodes may report:

```text
x509: certificate signed by unknown authority
```

The problem is then not necessarily RHACS itself.

It may be the OpenShift node/container runtime rejecting the registry certificate.

---

## 10. Registry Connectivity Must Be Tested First

Before installing RHACS, verify that OpenShift nodes can reach the registry.

For example:

```bash
oc debug node/<node-name>
```

Then inspect the host environment as appropriate.

Test DNS:

```bash
getent hosts registry.example.com
```

Test connectivity:

```bash
curl -vk https://registry.example.com/v2/
```

A successful authenticated registry request commonly returns an HTTP response such as:

```text
401 Unauthorized
```

This can actually indicate that:

```text
DNS works
TCP works
TLS works
Registry is reachable
```

Authentication is then the remaining requirement.

---

## 11. Verify the Registry Certificate

Use:

```bash
openssl s_client \
  -connect registry.example.com:443 \
  -showcerts
```

Check:

* Subject
* Issuer
* SAN
* Expiration
* Certificate chain

For example:

```text
Subject: CN=registry.example.com
Issuer: CN=Corporate-Intermediate-CA
```

Make sure the appropriate CA is trusted by the OpenShift environment.

---

## 12. Image Mirroring Workflow

A typical corporate workflow is:

```text
Step 1
Connected staging environment
        |
        v
Obtain RHACS release
        |
        v
Mirror required images
        |
        v
Internal registry
        |
        v
Export/import or replicate
        |
        v
Disconnected network
        |
        v
Disconnected registry
        |
        v
OpenShift
```

The exact commands depend on the RHACS and OpenShift versions and the organization's approved mirroring process.

## 13. Installation Order

A good disconnected RHACS installation sequence is:

```text
1. Prepare internal registry
        |
2. Configure registry DNS
        |
3. Configure registry TLS/CA
        |
4. Mirror required OpenShift/RHACS content
        |
5. Configure image mirrors
        |
6. Configure registry authentication
        |
7. Configure disconnected Operator catalog
        |
8. Verify RHACS Operator availability
        |
9. Install RHACS Operator
        |
10. Create Central
        |
11. Verify Central images
        |
12. Verify Scanner
        |
13. Verify Secured Cluster components
```

## 14. What Happens If an Image Is Missing?

Suppose Central requires an image that was not mirrored.

The Pod may show:

```bash
oc get pods -n stackrox
```

Example:

```text
NAME                      STATUS
central-xxxxxxxx          ImagePullBackOff
```

Inspect:

```bash
oc describe pod central-xxxxxxxx -n stackrox
```

Look at the Events section.

You may see:

```text
Failed to pull image
```

or:

```text
manifest unknown
```

or:

```text
repository does not exist
```

This usually indicates a registry/mirroring problem.

---

## 15. What Happens If Authentication Is Wrong?

You may see:

```text
unauthorized: authentication required
```

or:

```text
pull access denied
```

Check:

```bash
oc get secret -n stackrox
```

Then verify that the appropriate image pull credentials are available to the ServiceAccount used by the RHACS workload.

Do not store registry passwords directly in YAML committed to Git.

---

## 16. What Happens If the Registry CA Is Wrong?

A common error is:

```text
x509: certificate signed by unknown authority
```

Troubleshooting:

```text
DNS
 |
 +-- works?
 |
 v
TCP 443
 |
 +-- works?
 |
 v
TLS certificate
 |
 +-- trusted?
 |
 v
Registry authentication
 |
 +-- works?
 |
 v
Image pull
```

This sequence helps isolate the problem quickly.

## 17. Disconnected Registry and Central

Central itself runs inside the OpenShift cluster.

For example:

```text
OpenShift
   |
   +-- stackrox namespace
          |
          +-- Central
          +-- Scanner
          +-- Other RHACS components
```

Central does not require unrestricted internet access simply to run.

However, it may need access to services such as:

* Internal image registries
* Internal LDAP/LDAPS
* Internal proxy
* Internal notification endpoints
* Other enterprise services

Therefore, disconnected does not mean "no network connectivity."

It means connectivity is restricted to approved internal endpoints.

---

## 18. Disconnected Registry and Scanner

Scanner-related images must also be available from the internal registry.

For example:

```text
Internal Registry
       |
       +-- RHACS Operator
       +-- Central
       +-- Scanner
       +-- Scanner DB
       +-- Other RHACS images
```

If Scanner images are missing, Central may start while Scanner remains unhealthy.

Therefore:

```bash
oc get pods -n stackrox
```

should be checked after installation.

---

## 19. Vulnerability Feed Updates

One of the important disconnected-environment considerations is vulnerability data.

A connected RHACS deployment can obtain vulnerability data through supported update mechanisms.

In a disconnected environment, vulnerability intelligence must be handled according to the supported RHACS disconnected architecture and organizational process.

Conceptually:

```text
Connected environment
       |
       v
Vulnerability update process
       |
       v
Approved transfer mechanism
       |
       v
Disconnected environment
       |
       v
RHACS vulnerability data
```

This means a disconnected deployment requires an operational process for keeping security intelligence current.

---

## 20. RHACS Version Upgrades

Upgrades are more complicated in disconnected environments.

Connected:

```text
New RHACS release
       |
       v
External registry
       |
       v
OpenShift
```

Disconnected:

```text
New RHACS release
       |
       v
Approved mirroring process
       |
       v
Internal registry
       |
       v
Disconnected OpenShift
```

Before upgrading, verify that the required images and Operator catalog content for the target RHACS version are available internally.

## 21. Common Problems

| Problem        | Typical Symptom                                 | Likely Cause                         |
| -------------- | ----------------------------------------------- | ------------------------------------ |
| Missing image  | `manifest unknown`                              | Image not mirrored                   |
| Authentication | `unauthorized`                                  | Invalid/missing registry credentials |
| TLS            | `x509: certificate signed by unknown authority` | Registry CA not trusted              |
| DNS            | `no such host`                                  | Registry DNS problem                 |
| Network        | `connection timeout`                            | Firewall/routing problem             |
| Catalog        | RHACS Operator unavailable                      | Catalog not mirrored/configured      |
| Operator       | CSV fails                                       | Operator image/dependency issue      |
| Central        | `ImagePullBackOff`                              | Operand image unavailable            |
| Scanner        | Scanner unavailable                             | Scanner image/configuration issue    |
| Upgrade        | New version unavailable                         | Target images/catalog not mirrored   |

## 22. Recommended Pre-Installation Checklist

Before installing RHACS in a disconnected cluster:

* [ ] Confirm the internal registry is operational.
* [ ] Confirm registry DNS works from OpenShift nodes.
* [ ] Confirm registry TLS certificates are valid.
* [ ] Install/configure the required registry CA trust.
* [ ] Confirm registry authentication.
* [ ] Mirror the RHACS Operator content.
* [ ] Mirror all required RHACS operand images.
* [ ] Configure the disconnected Operator catalog.
* [ ] Configure image mirror rules where required.
* [ ] Verify OpenShift nodes can pull mirrored images.
* [ ] Verify the RHACS version matches the mirrored content.
* [ ] Verify required RHACS dependencies are also mirrored.
* [ ] Plan vulnerability-feed updates.
* [ ] Document the image-mirroring procedure.
* [ ] Document the upgrade/mirroring procedure.

## 24. Interview Answer

**Question:** How do disconnected registries affect RHACS installation?

**Answer:**

> In a disconnected environment, RHACS cannot rely on external registries or Operator catalogs. The RHACS Operator, Central, Scanner, admission, Sensor, and other required images must be mirrored into an approved internal registry. The disconnected OpenShift cluster must be configured to access that registry, including DNS, network connectivity, registry authentication, TLS/CA trust, and image mirror configuration. The RHACS Operator catalog must also be made available through the disconnected OLM configuration. Before installation, all required images and dependencies should be verified in the internal registry. Upgrades and vulnerability-data updates also require an established disconnected mirroring process.

---

## 25. Key Takeaway

The most important concept is:

```text
Disconnected RHACS
       |
       +-- Internal Registry
       |
       +-- Mirrored RHACS Images
       |
       +-- Mirrored Operator Catalog
       |
       +-- Registry Authentication
       |
       +-- Registry CA Trust
       |
       +-- Image Mirror Configuration
       |
       +-- Internal Network/DNS
       |
       +-- Vulnerability Update Process
       |
       +-- Upgrade/Mirroring Process
```

A disconnected registry does **not** prevent RHACS installation. It changes the installation from a direct internet-based deployment into a **controlled image-mirroring and internal-registry deployment**.

The critical rule is:

> **Before installing RHACS in a disconnected environment, make sure every required Operator and operand image, catalog dependency, certificate, credential, and update mechanism is available through the approved internal infrastructure.**
