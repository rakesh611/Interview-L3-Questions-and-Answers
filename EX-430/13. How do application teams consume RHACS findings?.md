# How Do Application Teams Consume RHACS Findings?

## Overview

Application teams consume Red Hat Advanced Cluster Security for Kubernetes (RHACS) findings to understand **what is wrong with their application, how serious the problem is, where it exists, and what action they need to take**.

RHACS findings can include:

* Container image vulnerabilities
* Kubernetes configuration violations
* Deployment policy violations
* Network exposure
* Runtime security alerts
* Risk indicators
* Compliance-related findings
* Security policy violations

The application team normally does **not own the RHACS platform itself**. Instead, it consumes findings from RHACS and remediates issues in application code, container images, manifests, Helm charts, and CI/CD pipelines.

---

# 1. Application Team's Role

The basic workflow is:

```text
                RHACS
                  |
                  v
          Security Finding
                  |
                  v
        Application Team
                  |
        +---------+---------+
        |         |         |
        v         v         v
      Code      Image     Manifest
        |         |         |
        +---------+---------+
                  |
                  v
              Remediation
                  |
                  v
              CI/CD
                  |
                  v
             New Release
                  |
                  v
                RHACS
                  |
                  v
             Re-evaluate
```

The application team consumes RHACS findings and turns them into **remediation work**.

# 2. Where Application Teams See RHACS Findings

Application teams can consume RHACS findings through several mechanisms.

* Vulnerabilities


# 3. CI/CD Pipeline Integration

A mature organization does not wait until production to discover security problems.

RHACS findings can be integrated into the software delivery lifecycle.

A typical pipeline looks like:

```text

   |
   v

   |
   v

   |
   +--> Build image
   |
   +--> Security checks
   |
   v

   |
   v

   |
   +--> Pass
   |     |
   |     v
   |   Deploy
   |
   +--> Fail
         |
         v
       Fix
```

This moves security earlier into the development lifecycle.

# 4. Vulnerability Findings

One of the most common RHACS findings is a container image vulnerability.

Example:

```text
Application:
payment-api

Image:
registry.example.com/payment-api:2.4.1

Finding:
CVE-XXXX-YYYY

Severity:
Critical

Component:
openssl

Current Version:
X.Y.Z

Fixed Version:
X.Y.Z+1
```

The application team should determine:

1. Is the affected image used by the application?
2. Which package contains the vulnerability?
3. Is a fixed version available?
4. Can the base image be upgraded?
5. Does the application require a dependency upgrade?
6. Does the new image pass testing?

---

# 5. Remediation Through the Container Image

A common remediation workflow is:

```text
RHACS Finding
      |
      v
Identify vulnerable package
      |
      v
Identify base image
      |
      v
Update Containerfile
      |
      v
Build new image
      |
      v
Run tests
      |
      v
Push new image
      |
      v
RHACS rescans image
      |
      v
Vulnerability resolved
```

For example:

```dockerfile
FROM registry.example.com/approved-base:latest

COPY application.jar /app/application.jar

USER 1001

CMD ["java", "-jar", "/app/application.jar"]
```

The application team may need to update the base image to a newer approved version.

# 6. Kubernetes Configuration Findings

RHACS can identify insecure Kubernetes/OpenShift configurations.

Examples include:

* Privileged containers
* Running as root
* Host networking
* Host PID
* Host IPC
* Dangerous capabilities
* Writable host mounts
* Insecure deployment configurations

Example:

```text
Deployment:
payment-api

RHACS Policy:
Container runs as root

Severity:
High
```

The application team investigates the deployment configuration.

---

# 7. Example: Running as Root

Suppose the workload contains:

```yaml
securityContext:
  runAsUser: 0
```

RHACS reports a policy violation.

The application team may change the workload to use a non-root UID:

```yaml
securityContext:
  runAsNonRoot: true
```

Depending on the application and platform, additional settings may be required.

After deployment:

```text
Old Deployment
      |
      v
RHACS violation
      |
      v
Manifest changed
      |
      v
New Deployment
      |
      v
RHACS evaluation
      |
      v
Violation resolved
```

---

# 8. Policy Violations

RHACS policies can identify application deployment risks.

For example:

```text
Policy:
Privileged Container

Application:
payment-api

Namespace:
production

Severity:
High
```

The application team should:

1. Open the finding.
2. Identify the affected deployment.
3. Understand why the policy triggered.
4. Determine the required configuration change.
5. Test the application.
6. Deploy the corrected configuration.
7. Verify that RHACS no longer reports the violation.

---

# 9. Runtime Findings

RHACS can also generate runtime security alerts.

For example:

```text
Application:
web-api

Runtime event:
Unexpected shell execution

Container:
web-api-7f8d9c

Process:
/bin/sh

Severity:
High
```

This is different from a normal vulnerability.

The application team should not simply change the configuration and close the alert.

The process should be:

```text
Runtime Alert
     |
     v
Security Team
     |
     v
Investigate
     |
     +---- Expected behavior
     |          |
     |          v
     |       Document
     |
     +---- Suspicious behavior
                |
                v
          Incident Response
```

The application team provides technical context about the application.

---

# 10. Application Team and Security Team Interaction

Application teams should not independently dismiss serious security findings.

A good model is:

```text
              RHACS Finding
                    |
          ┌─────────┴─────────┐
          |                   |
     Security Team       Application Team
          |                   |
      Assess risk       Understand application
          |                   |
          └─────────┬─────────┘
                    |
               Remediation
                    |
                    v
                Validation
```

The security team determines the security significance.

The application team determines how to safely fix the application.

# 11. Findings in CI/CD

RHACS can be integrated into CI/CD so that security findings become part of the release process.

Example:

```text
Developer Commit
       |
       v
Git
       |
       v
Jenkins / Tekton
       |
       v
Build Image
       |
       v
RHACS Security Check
       |
   +---+---+
   |       |
 PASS     FAIL
   |       |
   v       v
Deploy    Fix
```

For example, an organization may define:

```text
Critical vulnerabilities = Block
High vulnerabilities     = Review
Medium vulnerabilities   = Allow
Low vulnerabilities      = Allow
```

The exact thresholds should be defined by the organization's security policy.

Suppose the application uses Helm.

The RHACS finding reports:

```text

```

The application team may find this configuration in:

```text

```

They change the configuration:

```yaml

  privileged: false
```

Then:

```text

   |

   |
   v

   |
   v

   |
   v

   |
   v

```

The finding should disappear after the workload is corrected and RHACS reevaluates it.

# 17. Prioritizing Findings

Application teams may receive many findings.

They should not treat every finding equally.

A practical prioritization model is:

```text
Priority
   |
   +--> Critical vulnerability
   |
   +--> Exploitable vulnerability
   |
   +--> Internet-facing workload
   |
   +--> Production workload
   |
   +--> Privileged configuration
   |
   +--> High-risk runtime behavior
   |
   +--> Medium/Low findings
```

Risk should be evaluated using the organization's security policy.

---

# 18. Avoiding Alert Fatigue

If developers receive hundreds of security alerts without prioritization, they may start ignoring them.

A better model is:

```text
All RHACS Findings
        |
        v
Risk Filtering
        |
        v
Application-Relevant Findings
        |
        v
Prioritized Findings
        |
        v
Developer Action
```

Useful information includes:

* Application name
* Namespace
* Deployment
* Image
* Vulnerability
* Severity
* Policy
* Recommended remediation
* Environment
* Owner

* Kubernetes manifests

# 21. What Application Teams Normally Do Not Own

Application teams normally do not own:

* RHACS Central infrastructure
* RHACS Operator
* RHACS cluster-wide installation
* Sensor infrastructure
* RHACS platform upgrades
* Central storage
* RHACS platform availability
* Organization-wide security policy governance

These are usually platform/security responsibilities.

# 25. Finding Lifecycle

Application teams should understand the lifecycle of a finding:

```text
Detected
   |
   v
Reviewed
   |
   v
Assigned
   |
   v
Remediation
   |
   v
Tested
   |
   v
Deployed
   |
   v
Re-evaluated
   |
   v
Resolved
```

A finding should not simply be marked as "done" because a developer changed a Git file.

The actual deployed workload must be corrected.

# 26. False Positives and Exceptions

Sometimes a finding may be legitimate or incorrectly triggered.

The application team should provide technical information.

For example:

```text
Finding:
Container runs as root

Application Team:
Application requires UID 0 because of legacy behavior.
```

The security team can evaluate the risk.

If an exception is justified:

```text
Security Review
      |
      v
Exception approved
      |
      v
Document:
- Reason
- Application
- Scope
- Expiration
- Owner
```

Exceptions should be controlled and periodically reviewed.

# 29. Best Practices

## 1. Integrate RHACS into CI/CD

Do not depend only on production-time detection.

## 2. Assign findings to application owners

Every actionable finding should have a clear owner.

## 3. Prioritize by risk

Critical production findings should receive more attention than low-risk findings.

## 4. Fix the root cause

Do not repeatedly suppress the same finding.

## 5. Use GitOps where possible

Make remediation changes through Git so they are auditable.

## 6. Automate notifications

Use appropriate integrations for ticketing and team notifications.

## 7. Define remediation SLAs

For example:

```text
Critical → Immediate/short SLA
High     → Short SLA
Medium   → Normal remediation cycle
Low      → Planned remediation
```

The exact SLA should be defined by the organization's security policy.

## 8. Keep security and application ownership separate

Security decides the risk.

Application teams fix their workloads.

Platform teams operate RHACS.

---

# 30. Interview Answer

A strong interview answer is:

> "Application teams consume RHACS findings mainly through the RHACS console, CI/CD integrations, APIs, notifications, and ticketing workflows. They use findings to identify vulnerable images, insecure Kubernetes configurations, policy violations, and runtime security issues affecting their applications. The team investigates the finding, determines the root cause, updates the application code, container image, Helm chart, or Kubernetes manifest, and redeploys through the normal CI/CD or GitOps process. RHACS then continuously evaluates the new deployment to confirm whether the finding is resolved. Security owns the risk and policy decisions, while the application team owns remediation of its workloads."

> **Application teams consume RHACS findings as actionable security feedback. RHACS identifies the problem, security determines the risk, the application team fixes the application/image/configuration, CI/CD or GitOps delivers the fix, and RHACS continuously verifies the resulting workload.**
