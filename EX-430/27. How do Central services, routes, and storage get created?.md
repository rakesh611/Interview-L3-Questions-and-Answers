# How Central Services, Routes, and Storage Get Created in RHACS

## 1. Overview

When Red Hat Advanced Cluster Security for Kubernetes (RHACS) is installed using the **RHACS Operator**, the operator manages the lifecycle of the RHACS components.

The main flow is:

```text
RHACS Operator
      |
      v
Central Custom Resource (CR)
      |
      +------------------+
      |                  |
      v                  v
Central Deployment    Central Services
      |                  |
      |                  v
      |              Central Route
      |
      v
Central Storage
```

The RHACS Operator watches the `Central` custom resource and creates or reconciles the required Kubernetes/OpenShift resources.

---

# 2. Central Custom Resource

The starting point is normally a `Central` custom resource.

Example:

```yaml
apiVersion: platform.stackrox.io/v1alpha1
kind: Central
metadata:
  name: stackrox-central-services
  namespace: stackrox
spec:
  central:
    exposure:
      route:
        enabled: true
```

The exact CR fields depend on the RHACS version and deployment requirements.

After creating the CR:

```bash
oc apply -f central.yaml
```

the RHACS Operator detects it and starts reconciliation.

You can check the CR:

```bash
oc get central -n stackrox
```

and:

```bash
oc describe central stackrox-central-services -n stackrox
```

---

# 3. How the Operator Creates Central

The RHACS Operator acts as the controller for the `Central` resource.

Conceptually:

```text
Central CR
   |
   v
RHACS Operator
   |
   +--> Deployment
   +--> Service
   +--> Route
   +--> Secret
   +--> ConfigMap
   +--> PVC
   +--> Other supporting resources
```

The operator continuously compares the desired state in the CR with the actual cluster state.

If something is missing or modified, the operator attempts to reconcile it.

For example:

```text
Desired:
Central must exist
Central Service must exist
Route must expose Central
Storage must be available

        |
        v

Operator reconciliation

        |
        v

Actual resources created/updated
```

Therefore, administrators generally should **not manually manage operator-owned resources** unless RHACS documentation specifically requires it.

---

# 4. Central Deployment

The Central workload is created as Kubernetes/OpenShift resources managed by the operator.

Check the resources with:

```bash
oc get deployment -n stackrox
```

For example:

```text
NAME                         READY   UP-TO-DATE   AVAILABLE
central                      1/1     1            1
```

Check the Central pods:

```bash
oc get pods -n stackrox
```

Example:

```text
NAME                       READY   STATUS    RESTARTS
central-xxxxxxxxxx-xxxxx   1/1     Running   0
```

The Central pod runs the RHACS Central component responsible for functions such as:

* RHACS API
* RHACS web UI
* Security policy management
* Vulnerability management
* Compliance information
* Risk information
* Alert/violation processing
* Communication with secured clusters

---

# 5. Central Service

The operator creates Kubernetes Services to provide stable networking to Central.

Check them with:

```bash
oc get svc -n stackrox
```

Typical services may include:

```text
NAME
central
central-mtls
central-db
```

The exact service names and architecture can vary by RHACS release and configuration.

A Service provides a stable virtual endpoint in front of the Central pod.

Conceptually:

```text
                   +----------------+
                   |  Central Pod   |
                   |                |
                   | RHACS Central  |
                   +-------+--------+
                           ^
                           |
                     Kubernetes
                       Service
                           ^
                           |
              +------------+------------+
              |                         |
        Internal clients           External access
```

A Service can provide:

* Stable DNS name
* Stable virtual IP
* Port mapping
* Load balancing across matching pods

For example:

```bash
oc describe svc central -n stackrox
```

can be used to inspect:

* Service type
* Ports
* Target ports
* Selector
* Cluster IP

---

# 6. Central Route

On OpenShift, external access to Central can be provided through an OpenShift `Route`.

If route exposure is enabled in the Central configuration, the RHACS Operator creates and manages the Route.

Check:

```bash
oc get route -n stackrox
```

Example:

```text
NAME       HOST/PORT
central    central-stackrox.apps.example.com
```

The traffic flow is approximately:

```text
User Browser
     |
     v
OpenShift Router
     |
     v
Route
     |
     v
Central Service
     |
     v
Central Pod
```

The Route provides the externally accessible hostname.

For example:

```text
https://central-stackrox.apps.example.com
```

The actual hostname depends on the OpenShift cluster's application domain.

Check the route:

```bash
oc describe route central -n stackrox
```

---

# 7. Route and TLS

RHACS Central requires secure communication.

Depending on the RHACS configuration and exposure method, TLS certificates and secrets are used to secure communication.

Check relevant secrets:

```bash
oc get secrets -n stackrox
```

Inspect a particular secret:

```bash
oc describe secret <secret-name> -n stackrox
```

Do not manually modify operator-managed TLS secrets unless the RHACS documentation specifically instructs you to do so.

A simplified traffic model is:

```text
HTTPS Client
     |
     v
OpenShift Route
     |
     | TLS
     v
Central Service
     |
     v
Central
```

---

# 8. Central Storage

Central requires persistent storage for data that must survive pod restarts.

The operator can create the required storage resources based on the RHACS configuration.

The actual storage architecture depends on the RHACS version and selected Central database/storage configuration.

Check persistent volume claims:

```bash
oc get pvc -n stackrox
```

Example:

```text
NAME                STATUS   VOLUME       CAPACITY
central-db          Bound    pvc-xxxx     100Gi
```

The general storage relationship is:

```text
Central
   |
   v
PVC
   |
   v
StorageClass
   |
   v
Persistent Volume
   |
   v
Underlying Storage
```

---

# 9. StorageClass

A PVC normally requests storage through a `StorageClass`.

Check available StorageClasses:

```bash
oc get storageclass
```

Example:

```text
NAME                 PROVISIONER
lvms-vg1             topolvm.io
ocs-storagecluster   openshift-storage.rbd.csi.ceph.com
```

The RHACS deployment does not necessarily create the cluster's StorageClass.

Usually:

```text
Cluster Administrator
        |
        v
StorageClass already available

        +

RHACS Central configuration
        |
        v
PVC request
```

The underlying storage platform could be:

* OpenShift Data Foundation
* Ceph
* LVM Storage
* Cloud block storage
* NFS-based storage where supported
* Other CSI-based storage

The storage provisioner creates the actual persistent volume.

---

# 10. PVC Binding

When the RHACS operator creates or requests a PVC, Kubernetes attempts to bind it to storage.

Check:

```bash
oc get pvc -n stackrox
```

A healthy PVC should normally show:

```text
STATUS   Bound
```

Example:

```text
NAME         STATUS   VOLUME
central-db   Bound    pvc-123456
```

The lifecycle is:

```text
Central CR
   |
   v
Operator
   |
   v
PVC
   |
   v
StorageClass
   |
   v
CSI Provisioner
   |
   v
PV
   |
   v
Storage backend
```

---

# 11. What Happens During Central Restart?

Persistent storage is important because pod storage is ephemeral.

For example:

```text
Central Pod
     |
     +---- ephemeral container filesystem
     |
     +---- persistent storage
                 |
                 v
                PVC
```

If the Central pod is recreated:

```text
Old Central Pod
      X
      |
      v
New Central Pod
      |
      v
Same persistent storage
```

The goal is that required persistent data remains available after the pod is recreated.

---

# 12. Operator Reconciliation

The RHACS Operator continuously watches the `Central` resource and related resources.

For example, if someone deletes an operator-managed resource:

```bash
oc delete deployment <name> -n stackrox
```

the operator may detect that the desired resource is missing and recreate it.

Conceptually:

```text
Desired State
     |
     | Central CR
     v
RHACS Operator
     |
     | compare
     v
Actual State
     |
     +---- Deployment
     +---- Service
     +---- Route
     +---- PVC
     +---- Secrets
     |
     v
Reconciliation
```

This is one of the main advantages of using the Operator.

# 13. How to Troubleshoot Central Resource Creation

Start with the namespace:

```bash
oc get ns
```

Check RHACS resources:

```bash
oc get all -n stackrox
```

Check Central:

```bash
oc get central -n stackrox
```

Check the Central CR:

```bash
oc describe central stackrox-central-services -n stackrox
```

Check pods:

```bash
oc get pods -n stackrox
```

Check deployments:

```bash
oc get deployment -n stackrox
```

Check services:

```bash
oc get svc -n stackrox
```

Check routes:

```bash
oc get route -n stackrox
```

Check PVCs:

```bash
oc get pvc -n stackrox
```

Check events:

```bash
oc get events -n stackrox --sort-by=.lastTimestamp
```

---

# 14. Troubleshooting the Operator

If the Central resources are not being created, first check the RHACS Operator.

```bash
oc get pods -n rhacs-operator
```

Check the Operator deployment:

```bash
oc get deployment -n rhacs-operator
```

Check Operator logs:

```bash
oc logs deployment/rhacs-operator -n rhacs-operator
```

Also check the Operator CSV:

```bash
oc get csv -n rhacs-operator
```

A healthy CSV should normally show:

```text
PHASE
Succeeded
```

If the Operator is unhealthy, the Central CR may remain in a non-ready state.

---

# 15. Troubleshooting Route Problems

If Central is running but the UI is inaccessible:

```bash
oc get route -n stackrox
```

Then inspect:

```bash
oc describe route <route-name> -n stackrox
```

Check the service:

```bash
oc get svc -n stackrox
```

Check endpoints:

```bash
oc get endpoints -n stackrox
```

Also verify the Central pod:

```bash
oc get pods -n stackrox -o wide
```

The troubleshooting path is:

```text
DNS
 |
 v
Route
 |
 v
Service
 |
 v
Endpoint
 |
 v
Central Pod
```

If any layer is broken, external access can fail.

---

# 16. Troubleshooting Storage Problems

If a Central PVC is stuck in `Pending`:

```bash
oc get pvc -n stackrox
```

Then inspect:

```bash
oc describe pvc <pvc-name> -n stackrox
```

Check StorageClasses:

```bash
oc get storageclass
```

Check PVs:

```bash
oc get pv
```

Check CSI components:

```bash
oc get pods -A | grep -i csi
```

Typical troubleshooting flow:

```text
PVC Pending
    |
    +--> Is StorageClass available?
    |
    +--> Is StorageClass correct?
    |
    +--> Is CSI provisioner healthy?
    |
    +--> Is backend storage healthy?
    |
    +--> Are there capacity/topology constraints?
```

---

# 17. Important Administration Principle

The RHACS Operator follows the Kubernetes Operator pattern.

Therefore:

```text
Administrator
     |
     v
Central CR
     |
     v
RHACS Operator
     |
     v
Managed Resources
```

Instead of manually creating every resource:

```text
Deployment
Service
Route
Secret
PVC
ConfigMap
...
```

the administrator primarily defines the desired RHACS configuration in the appropriate Custom Resource.

The Operator then creates and maintains the required resources.

---

# 18. Summary

| Resource     | Purpose                       | Normally managed by                    |
| ------------ | ----------------------------- | -------------------------------------- |
| `Central` CR | Desired Central configuration | Administrator                          |
| Deployment   | Runs Central                  | RHACS Operator                         |
| Service      | Stable internal networking    | RHACS Operator                         |
| Route        | External OpenShift access     | RHACS Operator                         |
| Secret       | Credentials/TLS/configuration | Operator/configuration                 |
| PVC          | Persistent storage request    | Operator/configuration                 |
| PV           | Actual persistent volume      | Storage/CSI layer                      |
| StorageClass | Defines storage provisioning  | Cluster administrator/storage platform |
| CSI driver   | Provisions/attaches storage   | Storage platform                       |

The overall architecture is:

```text
                  Administrator
                       |
                       v
                Central CR
                       |
                       v
                RHACS Operator
                       |
       +---------------+----------------+
       |               |                |
       v               v                v
   Deployment       Service           Route
       |               |                |
       |               +-------+--------+
       |                       |
       v                       v
    Central <------------- External Access
       |
       v
      PVC
       |
       v
  StorageClass
       |
       v
  CSI Provisioner
       |
       v
 Persistent Storage
```

**Key point:** The RHACS Operator is the control plane for the RHACS Central deployment. The `Central` custom resource expresses the desired state, while the Operator creates and reconciles Central's workloads, Services, Routes, storage-related resources, and other supporting objects. The underlying `StorageClass` and storage infrastructure are generally provided by the OpenShift cluster's storage platform rather than by RHACS itself.
