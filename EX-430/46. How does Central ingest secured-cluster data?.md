# How Central Ingests Secured-Cluster Data in RHACS

## Overview

In Red Hat Advanced Cluster Security for Kubernetes (RHACS), **Central** acts as the central control plane for security information collected from one or more secured clusters.

The basic architecture is:

```text
                    RHACS Central
                         |
          +--------------+--------------+
          |              |              |
          v              v              v
     Secured Cluster  Secured Cluster  Secured Cluster
          #1               #2               #3
          |                |                |
          v                v                v
   Sensor/Collectors  Sensor/Collectors  Sensor/Collectors
```

Each secured cluster runs RHACS components that observe cluster activity and communicate relevant security information back to Central.

The key principle is:

> **Secured-cluster components collect and observe cluster-level information; Central receives, processes, stores, correlates, and exposes that information through the RHACS control plane.**

---

# 1. What Is a Secured Cluster?

A secured cluster is a Kubernetes or OpenShift cluster that is protected and monitored by RHACS.

A secured cluster typically contains RHACS components such as:

```text
Secured Cluster
      |
      +-- Sensor
      |
      +-- Admission Controller
      |
      +-- Collector
      |
      +-- Other RHACS components
```

The exact component deployment and responsibilities can vary by RHACS version and configuration.

---

# 2. High-Level Data Flow

A simplified data-ingestion path is:

```text
 Kubernetes / OpenShift Cluster
             |
             v
     +----------------+
     | Sensor         |
     |                |
     | Cluster events |
     | K8s resources  |
     | Security data  |
     +--------+-------+
              |
              |
              v
        RHACS Central
              |
      +-------+-------+
      |               |
      v               v
   Processing       Storage
      |               |
      +-------+-------+
              |
              v
       RHACS UI / API
```

Runtime information can also originate from the Collector and other secured-cluster components.

---

# 3. Sensor's Role

**Sensor** is the primary RHACS component responsible for communicating cluster-level information to Central.

Sensor observes Kubernetes/OpenShift resources and security-relevant events.

Examples include:

* Deployments
* Pods
* Services
* Namespaces
* Network policies
* Roles
* RoleBindings
* Service accounts
* Image references
* Kubernetes resource changes
* Security-related cluster events

Conceptually:

```text
Kubernetes API
       |
       v
     Sensor
       |
       v
     Central
```

Sensor should therefore be viewed as an important **cluster-side data collection and communication component**.

---

# 4. Collector's Role

The RHACS **Collector** provides runtime/container-level information from nodes.

A simplified flow is:

```text
Node
 |
 +-- Containers
 +-- Processes
 +-- Network activity
 +-- Runtime information
 |
 v
Collector
 |
 v
Sensor / Secured Cluster components
 |
 v
Central
```

The Collector is therefore different from Sensor.

A useful distinction is:

| Component            | Primary responsibility                                  |
| -------------------- | ------------------------------------------------------- |
| Sensor               | Kubernetes/OpenShift cluster/resource information       |
| Collector            | Runtime/node/container activity                         |
| Admission Controller | Admission-time policy enforcement                       |
| Central              | Central processing, storage, APIs, UI, and coordination |

---

# 5. Central as the Control Plane

Central receives security information from secured clusters and provides the centralized RHACS view.

Conceptually:

```text
                  Central
                    |
        +-----------+-----------+
        |           |           |
        v           v           v
     Cluster 1   Cluster 2   Cluster 3
```

Central can therefore maintain a consolidated security view across multiple Kubernetes/OpenShift clusters.

For example:

```text
Central
 |
 +-- Production Cluster
 |      |
 |      +-- Workloads
 |      +-- Vulnerabilities
 |      +-- Violations
 |
 +-- Development Cluster
 |      |
 |      +-- Workloads
 |      +-- Vulnerabilities
 |
 +-- DR Cluster
        |
        +-- Workloads
        +-- Violations
```

---

# 6. How Sensor Communicates With Central

The secured-cluster Sensor establishes communication with Central using RHACS's secured communication mechanisms.

The connection is authenticated and protected using TLS and RHACS-managed certificates/secrets.

Conceptually:

```text
Sensor
   |
   | Secure connection
   | Authentication
   | TLS
   v
Central
```

The exact service names, ports, certificate resources, and deployment details depend on the RHACS version and installation method.

Administrators should therefore inspect the actual deployed RHACS resources rather than assuming a particular service name or port across all releases.

---

# 7. Initial Secured-Cluster Registration

Before Central can receive data from a secured cluster, the cluster must be registered with Central.

The conceptual workflow is:

```text
Central
  |
  | Generate cluster registration information
  v
Secured Cluster
  |
  | Configure Sensor
  v
Sensor
  |
  | Establish secure connection
  v
Central
```

After successful registration, Central identifies the secured cluster as a managed RHACS cluster.

---

# 8. Cluster Identity

Central needs to distinguish data originating from different secured clusters.

Conceptually:

```text
                    Central
                       |
        +--------------+--------------+
        |              |              |
        v              v              v
   Cluster A       Cluster B       Cluster C
        |              |              |
        |              |              |
      Sensor         Sensor         Sensor
```

Data received from Sensor is associated with the appropriate secured cluster.

This allows Central to answer questions such as:

* Which cluster contains this deployment?
* Which cluster generated this violation?
* Which cluster has this vulnerability?
* Which cluster has this network policy?
* Which cluster contains the affected workload?

---

# 9. Kubernetes Resource Ingestion

Sensor watches relevant Kubernetes/OpenShift resources and sends information to Central.

A simplified example:

```text
Deployment created
       |
       v
Kubernetes API
       |
       v
Sensor observes change
       |
       v
Central receives information
       |
       v
Central updates RHACS state
```

For example, if an application deployment is created:

```text
payments-api
 |
 +-- Namespace: payments
 +-- Image: registry.example.com/payments/api:1.5
 +-- ServiceAccount: payments-sa
```

Sensor can communicate relevant information to Central.

Central can then associate the workload with:

* Image information
* Vulnerability information
* Security policies
* Risk
* Violations
* Cluster identity
* Namespace
* Deployment metadata

---

# 10. Runtime Data Ingestion

Runtime information follows a different path from Kubernetes API resource information.

A simplified architecture is:

```text
Container / Node
       |
       v
   Collector
       |
       v
Secured Cluster
       |
       v
     Central
```

The Collector observes runtime-relevant information on the node.

Examples can include:

* Process activity
* Network activity
* Container runtime information
* System-level runtime signals

Central can correlate this information with the Kubernetes objects it already knows about.

---

# 11. Central Correlates Different Data Sources

One of Central's important responsibilities is correlation.

For example:

```text
Kubernetes API
      |
      v
    Sensor
      |
      +----------------+
                       |
                       v
                    Central
                       ^
                       |
                    Collector
                       |
                       v
                 Runtime Data
```

Central can correlate:

```text
Cluster
   +
Namespace
   +
Deployment
   +
Pod
   +
Container
   +
Image
   +
Runtime Activity
   +
Vulnerabilities
   +
Policy Violations
```

This produces the consolidated RHACS security model.

---

# 12. Example: Vulnerable Workload

Suppose a production workload uses:

```text
payments-api
    |
    +-- Image: payments/api:v1.5
```

The workflow can conceptually look like:

```text
             Secured Cluster
                    |
          +---------+---------+
          |                   |
          v                   v
       Sensor             Collector
          |                   |
          |                   |
          +---------+---------+
                    |
                    v
                 Central
                    |
          +---------+---------+
          |                   |
          v                   v
   Image/Vulnerability    Runtime Context
       Information            |
          |                   |
          +---------+---------+
                    |
                    v
               Risk Analysis
                    |
                    v
                 RHACS UI
```

Central can therefore present a more complete security picture rather than treating the vulnerability as an isolated CVE.

# 13. Central Stores and Processes the Data

Central is responsible for maintaining the centralized RHACS security state.

The exact internal storage implementation depends on the RHACS version and configuration, but conceptually:

```text
Secured Cluster
      |
      v
    Sensor
      |
      v
   Central
      |
      v
Centralized RHACS State
```

Central uses this information to support:

* RHACS UI
* RHACS API
* Risk views
* Vulnerability views
* Policy violations
* Compliance information
* Cluster inventory
* Workload inventory
* Security reporting

---

# 14. Multiple Secured Clusters

One Central instance can manage multiple secured clusters.

For example:

```text
                    Central
                       |
       +---------------+---------------+
       |               |               |
       v               v               v
   Production       Staging        Development
       |               |               |
     Sensor          Sensor          Sensor
       |               |               |
     Collector       Collector       Collector
```

Central maintains the association between the received data and its originating cluster.

This is particularly important in enterprise environments where one RHACS deployment protects multiple clusters.

---

# 15. Central-to-Cluster vs Cluster-to-Central

There are two conceptual directions of communication.

### Secured Cluster → Central

Used for sending security-relevant information.

```text
Sensor
  |
  | Cluster data/events
  v
Central
```

### Central → Secured Cluster

Central can also coordinate/configure secured-cluster behavior through RHACS mechanisms.

```text
Central
  |
  | Configuration/control information
  v
Secured Cluster
```

Therefore, RHACS communication should not be thought of as a simple one-way data pipeline.

It is a secure control-plane relationship between Central and secured-cluster components.

---

# 16. Admission Controller Is Different

The Admission Controller has a specialized role.

It participates in admission-time enforcement:

```text
Developer
    |
    v
Kubernetes API
    |
    v
Admission Controller
    |
    +-- Allow
    |
    +-- Reject
```

It is not simply another general-purpose data-ingestion component.

A useful architectural distinction is:

```text
Sensor
  = Cluster observation / communication

Collector
  = Runtime observation

Admission Controller
  = Admission-time enforcement

Central
  = Centralized RHACS control plane
```

---

# 17. Network Architecture

A simplified enterprise architecture is:

```text
                 Management Network
                        |
                 +------+------+
                 |   Central   |
                 +------+------+
                        ^
                        |
                Secure communication
                        |
       +----------------+----------------+
       |                |                |
       v                v                v
   Cluster A        Cluster B        Cluster C
       |                |                |
    Sensor           Sensor           Sensor
    Collector        Collector        Collector
```

Network connectivity must allow the required RHACS communication paths.

Firewall, proxy, NetworkPolicy, load balancer, ingress, or routing configuration can affect this communication.

# 18. Troubleshooting Data Ingestion

If Central does not show expected secured-cluster information, troubleshoot from the cluster outward.

## Step 1 — Check Secured Cluster Pods

```bash
oc -n stackrox get pods
```

Look for:

```text
sensor
collector
admission-control
```

The exact pod names vary by deployment and version.

---

## Step 2 — Check Sensor Logs

```bash
oc -n stackrox logs deploy/sensor
```

Look for messages related to:

```text
connection
TLS
certificate
authentication
Central
RPC
timeout
```

---

## Step 3 — Check Collector

Check Collector pods:

```bash
oc -n stackrox get pods | grep collector
```

Then inspect logs:

```bash
oc -n stackrox logs <collector-pod>
```

Look for runtime collection or communication errors.

---

# 19. Check Central

On the Central cluster:

```bash
oc -n stackrox get pods
```

Check Central logs:

```bash
oc -n stackrox logs deploy/central
```

Search for:

```text
sensor
connection
certificate
TLS
authentication
timeout
cluster
```

---

# 20. Check Services and Endpoints

Inspect services:

```bash
oc -n stackrox get svc
```

Inspect endpoints:

```bash
oc -n stackrox get endpoints
```

For newer Kubernetes/OpenShift environments, also inspect EndpointSlices:

```bash
oc -n stackrox get endpointslices
```

The communication path should conceptually resolve as:

```text
Sensor
  |
  v
Central Service
  |
  v
Central Endpoint
  |
  v
Central Pod
```

---

# 21. Check DNS

If Sensor cannot resolve the Central endpoint, communication can fail.

From the appropriate secured-cluster pod:

```bash
oc -n stackrox exec -it <sensor-pod> -- \
  getent hosts <central-service>
```

The actual service name depends on the deployed RHACS configuration.

---

# 22. Check TLS and Certificates

Common symptoms include:

```text
x509: certificate signed by unknown authority
certificate expired
TLS handshake failure
authentication failed
```

Investigate:

* RHACS-managed certificates
* Certificate expiration
* CA trust
* Service DNS names
* SANs
* Secret configuration
* Central/Sensor registration
* Network path

Avoid permanently disabling certificate validation to work around production connectivity problems.

---

# 23. Check NetworkPolicy

NetworkPolicy can block Sensor-to-Central communication.

Check:

```bash
oc -n stackrox get networkpolicy
```

Conceptually:

```text
Sensor
  |
  X
NetworkPolicy
  |
  X
Central
```

If NetworkPolicy is used, verify that the RHACS communication path is allowed.

---

# 24. Common Failure Scenarios

| Symptom                                      | Likely Area                                         |
| -------------------------------------------- | --------------------------------------------------- |
| Sensor pod not running                       | Secured-cluster deployment                          |
| Collector not running                        | Node/runtime collection                             |
| Sensor cannot connect to Central             | Network/TLS/service                                 |
| TLS handshake failure                        | Certificate/trust                                   |
| Central service cannot be resolved           | DNS                                                 |
| Connection timeout                           | Firewall/NetworkPolicy/routing                      |
| Cluster not registered                       | Registration/configuration                          |
| Runtime data missing                         | Collector/runtime path                              |
| Kubernetes objects missing                   | Sensor/API-watch path                               |
| Central is healthy but cluster data is stale | Sensor communication/processing                     |
| Multiple clusters show incorrect state       | Cluster identity/registration or Central processing |

---

# 26. Important Distinction: Data Collection vs Data Processing

When troubleshooting, separate these questions:

### Question 1

> Is the secured cluster collecting the information?

Check:

```text
Sensor
Collector
Kubernetes API
Node/runtime
```

### Question 2

> Is the information reaching Central?

Check:

```text
Network
DNS
TLS
Authentication
Service
Endpoints
```

### Question 3

> Is Central processing and displaying it correctly?

Check:

```text
Central
RHACS state
API
UI
```

This prevents administrators from incorrectly blaming Sensor when the actual issue is Central processing or networking.

# 29. Interview Answer

> **"Central ingests secured-cluster information primarily through the RHACS Sensor and other secured-cluster components. Sensor observes Kubernetes/OpenShift resources and security-relevant events, while Collector provides node and runtime information. These components establish secure, authenticated communication with Central. Central receives the information, associates it with the originating cluster, processes and correlates it with vulnerability, policy, and runtime data, and maintains the centralized RHACS security state used by the UI and API."**

# 30. Final Summary

Central ingestion can be summarized as:

```text
Kubernetes/OpenShift Resources
             |
             v
          Sensor
             |
             |
Runtime/Node Data
             |
             v
         Collector
             |
             +----------------+
                              |
                              v
                           Central
                              |
                    +---------+---------+
                    |         |         |
                    v         v         v
                  Store     Correlate  Analyze
                    |         |         |
                    +---------+---------+
                              |
                              v
                       RHACS UI / API
```

### Remember

* **Sensor** is the primary cluster-observation and Central-communication component.
* **Collector** provides runtime/node-level security information.
* **Central** is the centralized RHACS control plane.
* Central associates incoming information with the correct secured cluster.
* Secure communication, authentication, TLS, DNS, services, endpoints, and network policies are important dependencies.
* Multiple secured clusters can send information to the same Central instance.
* Troubleshooting should distinguish **collection**, **transport**, and **Central-side processing** problems.
