# How Do You Troubleshoot a CSV in Failed State?

A `ClusterServiceVersion` (CSV) in `Failed` state means OpenShift's Operator Lifecycle Manager (OLM) could not successfully install, upgrade, or manage the Operator.

For RHACS, a failed CSV can prevent the RHACS Operator from becoming available and therefore prevent resources such as `Central` from being reconciled correctly.

The basic troubleshooting flow is:

```text
CSV = Failed
     |
     v
oc describe csv
     |
     +--> Conditions
     +--> Install status
     +--> Events
     |
     v
Check Subscription
     |
     v
Check InstallPlan
     |
     v
Check Operator Deployment/Pod
     |
     v
Check RBAC / SCC / Permissions
     |
     v
Check Images / Registry / CA
     |
     v
Check Dependencies
     |
     v
Fix root cause
     |
     v
Allow OLM to reconcile
     |
     v
CSV = Succeeded
```

---

## 1. What Is a CSV?

A `ClusterServiceVersion` represents an installed Operator version managed by OLM.

For example:

```text
id="n6w3zs"
rhacs-operator.vX.Y.Z
```

The CSV contains information about:

* Operator version
* Deployment
* Permissions
* Owned Custom Resource Definitions
* Required APIs
* Install strategy
* Related resources
* Install conditions

Check CSVs:

```bash
oc get csv -A
```

For RHACS:

```bash
oc get csv -n rhacs-operator
```

A healthy CSV normally shows:

```text
PHASE
Succeeded
```

A failed CSV may show:

```text
Failed
```

---

# 2. Confirm the CSV Is Actually Failed

Run:

```bash
oc get csv -n rhacs-operator
```

Example:

```text
NAME                       DISPLAY          VERSION   REPLACES   PHASE
rhacs-operator.vX.Y.Z      RHACS Operator   X.Y.Z                Failed
```

Do not immediately delete the CSV.

First collect diagnostic information.

---

# 3. Describe the CSV

This is usually the first and most important command:

```bash
oc describe csv rhacs-operator.vX.Y.Z \
  -n rhacs-operator
```

Focus on:

```text
Conditions
Install Strategy
Requirements
Related Objects
Events
```

The most useful section is often:

```text
Conditions:
```

For example, you may see:

```text
Reason: InstallComponentFailed
Message: deployment failed
```

or:

```text
Reason: ComponentFailed
Message: failed to create deployment
```

The message usually points toward the actual failure.

---

# 4. Check CSV Conditions

Extract the CSV status:

```bash
oc get csv rhacs-operator.vX.Y.Z \
  -n rhacs-operator \
  -o yaml
```

Look for:

```yaml
status:
  phase: Failed
  message: ...
  reason: ...
```

You may find:

```text
phase: Failed
reason: InstallComponentFailed
```

The `reason` and `message` are important clues.

---

# 5. Check Namespace Events

Events frequently contain more useful information than the CSV itself.

Run:

```bash
oc get events \
  -n rhacs-operator \
  --sort-by=.lastTimestamp
```

Look for:

```text
Failed
Warning
BackOff
FailedCreate
FailedMount
FailedScheduling
FailedPull
ErrImagePull
```

For a more focused view:

```bash
oc get events \
  -n rhacs-operator \
  --field-selector type=Warning \
  --sort-by=.lastTimestamp
```

---

# 6. Check the Subscription

A CSV can fail because the Subscription selected an unexpected Operator version or channel.

Run:

```bash
oc get subscription \
  -n rhacs-operator
```

Then:

```bash
oc describe subscription rhacs-operator \
  -n rhacs-operator
```

Check:

```text
Package
Channel
Source
Source Namespace
InstallPlan
Installed CSV
Current CSV
```

For example:

```text
Package: rhacs-operator
Channel: stable
Source: redhat-operators
```

Verify that these values are what you intended.

---

# 7. Check the InstallPlan

Run:

```bash
oc get installplan \
  -n rhacs-operator
```

Then:

```bash
oc describe installplan <installplan-name> \
  -n rhacs-operator
```

Look for:

```text
Approval
Approved
Phase
Status
Failed
```

If the InstallPlan is waiting for manual approval, the Operator installation may not proceed.

Check:

```bash
oc get installplan \
  -n rhacs-operator \
  -o wide
```

---

# 8. Check Whether the InstallPlan Is Approved

For manual approval installations:

```bash
oc get installplan <installplan-name> \
  -n rhacs-operator \
  -o jsonpath='{.spec.approved}'
```

Expected:

```text
true
```

If:

```text
false
```

the InstallPlan has not been approved.

Only approve an InstallPlan after verifying that the selected Operator version is the intended version.

Example:

```bash
oc patch installplan <installplan-name> \
  -n rhacs-operator \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

---

# 9. Check the Operator Deployment

The CSV normally creates or manages an Operator Deployment.

Run:

```bash
oc get deployment \
  -n rhacs-operator
```

Example:

```text
NAME             READY   UP-TO-DATE   AVAILABLE
rhacs-operator   0/1     1            0
```

If the Deployment is not available:

```bash
oc describe deployment rhacs-operator \
  -n rhacs-operator
```

Check:

```text
Replicas
Conditions
Events
Pod Template
Service Account
Image
```

---

# 10. Check the Operator Pod

Run:

```bash
oc get pods \
  -n rhacs-operator \
  -o wide
```

Common failure states include:

```text
ImagePullBackOff
ErrImagePull
CrashLoopBackOff
Pending
CreateContainerConfigError
CreateContainerError
ContainerCreating
```

Each state points toward a different problem.

---

# 11. If the Operator Pod Is Pending

Run:

```bash
oc describe pod <operator-pod> \
  -n rhacs-operator
```

Check Events.

Common causes:

```text
Insufficient CPU
Insufficient memory
Node selector mismatch
Affinity mismatch
Untolerated taint
PVC problem
Admission policy
```

For example:

```text
0/3 nodes are available:
Insufficient cpu
```

The solution is a cluster capacity or scheduling issue, not an OLM problem.

---

# 12. If the Operator Pod Has ImagePullBackOff

Check:

```bash
oc describe pod <operator-pod> \
  -n rhacs-operator
```

Look for:

```text
Failed to pull image
```

Common causes:

```text
Wrong image
Registry unavailable
Authentication failure
Missing mirror
Private registry CA
DNS failure
Network/firewall failure
```

Check the image:

```bash
oc get pod <operator-pod> \
  -n rhacs-operator \
  -o jsonpath='{.spec.containers[*].image}'
```

For disconnected environments, verify that the image exists in the internal registry.

---

# 13. Check Registry Authentication

If the event says:

```text
unauthorized
```

or:

```text
authentication required
```

check image pull secrets:

```bash
oc get secrets \
  -n rhacs-operator
```

Check the ServiceAccount:

```bash
oc get serviceaccount \
  -n rhacs-operator
```

Then inspect:

```bash
oc describe serviceaccount <serviceaccount> \
  -n rhacs-operator
```

Verify that the required registry credentials are available.

---

# 14. Check Registry CA

In a corporate environment, the internal registry may use a private CA.

Typical error:

```text
x509: certificate signed by unknown authority
```

Test the registry certificate:

```bash
openssl s_client \
  -connect registry.example.com:443 \
  -showcerts
```

Verify:

```text
Certificate chain
Issuer
Subject
SAN
Expiration
```

Make sure the OpenShift cluster trusts the registry CA.

Do not disable certificate verification as a workaround.

---

# 15. Check DNS

If the Operator cannot resolve the registry:

```text
no such host
```

or:

```text
lookup registry.example.com: no such host
```

test DNS from the cluster.

For example:

```bash
oc run dns-test \
  --rm -it \
  --restart=Never \
  --image=registry.access.redhat.com/ubi9/ubi-minimal \
  -- getent hosts registry.example.com
```

Also check:

```bash
oc get dns.operator/default -o yaml
```

and:

```bash
oc get pods -n openshift-dns
```

---

# 16. Check Network Connectivity

If DNS works but image pulling times out, investigate network connectivity.

Typical symptoms:

```text
connection timeout
connection refused
i/o timeout
```

Check the registry endpoint:

```bash
curl -vk https://registry.example.com/v2/
```

The test should be performed from an environment that accurately represents the OpenShift node's network path.

Check:

```text
Firewall
Routing
Proxy
NetworkPolicy
Registry load balancer
```

---

# 17. Check Operator Logs

If the Operator Pod starts but crashes or repeatedly fails reconciliation:

```bash
oc logs deployment/rhacs-operator \
  -n rhacs-operator
```

For the previous container instance:

```bash
oc logs <operator-pod> \
  -n rhacs-operator \
  --previous
```

Look for:

```text
ERROR
FATAL
panic
forbidden
unauthorized
timeout
connection refused
x509
reconcile failed
```

---

# 18. Check RBAC Problems

An Operator requires permissions to manage resources.

A common error is:

```text
forbidden
```

For example:

```text
User "system:serviceaccount:..." \
cannot create resource ...
```

Find the ServiceAccount:

```bash
oc get deployment rhacs-operator \
  -n rhacs-operator \
  -o jsonpath='{.spec.template.spec.serviceAccountName}'
```

Check the associated roles:

```bash
oc get role,rolebinding \
  -n rhacs-operator
```

Also check cluster-scoped permissions:

```bash
oc get clusterrole | grep -i rhacs
```

and:

```bash
oc get clusterrolebinding | grep -i rhacs
```

Do not manually grant broad `cluster-admin` privileges just to make the Operator work.

Determine which permission is actually missing.

---

# 19. Check SCC and Security Restrictions

On OpenShift, security restrictions can prevent an Operator or its managed workloads from starting correctly.

Check Pod events:

```bash
oc describe pod <operator-pod> \
  -n rhacs-operator
```

Look for messages involving:

```text
SecurityContextConstraints
SCC
permission denied
UID
SELinux
privileged
```

Also inspect the ServiceAccount and relevant SCC configuration.

Avoid assigning highly privileged SCCs unless they are explicitly required by the supported Operator configuration.

---

# 20. Check Required CRDs

Operators commonly depend on CustomResourceDefinitions.

Check RHACS-related CRDs:

```bash
oc get crd | grep -i stackrox
```

For example:

```text
centrals.platform.stackrox.io
securedclusters.platform.stackrox.io
```

The exact CRDs depend on the RHACS version.

If required CRDs are missing, inspect the CSV and InstallPlan rather than manually creating arbitrary CRDs.

---

# 21. Check API Dependencies

A CSV may require specific Kubernetes/OpenShift APIs.

Inspect:

```bash
oc describe csv rhacs-operator.vX.Y.Z \
  -n rhacs-operator
```

Look at:

```text
Requirements
```

Possible problems include:

```text
Required API not available
Required CRD missing
Required Operator missing
Unsupported API version
```

This can happen when the Operator version is incompatible with the OpenShift release.

---

# 22. Check Operator Version Compatibility

Always verify:

```text
OpenShift version
RHACS Operator version
RHACS version
```

For example:

```text
OpenShift 4.x
       |
       +-- supported RHACS release
              |
              +-- supported Operator channel
```

Do not select an Operator version simply because it is the newest available.

The selected RHACS version must be supported on the target OpenShift release.

---

# 23. Check Dependency Operators

Some Operator installations may depend on other platform services or APIs.

Check all CSVs:

```bash
oc get csv -A
```

Look for related Operators in:

```text
Pending
Failed
Installing
```

For example:

```bash
oc get csv -A | grep -E 'Failed|Pending'
```

A dependency failure can cause the RHACS CSV to fail.

---

# 24. Check CatalogSource Health

If the Subscription is using a custom or disconnected catalog, validate the CatalogSource.

Run:

```bash
oc get catalogsource \
  -n openshift-marketplace
```

Then:

```bash
oc describe catalogsource <catalog-name> \
  -n openshift-marketplace
```

Check the catalog Pod:

```bash
oc get pods \
  -n openshift-marketplace
```

If the catalog Pod is:

```text
ImagePullBackOff
CrashLoopBackOff
```

OLM may not be able to obtain the Operator bundle.

---

# 25. Disconnected Environment Checks

For disconnected RHACS installations, validate:

```text
Catalog image
Operator image
RHACS images
Internal registry
Registry authentication
Registry CA
Image mirror configuration
CatalogSource
```

Check mirror resources:

```bash
oc get imagedigestmirrorset
```

Depending on the OpenShift version, other supported mirror resources may also be present.

---

# 26. Check Generated Install Resources

The CSV contains related objects created during installation.

Run:

```bash
oc describe csv rhacs-operator.vX.Y.Z \
  -n rhacs-operator
```

Look at:

```text
Owned APIs
Install Strategy
Related Objects
```

If a related Deployment, ServiceAccount, Role, or other object failed to create, investigate that object directly.

---

# 27. Use `oc get all`

Get a quick overview:

```bash
oc get all \
  -n rhacs-operator
```

This can show:

```text
Pods
Services
Deployments
ReplicaSets
```

Then drill down into the failed resource.

---

# 28. Check ReplicaSets

If the Operator Deployment exists but its Pod does not become ready:

```bash
oc get rs \
  -n rhacs-operator
```

Then:

```bash
oc describe rs <replicaset-name> \
  -n rhacs-operator
```

This can expose Pod creation errors that are not obvious from the Deployment.

---

# 29. Check Recent Events First

For an L3 troubleshooting workflow, sort events by time:

```bash
oc get events \
  -n rhacs-operator \
  --sort-by=.lastTimestamp
```

The newest event often identifies the actual root cause.

For example:

```text
FailedCreate
      |
      v
ServiceAccount permission problem
```

or:

```text
FailedPull
      |
      v
Internal registry problem
```

or:

```text
FailedScheduling
      |
      v
Node capacity problem
```

---

# 30. Do Not Immediately Delete the CSV

A common mistake is:

```bash
oc delete csv ...
```

without collecting evidence.

Deleting the CSV can remove useful diagnostic information and may cause OLM to recreate or change resources.

Preferred workflow:

```text
Observe
  |
  v
Describe
  |
  v
Collect events
  |
  v
Check logs
  |
  v
Identify root cause
  |
  v
Fix root cause
  |
  v
Allow OLM reconciliation
```

Only delete/reinstall an Operator when there is a clear reason and the supported recovery procedure calls for it.

---

# 31. Example: CSV Failed Because of Image Pull

Suppose:

```bash
oc get csv -n rhacs-operator
```

returns:

```text
rhacs-operator.vX.Y.Z   Failed
```

Run:

```bash
oc describe csv rhacs-operator.vX.Y.Z \
  -n rhacs-operator
```

You discover the Operator Deployment failed.

Then:

```bash
oc get pods -n rhacs-operator
```

returns:

```text
rhacs-operator-xxxxx   0/1   ImagePullBackOff
```

Run:

```bash
oc describe pod rhacs-operator-xxxxx \
  -n rhacs-operator
```

Suppose the event says:

```text
x509: certificate signed by unknown authority
```

The troubleshooting chain becomes:

```text
CSV Failed
    |
    v
Operator Deployment failed
    |
    v
Operator Pod ImagePullBackOff
    |
    v
Registry TLS error
    |
    v
Registry CA not trusted
```

The solution is to correct registry CA trust and allow the Operator to reconcile.

---

# 32. Example: CSV Failed Because of RBAC

Suppose Operator logs show:

```text
forbidden: cannot create resource
```

The chain becomes:

```text
CSV Failed
    |
    v
Operator Pod running
    |
    v
Operator reconciliation fails
    |
    v
RBAC permission denied
    |
    v
Missing Role/ClusterRole permission
```

Investigate the exact denied resource and verb.

Do not solve it by blindly granting:

```text
cluster-admin
```

Instead, restore the permissions expected by the supported Operator installation.

---

# 33. Example: CSV Failed Because of Scheduling

If the Operator Pod is:

```text
Pending
```

run:

```bash
oc describe pod <operator-pod> \
  -n rhacs-operator
```

You might find:

```text
0/3 nodes are available:
Insufficient memory
```

The solution is to address cluster capacity rather than modifying the CSV.

Other possibilities:

```text
Node selector
Taints
Tolerations
Affinity
Resource quotas
Limit ranges
```

---

# 34. Recovery Workflow

After identifying and correcting the root cause:

```text
1. Verify the corrected configuration
        |
2. Check Operator Pod
        |
3. Check Operator logs
        |
4. Check CSV
        |
5. Check Subscription
        |
6. Wait for OLM reconciliation
        |
7. Confirm CSV = Succeeded
        |
8. Confirm Operator Pod = Ready
        |
9. Continue with Central validation
```

Check:

```bash
oc get csv -n rhacs-operator
```

Expected:

```text
PHASE
Succeeded
```

Then:

```bash
oc get pods -n rhacs-operator
```

Expected:

```text
1/1 Running
```

---

# 35. Validate After Recovery

Do not stop when the CSV becomes `Succeeded`.

Also verify:

```bash
oc get deployment -n rhacs-operator
oc get pods -n rhacs-operator
oc get central -n stackrox
oc get pods -n stackrox
```

The Operator may be healthy while Central still has a separate problem.

---

# 36. L3 Troubleshooting Decision Tree

```text
CSV = Failed
     |
     v
oc describe csv
     |
     +-------------------------+
     |                         |
     v                         v
Install error             Requirement error
     |                         |
     v                         v
Check Deployment          Check CRD/API
     |                     dependencies
     v
Check Operator Pod
     |
     +-------------------+
     |        |          |
     v        v          v
Pending   ImagePull   CrashLoop
  |          |           |
  v          v           v

  |        Auth/CA       |
  |        DNS           v
  |        Network    Config/RBAC
  |
  v

     |
     v

     |
     v

```

# 38. What Not to Do

Avoid these actions without understanding the root cause:

```text
Do not immediately delete the CSV.
Do not repeatedly restart Operator Pods.
Do not grant cluster-admin blindly.
Do not disable TLS verification.
Do not manually edit Operator-managed resources unnecessarily.
Do not install an arbitrary RHACS version.
Do not ignore a failed dependency.
Do not assume Running means Ready.
```

Instead:

```text
Observe → Diagnose → Fix → Reconcile → Validate
```

---

# 39. Interview Answer

**Question:** How do you troubleshoot a CSV in `Failed` state?

**Answer:**

> I start with `oc describe csv` and inspect the CSV conditions, reason, message, install strategy, and events. Then I check the Subscription and InstallPlan to confirm that the correct Operator package, channel, version, and approval state are being used. I inspect the Operator Deployment and Pod, including scheduling, image pulls, registry authentication, CA trust, RBAC, SCC, and Operator logs. I also verify required CRDs, APIs, dependencies, and CatalogSource health. In a disconnected environment I additionally validate the mirrored catalog, image availability, registry connectivity, authentication, and certificates. After fixing the root cause, I allow OLM to reconcile and verify that the CSV reaches `Succeeded` and the Operator Pod becomes Ready.

# 40. Final Checklist

```text
[ ] CSV confirmed Failed
[ ] CSV conditions inspected
[ ] CSV message/reason identified
[ ] CSV events reviewed
[ ] Subscription verified
[ ] InstallPlan verified
[ ] InstallPlan approval verified
[ ] CatalogSource verified
[ ] Required CRDs verified
[ ] API dependencies verified
[ ] Operator Deployment checked
[ ] Operator Pod checked
[ ] Scheduling checked
[ ] Image pull checked
[ ] Registry authentication checked
[ ] Registry CA checked
[ ] DNS checked
[ ] Network connectivity checked
[ ] Operator logs checked
[ ] RBAC checked
[ ] SCC/security restrictions checked
[ ] Dependency Operators checked
[ ] Root cause fixed
[ ] OLM reconciliation verified
[ ] CSV = Succeeded
[ ] Operator Pod = Ready
[ ] Central validation completed
```

The key principle is:

> **A failed CSV is a symptom, not necessarily the root cause. Start with the CSV conditions and events, then trace the failure through OLM → Deployment → Pod → registry/RBAC/scheduling/dependencies until the first real failure is identified. Fix that underlying problem and let OLM reconcile the Operator rather than repeatedly deleting or restarting resources.**
