# How Does RHACS Support Non-OpenShift Kubernetes Clusters?

## 1. Overview

Red Hat Advanced Cluster Security for Kubernetes (RHACS) is not limited to Red Hat OpenShift Container Platform. RHACS is designed to provide Kubernetes-native security across heterogeneous environments, including Kubernetes clusters that are not running OpenShift.

This allows an organization to use a **central RHACS Central instance** to manage security for multiple Kubernetes clusters, regardless of whether those clusters are:

* OpenShift clusters
* Upstream Kubernetes clusters
* Managed Kubernetes clusters
* Cloud-provider Kubernetes clusters
* On-premises Kubernetes clusters
* Disconnected or restricted-network Kubernetes clusters

The key architectural principle is:

```text
                         RHACS Central
                              |
             +----------------+----------------+
             |                |                |
       OpenShift          Kubernetes        Managed K8s
        Cluster            Cluster           Cluster
             |                |                |
       Sensor/Collector   Sensor/Collector   Sensor/Collector
             |                |                |
          Node data       Runtime data      Runtime data
```

RHACS Central provides centralized security management, while security components deployed in each Kubernetes cluster collect local information and enforce security controls.

---

# 2. OpenShift Is Not Required

RHACS uses Kubernetes APIs and Kubernetes-compatible security mechanisms rather than depending exclusively on OpenShift-specific APIs.

Therefore, a non-OpenShift Kubernetes cluster can participate in RHACS without installing OpenShift.

For example:

```text
Cluster 1
OpenShift
      |
      +---- RHACS Sensor
      +---- RHACS Collector


Cluster 2
RKE2 Kubernetes
      |
      +---- RHACS Sensor
      +---- RHACS Collector


Cluster 3
Upstream Kubernetes
      |
      +---- RHACS Sensor
      +---- RHACS Collector


Cluster 4
EKS / Managed Kubernetes
      |
      +---- RHACS Sensor
      +---- RHACS Collector

             |
             v

        RHACS Central
```

The Central instance provides the common security management plane.

---

# 3. RHACS Architecture for Non-OpenShift Kubernetes

A typical deployment consists of:

```text
                    RHACS Central
                         |
             Security Management Plane
                         |
        +----------------+----------------+
        |                |                |
        v                v                v
   Kubernetes 1      Kubernetes 2      Kubernetes 3
        |                |                |
     Sensor           Sensor           Sensor
        |                |                |
   Collector        Collector        Collector
        |                |                |
     Node data       Node data       Node data
```

The major components are:

| Component            | Purpose                                     |
| -------------------- | ------------------------------------------- |
| Central              | Central security management and analysis    |
| Sensor               | Cluster-level Kubernetes security component |
| Collector            | Collects runtime and node-level information |
| Admission Controller | Helps enforce deployment policies           |
| Scanner              | Scans container images for vulnerabilities  |
| Scanner DB           | Stores vulnerability information            |
| RHACS UI/API         | Administration and integration              |

Not every component necessarily needs to run independently in every cluster. The exact deployment architecture depends on the RHACS version and installation method.

---

# 4. Sensor in a Non-OpenShift Cluster

The RHACS Sensor communicates with the Kubernetes API server and monitors cluster resources.

It can observe resources such as:

* Pods
* Deployments
* Services
* Namespaces
* Roles
* RoleBindings
* ServiceAccounts
* NetworkPolicies
* ConfigMaps
* Secrets metadata
* Workloads
* Images

For example:

```text
Kubernetes API Server
        |
        | Kubernetes API
        v
     RHACS Sensor
        |
        | Security information
        v
     RHACS Central
```

Sensor therefore does not require the OpenShift API.

It can work with the standard Kubernetes API.

---

# 5. Collector in Non-OpenShift Kubernetes

RHACS Collector provides node-level and runtime-related visibility.

A simplified architecture is:

```text
Kubernetes Worker Node
+--------------------------------+
|                                |
| Container Runtime              |
|                                |
| Pods                           |
|                                |
| RHACS Collector                |
|                                |
+--------------------------------+
```

Depending on the Kubernetes and runtime environment, Collector obtains information needed for RHACS runtime security and network/process visibility.

This is particularly important because Kubernetes API information alone is not sufficient for complete runtime security.

# 6. Kubernetes Distribution Independence

A major benefit of RHACS is that security management can span different Kubernetes distributions.

For example:

```text
                 RHACS Central
                      |
       +--------------+--------------+
       |              |              |
       v              v              v
   OpenShift       RKE2/K3s      Upstream K8s
       |              |              |
       v              v              v
    Sensor         Sensor         Sensor
    Collector      Collector      Collector
```

An organization could therefore have:

```text
Production
    OpenShift

Development
    Upstream Kubernetes

Cloud
    EKS

Edge
    RKE2

Testing
    K3s
```

and still use RHACS as a centralized Kubernetes security platform, subject to the supported-platform matrix for the particular RHACS release.

# 7. Centralized Security Across Clusters

One of the most important capabilities is centralized security management.

Instead of deploying a separate security management platform for every cluster:

```text
Cluster A -> Security Platform A
Cluster B -> Security Platform B
Cluster C -> Security Platform C
```

an organization can use:

```text
                  RHACS Central
                       |
       +---------------+---------------+
       |               |               |
       v               v               v
    Cluster A       Cluster B       Cluster C
    OpenShift       Kubernetes        EKS
```

This provides a common place for security teams to:

* View vulnerabilities
* Review policy violations
* Investigate alerts
* Monitor deployments
* Analyze runtime activity
* Manage security policies
* Review compliance-related information
* Investigate risk across clusters

# 8. Multi-Cluster Security

RHACS can distinguish security information by cluster.

For example:

```text
RHACS Central
|
+-- Production-OpenShift
|
+-- Production-Kubernetes
|
+-- Development-Kubernetes
|
+-- AWS-EKS
|
+-- Edge-RKE2
```

This allows security teams to answer questions such as:

> Which cluster contains the vulnerable workload?

> Which namespace is running the vulnerable image?

> Which deployment violated the security policy?

> Which cluster generated the runtime alert?

---

# 9. Cluster Identification

Each secured cluster is represented separately in RHACS.

A security administrator can therefore associate findings with a particular cluster.

For example:

```text
Cluster: production-eks
Namespace: payments
Deployment: payment-api
Image: payment-api:v4
Finding: Critical vulnerability
```

This is much more useful than receiving an alert that simply says:

```text
Critical vulnerability detected
```

without knowing where it occurred.

---

# 10. Admission Control on Non-OpenShift Kubernetes

RHACS can also provide admission-control capabilities for Kubernetes workloads.

The basic flow is:

```text
Developer
   |
   v
kubectl apply
   |
   v
Kubernetes API Server
   |
   v
Admission Control
   |
   +---- Policy violation ---> Reject
   |
   +---- Policy compliant --> Allow
```

For example, an organization could define a policy requiring:

```text
Image must not contain Critical vulnerabilities
```

A deployment containing a prohibited image could then be blocked according to the configured RHACS policy and enforcement mode.

This works with Kubernetes admission mechanisms rather than requiring OpenShift-specific admission APIs.

# 12. Network Visibility

RHACS can provide Kubernetes network-related security visibility.

For example:

```text

payment-api
     |
     | TCP/443
     v
payment-db
```

Security teams can use this information to understand workload communication and identify unexpected network behavior.

This is useful in environments where Kubernetes networking is implemented using different CNI technologies, subject to RHACS support for the specific environment.

# 13. RBAC and Kubernetes Security

Non-OpenShift Kubernetes clusters use standard Kubernetes RBAC.

RHACS can analyze Kubernetes security configurations such as:

```text
User
 |
 +-- Role
 |
 +-- RoleBinding
 |
 +-- ServiceAccount
 |
 +-- ClusterRole
 |
 +-- ClusterRoleBinding
```

This allows security teams to identify potentially risky permissions.

For example:

```text
ServiceAccount
      |
      v
ClusterRole
      |
      +-- get
      +-- list
      +-- create
      +-- delete
      |
      v
Cluster-wide privileges
```

Such excessive privileges can become security findings or contribute to a higher risk assessment.

# 14. Secrets and Configuration Security

These checks are useful on both OpenShift and standard Kubernetes clusters.

# 21. What Changes Compared With OpenShift?

The main difference is the underlying platform.

| Area                         | OpenShift | Non-OpenShift Kubernetes   |
| ---------------------------- | --------- | -------------------------- |
| Kubernetes API               | Yes       | Yes                        |
| RHACS Sensor                 | Supported | Supported                  |
| RHACS Collector              | Supported | Supported                  |
| Runtime security             | Supported | Supported                  |
| Image security               | Supported | Supported                  |
| Admission control            | Supported | Supported                  |
| Kubernetes RBAC              | Supported | Supported                  |
| Network visibility           | Supported | Depends on environment/CNI |
| OpenShift SCC                | Available | Not available              |
| OpenShift-specific resources | Available | Not available              |
| OpenShift OAuth integration  | Available | Not applicable             |
| Kubernetes RBAC analysis     | Yes       | Yes                        |

The important point is that **OpenShift-specific features should not be confused with RHACS core Kubernetes security capabilities**.

---

# 22. SCC vs Kubernetes Security Context

OpenShift provides Security Context Constraints (SCC).

Standard Kubernetes does not use SCC.

Therefore:

```text
OpenShift
   |
   +-- SCC
   +-- RBAC
   +-- Pod Security
   +-- RHACS
```

while a standard Kubernetes environment may use:

```text
Kubernetes
   |
   +-- RBAC
   +-- Pod Security Admission
   +-- SecurityContext
   +-- NetworkPolicy
   +-- RHACS
```

RHACS can provide security visibility across both environments, but it cannot make a non-OpenShift Kubernetes cluster behave exactly like OpenShift.

---

# 23. Kubernetes Pod Security

For a standard Kubernetes cluster, security may be implemented using Pod Security Admission.

For example:

```text
Namespace
   |
   +-- Pod Security: restricted
   |
   +-- Deployment
           |
           +-- SecurityContext
           +-- runAsNonRoot
           +-- allowPrivilegeEscalation=false
```

RHACS can complement these native Kubernetes controls by providing additional security policies, visibility, risk assessment, and runtime detection.

---

# 24. RHACS Does Not Replace Kubernetes Security Controls

RHACS should not be considered a replacement for the Kubernetes platform's native security mechanisms.

A mature architecture normally looks like:

```text

                         |
       +-----------------+-----------------+
       |                 |                 |
       v                 v                 v
     RBAC          Pod Security       NetworkPolicy
       |                 |                 |
       +-----------------+-----------------+
                         |
                         v
                       RHACS
                         |
       +-----------------+-----------------+
       |                 |                 |
       v                 v                 v
 Vulnerability       Runtime          Risk Analysis
   Management        Security
```

RHACS adds security capabilities across these controls.

# 25. Central vs Secured Cluster

A useful way to understand RHACS is to divide responsibilities.

### RHACS Central

Typically provides:

* Central management
* Security policies
* Vulnerability information
* Security findings
* API/UI
* Centralized investigation
* Multi-cluster visibility

### Secured Cluster

Typically runs components such as:

* Sensor
* Collector
* Admission Controller

These components obtain local cluster and runtime information.

Conceptually:

```text
                    RHACS Central
                         |
             Security Management Plane
                         |
       +-----------------+-----------------+
       |                 |                 |
       v                 v                 v
   Cluster A         Cluster B         Cluster C
       |                 |                 |
    Sensor            Sensor            Sensor
    Collector         Collector         Collector
```

# 26. Failure Isolation

With multiple Kubernetes clusters, each secured cluster has its own local security components.

For example:

```text
RHACS Central
      |
      +------ Cluster A
      |          |
      |       Sensor
      |       Collector
      |
      +------ Cluster B
      |          |
      |       Sensor
      |       Collector
      |
      +------ Cluster C
                 |
              Sensor
              Collector
```

If one Kubernetes cluster becomes unavailable, the other clusters can continue operating.

However, the effect of Central availability and the behavior of cluster-local components depend on the specific RHACS architecture and version.

# 28. Benefits of Supporting Non-OpenShift Kubernetes

The major benefits are:

### 1. Hybrid Kubernetes Security

Organizations can secure both OpenShift and non-OpenShift Kubernetes.

### 2. Multi-Cloud Security

The same security architecture can span multiple cloud providers and on-premises environments.

### 3. Centralized Visibility

Security teams can see security information across multiple clusters.

### 4. Consistent Policies

Organizations can establish common security policies across heterogeneous Kubernetes environments.

### 5. Runtime Protection

Security is not limited to container image scanning.

### 6. DevSecOps Integration

RHACS can be incorporated into CI/CD workflows.

### 7. Reduced Tool Sprawl

Security teams do not necessarily need a separate Kubernetes security platform for every Kubernetes distribution.

---

# 29. Important Limitations

Supporting non-OpenShift Kubernetes does not mean every OpenShift feature is available everywhere.

Consider:

```text
RHACS
 |
 +-- Kubernetes capabilities
 |       |
 |       +-- Available across supported Kubernetes environments
 |
 +-- OpenShift-specific capabilities
         |
         +-- Require OpenShift
```

Examples of platform-specific differences include:

* SCC
* OpenShift-specific APIs
* OpenShift-specific operators
* OpenShift authentication mechanisms
* OpenShift-specific platform resources

Therefore, always verify the **RHACS support matrix for the exact RHACS release, Kubernetes distribution, version, container runtime, CNI, and installation method** before deploying in production.

# 31. Interview Answer

A concise interview answer would be:

> **RHACS supports non-OpenShift Kubernetes by using Kubernetes-native APIs and security mechanisms rather than depending exclusively on OpenShift-specific functionality. RHACS Central provides centralized security management, while Sensor, Collector, and other secured-cluster components run inside supported Kubernetes clusters. This allows an organization to monitor vulnerabilities, workload configurations, runtime activity, network behavior, admission policies, and security risks across OpenShift and non-OpenShift Kubernetes environments from a centralized security platform. OpenShift-specific capabilities such as SCC remain specific to OpenShift, but the core Kubernetes security capabilities can be used across supported Kubernetes distributions.**
