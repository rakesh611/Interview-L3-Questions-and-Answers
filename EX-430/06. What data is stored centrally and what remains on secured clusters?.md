# What Data Is Stored Centrally and What Remains on Secured Clusters?

## Overview

In a Red Hat hybrid or disconnected security architecture, it is important to understand **which information is centralized** and **which information remains inside secured OpenShift clusters**.

For a typical **RHACS (Red Hat Advanced Cluster Security)** deployment, the central RHACS services provide security management and visibility across multiple clusters, while cluster-local components continue to enforce security policies and collect runtime information.

The basic model is:

```text
                         CENTRAL RHACS
                    ┌─────────────────────┐
                    │ Central Services    │
                    │                     │
                    │ - Security policies │
                    │ - Vulnerability data │
                    │ - Configuration      │
                    │ - Central metadata   │
                    │ - Alert information  │
                    └──────────┬──────────┘
                               │
                         TLS / Secured
                               │
              ┌────────────────┼────────────────┐
              │                │                │
              ▼                ▼                ▼
        OpenShift       OpenShift        OpenShift
        Cluster-1       Cluster-2        Cluster-3
       SECURED ZONE     SECURED ZONE     SECURED ZONE

       ┌──────────┐     ┌──────────┐     ┌──────────┐
       │ Sensor   │     │ Sensor   │     │ Sensor   │
       │ Collector│     │ Collector│     │ Collector│
       │ Admission│     │ Admission│     │ Admission│
       └──────────┘     └──────────┘     └──────────┘
```

---

# 1. What Is Stored Centrally?

The RHACS Central component maintains information required for **centralized security management, analysis, reporting, and administration**.

## 1.1 Security Policies

Security policies are centrally managed.

Examples:

```text
- Privileged container
- Container running as root
- Host namespace access
- Dangerous capabilities
- Image vulnerability severity
- Kubernetes RBAC violations
- Network policy violations
- Runtime behavior violations
```

Administrators can create policies centrally and apply them to selected clusters, namespaces, deployments, or workloads.

Example:

```text
Policy:
    Name: Privileged Container

Severity:
    HIGH

Scope:
    Production clusters

Action:
    Alert
```

---

# 2. Vulnerability Information

Central RHACS stores vulnerability-related information needed for security analysis.

Examples include:

```text
Image
  │
  ├── Repository
  ├── Tag
  ├── Digest
  ├── Components
  ├── CVEs
  ├── Severity
  └── Fix availability
```

Example:

```text
Image:
registry.example.com/payment:v2.5

Vulnerabilities:

CVE-XXXX-XXXX
Severity: CRITICAL

CVE-YYYY-YYYY
Severity: HIGH
```

This allows security teams to obtain a centralized view of vulnerable workloads across clusters.

Examples:


Examples:


The centralized view allows the security team to investigate events across multiple clusters.

# 8. What Remains on the Secured Cluster?

Not everything is moved to RHACS Central.

Cluster-local components continue to operate inside the secured OpenShift environment.

The important components include:

```text
Central
  │
  └── Central Server

Secured Cluster
  │
  ├── Sensor
  ├── Admission Controller
  └── Collector
```

---

# 9. Sensor

The **Sensor** runs inside the secured OpenShift cluster.

Its primary purpose is to monitor Kubernetes/OpenShift resources and communicate security information to Central.

Conceptually:

```text
OpenShift API
      │
      ▼
   Sensor
      │
      │ TLS
      ▼
   Central
```

Sensor interacts with the cluster locally rather than requiring administrators to expose the Kubernetes API directly to the Internet.

---

# 10. Collector

The Collector operates on cluster nodes and is responsible for collecting runtime-related information.

It can provide information about:

```text
Processes
Container activity
Network activity
Runtime behavior
Container/node relationships
```

This information is important for runtime security.

For example:

```text
Pod
 │
 ├── Expected process
 │
 └── Unexpected process
          │
          ▼
      Security event
```

The event can then be analyzed by RHACS.

---

# 11. Admission Controller

The Admission Controller operates inside the OpenShift cluster.

Its purpose is to enforce security decisions during workload admission.

Example:

```text
Developer
    │
    │ oc apply
    ▼
OpenShift API
    │
    ▼
Admission Controller
    │
    ├── Policy PASS ─────► Workload created
    │
    └── Policy FAIL ─────► Workload rejected
```

Example policy:

```text
Do not allow deployment
if image contains CRITICAL vulnerability.
```

The decision can therefore happen **inside the secured cluster before the workload is created**.

---

# 12. Runtime Data Stays Closely Associated With the Cluster

Runtime security requires information generated by workloads and nodes.

Examples:

```text
Process execution
Container behavior
Network connections
Runtime events
Node/container relationships
```

This information originates inside the secured cluster.

It should not be interpreted as meaning that every raw piece of runtime data is permanently stored centrally in exactly the same form.

Instead, RHACS components collect and process security-relevant information and communicate the information required for centralized analysis and security operations.

---

# 13. Secrets and Credentials

Secrets should remain protected inside the secured environment.

Examples:

```text
Application secrets
TLS private keys
Service-account credentials
Database passwords
Registry credentials
Cluster credentials
```

The architecture should follow the principle:

```text
Secret
  │
  ▼
Secured cluster / Kubernetes Secret
```

rather than unnecessarily copying application secrets into a central security platform.

RHACS should not be treated as an application-secret-management system.

For enterprise environments, dedicated secret-management systems such as Vault or an enterprise secrets platform can be used.

---

# 14. Application Data

Business/application data should normally remain in the secured cluster or its protected backend.

Examples:

```text
Customer records
Database records
Application files
Transaction information
User documents
Business transactions
```

RHACS is a security platform, not an application-data replication platform.

Therefore:

```text
Application
     │
     ▼
Database / Storage
     │
     ▼
Secured environment
```

RHACS provides security visibility around the application rather than becoming the application's primary data store.

---

# 15. Example: Banking Application

Consider:

```text
OpenShift Cluster
      │
      ├── payment-api
      ├── payment-db
      └── frontend
```

The application database contains:

```text
Customer information
Transaction records
Account information
```

This data should remain within the protected application environment.

RHACS may know:

```text
Namespace:
payments

Deployment:
payment-api

Image:
payment-api:v4.2

Image vulnerability:
HIGH

Runtime process:
java

Network communication:
payment-api → payment-db

Policy:
PASS
```

But RHACS is not intended to become a copy of the payment database.

# 16. Central vs Cluster Data

| Data / Information        |                          Central RHACS |              Secured Cluster |
| ------------------------- | -------------------------------------: | ---------------------------: |
| Security policies         |                                    Yes |   Policy enforcement locally |
| Cluster metadata          |                                    Yes |                          Yes |
| Workload metadata         |                                    Yes |                          Yes |
| Vulnerability information |                                    Yes | Local image/workload context |
| Security alerts           |                                    Yes |     Event originates locally |
| Runtime events            |          Security-relevant information |   Raw/local runtime activity |
| Process information       |                      Security analysis |            Collected locally |
| Network activity          |                      Security analysis |             Observed locally |
| Admission decisions       | Policy/configuration centrally managed |          Enforcement locally |
| Application secrets       |                                     No |                          Yes |
| Application database      |                                     No |                          Yes |
| Customer/business data    |                                     No |                          Yes |
| TLS/private credentials   |         Protected/local as appropriate |                          Yes |
| Kubernetes objects        |          Cluster remains authoritative |                          Yes |
| Security configuration    |                     Central management |            Local enforcement |

# 17. Important Security Principle

The key principle is:

> **Centralize security management and visibility, but keep sensitive application and operational data inside the secured environment whenever possible.**

Architecture:

```text
                    CENTRAL SECURITY
                         │
        ┌────────────────┼─────────────────┐
        │                │                 │
        ▼                ▼                 ▼
     Policy           Analysis          Reporting
        │                │                 │
        └────────────────┼─────────────────┘
                         │
                    TLS Connection
                         │
        ┌────────────────┼─────────────────┐
        ▼                ▼                 ▼
    Cluster A         Cluster B         Cluster C
        │                │                 │
     Sensor           Sensor            Sensor
     Collector        Collector         Collector
     Admission        Admission         Admission
        │                │                 │
        ▼                ▼                 ▼
    Workloads         Workloads         Workloads
    Secrets           Secrets           Secrets
    Databases         Databases         Databases
```

# 20. Data Flow Example

Suppose an administrator deploys:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
spec:
  template:
    spec:
      containers:
      - name: payment
        image: registry.example.com/payment:v1
```

The process can conceptually be:

```text
1. Developer creates Deployment
              │
              ▼
2. Admission Controller evaluates policy
              │
              ▼
3. Workload is admitted/rejected
              │
              ▼
4. Sensor observes workload metadata
              │
              ▼
5. Collector observes runtime activity
              │
              ▼
6. Security-relevant information sent to Central
              │
              ▼
7. Central evaluates/displays security posture
```

Application data remains with the application:

```text
payment-api
     │
     ▼
payment-db
     │
     ▼
Application data
```

RHACS does not become the database for the application's business information.

# 21. Central Does Not Mean "Everything Is Copied"

This distinction is very important for security architecture interviews.

Do not say:

> "All cluster data is copied to RHACS Central."

A better statement is:

> "RHACS Central maintains the security management data, metadata, findings, alerts, and information required for centralized security analysis. Cluster-local components continue to collect and enforce security controls inside the cluster, while sensitive application data, secrets, and databases remain in their protected environments."

---

# 22. Interview Answer

### Question

**What data is stored centrally and what remains on secured clusters?**

### Answer

In RHACS, **Central** maintains centralized security information such as security policies, vulnerability findings, cluster and workload metadata, alerts, risk information, and configuration required for centralized security management.

The secured OpenShift clusters retain the actual workloads, application data, databases, Kubernetes resources, secrets, and other sensitive operational data. Cluster-local RHACS components such as **Sensor, Collector, and Admission Controller** perform monitoring and enforcement inside the cluster.

The design principle is:

```text
Central:
    Security management
    Security visibility
    Vulnerability analysis
    Policies
    Alerts
    Reporting

Secured Cluster:
    Applications
    Application data
    Secrets
    Databases
    Runtime environment
    Local enforcement
```

This provides **centralized security governance without turning the central security platform into a repository for application/business data**.
