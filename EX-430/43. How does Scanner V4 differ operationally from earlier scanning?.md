# How Does Scanner V4 Differ Operationally from Earlier Scanning?

## 1. Overview

RHACS Scanner V4 is the newer image-scanning architecture introduced in RHACS 4.4 and built on **ClairCore**. It replaced the older StackRox Scanner architecture for image vulnerability scanning and became the default scanner in RHACS 4.8. The older StackRox Scanner, also called Scanner V2, is deprecated beginning with RHACS 4.6.

The operational difference is important because Scanner V4 changes not only the scanner engine but also how image indexing, vulnerability matching, databases, vulnerability data, and deployment responsibilities are handled.

A simplified comparison is:

```text
Older StackRox Scanner
----------------------

Image
  |
  v
StackRox Scanner
  |
  +-- Image analysis
  +-- Vulnerability matching
  |
  v
Scanner-DB
  |
  v
Results


Scanner V4
----------

Image
  |
  v
Scanner V4 Indexer
  |
  +-- Pull image
  +-- Analyze layers
  +-- Identify OS/packages/dependencies
  |
  v
Index Report
  |
  v
Scanner V4 Matcher
  |
  +-- Vulnerability data
  +-- Matching
  |
  v
Scanner V4 DB
  |
  v
Vulnerability Report
```

---

# 2. Scanner V2 vs Scanner V4

| Area                         | Older StackRox Scanner                  | Scanner V4                             |
| ---------------------------- | --------------------------------------- | -------------------------------------- |
| Architecture                 | StackRox Scanner based on Clair v2 fork | ClairCore-based                        |
| RHACS status                 | Deprecated beginning RHACS 4.6          | Recommended/default scanner            |
| Image scanning               | Yes                                     | Yes                                    |
| Image indexing               | Scanner image analysis                  | Dedicated Indexer                      |
| Vulnerability matching       | Older Scanner architecture              | Dedicated Matcher                      |
| Database                     | Scanner-DB                              | Scanner V4 DB                          |
| Language package scanning    | Supported capabilities                  | Expanded/newer architecture            |
| OS package scanning          | Yes                                     | Yes                                    |
| Vulnerability sources        | Older source model                      | Modern vulnerability-source model      |
| Index reports                | Older architecture                      | Explicit index-report model            |
| RHCOS/node/platform scanning | Older scanner capability                | Supported in newer Scanner V4 releases |
| Operational model            | More monolithic                         | Indexing and matching separated        |

Scanner V4's Indexer, Matcher, and DB are distinct components in the newer architecture.

---

# 3. Why Scanner V4 Was Introduced

The main objective was to provide a more modern scanning architecture capable of better handling:

* Operating-system packages
* Programming-language packages
* Image layers
* Vulnerability matching
* Modern vulnerability data
* Indexing and matching separation
* Improved scalability
* More accurate vulnerability applicability

Scanner V4 is built on **ClairCore**, the same core technology used by Clair.

---

# 4. Operational Architecture of Scanner V4

Scanner V4 separates image analysis from vulnerability matching.

```text
                   RHACS Central
                        |
            +-----------+-----------+
            |                       |
            v                       v
    Scanner V4 Indexer       Scanner V4 Matcher
            |                       |
            v                       v
      Scanner V4 DB <---------------+
            |
            v
       Index Reports
```

The important operational components are:

### Scanner V4 Indexer

Responsible for:

* Pulling image metadata
* Downloading required image layers
* Analyzing the image
* Detecting the operating system
* Finding packages
* Finding language-level dependencies
* Producing an index report

### Scanner V4 Matcher

Responsible for:

* Obtaining vulnerability information
* Reading index reports
* Matching components against vulnerability definitions
* Producing vulnerability results

### Scanner V4 DB

Stores Scanner V4 information, including index reports and vulnerability data.

---

# 5. Image Indexing Is Now a Distinct Operation

One of the most important operational differences is the explicit **indexing** concept.

Previously, administrators commonly thought of the scanner operation as:

```text
Image
  |
  v
Scanner
  |
  v
Vulnerability Result
```

Scanner V4 separates this into:

```text
Image
  |
  v
Indexer
  |
  v
Index Report
  |
  v
Matcher
  |
  v
Vulnerability Report
```

Red Hat documentation describes Scanner V4 Indexer as performing image indexing, previously called image analysis.

---

# 6. What the Indexer Does

When Scanner V4 receives an image for scanning, the Indexer:

1. Obtains the image reference.
2. Uses registry credentials as required.
3. Retrieves image metadata.
4. Determines image layers.
5. Downloads layers that have not already been indexed.
6. Identifies the base operating system.
7. Identifies installed packages.
8. Identifies supported language/application dependencies.
9. Produces an index report.

Conceptually:

```text
Image Reference
      |
      v
Registry
      |
      v
Manifest
      |
      v
Image Layers
      |
      v
Indexer
      |
      +-- OS detection
      +-- Package detection
      +-- Language dependency detection
      |
      v
Index Report
```

This workflow is documented by Red Hat for Scanner V4.

---

# 7. Index Report

The Indexer produces an **index report**.

Conceptually:

```text
Index Report
 |
 +-- Image identity
 +-- OS
 +-- Packages
 +-- Versions
 +-- Language dependencies
 +-- Component information
```

The index report represents what Scanner V4 learned about the image.

The Matcher can then use this information without having to repeat the complete image-analysis process for every vulnerability lookup.

---

# 8. Vulnerability Matching Is Separate

Scanner V4 separates:

```text
"What is inside the image?"
```

from:

```text
"Which vulnerabilities affect those components?"
```

The Indexer answers the first question.

The Matcher answers the second.

```text
             Image
               |
               v
            Indexer
               |
               v
         Index Report
               |
               v
            Matcher
               |
       +-------+-------+
       |               |
       v               v
 Vulnerability      Component
    Data             Identity
       |               |
       +-------+-------+
               |
               v
       Vulnerability Report
```

This separation is one of the major operational differences from the older scanning model.

---

# 9. Scanner V4 DB

Scanner V4 has its own database architecture.

The Scanner V4 DB stores information used by Scanner V4, including:

* Vulnerability data
* Index reports
* Scanner-related information

Red Hat recommends persistent storage for Scanner V4 DB for best performance.

This creates a new operational consideration:

```text
Scanner V4
    |
    v
Scanner V4 DB
    |
    +-- Persistent storage
    +-- Capacity
    +-- Performance
    +-- Backup/recovery considerations
```

---

# 10. Earlier Scanner-DB vs Scanner V4 DB

Do not assume that:

```text
Scanner-DB
```

and:

```text
Scanner V4 DB
```

are the same database.

They belong to different scanner architectures.

```text
Older Architecture
-------------------

StackRox Scanner
       |
       v
Scanner-DB


Scanner V4 Architecture
-----------------------

Scanner V4 Indexer
       |
       +----> Scanner V4 DB
       |
       v
Index Report

Scanner V4 Matcher
       |
       +----> Scanner V4 DB
```

Red Hat documentation explicitly distinguishes Scanner-DB for the StackRox Scanner from Scanner V4 DB.

---

# 11. Vulnerability Sources Changed

Scanner V4 uses a newer vulnerability-data model.

Current RHACS documentation lists sources including:

* Red Hat VEX
* National Vulnerability Database
* OSV
* Operating-system vulnerability feeds

Scanner V4's vulnerability-source behavior differs from the older StackRox Scanner.

For Red Hat data, newer RHACS releases use **Red Hat Vulnerability Exchange (VEX)**. Red Hat describes VEX as reducing the time and storage needed for initial vulnerability-data loading.

---

# 12. VEX Changes Operational Results

The vulnerability results shown by Scanner V4 can differ from results produced by the older scanner.

This does not automatically mean Scanner V4 is incorrect.

The underlying vulnerability data and applicability logic can be different.

For example:

```text
Old Scanner
    |
    v
Older vulnerability source
    |
    v
Finding


Scanner V4
    |
    v
Modern vulnerability source / VEX
    |
    v
Different applicability result
```

Red Hat notes that RHACS versions using VEX can display different vulnerability counts compared with versions using older OVAL data. For example, vulnerabilities marked "under investigation" in earlier data may no longer be displayed in the same way.

---

# 13. Why Vulnerability Counts Can Change

After migrating to Scanner V4, teams may observe:

```text
Before:
100 vulnerabilities

After:
65 vulnerabilities
```

or:

```text
Before:
50 vulnerabilities

After:
90 vulnerabilities
```

This does not necessarily indicate a scanner failure.

Possible reasons include:

* Different vulnerability sources
* Better applicability determination
* Vendor-specific data
* VEX information
* Different package matching
* Different handling of vulnerability status
* Different historical vulnerability coverage

Therefore, compare the underlying vulnerability definitions rather than comparing only the CVE count.

---

# 14. RHCOS and Node Scanning

The role of Scanner V4 has expanded over RHACS releases.

In earlier Scanner V4 releases, the older StackRox Scanner still had to remain enabled for some capabilities, including node and platform scanning.

In newer RHACS releases, Scanner V4 supports RHCOS scanning and broader node/platform capabilities.

Therefore, the exact coexistence requirements depend strongly on the RHACS release.

For production operations:

> Always check the documentation for the exact RHACS version before disabling the older Scanner.

# 16. Delegated Scanning

Enterprise environments may use delegated scanning.

The basic idea is:

```text
Central
   |
   | Scan request
   v
Secured Cluster
   |
   v
Scanner V4
   |
   v
Registry
```

This can be useful when the secured cluster has network access to an internal registry that Central cannot directly access.

For registry-mirror scenarios, RHACS documentation describes delegated scanning as an important part of scanning images through configured registry mirrors.

# 17. Registry Operations Change

With Scanner V4, administrators should pay close attention to registry connectivity.

The Indexer needs access to image metadata and layers.

```text
Scanner V4 Indexer
        |
        v
Registry
        |
        +-- Manifest
        +-- Config
        +-- Layer 1
        +-- Layer 2
        +-- Layer 3
```

Operational requirements include:

* Registry DNS
* Network connectivity
* Authentication
* TLS trust
* Proxy configuration
* Registry mirrors
* Image pull permissions

---

# 18. Layer Reuse and Indexing

Scanner V4 does not necessarily need to download and process every layer repeatedly.

The Indexer downloads layers that have not already been indexed.

Conceptually:

```text
Image A
 |
 +-- Layer 1  --> Already indexed
 +-- Layer 2  --> Already indexed
 +-- Layer 3  --> New
                   |
                   v
                Analyze
```

This can improve operational efficiency when many images share common base layers.

Red Hat documents that Scanner V4 Indexer downloads each previously unindexed layer.

# 26. Minimal and Distroless Images

Scanner V4 still depends on discoverable information inside the image.

If an image removes important metadata files, scanner component identification can be affected.

Examples include:

```text
/etc/os-release
/etc/redhat-release
/etc/debian_version
package.json
Python package metadata
Java MANIFEST.MF
```

Red Hat documents that removing such files from the final image can prevent identification of installed components or vulnerabilities.

Therefore:

> Do not deliberately remove package or OS metadata simply to reduce image size if doing so prevents reliable security scanning.

With Scanner V4, enterprises should think about scanning as two logical operations:

```text

     |
     v

     |
     v

     |
     v

     |
     v
```

This makes it easier to understand why:

```text

```

does not necessarily mean:


Both stages must work.

# 33. Scanner V4 vs Earlier Scanning: Key Differences

The most important operational differences are:

### 1. Modern architecture

Scanner V4 is built on ClairCore rather than the older StackRox/Clair v2-derived scanner.

### 2. Indexer/Matcher separation

Image indexing and vulnerability matching are distinct operational stages.

### 3. Dedicated Scanner V4 DB

Scanner V4 uses a dedicated database for vulnerability data and index reports.

### 4. Modern vulnerability intelligence

Scanner V4 uses newer vulnerability sources, including Red Hat VEX in applicable releases.

### 5. Different results are possible

CVE counts and vulnerability status can change because the underlying vulnerability data and applicability logic differ.

### 6. More explicit operational troubleshooting

Administrators need to distinguish:

```text
Registry problem
     |
Indexer problem
     |
Scanner V4 DB problem
     |
Matcher problem
     |
Vulnerability-data problem
```

# 34. Interview Explanation

If asked:

> **How does Scanner V4 differ operationally from earlier RHACS scanning?**

A strong answer is:

> Scanner V4 is the newer ClairCore-based scanning architecture. Unlike the older StackRox Scanner, it separates image indexing from vulnerability matching. The Scanner V4 Indexer retrieves image metadata and layers and creates an index report containing the identified operating system, packages, and supported language dependencies. The Scanner V4 Matcher then compares that indexed component data against vulnerability intelligence and produces the vulnerability report. Scanner V4 also uses a dedicated Scanner V4 DB for index reports and vulnerability data, and newer RHACS releases use modern sources such as Red Hat VEX. Operationally, this means administrators must monitor and troubleshoot the Indexer, Matcher, database, registry connectivity, storage, and vulnerability-data update path separately.

Scanner V4 is therefore more than simply a newer scanner binary. It introduces a more modular operational model around **indexing, matching, vulnerability intelligence, and persistent scanner data**.

For enterprise RHACS administration, the key operational lesson is:

> **When troubleshooting Scanner V4, do not treat scanning as one single operation. Determine whether the failure is in image retrieval, indexing, index-report storage, vulnerability-data availability, or vulnerability matching.**

Always validate the exact Scanner V4 behavior, component requirements, and coexistence requirements against the RHACS version deployed in your environment.
