# How Do You Assess Overall RHACS Platform Health?

## 1. Overview

Assessing RHACS platform health means verifying that the **entire RHACS security platform is operational**, not simply checking whether the RHACS Central pod is running.

A healthy RHACS deployment should provide:

* Healthy RHACS Central
* Healthy secured-cluster components
* Working Kubernetes API connectivity
* Working Central-to-Sensor communication
* Working Collector runtime visibility
* Working admission control
* Working vulnerability scanning
* Healthy RHACS database/storage
* Healthy certificates and TLS communication
* Working UI and API
* No unexpected component restarts
* No persistent errors
* Current vulnerability data
* Normal resource consumption

A useful mental model is:

```text
                    RHACS Platform Health
                            |
       +--------------------+--------------------+
       |                    |                    |
       v                    v                    v
   Central Health      Secured Cluster      Security Services
       |                    |                    |
       v                    v                    v
   Database             Sensor             Scanner
   API/UI               Collector          Admission
   TLS                  Connectivity       Vulnerability DB
```

---

# 2. Health Is More Than "Pods Are Running"

A common mistake is checking:

```bash
oc get pods -n stackrox
```

and assuming:

```text
All pods Running = RHACS healthy
```

This is not sufficient.

For example:

```text
Central
Running
```

does not guarantee:

```text
Central API works
        +
Database works
        +
Sensors connected
        +
Scanner works
        +
Admission controller works
        +
TLS is healthy
```

Therefore, RHACS health should be evaluated at multiple layers.

---

# 3. RHACS Health Model

A practical health model is:

```text
Layer 1  -> Kubernetes/OpenShift
Layer 2  -> RHACS Components
Layer 3  -> Component Connectivity
Layer 4  -> Data/Storage
Layer 5  -> Security Functions
Layer 6  -> Monitoring and Alerts
Layer 7  -> Operational Capacity
```

You can think of the platform as:

```text
Infrastructure
      |
      v
RHACS Components
      |
      v
Communication
      |
      v
Data
      |
      v
Security Functions
      |
      v
Monitoring
```

# 4. Step 1 — Identify the RHACS Installation Model

Before troubleshooting, determine how RHACS was installed.

Common approaches include:

```text
Operator-based installation
```

or:

```text
Helm-based installation
```

The namespace and resource names can vary according to the installation.

A common OpenShift deployment uses:

```text
stackrox
```

namespace.

Start with:

```bash
oc get ns
```

Then identify RHACS resources:

```bash
oc get pods -n stackrox
oc get deploy -n stackrox
oc get sts -n stackrox
oc get svc -n stackrox
```

For Kubernetes:

```bash
kubectl get pods -n stackrox
kubectl get deploy -n stackrox
kubectl get sts -n stackrox
kubectl get svc -n stackrox
```

---

# 5. Step 2 — Check All RHACS Pods

Start with:

```bash
oc get pods -n stackrox -o wide
```

Look for:

```text
STATUS
READY
RESTARTS
AGE
NODE
```

A healthy environment should generally show expected components in:

```text
Running
```

or an expected completed/ready state.

Example:

```text
NAME                         READY   STATUS    RESTARTS
central-xxxxx                1/1     Running   0
scanner-xxxxx                1/1     Running   0
scanner-db-xxxxx             1/1     Running   0
sensor-xxxxx                 1/1     Running   0
admission-control-xxxxx      1/1     Running   0
collector-xxxxx              1/1     Running   0
```

Do not focus only on `STATUS`.

A pod may show:

```text
Running
```

while repeatedly restarting or experiencing application-level failures.

---

# 6. Step 3 — Check Pod Restarts

Use:

```bash
oc get pods -n stackrox
```

Look at:

```text
RESTARTS
```

For example:

```text
central-xxxxx       1/1   Running   0
sensor-xxxxx        1/1   Running   12
scanner-xxxxx       1/1   Running   0
```

Sensor having repeated restarts deserves investigation.

Check:

```bash
oc describe pod sensor-xxxxx -n stackrox
```

And:

```bash
oc logs sensor-xxxxx -n stackrox
```

For the previous container:

```bash
oc logs sensor-xxxxx -n stackrox --previous
```

---

# 7. Step 4 — Check RHACS Deployments

Run:

```bash
oc get deployment -n stackrox
```

Then:

```bash
oc get deployment -n stackrox -o wide
```

Check:

```text
DESIRED
CURRENT
READY
AVAILABLE
```

Example:

```text
NAME       READY   UP-TO-DATE   AVAILABLE
central    1/1     1            1
scanner    1/1     1            1
sensor     1/1     1            1
```

If:

```text
DESIRED = 1
READY   = 0
```

the component is unhealthy.

# 8. Step 5 — Check Stateful Components

Some RHACS installations use stateful components.

Check:

```bash
oc get statefulset -n stackrox
```

Then:

```bash
oc get pvc -n stackrox
```

Check whether storage is:

```text
Bound
```

and not:

```text
Pending
Lost
```

Storage problems can eventually affect RHACS availability and data persistence.

# 9. Step 6 — Check Central

Central is one of the most important RHACS components.

Conceptually:

```text
Users / API Clients
        |
        v
      Central
        |
   +----+----+
   |         |
   v         v
 Storage   RHACS Services
```

Check Central:

```bash
oc get pods -n stackrox | grep central
```

Check logs:

```bash
oc logs deployment/central -n stackrox
```

Look for repeated errors involving:

```text
database
TLS
certificate
connection
authentication
storage
timeout
panic
```

# 10. Step 7 — Check Central Service

Run:

```bash
oc get svc -n stackrox
```

Identify the Central service.

Then:

```bash
oc describe svc central -n stackrox
```

Verify:

```text
Selector
Endpoints
Port
TargetPort
```

Check endpoints:

```bash
oc get endpoints -n stackrox
```

or:

```bash
oc get endpointslices -n stackrox
```

A service with no endpoints can indicate that the backend pod is unavailable or selectors do not match.

# 11. Step 8 — Check RHACS UI

The RHACS UI should be accessible.

Depending on the platform, this may be through:

```text
OpenShift Route
```

or:

```text
Kubernetes Ingress
```

On OpenShift:

```bash
oc get route -n stackrox
```

Then:

```bash
oc describe route <route-name> -n stackrox
```

Verify:

```text
Hostname
Service
Port
TLS
```

Test connectivity:

```bash
curl -k https://<rhacs-hostname>
```

A successful HTTP response indicates that the endpoint is reachable, but UI accessibility alone does not prove that the entire RHACS platform is healthy.

# 12. Step 9 — Check Central API

RHACS is API-driven.

A healthy UI does not necessarily mean every API operation works.

Verify API connectivity using the RHACS CLI or appropriate API endpoint.

For example:

```bash
roxctl central whoami
```

Depending on your environment, authentication and Central endpoint parameters may be required.

The goal is to verify:

```text
Client
  |
  v
TLS
  |
  v
Central
  |
  v
Authentication
  |
  v
API
```

# 13. Step 10 — Check Sensor Health

Sensor is critical for secured-cluster communication.

Architecture:

```text
Kubernetes API Server
        |
        v
      Sensor
        |
        v
      Central
```

Check:

```bash
oc get pods -n stackrox | grep sensor
```

Check logs:

```bash
oc logs deployment/sensor -n stackrox
```

Look for:

```text
connection errors
TLS errors
authentication failures
API errors
Central connection failures
watch errors
timeouts
```

---

# 14. Step 11 — Check Secured Cluster Connectivity

A major RHACS health check is determining whether secured clusters are actually connected to Central.

A Central instance can be healthy while one or more secured clusters are disconnected.

Conceptually:

```text
                 Central
                    |
       +------------+------------+
       |            |            |
       v            v            v
   Cluster A    Cluster B    Cluster C
      OK           OK          ERROR
```

The platform is only partially healthy.

Check secured-cluster information from the RHACS UI or API/CLI.

Look for:

```text
Cluster name
Health
Sensor status
Last contact
Collector status
```

---

# 15. Step 12 — Check Collector

Collector provides important runtime and node-level visibility.

Check Collector pods:

```bash
oc get pods -n stackrox -l app=collector
```

Depending on deployment labels and RHACS version, use the labels actually present in your environment.

Check:

```bash
oc get daemonset -n stackrox
```

Collector is commonly deployed as a DaemonSet so that the required nodes can run Collector instances.

Check:

```bash
oc get daemonset -n stackrox
```

Look for:

```text
DESIRED
CURRENT
READY
AVAILABLE
```

For example:

```text
DESIRED   CURRENT   READY
3         3         3
```

is generally healthy.

---

# 16. Step 13 — Check Collector Coverage

Suppose the cluster has:

```text
6 worker nodes
```

but Collector is running on:

```text
4 nodes
```

Then runtime visibility may be incomplete.

Check:

```bash
oc get daemonset -n stackrox
```

and:

```bash
oc get pods -n stackrox -o wide
```

Compare the Collector placement with the expected node coverage.

Investigate:

```text
Node taints
Tolerations
Resource constraints
Scheduling failures
Pod security restrictions
Container runtime compatibility
```

---

# 17. Step 14 — Check Admission Controller

If RHACS admission control is enabled, verify that its components are healthy.

Check:

```bash
oc get pods -n stackrox
```

Look for the admission-control components.

The conceptual path is:

```text
Developer
    |
    v
kubectl apply
    |
    v
Kubernetes API Server
    |
    v
Admission Controller
    |
    +---- Policy violation ---> Reject
    |
    +---- Compliant ----------> Allow
```

A broken admission controller can have a significant impact.

Depending on enforcement configuration, workloads may:

* Continue to deploy
* Fail admission
* Experience deployment delays
* Lose expected security enforcement

Therefore, verify both **component health** and **policy behavior**.

---

# 18. Step 15 — Test Admission Control Carefully

Do not test production admission policies by deploying arbitrary workloads.

Use a controlled test namespace.

For example:

```bash
oc new-project rhacs-test
```

Deploy a known test workload according to your organization's RHACS policy.

Then verify:

```text
Expected compliant workload -> Allowed
Expected violating workload -> Blocked
```

Only perform this when the admission policy is intentionally configured for enforcement.

---

# 19. Step 16 — Check Scanner

RHACS vulnerability scanning depends on scanner-related components.

Check:

```bash
oc get pods -n stackrox | grep scanner
```

Check logs:

```bash
oc logs deployment/scanner -n stackrox
```

Also check scanner database components where applicable.

Look for:

```text
database connection failures
download/update failures
TLS errors
scan failures
timeouts
resource exhaustion
```

---

# 20. Step 17 — Check Vulnerability Data Freshness

A scanner can be:

```text
Running
```

but its vulnerability information may not be current.

Therefore, check:

```text
Last vulnerability database update
Scanner status
Database status
Scan success/failure
```

This is important because:

```text
Healthy scanner process
        !=
Current vulnerability intelligence
```

A security platform with stale vulnerability data can produce incomplete results.

---

# 21. Step 18 — Check Database Health

RHACS data persistence is critical.

Check the relevant storage/database components used by your RHACS deployment.

Look for:

```text
Storage errors
Database errors
Disk exhaustion
Corruption
Connection failures
Slow I/O
```

On OpenShift:

```bash
oc get pvc -n stackrox
```

Check:

```bash
oc describe pvc <pvc-name> -n stackrox
```

If the platform uses a specific RHACS-supported database architecture, follow the health checks documented for that RHACS release.

---

# 22. Step 19 — Check Disk Capacity

Disk exhaustion can cause apparently unrelated failures.

Check:

```bash
oc adm top nodes
```

and:

```bash
oc get pvc -n stackrox
```

On a node:

```bash
df -h
```

Look for:

```text
Use%
```

A filesystem approaching full capacity should be investigated before it causes service degradation.

---

# 23. Step 20 — Check CPU and Memory

Check node resource usage:

```bash
oc adm top nodes
```

Check pods:

```bash
oc adm top pods -n stackrox
```

Look for:

```text
CPU
MEMORY
```

High resource usage may indicate:

```text
Large cluster
High workload count
Large number of security events
Scanner load
Memory leak
Insufficient resource requests/limits
```

---

# 24. Step 21 — Check Events

Cluster events often provide early warning.

Run:

```bash
oc get events -n stackrox --sort-by=.lastTimestamp
```

Look for:

```text
FailedScheduling
FailedMount
BackOff
Unhealthy
Failed
Killing
OOMKilled
```

For broader OpenShift troubleshooting:

```bash
oc get events -A --sort-by=.lastTimestamp
```

---

# 25. Step 22 — Check Node Health

RHACS components depend on the underlying Kubernetes/OpenShift platform.

Check:

```bash
oc get nodes
```

Expected:

```text
Ready
```

Then:

```bash
oc describe node <node-name>
```

Look for:

```text
MemoryPressure
DiskPressure
PIDPressure
NetworkUnavailable
```

A RHACS component running on an unhealthy node may appear unhealthy even though the RHACS configuration itself is correct.

---

# 26. Step 23 — Check Certificates and TLS

RHACS relies heavily on TLS communication.

The architecture can be simplified as:

```text
Sensor
   |
   | TLS
   v
Central
   |
   | TLS
   v
Clients / APIs
```

Certificate problems can produce errors such as:

```text
certificate expired
certificate unknown
x509 errors
TLS handshake failure
unknown authority
```

Check relevant secrets:

```bash
oc get secrets -n stackrox
```

Do not expose secret contents during troubleshooting.

Instead, inspect certificate metadata where appropriate.

For example:

```bash
oc describe secret <secret-name> -n stackrox
```

Follow the RHACS-supported certificate management process rather than manually replacing RHACS-managed certificates.

---

# 27. Step 24 — Check DNS

RHACS components require reliable DNS.

Test from an appropriate RHACS pod:

```bash
oc exec -n stackrox <pod-name> -- getent hosts <service-name>
```

If `getent` is unavailable, use an appropriate DNS utility available in the container.

Check:

```text
Central hostname
Kubernetes API
RHACS services
Registry endpoints
External services
```

DNS failures can appear as:

```text
connection timeout
connection refused
name resolution failure
```

---

# 28. Step 25 — Check Network Connectivity

The basic path is:

```text
Sensor
  |
  v
Network
  |
  v
Central
```

Verify that:

```text
TCP connectivity
TLS handshake
Authentication
Application protocol
```

are all working.

A successful TCP connection alone does not prove that the RHACS service is healthy.

---

# 29. Step 26 — Check Logs Systematically

Do not start by reading every log.

Use a component-oriented approach:

```text
Central
Sensor
Collector
Scanner
Admission Controller
Database
```

For each component:

```text
1. Check pod status
2. Check restarts
3. Check recent events
4. Check recent logs
5. Check dependencies
6. Check resource consumption
```

Example:

```bash
oc logs deployment/central -n stackrox --since=30m
```

Then:

```bash
oc logs deployment/sensor -n stackrox --since=30m
```

And:

```bash
oc logs deployment/scanner -n stackrox --since=30m
```

---

# 30. Step 27 — Search Logs for Important Errors

Useful patterns include:

```text
error
fatal
panic
timeout
failed
denied
unauthorized
forbidden
certificate
TLS
x509
connection refused
connection reset
database
OOM
```

For example:

```bash
oc logs deployment/sensor -n stackrox --since=1h | \
grep -Ei 'error|fatal|panic|timeout|x509|certificate'
```

Do not treat every `warning` as a platform failure.

Determine whether the message is:

```text
Transient
Expected
Recoverable
Persistent
Service-impacting
```

The goal is to validate:

 v

 |
 v

 v

 v

# 32. Step 29 — Check Security Policy Processing

A healthy RHACS platform should be able to process security policies.

Check:

```text
Policies visible
Policies synchronized
Alerts generated when expected
Policy enforcement works where configured
```

A controlled test can verify:

```text
Test workload
      |
      v
Known policy condition
      |
      v
RHACS
      |
      v
Expected violation
```

This tests the actual security function rather than simply checking pod status.

       |
       v

       |

Important metrics include:

# 36. Step 33 — Check Alerts

A healthy security platform should be able to generate and deliver alerts as designed.

Verify:

```text
Policy violation
      |
      v
RHACS
      |
      +---- UI
      |
      +---- API
      |
      +---- Webhook
      |
      +---- SIEM
      |
      +---- Email / integration
```

Do not assume that because an alert appears in RHACS it will automatically reach external systems.

Test the complete integration path.

Check:

# 38. Step 35 — Check Identity and Authentication

If RHACS uses an external identity provider, verify authentication.

The flow may be:

```text
User
 |
 v
Identity Provider
 |
 v
RHACS
 |
 v
RBAC
 |
 v
RHACS UI/API
```

Check:

```text
Login
Identity provider connectivity
Certificates
Groups
Roles
Permissions
```

A user being able to open the login page does not necessarily prove that external identity synchronization is working correctly.

---

# 39. Step 36 — Check RBAC

Verify that administrators and security teams have appropriate permissions.

Examples:

```text
Security Administrator
Platform Administrator
Read-only Security User
Application Team
```

Check that:

```text
Expected access -> Allowed
Unauthorized access -> Denied
```

This is part of platform health because a technically running RHACS installation can still have an operational security problem if RBAC is incorrectly configured.

---

# 40. Step 37 — Check Upgrade Status

An RHACS environment should be checked for:

```text
Current version
Available updates
Component version consistency
Pending migrations
Upgrade failures
```

Check your RHACS deployment resources according to the installation method.

For Operator-based installations, inspect the relevant Operator/CSV resources.

For example:

```bash
oc get csv -A | grep -i advanced
```

The exact CSV name varies by release.

# 41. Step 38 — Check Operator Health

If RHACS was installed through an Operator, verify the Operator.

Check:

```bash
oc get csv -A
```

Look for the RHACS Operator status.

Also check:

```bash
oc get subscriptions -A
```

and relevant ClusterServiceVersion resources.

The desired state is generally:

```text
Succeeded
```

Investigate:

```text
Installing
Pending
Failed
Deleting
```

when they persist unexpectedly.

# 42. Step 39 — Check RHACS Custom Resources

Operator-managed RHACS deployments may expose custom resources representing the installation.

Check:

```bash
oc get crd | grep -i stackrox
```

Then inspect the RHACS-related custom resources available in your environment.

For example:

```bash
oc get <rhacs-resource> -A
```

The exact resource names depend on the RHACS Operator version.

The important point is to verify that:

```text
Desired state
        =
Actual state
```

---

# 43. Step 40 — Check Resource Requests and Limits

RHACS components should have appropriate resources.

Check:

```bash
oc describe pod <pod-name> -n stackrox
```

Look at:

```text
Requests
Limits
QoS
```

Resource starvation can cause:

```text
OOMKilled
CPU throttling
Slow response
Pod eviction
Restart loops
```

Use:

```bash
oc adm top pods -n stackrox
```

to identify unusually high consumers.

---

# 44. Step 41 — Check for OOMKilled

Run:

```bash
oc get pods -n stackrox
```

Then:

```bash
oc describe pod <pod-name> -n stackrox
```

Look for:

```text
Reason: OOMKilled
```

Also inspect:

```text
Last State
Exit Code
Restart Count
```

Repeated OOM kills indicate that resource sizing or workload characteristics need investigation.

---

# 45. Step 42 — Check Scheduling Problems

RHACS components may fail to schedule because of:

```text
Node taints
Insufficient CPU
Insufficient memory
Affinity rules
Toleration problems
Node selectors
Resource quotas
```

Check:

```bash
oc get events -n stackrox --sort-by=.lastTimestamp
```

For a pending pod:

```bash
oc describe pod <pod-name> -n stackrox
```

Look at the `Events` section.

---

# 46. Step 43 — Check Namespace-Level Constraints

Check:

```bash
oc get resourcequota -n stackrox
```

and:

```bash
oc get limitrange -n stackrox
```

A quota problem can prevent RHACS components from starting or scaling.

---

# 47. Step 44 — Check Network Policies

If NetworkPolicies are used, ensure they do not unintentionally block RHACS communication.

Conceptually:

```text
Sensor
  |
  | NetworkPolicy
  X
Central
```

This can cause:

```text
Sensor disconnected
TLS timeout
API timeout
Scanner unavailable
```

Check:

```bash
oc get networkpolicy -n stackrox
```

Review any policies affecting RHACS pods.

---

# 48. Step 45 — Check Service Mesh Interaction

If the cluster uses a service mesh, verify that RHACS traffic is compatible with the mesh architecture.

Potential issues can involve:

```text
TLS interception
mTLS
Sidecars
Traffic policies
NetworkPolicy
Port handling
```

Do not automatically assume that disabling security controls is the correct solution.

First identify which communication path is failing.

---

# 49. Step 46 — Check Registry Connectivity

RHACS may need access to container registries.

Verify:

```text
Registry DNS
Registry TLS
Registry credentials
Network connectivity
Image pull access
Scanner access
```

A registry problem can appear as:

```text
Image scan failure
Image metadata failure
Authentication failure
```

---

# 50. Step 47 — Check Backup and Recovery

Platform health also includes recoverability.

Verify that appropriate backups exist for the RHACS deployment and that the organization understands:

```text
What is backed up?
Where is it stored?
How frequently?
How is it restored?
Who performs recovery?
```

A platform that is running today but cannot be recovered after a failure is not operationally healthy.

---

# 51. Step 48 — Check Time Synchronization

Time synchronization is important for:

```text
TLS
Certificates
Logs
Authentication
Event correlation
```

Check node time:

```bash
timedatectl
```

Check:

```text
NTP synchronization
Timezone
System clock
```

Significant clock differences can create confusing authentication and certificate problems.

# 59. Interview Answer

A concise interview answer is:

> **I assess RHACS health at multiple levels rather than only checking pod status. First, I verify the RHACS Operator or deployment state and all Central, Sensor, Collector, Scanner, Admission Controller, and database/storage components. Then I verify Central-to-Sensor connectivity for every secured cluster, Collector coverage across nodes, scanner and vulnerability-data freshness, admission-control functionality, UI/API availability, TLS certificates, DNS and network connectivity, resource utilization, restarts and events. Finally, I perform end-to-end tests for image scanning, runtime visibility, policy enforcement, authentication, and external integrations. This gives me both component-level and functional health of the RHACS platform.**
