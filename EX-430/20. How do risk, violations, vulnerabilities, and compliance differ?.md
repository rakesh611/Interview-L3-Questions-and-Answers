# How Do Risk, Violations, Vulnerabilities, and Compliance Differ?

## 1. Overview

In RHACS, **risk, violations, vulnerabilities, and compliance** are related but represent different security concepts.

A simple way to remember them is:

```text
Vulnerability
     |
     v
Technical weakness

Violation
     |
     v
Security policy was broken

Compliance
     |
     v
Required security controls are satisfied or not

Risk
     |
     v
Overall security impact / priority
```

These concepts should not be treated as interchangeable.

For example:

```text
Container image
      |
      +-- Contains CVE
      |       |
      |       +-- Vulnerability
      |
      +-- Violates security policy
      |       |
      |       +-- Violation
      |
      +-- Fails required benchmark
      |       |
      |       +-- Compliance issue
      |
      +-- Combined security impact
              |
              +-- Risk
```

---

# 2. Vulnerability

A **vulnerability** is a known weakness in software, an operating-system package, library, or other component that could potentially be exploited.

Examples include:

* Vulnerable OpenSSL package
* Vulnerable Linux package
* Vulnerable application dependency
* Vulnerable container image
* Known CVE

A simplified example:

```text
Image: payment-api:v10

Packages:
    |
    +-- openssl
    |
    +-- glibc
    |
    +-- curl
```

Suppose the image contains a package affected by a known CVE:

```text
openssl
   |
   +-- CVE
   |
   +-- High severity
```

That is a **vulnerability**.

---

# 3. Vulnerability Does Not Automatically Mean Exploitation

An important distinction is:

```text
Vulnerability
     !=
Compromise
```

If an image contains a vulnerable package, it does not necessarily mean that an attacker has exploited it.

For example:

```text
Image
 |
 +-- Vulnerable package
 |
 +-- Application never exposes affected functionality
```

The vulnerability still exists, but the practical risk may depend on additional context.

This is why RHACS can combine vulnerability information with workload and deployment context.

---

# 4. Vulnerability Example

Consider:

```text
Image:
web-app:v5

Vulnerability:
CVE-XXXX

Severity:
Critical
```

The security team can ask:

```text
Where is this image running?
Which cluster?
Which namespace?
Which deployment?
Is it production?
Is the vulnerable component reachable?
```

These questions help move from simply identifying a vulnerability toward understanding **risk**.

---

# 5. Violation

A **violation** occurs when a configured security policy or rule is not satisfied.

For example, an organization may define a policy:

```text
Policy:
Containers must not run as root
```

A workload runs as:

```text
User: root
```

The result is:

```text
Security Policy
       |
       v
"Must not run as root"
       |
       v
Workload runs as root
       |
       v
Policy Violation
```

A violation is therefore about **breaking a security policy or control**.

---

# 6. Examples of Violations

A security policy might require:

```text
No privileged containers
```

But a deployment contains:

```yaml
securityContext:
  privileged: true
```

Result:

```text
Policy
  |
  v
No privileged containers
  |
  v
Privileged container
  |
  v
Violation
```

Other examples can include policies related to:

* Privileged containers
* Host networking
* Host filesystem access
* Dangerous Linux capabilities
* Image vulnerabilities
* Insecure configurations
* Required labels or annotations
* Deployment security requirements
* Admission-control policies

The exact policy types and enforcement behavior depend on the RHACS configuration and version.

---

# 7. Violation vs Vulnerability

These are frequently confused.

| Concept       | Meaning                                        |
| ------------- | ---------------------------------------------- |
| Vulnerability | A known technical weakness                     |
| Violation     | A configured security policy was not satisfied |

Example:

```text
Image contains CVE
        |
        v
Vulnerability
```

Whereas:

```text
Container runs privileged
        |
        v
Security policy says "not allowed"
        |
        v
Violation
```

A workload can have:

```text
No known vulnerabilities
+
Security violation
```

or:

```text
Known vulnerabilities
+
No matching policy violation
```

Therefore, they are different concepts.

---

# 8. Compliance

**Compliance** asks whether systems satisfy a defined set of security requirements, standards, or controls.

Examples can include security frameworks and Kubernetes-related benchmarks.

The question is generally:

> Does this environment satisfy the required security controls?

For example:

```text
Compliance Requirement
        |
        v
Control:
Workloads should follow required security configuration
        |
        v
Cluster Assessment
        |
        +---- Pass
        |
        +---- Fail
```

Compliance is therefore broader than an individual vulnerability or policy violation.

---

# 9. Compliance Example

Suppose an organization has a Kubernetes security requirement:

```text
Control:
Containers should not run with unnecessary privileges.
```

The environment is evaluated against the control.

Results could be:

```text
Control 1    PASS
Control 2    PASS
Control 3    FAIL
Control 4    PASS
```

The failed control contributes to the organization's compliance posture.

The exact compliance framework and controls depend on the RHACS version and configured standards.

---

# 10. Compliance vs Violation

These concepts can overlap, but they are not identical.

### Violation

Usually focuses on:

```text
A specific configured security policy was violated.
```

### Compliance

Usually focuses on:

```text
A broader set of required controls or standards.
```

For example:

```text
RHACS Policy
      |
      v
Privileged container
      |
      v
Violation
```

At the same time:

```text
Compliance Standard
      |
      v
Security control
      |
      v
Privileged workload found
      |
      v
Compliance failure
```

The same technical condition can therefore contribute to both a policy violation and a compliance failure, depending on configuration.

---

# 11. Risk

**Risk** is the broader concept of how serious a security condition is in its actual context.

Risk is not simply:

```text
Number of vulnerabilities
```

A useful conceptual model is:

```text
Risk
  =
Threat/Weakness
  +
Exposure
  +
Impact
  +
Context
```

For example:

```text
Critical vulnerability
        +
Production workload
        +
Internet-facing service
        +
Sensitive application
        |
        v
Higher priority risk
```

The same vulnerability in a completely different environment may have a different practical priority.

---

# 12. Risk Is Contextual

Consider two workloads.

### Workload A

```text
Development
   |
   +-- Internal
   +-- Not externally exposed
   +-- Low business impact
```

### Workload B

```text
Production
   |
   +-- Internet-facing
   +-- Financial application
   +-- High business impact
```

Both contain the same vulnerability:

```text
CVE-XXXX
Severity: High
```

The vulnerability itself is the same.

But the security team's priority may be different because:

```text
Workload B
   |
   +-- Higher exposure
   +-- Higher business impact
   |
   v
Higher practical risk
```

---

# 13. Risk vs Vulnerability

This is one of the most important distinctions.

```text
Vulnerability
=
A technical weakness exists.
```

Whereas:

```text
Risk
=
How important/dangerous that weakness is in context.
```

For example:

```text
Vulnerability:
Critical CVE
```

does not by itself tell you:

```text
Is the affected workload deployed?
Is it production?
Is it exposed?
Is it exploitable in this environment?
What business service does it support?
```

Those contextual factors contribute to understanding risk.

---

# 14. Risk vs Violation

A violation means:

```text
Policy requirement was not satisfied.
```

Risk asks:

```text
How significant is the security exposure?
```

Example:

```text
Policy:
Do not run privileged containers.

Workload:
Privileged container.

Result:
Violation
```

The risk depends on context:

```text
Privileged container
       +
Sensitive production workload
       +
Host access
       |
       v
Potentially high risk
```

A violation therefore does not automatically equal a specific risk level.

---

# 15. Risk vs Compliance

Compliance primarily asks:

```text
"Are required controls being met?"
```

Risk asks:

```text
"What security exposure is most important?"
```

An organization can be:

```text
Highly compliant
```

and still have:

```text
Significant security risk
```

For example, an organization may satisfy many compliance controls but still have a newly discovered critical vulnerability.

Conversely:

```text
Compliance failure
```

does not always mean:

```text
Immediate critical security incident
```

Compliance and risk are related but serve different purposes.

---

# 16. Four Concepts Together

Consider this example:

```text
Production payment application
        |
        v
Container image
        |
        +-- Known critical CVE
        |
        +-- Runs as root
        |
        +-- Violates configured policy
        |
        +-- Fails security control
        |
        +-- Internet-facing
        |
        v
     RHACS Analysis
```

The four concepts can be separated as follows.

### Vulnerability

```text
Known critical CVE
```

### Violation

```text
Workload violates:
"Containers must not run as root"
```

### Compliance

```text
Required security control is not satisfied
```

### Risk

```text
Critical vulnerability
+
Production
+
Internet exposure
+
Sensitive application
=
High-priority security risk
```

# 18. How Security Teams Use Them

Different teams may focus on different concepts.

## Security Operations

Typically focuses on:

```text
Risk
Violations
Runtime alerts
Vulnerabilities
```

Their question is:

> What needs attention first?

---

## Vulnerability Management Team

Focuses heavily on:

```text
Vulnerabilities
Affected images
Affected workloads
Severity
Remediation
```

Their question is:

> Which software weaknesses need to be fixed?

---

## Platform Team

Often focuses on:

```text
Violations
Kubernetes configuration
Runtime behavior
Cluster security
```

Their question is:

> Which platform or workload configuration needs to change?

---

## Compliance Team

Focuses on:

```text
Compliance controls
Standards
Control failures
Evidence
Reports
```

Their question is:

> Are we meeting the required security controls?

# 20. Why Counting Vulnerabilities Is Not Enough

Suppose RHACS reports:

```text
1,000 vulnerabilities
```

This number alone is not enough to decide what to fix first.

The security team needs to understand:

```text
Which vulnerabilities?
Which severity?
Which images?
Which workloads?
Which clusters?
Which namespaces?
Production or development?
Internet-facing or internal?
Are policies violated?
Does compliance depend on them?
Is runtime activity suspicious?
```

This contextual information helps determine risk and remediation priority.

---

# 21. Example: Same Vulnerability, Different Risk

Consider:

```text
CVE-XXXX
Severity: Critical
```

### Case 1

```text
Image
 |
 +-- Development
 +-- No active workload
```

### Case 2

```text
Image
 |
 +-- Production
 +-- Internet-facing
 +-- Critical business service
 +-- Actively running
```

The underlying vulnerability is identical.

But the security priority may be significantly higher in Case 2.

This illustrates:

```text
Vulnerability != Risk
```

# 22. Example: Violation Without a Vulnerability

Consider:

```text
Container:
nginx:latest

Known vulnerabilities:
None detected
```

But the workload is configured as:

```yaml
securityContext:
  privileged: true
```

If the organization's policy prohibits privileged containers:

```text
No known vulnerability
        |
        +
        |
Privileged configuration
        |
        v
Policy violation
```

Therefore:

```text
No vulnerability
!=
No security issue
```

---

# 23. Example: Vulnerability Without a Policy Violation

Conversely:

```text
Image:
application:v10

Known vulnerability:
CVE-XXXX
```

But no configured policy currently blocks that vulnerability.

The image can still contain a vulnerability even if:

```text
No policy violation
```

Therefore:

```text
No violation
!=
No vulnerability
```

# 24. Example: Compliance Failure Without Immediate Incident

Suppose a compliance assessment identifies:

```text
Control:
Required Kubernetes security configuration
Status:
FAIL
```

This indicates that the environment does not satisfy the required control.

It does not necessarily mean:

```text
The cluster has been compromised.
```

Instead:

```text
Compliance Failure
       |
       v
Remediation Required
```

This distinction is important during audits and security reviews.

A mature security operation should prioritize remediation based on context.

Conceptually:

Additional context can include:

* Cluster

The exact RHACS risk calculations and scoring behavior depend on the RHACS release and configuration.

# 27. Interview Answer

A concise interview answer is:

> **A vulnerability is a known technical weakness in software or an image, such as a CVE. A violation occurs when a configured RHACS security policy is not satisfied, such as allowing a privileged container when that is prohibited. Compliance measures whether the environment satisfies defined security controls or standards. Risk is the broader assessment of the security impact and priority of an issue, taking into account factors such as vulnerabilities, workload context, exposure, configuration, and environment. These concepts are related, but one does not automatically imply another.**

## Key Takeaway

**Vulnerabilities identify weaknesses, violations identify broken security policies, compliance identifies whether required controls are satisfied, and risk helps determine the overall security priority.**

In RHACS, understanding the relationship between all four is important because effective Kubernetes security is not simply about finding the largest number of vulnerabilities—it is about understanding **what is vulnerable, what violates policy, what fails required controls, and what presents the greatest practical risk.**
