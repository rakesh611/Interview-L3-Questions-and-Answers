# How Do Failure Domains Affect RHACS Central Design?

## Overview

A **failure domain** is a set of infrastructure components that can fail together because they share a common dependency.

For RHACS, failure-domain design is important because **Central is the central management and security platform**. If Central is placed entirely inside one failure domain, a single infrastructure failure can affect RHACS management for many secured clusters.

A simple example:

```text
                RHACS Central
                     |
              Single Failure Domain
                     |
        +------------+------------+
        |            |            |
       Node         Node         Node
        |
        v
     Failure
        |
        v
RHACS Central unavailable
```

A better design deliberately separates important dependencies:

```text
              RHACS Central
                    |
        +-----------+-----------+
        |                       |
   Failure Domain A        Failure Domain B
        |                       |
      Node A                  Node B
        |                       |
        +-----------+-----------+
                    |
              Shared Services
```

The objective is:

> **A single infrastructure failure should not unnecessarily take down the entire RHACS security-management plane.**

---

# 1. What Is a Failure Domain?

A failure domain is an area where multiple components can fail because they share the same underlying dependency.

Examples include:

* One Kubernetes node
* One rack
* One power source
* One availability zone
* One storage system
* One network switch
* One data center
* One cloud region
* One RHACS Central cluster

For example:

```text
Rack 1
|
+-- Node 1
+-- Node 2
+-- Node 3
|
+-- Power Supply A
+-- Network Switch A
```

If the rack loses power:

```text
Rack Failure
     |
     +--> Node 1 DOWN
     +--> Node 2 DOWN
     +--> Node 3 DOWN
```

All three nodes belong to the same failure domain.

---

# 2. Why Failure Domains Matter for RHACS

RHACS Central provides centralized security capabilities.

If one Central deployment manages many clusters:

```text
                       RHACS Central
                            |
          +-----------------+-----------------+
          |                 |                 |
          v                 v                 v
       Cluster A         Cluster B         Cluster C
```

Central becomes an important dependency.

If Central is unavailable:

```text
                       RHACS Central
                            X
                            |
          +-----------------+-----------------+
          |                 |                 |
       Cluster A         Cluster B         Cluster C
```

Therefore, Central should be designed according to the organization's availability requirements.

---

# 3. Central Is a Different Failure Domain From Secured Clusters

A useful architecture separates:

```text
RHACS Central
      |
      v
Central Failure Domain
      |
      X
      |
Secured Cluster Failure Domain
```

For example:

```text
Failure Domain A
----------------
RHACS Central
RHACS storage


Failure Domain B
----------------
OpenShift Cluster 1


Failure Domain C
----------------
OpenShift Cluster 2
```

This prevents one cluster failure from automatically becoming a Central failure.

---

# 4. Node Failure Domain

The simplest failure domain is the Kubernetes/OpenShift node.

Suppose Central depends on one node:

```text
OpenShift
|
+-- Worker-1
     |
     +-- RHACS Central
```

If Worker-1 fails:

```text
Worker-1
   X
   |
Central
   X
```

This is a single-node failure domain.

For production, Central should be deployed according to the supported RHACS architecture and availability requirements rather than relying on one node.

---

# 5. Multiple Nodes

A more resilient architecture distributes Central workloads across nodes:

```text
OpenShift Cluster
|
+-- Node 1
|     |
|   Central instance
|
+-- Node 2
|     |
|   Central instance
|
+-- Node 3
      |
    Central instance
```

The goal is to prevent all required Central components from depending on one node.

However:

> **Running components on different nodes is not automatically the same as eliminating failure domains.**

If all nodes depend on the same rack, storage array, or network switch, they may still share a larger failure domain.

---

# 6. Rack Failure Domain

Consider:

```text
Rack 1
|
+-- Node 1
+-- Node 2
+-- Node 3
```

Even though Central is distributed across three nodes:

```text
Rack 1
   |
   X
Power Failure
   |
   +--> Node 1 DOWN
   +--> Node 2 DOWN
   +--> Node 3 DOWN
```

The cluster still has a common rack-level failure domain.

A stronger architecture spreads critical infrastructure across separate racks where possible:

```text
Rack 1              Rack 2              Rack 3
------              ------              ------
Node 1              Node 2              Node 3
Central             Central             Central
```

---

# 7. Availability Zone Failure Domain

In cloud environments, availability zones are common failure domains.

For example:

```text
             Region
                |
       +--------+--------+
       |        |        |
      AZ-1     AZ-2     AZ-3
       |        |        |
      Node     Node     Node
```

Central components can be distributed across zones when supported and appropriate.

Example:

```text
              RHACS Central
                    |
        +-----------+-----------+
        |           |           |
       AZ-1        AZ-2        AZ-3
        |           |           |
      Node A      Node B      Node C
```

If AZ-1 fails:

```text
AZ-1
 X

AZ-2 -> Available
AZ-3 -> Available
```

The remaining infrastructure can continue to provide service, subject to the supported RHACS architecture and quorum/storage requirements.

---

# 8. Data Center Failure Domain

For on-premises environments, a data center can be a major failure domain.

Example:

```text
Data Center 1
|
+-- OpenShift
+-- RHACS Central
+-- Storage
+-- Network


Data Center 2
|
+-- DR Infrastructure
```

If all RHACS Central infrastructure is in Data Center 1:

```text
DC1
 |
 X
 |
RHACS Central
```

RHACS may become unavailable even though secured clusters elsewhere remain operational.

---

# 9. Central vs Disaster Recovery

For business-critical environments, distinguish between:

```text
High Availability
```

and:

```text
Disaster Recovery
```

### High Availability

Protects against failures such as:

* Node failure
* Pod failure
* Component failure
* Some infrastructure failures

### Disaster Recovery

Protects against larger failures such as:

* Data center loss
* Region loss
* Major storage failure
* Catastrophic infrastructure failure

Conceptually:

```text
High Availability
-----------------

        RHACS Central
        /     |     \
     Node A Node B Node C


Disaster Recovery
-----------------

Primary Site          DR Site
     |                   |
Central                Recovery
```

These solve different problems.

---

# 10. Storage Is a Failure Domain

Storage is often overlooked.

Consider:

```text
Central
  |
  v
Storage Array
  |
  X
Storage Failure
```

Even if Central components are distributed across nodes, a shared storage failure can affect the entire service.

Therefore, storage architecture should be evaluated separately.

Questions include:

* Where is RHACS data stored?
* Is the storage highly available?
* What happens if the storage backend fails?
* Are backups available?
* Where are backups stored?
* Can the data be restored in another failure domain?

---

# 11. Network Failure Domain

Network infrastructure can also create a shared failure domain.

For example:

```text
Central Nodes
   |   |   |
   +---+---+
       |
 Network Switch
       |
       X
       |
   Network Failure
```

All Central nodes may become unreachable even though the nodes themselves are healthy.

A resilient design considers:

* Multiple network paths
* Redundant switches
* Load balancers
* DNS
* Firewall redundancy
* Network segmentation

---

# 12. Load Balancer Failure Domain

If RHACS Central is accessed through a load balancer:

```text
Clients
   |
   v
Load Balancer
   |
   v
RHACS Central
```

The load balancer itself can become a failure domain.

If it fails:

```text
Clients
   |
   X
Load Balancer
   |
Central
```

Therefore, production architecture should consider whether the load-balancing layer itself is redundant.

---

# 13. DNS Failure Domain

DNS is another common hidden dependency.

Example:

```text
Sensor
  |
  v
rhacs-central.example.com
  |
  v
DNS
  |
  X
DNS Failure
```

Even if Central is healthy:

```text
Central = UP
DNS     = DOWN
```

Sensors may be unable to resolve the Central endpoint.

Therefore, DNS should be treated as part of the RHACS availability architecture.

---

# 14. Certificate/PKI Failure Domain

Certificates can create another dependency.

For example:

```text
Sensor
   |
   v
TLS
   |
   v
Certificate / CA
   |
   X
Certificate expired
```

Central may be running, but communication can fail.

A production design should consider:

* CA availability
* Certificate expiration
* Certificate rotation
* Trust distribution
* Internal PKI failure

---

# 15. Firewall Failure Domain

Security controls can also become availability dependencies.

Example:

```text
Sensor
   |
   v
Firewall
   |
   X
Firewall failure
   |
Central
```

The RHACS platform may be healthy, but connectivity is unavailable.

For enterprise environments, network security infrastructure should be designed with appropriate redundancy.

---

# 16. Failure Domain Dependency Chain

A useful way to analyze RHACS Central is:

```text
                 RHACS Central
                      |
       +--------------+--------------+
       |              |              |
    Compute         Storage        Network
       |              |              |
      Node           SAN          Switch
       |              |              |
       +--------------+--------------+
                      |
                    DNS
                      |
                    PKI
                      |
                 Load Balancer
```

Every dependency can become a failure domain.

---

# 17. Centralized Security Creates a Blast Radius

Suppose one Central manages:

```text
Central
 |
 +-- Production Cluster 1
 +-- Production Cluster 2
 +-- Production Cluster 3
 +-- Development Cluster 1
 +-- DR Cluster 1
```

If Central fails, the impact potentially affects the security-management plane for all these clusters.

This is called a **large blast radius**.

Therefore:

> The more secured clusters a Central instance manages, the more important Central availability becomes.

---

# 18. Single Central vs Multiple Central Instances

An organization may consider:

```text
Model A
-------
One Central
   |
Many clusters
```

versus:

```text
Model B
-------
Central A
   |
Production clusters

Central B
   |
Restricted clusters
```

### Single Central

Advantages:

* Centralized visibility
* Easier policy management
* Lower operational complexity

Disadvantages:

* Larger blast radius
* Central becomes a critical dependency

### Multiple Central Environments

Advantages:

* Smaller failure domains
* Isolation between environments
* Independent security domains

Disadvantages:

* More infrastructure
* More administration
* More upgrades
* More policy management
* More reporting complexity

The correct architecture depends on organizational requirements and supported RHACS deployment patterns.

---

# 19. Production vs Development Failure Domains

A practical enterprise design may separate security environments:

```text
                    Security Platform
                          |
              +-----------+-----------+
              |                       |
              v                       v
        Production RHACS        Non-Prod RHACS
              |                       |
        +-----+-----+           +-----+-----+
        |           |           |           |
       PROD-1      PROD-2      DEV-1       QA-1
```

This reduces the impact of non-production changes or failures on production security operations.

However, separate Central environments increase operational overhead.

---

# 20. Disconnected Environment Failure Domain

Disconnected clusters introduce additional failure boundaries.

For example:

```text
Corporate Network
|
+-- RHACS Central
|
+-- Firewall
     |
     X
     |
Restricted Network
|
+-- Cluster A
+-- Cluster B
```

The firewall/network boundary becomes a failure domain.

If it fails:

```text
Cluster A ----\
               X ---- RHACS Central
Cluster B ----/
```

Both clusters may lose connectivity to Central.

---

# 21. Regional Failure Domains

Global organizations may have:

```text
Region India
|
+-- Central India
+-- Production clusters


Region Europe
|
+-- Central Europe
+-- Production clusters


Region US
|
+-- Central US
+-- Production clusters
```

This reduces the impact of a regional failure.

However, it also creates multiple security-management domains.

The organization must decide whether regional isolation is worth the operational complexity.

---

# 22. Failure Domain Matrix

A useful planning tool is:

| Failure Domain    | Example Failure       | Potential Impact              | Design Response                       |
| ----------------- | --------------------- | ----------------------------- | ------------------------------------- |
| Pod               | Central pod crashes   | Temporary Central disruption  | Controller restarts                   |
| Node              | OpenShift node fails  | Central component unavailable | Spread components                     |
| Rack              | Rack loses power      | Multiple nodes unavailable    | Rack-aware placement                  |
| Storage           | Storage backend fails | Data/service impact           | Resilient storage + backup            |
| Network           | Switch failure        | Connectivity loss             | Network redundancy                    |
| Load Balancer     | LB failure            | Central endpoint unavailable  | HA load balancing                     |
| DNS               | DNS outage            | Endpoint resolution failure   | DNS redundancy                        |
| PKI               | CA/certificate issue  | TLS communication failure     | Certificate lifecycle                 |
| Availability Zone | AZ outage             | Multiple nodes unavailable    | Multi-AZ design where supported       |
| Data Center       | Site failure          | RHACS unavailable             | DR architecture                       |
| Region            | Regional outage       | Regional RHACS unavailable    | Multi-region strategy where justified |

# 23. Failure Domain vs Blast Radius

These concepts are related but different.

### Failure Domain

Where a failure can happen together.

```text
Rack
|
+-- Node 1
+-- Node 2
+-- Node 3
```

### Blast Radius

How much of the system is affected.

```text
Central
 |
 +-- Cluster A
 +-- Cluster B
 +-- Cluster C
```

If Central fails:

```text
Central
  X
  |
  +-- A affected
  +-- B affected
  +-- C affected
```

The blast radius is large even if the original failure is small.

---

# 24. Failure Domain Design Principle

A good principle is:

> **Do not place all critical RHACS dependencies inside the same failure domain.**

For example, avoid:

```text
Rack 1
|
+-- All Central nodes
+-- Storage
+-- DNS
+-- Load Balancer
+-- Network switch
```

A rack failure would potentially affect everything.

Instead:

```text
Rack 1              Rack 2              Rack 3
------              ------              ------
Central             Central             Central
Network             Network             Network
```

with appropriately redundant shared services.

# 25. Failure Domain and OpenShift Scheduling

In OpenShift, workload placement can be influenced using scheduling mechanisms such as:

* Node labels
* Node affinity
* Pod anti-affinity
* Topology constraints
* Taints and tolerations

Conceptually:

```text
Central
 |
 +--> Node 1 / Rack A
 |
 +--> Node 2 / Rack B
 |
 +--> Node 3 / Rack C
```

The goal is to prevent critical replicas from being concentrated in one failure domain.

The exact RHACS-supported deployment configuration should always be followed.

---

# 26. Central Availability Is More Than Pod Replicas

A common misconception is:

```text
3 Central Pods = HA
```

This is incomplete.

You must consider:

```text
             RHACS Central
                  |
       +----------+----------+
       |          |          |
     Compute    Storage    Network
       |          |          |
      HA         HA         HA
```

Three application replicas cannot protect against a shared storage, network, rack, or data-center failure.

Therefore:

> **High availability must be designed across dependencies, not just replicas.**

---

# 27. Central and Secured Cluster Failure Independence

Consider:

```text
                 RHACS Central
                      |
       +--------------+--------------+
       |              |              |
   Cluster A       Cluster B       Cluster C
```

Ideally:

```text
Cluster A failure
       |
       X
       |
Cluster B = Healthy
Cluster C = Healthy
Central    = Healthy
```

A single application cluster failure should not bring down Central or other secured clusters.

Similarly:

```text
Cluster B failure
       |
       X
       |
Central remains available
```

This is a key benefit of separating failure domains.

---

# 28. Central Failure Should Be Contained

A well-designed architecture tries to contain Central failures.

For example:

```text
Central Component Failure
          |
          v
       Recovery
          |
          v
Other secured clusters remain operational
```

The exact security behavior during Central connectivity loss depends on the RHACS components and configured enforcement mechanisms.

Therefore, organizations should test the failure behavior rather than assuming that all security functions behave identically during a Central outage.

# 31. SLO and RTO/RPO

Failure-domain planning should be connected to business requirements.

### SLO

# 33. Backup Is Not the Same as HA

This distinction is important.

### HA

Protects against:

```text
Node failure
Pod failure
Some infrastructure failures
```

### Backup

Protects against:

```text
Data loss
Configuration loss
Disaster recovery scenarios
```

For example:

```text
3 Central replicas
+
No backup
```

is not a complete disaster-recovery strategy.

Similarly:

```text
Excellent backup
+
Single Central node
```

does not provide high availability.

You need both when business requirements demand both.

# 40. Common Mistakes

## Mistake 1 — Assuming Three Pods Means Full HA

```text
3 Pods
   |
Same node/rack/storage
```

This may still represent one failure domain.

---

## Mistake 2 — Ignoring Storage

Central survives node failure but storage fails.

Result:

```text
Central
  |
  v
Storage
  |
  X
```

---

## Mistake 3 — Ignoring DNS

Central is healthy but clients cannot resolve it.

---

## Mistake 4 — Ignoring Network

All Central components are healthy but unreachable.

---

## Mistake 5 — Ignoring Load Balancer

The backend is healthy but the Central endpoint is unavailable.

---

## Mistake 6 — Ignoring Certificates

Expired certificates can break communication.

---

## Mistake 7 — No DR Plan

HA does not protect against every disaster.

# 43. Interview Answer

A strong interview answer is:

> "Failure domains are important when designing RHACS Central because Central becomes a shared security-management dependency for multiple secured clusters. I would first identify the failure domains around compute, storage, network, DNS, load balancing, racks, availability zones, and data centers. Then I would ensure that critical Central components and their dependencies are not unnecessarily concentrated in one failure domain. For production, I would design appropriate HA, resilient storage, network redundancy, backups, monitoring, and disaster recovery according to the organization's RTO and RPO. I would also distinguish HA from DR: HA protects against smaller infrastructure failures, while DR protects against larger site or regional failures. Finally, I would perform controlled failure testing to validate that the architecture behaves as expected."

# 44. Final Mental Model

Remember RHACS Central as:

```text
                         RHACS CENTRAL
                              |
          +-------------------+-------------------+
          |                   |                   |
       Compute             Storage             Network
          |                   |                   |
      +---+---+           +---+---+           +---+---+
      |       |           |       |           |       |
    Node A  Node B      Store A Store B     Path A  Path B
      |       |           |       |           |       |
      +-------+-----------+-------+-----------+-------+
                              |
                        Secured Clusters
```

And think about failure domains from **smallest to largest**:

```text
Pod
 ↓
Node
 ↓
Rack
 ↓
Availability Zone
 ↓
Data Center
 ↓
Region
```

The design goal is:

> **Do not let a failure at one level unnecessarily become a failure of the entire RHACS security-management plane.**

The most important lesson is:

```text
HA ≠ Just More Pods

Good RHACS HA =
Compute resilience
+ Storage resilience
+ Network resilience
+ DNS resilience
+ Certificate management
+ Load-balancer resilience
+ Backup
+ Disaster Recovery
+ Failure testing
```

For RHACS specifically, always validate the exact HA topology, storage requirements, and recovery behavior against the **supported architecture for the RHACS release you are deploying** rather than assuming that a generic Kubernetes HA pattern applies unchanged.
