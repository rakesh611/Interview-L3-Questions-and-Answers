# How RHACS Protects Build, Deploy, and Runtime Stages

Red Hat Advanced Cluster Security for Kubernetes (**RHACS**) provides security controls across the application lifecycle:

```text
                APPLICATION LIFECYCLE
                       |
        +--------------+--------------+
        |              |              |
        v              v              v
      BUILD          DEPLOY         RUNTIME
        |              |              |
        v              v              v
    Image/CI        Admission       Runtime
    security        control         monitoring
        |              |              |
        v              v              v
      PASS/FAIL     ALLOW/BLOCK    DETECT/ENFORCE
```

The key idea is:

> **Build:** stop known-bad images from progressing.  
> **Deploy:** stop insecure workloads from entering the cluster.  
> **Runtime:** detect and, where appropriate, enforce against dangerous behavior after deployment.

---

# 1. Build Stage

## 1.1 Purpose

The Build stage protects the container image before it is promoted to a registry or deployed to OpenShift.

RHACS can integrate with CI/CD pipelines using the `roxctl` CLI. The pipeline can check an image against RHACS security policies and fail the pipeline when an enforced policy is violated.

Typical build-stage checks include:

- Container image vulnerabilities
- Critical or high-severity CVEs
- Fixable vulnerabilities
- Image registry/source
- Image configuration
- Security-related image criteria
- Other RHACS policy criteria configured for the Build lifecycle

---

## 1.2 Build Flow

```text
Developer
    |
    v
Source Code
    |
    v
CI/CD Pipeline
    |
    v
Build Container Image
    |
    v
Container Image
    |
    v
RHACS / roxctl image check
    |
    v
RHACS Policy Engine
    |
    +----------------------+
    |                      |
   PASS                  VIOLATION
    |                      |
    v                      v
Continue CI            Fail CI Build
    |                      |
    v                      v
Push Image              Fix Issue
to Registry
```

---

## 1.3 Example

A CI pipeline builds:

```text
myregistry.example.com/myapp:v1.2.0
```

The pipeline can use RHACS to check the image:

```bash
roxctl image check \
  --image myregistry.example.com/myapp:v1.2.0
```

If the image violates an enforced Build policy:

```text
RHACS policy violation
        |
        v
roxctl returns failure
        |
        v
CI pipeline fails
        |
        v
Image is not promoted
```

The exact `roxctl` authentication and command options depend on the RHACS release and CI/CD configuration.


This prevents a known vulnerable image from automatically progressing to the next stage.

# 3. Deploy Stage

## 3.1 Purpose

The Deploy stage protects the OpenShift/Kubernetes cluster from insecure workload configurations.

Unlike the Build stage, Deploy policies can evaluate the workload configuration in addition to the image.

Examples include:

- Privileged containers
- Dangerous capabilities
- Host namespaces
- Host filesystem mounts
- Docker/container runtime socket mounts
- Excessive RBAC permissions
- Insecure deployment configurations
- Image vulnerabilities
- Untrusted image registries
- Network exposure
- Service account configuration

---

# 4. Deploy Flow

```text
Developer / CI-CD
       |
       v
oc apply / Deployment
       |
       v
OpenShift API Server
       |
       v
RHACS Admission Controller
       |
       v
RHACS Policy Engine
       |
       +----------------+
       |                |
      PASS           VIOLATION
       |                |
       v                v
    Allow             Reject
       |             Deployment
       v
Workload Created
```

RHACS Admission Controller uses Kubernetes admission mechanisms to evaluate workload requests before they are admitted.

---

# 5. Deploy Policy Example

Consider this workload:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo
spec:
  template:
    spec:
      containers:
        - name: demo
          image: example.com/demo:latest
          securityContext:
            privileged: true
```

Suppose RHACS has this policy:

```text
Policy:
Privileged Container

Lifecycle:
Deploy

Enforcement:
Enabled
```

The request flows through:

```text
oc apply
   |
   v
OpenShift API Server
   |
   v
RHACS Admission Controller
   |
   v
Policy Evaluation
   |
   v
privileged = true
   |
   v
POLICY VIOLATION
   |
   v
Deployment rejected
```

The insecure workload is blocked before it can be admitted normally.

# 6. Hard and Soft Deploy Enforcement

RHACS can enforce Deploy policies in different ways.

## 6.1 Admission Controller Enforcement

The Admission Controller can reject a workload request when an enforced policy is violated.

```text
Deployment Request
       |
       v
Admission Controller
       |
       v
Policy Violation
       |
       v
API Request Rejected
```

This is the strongest preventive control because the workload is stopped at admission.

---

## 6.2 Sensor Enforcement

RHACS Sensor can also enforce certain Deploy policies.

The flow can be:

```text
Workload Created
       |
       v
Sensor Detects Violation
       |
       v
Policy Enforcement
       |
       v
Workload Scaled Down
       |
       v
Replicas = 0
```

Use the enforcement method appropriate to the policy and RHACS version.

---

# 7. Runtime Stage

## 7.1 Purpose

Build and Deploy security do not completely protect a running application.

A workload can behave unexpectedly after it has been deployed.

Examples:

```text
Unexpected process starts
Unexpected network connection
Suspicious container activity
Unauthorized Kubernetes operation
Unexpected use of exec
Unexpected port-forward activity
Sensitive resource access
```

RHACS provides continuous runtime monitoring and policy evaluation for supported runtime activity.

---

# 12. What Happens When a New CVE Is Discovered?

An important feature of lifecycle security is that the security state of an image can change after it was originally built.

Example:

```text
Day 1
   |
   v
Image built
   |
   v
No known critical CVE
   |
   v
Build passes
   |
   v
Application deployed
```

Later:

```text
Day 10
   |
   v
New CVE published
   |
   v
RHACS vulnerability data updated
   |
   v
Existing image now matches a vulnerability policy
   |
   v
RHACS identifies increased risk
```

Depending on the configured policy and lifecycle, RHACS can alert or enforce when the vulnerable image is evaluated.

This is why runtime and continuous vulnerability visibility are important even when the original CI build passed.

---

# 13. Build vs Deploy vs Runtime

| Stage | Main Security Question | RHACS Mechanism | Example |
|---|---|---|---|
| Build | Is the image safe to promote? | `roxctl` + Build policies | Critical CVE |
| Deploy | Is this workload safe to admit? | Admission Controller / Sensor | Privileged container |
| Runtime | Is the workload behaving safely? | Sensor + Runtime policies | Unexpected process |
| Runtime Audit | Is someone performing a sensitive Kubernetes action? | Audit logs + Runtime policies | Secret access |

# 15. Defense-in-Depth

The three stages provide multiple security gates:

```text
                 DEFENSE IN DEPTH

                       BUILD
                         |
                         v
              Stop vulnerable images
                         |
                         v
                      DEPLOY
                         |
                         v
             Stop insecure workloads
                         |
                         v
                     RUNTIME
                         |
                         v
             Detect suspicious behavior
                         |
                         v
                      RESPONSE
```

Instead of relying on a single container scan, RHACS continuously applies security controls throughout the application lifecycle.

---

# 16. Recommended Lifecycle Strategy

A practical RHACS security strategy is:

```text
BUILD
 |
 +-- Block critical/fixable vulnerabilities
 +-- Restrict trusted image registries
 +-- Check image security criteria
 |
 v
DEPLOY
 |
 +-- Block privileged containers
 +-- Block dangerous capabilities
 +-- Block dangerous host mounts
 +-- Restrict excessive RBAC permissions
 +-- Block vulnerable images
 +-- Enforce workload security configuration
 |
 v
RUNTIME
 |
 +-- Monitor process activity
 +-- Monitor network activity
 +-- Monitor Kubernetes activity
 +-- Monitor exec / port-forward activity
 +-- Monitor sensitive API operations
 +-- Detect unexpected behavior
 +-- Enforce selected high-confidence runtime policies
```

# 17. Simple Explanation

RHACS can be remembered with three questions:

```text
BUILD
"Should we allow this image to move forward?"
        |
        v
    Image security


DEPLOY
"Should we allow this workload into the cluster?"
        |
        v
    Workload security


RUNTIME
"Is this running workload behaving as expected?"
        |
        v
    Runtime security
```

Therefore:

> **Build = Prevent.**  
> **Deploy = Prevent.**  
> **Runtime = Detect and Respond.**

Together, these controls create a continuous security loop across the application lifecycle.

# 18. Example End-to-End Scenario

Consider an application called:

```text
payments-api
```

## Step 1 — Build

The developer builds:

```text
payments-api:v1.0
```

RHACS detects a critical fixable vulnerability.

```text
Build Policy
     |
     v
Critical CVE
     |
     v
CI pipeline fails
```

The image is fixed before deployment.

---

## Step 2 — Deploy

The fixed image is deployed, but the Kubernetes manifest contains:

```yaml
securityContext:
  privileged: true
```

RHACS Deploy policy detects the violation:

```text
Admission Controller
        |
        v
Privileged container
        |
        v
Deployment blocked
```

The manifest is corrected.

---

## Step 3 — Runtime

The corrected application is deployed successfully.

Later, an unexpected shell process starts inside the container:

```text
/bin/bash
```

RHACS runtime monitoring detects the behavior:

```text
Runtime Activity
       |
       v
Unexpected Process
       |
       v
Runtime Policy
       |
       v
Alert / Enforcement
```

This demonstrates the value of protecting all three lifecycle stages.

# 19. Final Summary

RHACS provides lifecycle security by combining:

```text
+------------------------------------------------+
|                    RHACS                       |
+------------------------------------------------+
|                                                |
|  BUILD                                         |
|  - Image scanning                              |
|  - Vulnerability policies                      |
|  - roxctl / CI integration                     |
|  - Fail insecure builds                        |
|                                                |
|  DEPLOY                                        |
|  - Admission Controller                        |
|  - Deployment policies                         |
|  - Image + workload configuration checks       |
|  - Block insecure deployments                  |
|                                                |
|  RUNTIME                                       |
|  - Process monitoring                           |
|  - Network/activity monitoring                  |
|  - Kubernetes audit monitoring                  |
|  - Runtime policies                             |
|  - Alert and selected enforcement               |
|                                                |
+------------------------------------------------+
```

The overall security model is:

```text
             BUILD
               |
       "Is the image safe?"
               |
               v
             DEPLOY
               |
       "Is the workload safe?"
               |
               v
            RUNTIME
               |
      "Is it behaving safely?"
               |
               v
        DETECT / RESPOND
```

**Bottom line:** RHACS does not treat container security as a one-time image scan. It extends security from **CI/CD build checks**, through **OpenShift admission and deployment controls**, into **continuous runtime monitoring and response**.
