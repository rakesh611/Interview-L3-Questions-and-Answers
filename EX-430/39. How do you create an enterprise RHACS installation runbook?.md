# Enterprise RHACS Installation Runbook

## 1. Purpose

This runbook provides a standardized procedure for planning, installing, validating, securing, and handing over Red Hat Advanced Cluster Security for Kubernetes (RHACS) in an enterprise OpenShift environment.

It covers:

* Architecture and prerequisites
* RHACS Operator installation
* Central deployment
* Secured Cluster deployment
* TLS and certificate management
* Registry and disconnected environments
* Storage and availability
* Proxy configuration
* Network requirements
* Validation
* Troubleshooting
* Backup and recovery considerations
* Operational handover

---

## 2. Scope

This runbook applies to enterprise RHACS deployments where:

* OpenShift is the primary Kubernetes platform.
* RHACS Central is deployed on a dedicated management cluster or selected OpenShift cluster.
* One or more OpenShift/Kubernetes clusters are secured by RHACS.
* Enterprise DNS, certificates, registries, proxies, identity providers, and monitoring are used.
* Production security and operational controls are required.

The exact RHACS version, OpenShift version, Operator channel, storage class, and supported topology must be validated against the Red Hat support matrix before implementation.

---

## 3. Enterprise Architecture

A typical architecture consists of:

```text
                         Enterprise Users
                               |
                    +----------+----------+
                    |                     |
                SSO / LDAP             API Clients
                    |                     |
                    +----------+----------+
                               |
                         RHACS Central
                               |
              +----------------+----------------+
              |                |                |
        Central DB/API     Sensor/Collector   Admission
              |                |                |
              |        +-------+-------+        |
              |        |               |        |
              |    Cluster A       Cluster B    |
              |    Sensor           Sensor      |
              |        |               |        |
              +--------+---------------+--------+
                       |
              OpenShift / Kubernetes
                 Secured Clusters
```

### Major RHACS components

| Component            | Responsibility                                          |
| -------------------- | ------------------------------------------------------- |
| Central              | RHACS management plane and API                          |
| Central DB           | Persistent RHACS data                                   |
| Sensor               | Communicates with Central and monitors secured clusters |
| Collector            | Runtime/container-level security data collection        |
| Admission Controller | Admission-time security enforcement                     |
| Scanner              | Image vulnerability scanning                            |
| Operator             | Lifecycle management of RHACS components                |

# 12. TLS and Certificates

Production deployments should use enterprise-approved certificates where required.

Validate:

* Certificate CN/SAN
* Certificate expiration
* Issuing CA
* Intermediate CA
* TLS protocol
* Trust chain
* Corporate proxy inspection requirements

Check certificate:

```bash
openssl s_client \
  -connect central-rhacs.apps.example.com:443 \
  -servername central-rhacs.apps.example.com </dev/null
```

Display certificate:

```bash
openssl x509 -noout -subject -issuer -dates
```

Document certificate ownership and renewal responsibility.

# 17. Secured Cluster Installation

Each Kubernetes/OpenShift cluster that needs RHACS protection must be registered with Central.

Example architecture:

```text
RHACS Central
     |
     +---- prod-ocp01
     |
     +---- prod-ocp02
     |
     +---- dev-ocp01
     |
     +---- qa-ocp01
```

For each cluster:

1. Register cluster with Central.
2. Generate secured-cluster deployment configuration.
3. Apply Sensor configuration.
4. Deploy Sensor.
5. Deploy Collector.
6. Deploy Admission Controller if required.
7. Validate registration.
8. Validate data flow.
9. Validate policies.
