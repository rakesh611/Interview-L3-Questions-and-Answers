# How Do Custom Certificate Authorities Affect RHACS Central Installation?

Custom Certificate Authorities (CAs) affect RHACS installation whenever RHACS components must establish TLS connections to services that use certificates signed by an internal or private CA.

This is common in corporate environments where organizations use an internal PKI instead of publicly trusted certificates.

## 1. Why Custom CAs Matter

RHACS components communicate with several external and internal services over TLS, for example:

* RHACS Central
* Secured Clusters
* OpenShift API servers
* Image registries
* LDAP/LDAPS servers
* Proxy servers
* Cloud or object-storage endpoints
* Private container registries
* Webhook endpoints

If a remote service presents a certificate signed by a CA that the RHACS component does not trust, TLS verification can fail.

Typical symptoms include:

```text
x509: certificate signed by unknown authority
```

or:

```text
certificate verification failed
```

Therefore, the CA certificate must be made available to the appropriate RHACS component.

---

## 2. Custom CA vs RHACS Server Certificate

A custom CA and a server certificate are not the same thing.

### Custom CA

The CA certificate establishes trust:

```text
Corporate Root CA
       |
       +---- LDAP Server Certificate
       |
       +---- Registry Certificate
       |
       +---- Proxy Certificate
```

RHACS needs the CA certificate when it must verify those server certificates.

### Server Certificate

A server certificate identifies a specific endpoint:

```text
registry.example.com
ldap.example.com
central.example.com
```

The server certificate is normally signed by the corporate CA.

---

## 3. When RHACS Needs the Custom CA

Common scenarios include:

### Internal Container Registry

For example:

```text
registry.example.com
```

If the registry certificate is signed by:

```text
Corporate-Root-CA
```

RHACS must trust that CA to communicate securely with the registry.

### LDAPS

For example:

```text
ldaps://ldap.example.com:636
```

If LDAP uses an internally signed certificate, RHACS must trust the LDAP CA.

### HTTPS Proxy

A corporate TLS-inspecting proxy may re-sign HTTPS traffic using an internal CA.

RHACS components must trust that CA.

### Private Webhook

If RHACS sends notifications to an HTTPS endpoint using an internally signed certificate, the appropriate CA may also be required.

---

## 4. CA Trust Is Component-Specific

A common mistake is assuming that installing a CA on the OpenShift worker node automatically makes RHACS trust it.

It does not necessarily work that way.

RHACS components run in containers and have their own trust configuration.

For example:

```text
OpenShift Node
      |
      +-- Host CA trust
      |
      +-- RHACS Central container
      |      |
      |      +-- RHACS CA trust
      |
      +-- Scanner container
      |
      +-- Admission components
```

Therefore, determine **which RHACS component is making the TLS connection** and configure trust for that component.

---

## 5. Custom CA During Installation

Before installing RHACS, identify all private PKI dependencies.

A corporate installation may look like:

```text
OpenShift
   |
   +-- RHACS Operator
   |
   +-- Central
   |
   +-- Scanner
   |
   +-- Secured Clusters
   |
   +-- Internal Registry
   |
   +-- LDAP/LDAPS
   |
   +-- Corporate Proxy
```

Create a dependency list:

| Dependency        | TLS |        Private CA |
| ----------------- | --: | ----------------: |
| OpenShift API     | Yes |         Sometimes |
| Internal Registry | Yes |            Common |
| LDAPS             | Yes |            Common |
| Proxy             | Yes |            Common |
| Webhook           | Yes |          Possible |
| Public Internet   | Yes | Usually public CA |

This should be completed before troubleshooting RHACS installation.

---

## 6. CA Certificate Format

The CA should normally be provided as PEM-encoded X.509 certificate data.

Example:

```text
-----BEGIN CERTIFICATE-----
MIID...
...
-----END CERTIFICATE-----
```

A CA bundle may contain multiple certificates:

```text
-----BEGIN CERTIFICATE-----
Corporate Root CA
-----END CERTIFICATE-----

-----BEGIN CERTIFICATE-----
Corporate Intermediate CA
-----END CERTIFICATE-----
```

If the server certificate is signed through an intermediate CA, make sure the required certificate chain is trusted.

---

## 7. OpenShift CA ConfigMap

OpenShift commonly uses ConfigMaps in `openshift-config` for CA trust used by platform components.

For example:

```bash
oc create configmap corporate-ca \
  --from-file=ca-bundle.crt=/path/to/corporate-ca.crt \
  -n openshift-config
```

Verify:

```bash
oc get configmap corporate-ca -n openshift-config
```

However, **do not assume that adding a CA to `openshift-config` automatically configures RHACS**.

RHACS-specific configuration must still be followed for the component that needs the CA.

## 8. Example: RHACS and an Internal Registry

Suppose the registry is:

```text
registry.example.com
```

and its certificate chain is:

```text
registry.example.com
        |
        v
Corporate Intermediate CA
        |
        v
Corporate Root CA
```

Without the appropriate CA trust, RHACS may report:

```text
x509: certificate signed by unknown authority
```

The troubleshooting process should be:

```text
1. Identify the failing RHACS component
2. Identify the registry endpoint
3. Inspect the registry certificate
4. Identify the issuing CA
5. Provide the CA to the required RHACS component
6. Restart/reconcile if required
7. Test the connection again
```

---

## 9. Example: RHACS and LDAPS

For:

```text
ldaps://ldap.example.com:636
```

test the certificate chain from a suitable environment:

```bash
openssl s_client \
  -connect ldap.example.com:636 \
  -showcerts
```

Look for:

```text
Verify return code: 0 (ok)
```

If the certificate is signed by a private CA and RHACS does not trust that CA, authentication may fail even though:

```text
DNS works
TCP/636 works
LDAP server is running
```

The problem is then TLS trust rather than LDAP credentials.

---

## 10. Custom CA and Proxies

Corporate environments frequently use an HTTPS proxy.

Example:

```text
RHACS
  |
  v
HTTPS Proxy
  |
  v
Internet / Registry
```

A TLS-inspecting proxy can replace the original certificate with one signed by:

```text
Corporate TLS Inspection CA
```

Therefore RHACS must trust that CA.

Without it, errors may appear as:

```text
x509: certificate signed by unknown authority
```

or:

```text
TLS handshake failed
```

Proxy configuration and CA trust should therefore be treated as two separate requirements:

```text
Proxy configuration
        +
Proxy CA trust
        =
Successful HTTPS connection
```

---

## 11. Certificate Chain Problems

A CA problem is not always caused by a missing root CA.

The server may provide an incomplete certificate chain.

For example:

```text
Server Certificate
       |
       v
Intermediate CA
       |
       v
Root CA
```

The server should normally provide the necessary intermediate certificates.

Check with:

```bash
openssl s_client \
  -connect registry.example.com:443 \
  -showcerts
```

An incomplete chain can produce certificate validation errors even when the root CA exists.

---

## 12. CA Rotation

Corporate PKIs periodically replace certificates.

For example:

```text
Old Root CA
     |
     v
Old Registry Certificate
```

may become:

```text
New Root CA
     |
     v
New Registry Certificate
```

RHACS must continue trusting the new CA.

During CA migration, organizations may temporarily use a bundle:

```text
Old Root CA
New Root CA
```

This allows services to transition without immediately breaking TLS connectivity.

---

## 13. Security Considerations

Never solve a CA problem by disabling TLS verification unless there is a controlled and documented reason.

Avoid approaches such as:

```text
skip certificate verification
```

or:

```text
insecure TLS
```

These weaken security and can allow man-in-the-middle attacks.

The preferred approach is:

```text
Correct server certificate
        +
Correct certificate chain
        +
Correct trusted CA
        =
Secure TLS validation
```

## 14. Troubleshooting Workflow

When RHACS reports a TLS or certificate error, follow this sequence.

### Step 1: Identify the failing component

Check RHACS pods:

```bash
oc get pods -n stackrox
```

Check logs:

```bash
oc logs <pod> -n stackrox
```

Look for:

```text
x509
certificate
TLS
unknown authority
handshake
```

### Step 2: Identify the destination

Determine whether the connection is going to:

```text
LDAP
Registry
Proxy
Webhook
OpenShift API
Other HTTPS service
```

### Step 3: Validate DNS

```bash
oc run dns-test \
  --rm -it \
  --image=registry.access.redhat.com/ubi9/ubi-minimal \
  -- getent hosts registry.example.com
```

### Step 4: Validate TCP connectivity

For example:

```bash
nc -vz registry.example.com 443
```

### Step 5: Inspect the certificate

```bash
openssl s_client \
  -connect registry.example.com:443 \
  -showcerts
```

### Step 6: Identify the CA

Determine:

```text
Issuer
Subject
Root CA
Intermediate CA
Validity dates
SAN
```

### Step 7: Verify RHACS trust configuration

Confirm that the required CA is configured for the RHACS component making the connection.

### Step 8: Allow Operator reconciliation

After changing the relevant RHACS configuration, allow the Operator to reconcile the deployment.

Check:

```bash
oc get pods -n stackrox
```

and:

```bash
oc get central -n stackrox
```

### Step 9: Re-test

Verify the original operation again.

## 16. Corporate Installation Best Practice

For a production RHACS deployment, document the certificate architecture before installation.

Example:

```text
Corporate PKI
     |
     +-- Root CA
     |
     +-- Intermediate CA
            |
            +-- Registry
            +-- LDAP
            +-- Proxy
            +-- Webhooks
```

Maintain:

* Root CA certificates
* Intermediate CA certificates
* Certificate expiration dates
* Certificate owners
* Renewal procedures
* RHACS trust configuration
* Proxy configuration
* Registry configuration
* LDAP/LDAPS configuration

This makes certificate rotation and troubleshooting much easier.

---

## 17. Important Interview Point

**Question:** Why can RHACS installation or operation fail when an internal CA is used?

**Answer:**

> RHACS components must trust the CA that signed the certificates of services they communicate with. In corporate environments, private registries, LDAPS servers, proxies, and other HTTPS endpoints may use certificates signed by an internal CA. If that CA is not trusted by the RHACS component making the connection, TLS validation fails with errors such as `x509: certificate signed by unknown authority`. The correct solution is to configure the appropriate RHACS component with the corporate CA or CA bundle rather than disabling certificate verification.

---

## 18. Key Takeaways

```text
Custom CA
   |
   +-- Required for private PKI endpoints
   |
   +-- Must be trusted by the component making the connection
   |
   +-- Does not automatically become trusted everywhere
   |
   +-- Must include the appropriate CA chain
   |
   +-- Important for Registry / LDAPS / Proxy / HTTPS services
   |
   +-- Must be considered during installation planning
   |
   +-- Should be rotated before certificates expire
```

The main rule is:

> **If an RHACS component connects to a TLS endpoint whose certificate is signed by a private CA, that component must have a trust path to the required CA.**
