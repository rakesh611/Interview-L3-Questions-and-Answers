# How Do You Create an RHACS Central Custom Resource?

## 1. Overview

After installing the **RHACS Operator**, the next step is to create a **Central custom resource (CR)**.

The Central CR tells the RHACS Operator:

> **I want an RHACS Central instance with this configuration.**

The Operator then reconciles the CR and creates the required RHACS Central components.

The overall workflow is:

```text
RHACS Operator
      │
      ▼
Central Custom Resource
      │
      ▼
RHACS Operator reconciliation
      │
      ▼
RHACS Central components
      │
      ▼
RHACS UI/API
```

A typical namespace arrangement is:

```text
rhacs-operator
└── RHACS Operator

stackrox
└── RHACS Central
```

---

# 2. Prerequisites

Before creating the Central CR, verify:

* OpenShift cluster is healthy.
* RHACS Operator is installed.
* RHACS Operator CSV is `Succeeded`.
* RHACS Operator pod is `Running`.
* The required RHACS CRDs are installed.
* You have sufficient cluster permissions.
* Storage is available if the Central configuration requires persistent storage.
* DNS and networking are correctly configured.
* You have selected the RHACS version/channel appropriate for your environment.

Check the Operator:

```bash
oc get csv -n rhacs-operator
```

Expected:

```text
NAME                         DISPLAY
rhacs-operator.v4.x.x        Red Hat Advanced Cluster Security ...
```

Check the phase:

```bash
oc get csv -n rhacs-operator \
  -o jsonpath='{.items[*].status.phase}{"\n"}'
```

Expected:

```text
Succeeded
```

---

# 3. Verify the Central CRD

Before creating a Central CR, verify that the RHACS Operator has installed the Central API.

Run:

```bash
oc api-resources | grep -i central
```

You can also check CRDs:

```bash
oc get crd | grep -i stackrox
```

Depending on the RHACS version, the exact CRD names and API versions can differ.

The important point is that the RHACS Operator must have installed the `Central` custom resource definition before you create a Central object.

---

# 4. Understand the Central Custom Resource

A Custom Resource is a Kubernetes API object that represents the desired state of an application managed by an Operator.

Conceptually:

```text
Central CR
    │
    ├── Name
    ├── Namespace
    ├── Central configuration
    ├── Exposure configuration
    ├── Persistence configuration
    └── Resource configuration
```

The RHACS Operator watches the Central CR.

When you create or modify it:

```text
Central CR changed
      │
      ▼
RHACS Operator detects change
      │
      ▼
Operator reconciles desired state
      │
      ▼
RHACS resources created/updated
```

RHACS Central is commonly deployed in:

```text
stackrox
```

Create it if required by your installation workflow:

```bash
oc create namespace stackrox
```

Verify:

```bash
oc get namespace stackrox
```

Expected:

```text
NAME       STATUS   AGE
stackrox   Active   ...
```

> Follow the RHACS version-specific installation workflow if the Operator is expected to create/manage the Central namespace as part of the deployment.

# 6. Basic Central CR

The exact Central CR schema depends on the RHACS version.

A minimal conceptual example is:

```yaml
apiVersion: platform.stackrox.io/v1alpha1
kind: Central
metadata:
  name: central
  namespace: stackrox
spec: {}
```

Save it as:

```text
central.yaml
```

The important fields are:

```yaml
apiVersion: platform.stackrox.io/v1alpha1
kind: Central
metadata:
  name: central
  namespace: stackrox
spec: {}
```

> **Important:** RHACS APIs and fields can change between releases. Always verify the schema exposed by the Operator installed in your cluster before applying a production manifest.

---

# 7. Inspect the Supported Central Schema

You can inspect the installed CRD:

```bash
oc explain central
```

For the specification:

```bash
oc explain central.spec
```

You can also inspect the CRD directly:

```bash
oc get crd central.platform.stackrox.io -o yaml
```

If the CRD name differs in your installed RHACS version, identify it first:

```bash
oc get crd | grep -i central
```

This is one of the safest ways to determine which fields are supported by the installed Operator.

---

# 8. Create the Central CR Using YAML

Create a file:

```bash
vi central.yaml
```

Example:

```yaml
apiVersion: platform.stackrox.io/v1alpha1
kind: Central
metadata:
  name: central
  namespace: stackrox
spec: {}
```

Apply it:

```bash
oc apply -f central.yaml
```

Expected:

```text
central.platform.stackrox.io/central created
```

---


Example:

```text
NAME      AGE
```

```bash
  -n stackrox \
```

# 10. Watch the Operator Reconcile the CR

After creating the Central CR, monitor the RHACS Operator:

```bash
oc get pods -n rhacs-operator
```

Then monitor Central:

```bash
watch oc get pods -n stackrox
```

Initially, you may see resources being created.

For example:

```text
NAME                         READY   STATUS
central-xxxxx-xxxxx          0/1     ContainerCreating
```

Eventually:

```text
NAME                         READY   STATUS
central-xxxxx-xxxxx          1/1     Running
```

The exact resource names depend on the RHACS version and configuration.

# 14. Configure Central Exposure

Central needs a way for administrators and clients to access the RHACS API/UI.

Depending on your RHACS version and deployment design, Central can be exposed using the supported RHACS configuration.

Conceptually:

```text
                    RHACS Central
                         │
                         ▼
                    Service/API
                         │
              ┌──────────┴──────────┐
              │                     │
              ▼                     ▼
          OpenShift Route       Load Balancer
              │                     │
              └──────────┬──────────┘
                         ▼
                     RHACS UI
```

Do not copy an exposure configuration from another RHACS version without checking the CRD schema installed in your cluster.

Use:

```bash
oc explain central.spec
```

and the RHACS documentation for your installed release to determine the supported configuration.

---

# 15. Configure Persistent Storage

Central is a stateful RHACS component, so storage planning is important.

First check available StorageClasses:

```bash
oc get storageclass
```

Example:

```text
NAME                     PROVISIONER
lvms-vg1                 topolvm.io
ocs-storagecluster-ceph-rbd   ...
```

The exact storage configuration should be selected according to your RHACS version and infrastructure.

Check PVCs after Central deployment:

```bash
oc get pvc -n stackrox
```

If a PVC is stuck:

```bash
oc describe pvc <pvc-name> \
  -n stackrox
```

Typical problems include:

```text
No StorageClass
Insufficient storage
CSI failure
Topology constraints
Provisioning failure
```

---

# 16. Configure Resource Requests and Limits

Production environments should plan resource requirements for Central.

Conceptually:

```yaml
spec:
  central:
    resources:
      requests:
        cpu: ...
        memory: ...
      limits:
        cpu: ...
        memory: ...
```

However, **do not use arbitrary resource values in production**.

Use the resource fields supported by your RHACS version:

```bash
oc explain central.spec --recursive
```

and follow the RHACS sizing guidance for your deployment.

---

# 17. Use `oc explain` Before Editing the CR

This is one of the most useful RHACS administration techniques.

Start with:

```bash
oc explain central.spec
```

If a field is available:

```bash
oc explain central.spec.<field>
```

For a complete schema:

```bash
oc explain central.spec --recursive
```

This helps avoid errors caused by using fields from a different RHACS release.

---

# 18. Central CR Lifecycle

Once the CR exists, the Operator continuously reconciles it.

```text
              Central CR
                  │
                  ▼
          Desired configuration
                  │
                  ▼
           RHACS Operator
                  │
                  ▼
              Reconcile
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
    Central     Storage    Services
    Pods        Resources  / Routes
```

If you modify the Central CR:

```text
Central CR modified
        │
        ▼
Operator detects change
        │
        ▼
Reconciliation
        │
        ▼
RHACS resources updated
```

This is the core Operator pattern.

# 21. Common Mistake: Creating the Central CR Before the Operator

Do not start by creating the Central CR on a cluster where the RHACS CRD/operator is not installed.

Incorrect sequence:

```text
Central CR
    │
    ▼
No RHACS Operator/CRD
    │
    ▼
Failure
```

Correct sequence:

```text
1. Install RHACS Operator
       │
       ▼
2. Verify CSV = Succeeded
       │
       ▼
3. Verify Central CRD
       │
       ▼
4. Create Central CR
       │
       ▼
5. Operator reconciles Central
```

---

# 22. Common Mistake: Using an Old RHACS YAML

RHACS CR schemas can change between releases.

For example, a Central manifest copied from an older environment may contain:

```yaml
spec:
  someOldField: ...
```

The installed Operator may reject it.

Always inspect the current schema:

```bash
oc explain central.spec --recursive
```

and compare it with the documentation for your installed RHACS release.

---

# 23. Common Mistake: Assuming `spec: {}` Is a Complete Production Configuration

A minimal Central CR can be useful for understanding the Operator workflow:

```yaml
spec: {}
```

But a production deployment usually requires deliberate decisions around:

```text
Storage
Resources
Exposure
TLS
Availability
Backup
Networking
Authentication
Sizing
```

Therefore, treat the minimal CR as a starting point, not as a complete production architecture.

# 29. Interview Answer

### Question

**How do you create a Central custom resource?**

### Answer

First, install and verify the RHACS Operator. Then verify that the `Central` CRD is available. Create a Central custom resource in the appropriate namespace, commonly `stackrox`, and apply it with `oc apply`.

Example:

```yaml
apiVersion: platform.stackrox.io/v1alpha1
kind: Central
metadata:
  name: central
  namespace: stackrox
spec: {}
```

Apply it:

```bash
oc apply -f central.yaml
```

Then monitor:

```bash
oc get central -n stackrox
oc get pods -n stackrox
oc get events -n stackrox
```

The RHACS Operator watches the Central CR and reconciles it by creating and managing the required RHACS Central components.

For production, I would first verify the exact CR schema and supported configuration for the installed RHACS version using:

```bash
oc explain central.spec --recursive
```

and the corresponding Red Hat RHACS documentation.

# Key Takeaway

The Central custom resource is the **desired-state declaration for RHACS Central**.

```text
RHACS Operator
      │
      ▼
Central CR
      │
      ▼
Operator reconciliation
      │
      ▼
RHACS Central
      │
      ├── API/UI
      ├── Storage
      ├── Scanner-related components
      └── Management functions
```

The most important operational principle is:

> **Do not treat the Central CR as a static deployment YAML. It is a declarative API object that the RHACS Operator continuously reconciles.**

Always use the **CRD schema installed by your specific RHACS Operator version** rather than blindly reusing a Central manifest from another RHACS release.
