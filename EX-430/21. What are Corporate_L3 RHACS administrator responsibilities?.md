# What Are Corporate/L3 RHACS Administrator Responsibilities?

## 1. Overview

A **Corporate/L3 RHACS Administrator** is responsible for the advanced administration, architecture, security operations, troubleshooting, governance, and lifecycle management of RHACS across an enterprise Kubernetes environment.

L1/L2 teams usually handle routine monitoring and standard incidents.

L3 administrators handle:

* Complex incidents
* Platform architecture
* Multi-cluster security
* RHACS upgrades
* Advanced troubleshooting
* Security policy governance
* Integrations
* Performance
* Certificates
* Disaster recovery
* Automation
* Enterprise standards
* Vendor escalation

A simplified enterprise model is:

```text
                         Corporate Security
                                |
                                v
                         RHACS L3 Team
                                |
          +---------------------+---------------------+
          |                     |                     |
          v                     v                     v
    Platform Teams        Security Teams       Application Teams
          |                     |                     |
          v                     v                     v
   OpenShift/K8s           Policies/Risk       Remediation
   Infrastructure          Compliance          Vulnerabilities
```

---

# 2. L3 Administrator vs L1/L2

A corporate RHACS team should have clearly separated responsibilities.

| Area                         | L1         | L2        | L3                |
| ---------------------------- | ---------- | --------- | ----------------- |
| Basic monitoring             | Yes        | Yes       | Oversight         |
| Pod restart                  | Yes        | Yes       | Troubleshooting   |
| Basic log collection         | Yes        | Yes       | Advanced analysis |
| Sensor troubleshooting       | Limited    | Yes       | Advanced          |
| Central troubleshooting      | Limited    | Yes       | Advanced          |
| Policy creation              | No/limited | Limited   | Yes               |
| Enterprise policy governance | No         | Limited   | Yes               |
| Multi-cluster architecture   | No         | Limited   | Yes               |
| RHACS upgrade                | No         | Assisted  | Yes               |
| Certificates                 | Basic      | Yes       | Advanced          |
| Performance tuning           | No         | Limited   | Yes               |
| DR design                    | No         | Limited   | Yes               |
| Vendor escalation            | No         | Sometimes | Yes               |
| Security architecture        | No         | Limited   | Yes               |
| Automation                   | Limited    | Some      | Yes               |
| Root-cause analysis          | Limited    | Yes       | Yes               |

The L3 administrator is normally the **technical authority for RHACS**.

# 15. False Positive Management

A security policy can sometimes generate findings that are technically valid but operationally expected.

For example:

```text id="j68uw4"
Policy:
Detect shell execution

Application:
Debug-enabled container

Result:
Alert
```

The L3 administrator investigates whether the activity is:

```text id="5u6d3s"
Expected
or
Suspicious
```

If it is expected, the administrator determines whether an appropriate policy exception is required.

Exceptions should be:

```text id="b0w4cz"
Documented
Approved
Scoped
Time-bound where appropriate
Auditable
```

# 65. Key Takeaway

The Corporate/L3 RHACS Administrator is essentially the **technical owner and escalation authority for the RHACS security platform**.

The role can be summarized as:

```text
                  CORPORATE RHACS L3
                         |
       +-----------------+-----------------+
       |                 |                 |
       v                 v                 v
    BUILD              OPERATE          PROTECT
       |                 |                 |
 Architecture       Monitoring        Policies
 Deployment          Troubleshooting   Vulnerabilities
 Integration         Performance       Runtime Security
 Automation          Upgrades          Compliance
       |                 |                 |
       +-----------------+-----------------+
                         |
                         v
                  CONTINUOUS IMPROVEMENT
```

The key difference between an L2 and L3 administrator is that **L2 generally restores service, while L3 determines why the service failed, fixes the underlying architectural or configuration problem, validates the security function, and implements preventive measures so the issue does not repeatedly occur.**
