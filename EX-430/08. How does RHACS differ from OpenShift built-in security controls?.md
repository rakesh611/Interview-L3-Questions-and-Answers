# How Does RHACS Differ From OpenShift Built-in Security Controls?

## Overview

**OpenShift already provides strong built-in security controls**, including:

* Security Context Constraints (SCC)
* RBAC
* NetworkPolicy
* SELinux
* seccomp
* OAuth and authentication
* Kubernetes API authorization
* Pod security controls
* Secrets
* TLS
* Container isolation

RHACS does **not replace these controls**.

Instead, RHACS adds a dedicated **security visibility, policy, detection, risk-analysis, and enforcement layer** on top of Kubernetes/OpenShift security.

A simple way to remember it:

```text
OpenShift Built-in Security
        │
        ├── Prevent unauthorized access
        ├── Restrict pod privileges
        ├── Isolate workloads
        ├── Authenticate users
        └── Protect the cluster

RHACS
        │
        ├── Discover security risks
        ├── Analyze workloads
        ├── Scan images
        ├── Analyze runtime behavior
        ├── Detect policy violations
        ├── Enforce security policies
        ├── Prioritize risk
        └── Provide centralized security visibility
```

OpenShift SCCs, for example, control what security context a pod is allowed to use, including privileged containers, host namespaces, capabilities, volume types, SELinux context, and related settings.

---

# 1. OpenShift Built-in Security

OpenShift security is primarily part of the **cluster platform itself**.

Important controls include:

```text
OpenShift
   │
   ├── Authentication
   ├── OAuth
   ├── RBAC
   ├── SCC
   ├── SELinux
   ├── seccomp
   ├── NetworkPolicy
   ├── Secrets
   ├── TLS
   └── API authorization
```

These controls protect the cluster and determine what users, service accounts, pods, and workloads are allowed to do.

---

# 2. Security Context Constraints (SCC)

SCC is one of the most important OpenShift-native security mechanisms.

It controls whether pods can perform potentially dangerous operations.

For example:

```text
SCC
 │
 ├── Privileged container?
 ├── HostNetwork?
 ├── HostPID?
 ├── HostIPC?
 ├── HostPath?
 ├── Linux capabilities?
 ├── SELinux context?
 ├── Container UID?
 └── Read-only filesystem?
```

Red Hat documents SCC as a mechanism for controlling permissions that pods can use.

Example:

```bash
oc get scc
```

Example output:

```text
NAME           PRIV
anyuid         false
hostaccess     false
hostmount-anyuid
hostnetwork    true
nonroot        false
privileged     true
restricted     false
```

SCC answers:

> **"Is this pod allowed to run with these security characteristics?"**

---

# 3. RHACS and SCC

RHACS does not replace SCC.

Instead, RHACS can identify workloads that violate security best practices or organizational security policies.

Example:

```text
Deployment
     │
     ▼
Runs as root
     │
     ├── OpenShift SCC
     │       │
     │       └── Controls whether this is allowed
     │
     └── RHACS
             │
             └── Can identify/report the workload
                 as a security risk according to policy
```

Therefore:

```text
SCC = Platform enforcement

RHACS = Security analysis + policy + visibility + enforcement
```

---

# 4. RBAC

OpenShift uses Kubernetes RBAC to control what users and service accounts can do.

Example:

```text
User
 │
 ▼
RoleBinding
 │
 ▼
Role
 │
 ▼
Permissions
```

Example:

```yaml
rules:
- apiGroups: [""]
  resources:
  - pods
  verbs:
  - get
  - list
  - watch
```

RBAC answers:

> **"What is this user or service account allowed to do?"**

---

# 5. RHACS and RBAC

RHACS has its own RBAC for controlling access to the **RHACS platform itself**. Red Hat documents RHACS roles and scoped access controls for determining what RHACS users and groups can access and what actions they can perform.

So there are two different concepts:

```text
OpenShift RBAC
      │
      └── Controls access to OpenShift/Kubernetes resources


RHACS RBAC
      │
      └── Controls access to RHACS security resources/functions
```

RHACS can also analyze Kubernetes/OpenShift RBAC configuration as part of its security posture.

---

# 6. NetworkPolicy

OpenShift supports Kubernetes NetworkPolicy.

A NetworkPolicy controls network traffic between workloads.

Example:

```text
Frontend
   │
   │ allowed
   ▼
Backend
   │
   │ allowed
   ▼
Database
```

But:

```text
Internet
   │
   X
Database
```

A NetworkPolicy answers:

> **"Which network traffic should be allowed or denied?"**

---

# 7. RHACS and NetworkPolicy

RHACS can provide network visibility and help security teams understand workload communication.

RHACS can also generate NetworkPolicy resources from observed network relationships. Red Hat documents this as a way to turn network-graph information into policies.

Conceptually:

```text
                    RHACS
                      │
                 Network Graph
                      │
                      ▼
             Understand traffic
                      │
                      ▼
             Generate NetworkPolicy
                      │
                      ▼
                  OpenShift
                      │
                      ▼
              Enforce network rules
```

Important distinction:

```text
NetworkPolicy
    =
Actual Kubernetes/OpenShift network enforcement

RHACS
    =
Visibility + analysis + policy management
    + optional policy generation
```

# 8. Image Vulnerability Security

OpenShift itself provides the platform on which images run, but RHACS adds dedicated container-security capabilities.

Example:

```text
Image:
payment:v10

Vulnerabilities:
CRITICAL = 2
HIGH     = 8
```

RHACS can associate this information with the workload and its environment.

For example:

```text
Image
 │
 ├── CVE
 ├── Deployment
 ├── Namespace
 ├── Cluster
 ├── Exposure
 ├── Runtime information
 └── Security policy
```

This provides security context beyond the image itself.

# 9. Runtime Security

OpenShift provides strong workload isolation through mechanisms such as:

```text
SELinux
seccomp
cgroups
Linux namespaces
SCC
container runtime
```

These are platform security controls.

RHACS adds security monitoring and detection capabilities around workload behavior.

Conceptually:

```text
OpenShift
    │
    └── Provides workload isolation

RHACS
    │
    └── Observes and analyzes workload behavior
```

Example:

```text
Container
    │
    ├── Normal process
    ├── Normal network connection
    │
    └── Unexpected process
             │
             ▼
          RHACS
             │
             ▼
           Alert
```

---

# 10. Admission Control

OpenShift has Kubernetes admission mechanisms and OpenShift-specific admission-related controls.

RHACS adds its own security policy evaluation and Admission Controller.

Red Hat describes RHACS policies as being usable across build, deploy, and runtime stages, including rejecting deployments and responding to runtime violations.

Example:

```text
Developer
    │
    ▼
oc apply
    │
    ▼
OpenShift API
    │
    ▼
RHACS Admission Controller
    │
    ├── PASS
    │     │
    │     ▼
    │   Deployment
    │
    └── FAIL
          │
          ▼
       Rejected
```

Example RHACS policy:

```text
Reject deployment when:

CRITICAL vulnerability
AND
fix is available
AND
namespace = production
```

# 11. Security Policy Difference

OpenShift-native controls generally focus on **platform and workload security**.

Examples:

```text
SCC
RBAC
NetworkPolicy
SELinux
seccomp
Authentication
Authorization
```

RHACS policies can combine multiple security conditions.

Example:

```text
IF

Image severity = CRITICAL
AND
Deployment = production
AND
Internet exposed = true
AND
Container runs as root

THEN

Generate high-priority violation
or enforce policy
```

This contextual approach is one of the major differences.

---

# 12. Centralized Multi-Cluster Security

OpenShift provides security controls independently inside each cluster.

For example:

```text
Cluster A
   ├── RBAC
   ├── SCC
   └── NetworkPolicy

Cluster B
   ├── RBAC
   ├── SCC
   └── NetworkPolicy

Cluster C
   ├── RBAC
   ├── SCC
   └── NetworkPolicy
```

RHACS can provide a centralized security view:

```text
                 RHACS Central
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
     Cluster A     Cluster B     Cluster C
        │             │             │
      Sensor        Sensor        Sensor
        │             │             │
        └─────────────┼─────────────┘
                      │
                      ▼
             Central Security View
```

This is especially useful for enterprises running many OpenShift clusters.

# 13. Compliance and Security Posture

OpenShift provides the mechanisms needed to configure a secure cluster.

RHACS adds centralized security posture analysis and reporting.

For example:

```text
                    RHACS
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
    Cluster A     Cluster B     Cluster C
        │             │             │
        ▼             ▼             ▼
     Security       Security      Security
     Findings       Findings      Findings
        │             │             │
        └─────────────┼─────────────┘
                      ▼
                Central Report
```

RHACS includes security policies and best-practice-oriented controls, including categories related to Kubernetes and CIS.

# 18. RHACS Does Not Replace OpenShift Security

This is extremely important.

Do **not** design an architecture like:

```text
OpenShift
   │
   └── Remove SCC/RBAC/NetworkPolicy
             │
             ▼
           RHACS
```

That is incorrect.

Instead:

```text
                    OpenShift
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
       SCC            RBAC      NetworkPolicy
        │              │              │
        └──────────────┼──────────────┘
                       │
                       ▼
                     RHACS
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
      Policy         Runtime        Risk
      Engine         Security      Analysis
        │              │              │
        └──────────────┼──────────────┘
                       ▼
                Central Security
```

RHACS **complements** OpenShift security rather than replacing it.

# 23. Interview Answer

### Question

**How does RHACS differ from OpenShift built-in security controls?**

### Answer

OpenShift provides native platform security controls such as **RBAC, SCC, SELinux, seccomp, NetworkPolicy, authentication, authorization, and secrets**. These controls enforce security directly within the OpenShift cluster.

RHACS is a dedicated Kubernetes/OpenShift security platform that **complements those controls**. It provides centralized security visibility, vulnerability analysis, policy management, admission control, runtime security, risk prioritization, network analysis, and multi-cluster security management.

For example:

```text
OpenShift SCC:
    Controls whether a pod can run with privileged
    or other restricted security characteristics.

RHACS:
    Can identify that workload as a security risk,
    correlate it with other factors such as image
    vulnerabilities and exposure, and apply an
    RHACS policy at the appropriate lifecycle stage.
```

Therefore:

> **OpenShift provides the foundational security controls and enforcement mechanisms, while RHACS adds centralized security intelligence, policy, detection, risk analysis, and additional enforcement across the application lifecycle.**
