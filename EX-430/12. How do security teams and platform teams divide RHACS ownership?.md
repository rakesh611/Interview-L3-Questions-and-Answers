# How Do Security Teams and Platform Teams Divide RHACS Ownership?

## Overview

Red Hat Advanced Cluster Security for Kubernetes (RHACS) is most effective when **security teams and platform teams share responsibility** rather than treating RHACS as a security-only or platform-only product.

A common enterprise model is:

```text
                 RHACS
                   |
        ┌──────────┴──────────┐
        |                     |
 Security Team           Platform Team
        |                     |
 Security policy         Cluster integration
 Risk management         RHACS deployment
 Compliance              Sensor/Collector
 Vulnerability policy    Networking
 Incident response       Upgrades/operations
 Exceptions              Troubleshooting
        |                     |
        └──────────┬──────────┘
                   |
              Application Teams
```

The exact ownership model varies by organization, but the principle is:

> **Security defines what is allowed and why; platform teams make sure RHACS and the clusters can enforce and operate those requirements.**

---

# 1. Security Team Responsibilities

The security team primarily owns **security policy, risk decisions, compliance, and security response**.

## 1.1 Define Security Policies

Security teams decide what workloads should and should not be allowed to do.

Examples:

* Containers must not run as root.
* Images must not contain critical vulnerabilities.
* Privileged containers require approval.
* Containers must not use host networking unless approved.
* Images must come from approved registries.
* Kubernetes workloads must have appropriate security controls.
* Sensitive namespaces require stricter policies.

Example RHACS policy:

```text
Policy:
Container runs in privileged mode

Severity:
High

Lifecycle:
Deploy

Action:
Alert
```

The security team determines whether this behavior represents an unacceptable risk.

---

# 2. Vulnerability Management

Security teams define the organization's vulnerability requirements.

They determine:

* Which CVEs are critical.
* Which CVEs require immediate remediation.
* Acceptable vulnerability thresholds.
* Exceptions for specific applications.
* Remediation deadlines.
* Approved base images.

For example:

```text
Critical CVE
     |
     v
Security Team
     |
     +--> Is it exploitable?
     |
     +--> Is mitigation available?
     |
     +--> Is exception justified?
     |
     v
Security Decision
```

Platform teams generally provide the technical information and remediation capability, while security owns the risk decision.

---

# 3. Security Policy Governance

Security teams should own the **policy intent**.

For example:

```text
Requirement:
Production containers must not run as root.
```

The security team defines the requirement.

The platform team then determines how that requirement is technically implemented using:

* RHACS policies
* Kubernetes/OpenShift controls
* SCC
* Admission control
* Namespace configuration
* CI/CD checks

---

# 4. Compliance and Audit

Security teams commonly use RHACS data for:

* Compliance reporting
* Security assessments
* Audit evidence
* Risk dashboards
* Vulnerability reports
* Policy violations
* Security posture reporting

Typical questions include:

```text
How many critical vulnerabilities exist?

Which production workloads violate security policies?

Which clusters have high-risk configurations?

Which applications are running privileged containers?

Which images contain known vulnerabilities?
```

The security team interprets this information from a **risk and compliance perspective**.

---

# 5. Incident Response

Security teams typically own the security incident process.

Example:

```text
RHACS detects suspicious behavior
             |
             v
       Security Team
             |
       Investigate
             |
       Determine risk
             |
      Incident declared
             |
             v
       Platform Team
             |
      Technical action
```

Possible actions include:

* Investigating anomalous network activity.
* Reviewing process execution.
* Investigating compromised containers.
* Identifying affected namespaces.
* Identifying affected clusters.
* Coordinating containment.
* Escalating incidents.

---

# 6. Security Exceptions

Security teams should generally own **risk acceptance**.

Example:

```text
Application:
Legacy-payment-service

Violation:
Container runs as root

Application team:
Cannot immediately change application.

Platform team:
Can technically permit the workload.

Security team:
Reviews business/security risk.

Decision:
Temporary exception approved
```

The platform team should not independently decide that a security violation is acceptable simply because the application requires it.

---

# 7. Platform Team Responsibilities

The platform team owns the **technical operation of RHACS and integration with Kubernetes/OpenShift**.

Typical responsibilities include:

* Installing RHACS.
* Upgrading RHACS.
* Managing Central.
* Deploying Sensor.
* Managing Collector.
* Managing Admission Controller.
* Integrating RHACS with OpenShift/Kubernetes.
* Managing certificates.
* Networking.
* Storage.
* High availability.
* Monitoring.
* Troubleshooting.

---

The platform team normally owns RHACS deployment.

Typical components include:

              |                     |
          Sensor                  APIs/UI
              |
       ┌──────┴──────┐

Platform responsibilities include:

* RHACS operator installation.

* Collector deployment.

* Backup/recovery planning.
* Resource sizing.

---

# 9. Cluster Integration

Platform teams connect RHACS to managed clusters.

For example:

```text
OpenShift Cluster 1
        |
      Sensor
        |
        v
     RHACS Central
```

The platform team ensures that:

* Sensor can communicate with Central.
* Collector runs correctly.
* Admission Controller works.
* Required RBAC exists.
* Certificates are valid.
* Network connectivity is available.
* Required namespaces exist.
* RHACS components are healthy.

---

# 11. Platform Team Does Not Own Security Risk Decisions

A common mistake is giving the platform team complete ownership of RHACS.

For example:

```text
RHACS reports:

Critical vulnerability found
```

The platform team can:

* Identify the affected workload.
* Identify the affected image.
* Help update the image.
* Restart/redeploy workloads.
* Provide technical information.

But the platform team should not normally decide:

```text
"Security risk is acceptable."
```

That decision belongs to the appropriate security/risk owner.

---

# 12. Application Team Responsibilities

Although the question focuses on security and platform teams, application teams are also important RHACS stakeholders.

Application teams typically own:

* Application container images.
* Dockerfiles/Containerfiles.
* Application dependencies.
* Vulnerability remediation.
* Kubernetes manifests.
* Helm charts.
* Application configuration.
* Application-specific security violations.

Example:

```text
RHACS
  |
  v
Image contains vulnerable OpenSSL
  |
  v
Application Team
  |
  +--> Update base image
  +--> Update dependency
  +--> Build new image
  +--> Test
  +--> Deploy
```

# 13. Recommended Enterprise RACI Model

A simple ownership model can look like this:

| Activity                    | Security | Platform | Application |
| --------------------------- | -------- | -------- | ----------- |
| Security policy definition  | **A/R**  | C        | C           |
| RHACS installation          | C        | **A/R**  | I           |
| RHACS upgrade               | C        | **A/R**  | I           |
| Central operations          | C        | **A/R**  | I           |
| Sensor deployment           | I        | **A/R**  | I           |
| Collector operations        | I        | **A/R**  | I           |
| Admission Controller        | C        | **A/R**  | I           |
| Vulnerability policy        | **A/R**  | C        | C           |
| Vulnerability remediation   | C        | C        | **A/R**     |
| Security exceptions         | **A/R**  | C        | C           |
| Compliance reporting        | **A/R**  | C        | I           |
| Security incident           | **A/R**  | R        | C           |
| Cluster troubleshooting     | I        | **A/R**  | C           |
| Application troubleshooting | C        | C        | **A/R**     |
| Risk acceptance             | **A/R**  | I/C      | C           |
| RHACS availability          | I        | **A/R**  | I           |

Where:

```text
A = Accountable
R = Responsible
C = Consulted
I = Informed
```

# 14. Example: Privileged Container

Suppose RHACS detects:

```text
Deployment:
payment-api

Violation:
Privileged container

Severity:
High
```

A good enterprise workflow is:

```text
                  RHACS
                    |
                    v
            Security Violation
                    |
        ┌───────────┴───────────┐
        |                       |
    Security                 Platform
        |                       |
  Assess risk            Verify configuration
        |                       |
        └───────────┬───────────┘
                    |
              Application Team
                    |
              Fix workload
                    |
                    v
              RHACS validates
```

Security decides whether the violation is acceptable.

Platform helps verify the cluster/security configuration.

Application developers fix the workload.

# 16. Separation of Duties

Enterprise environments should avoid giving one team unrestricted control over everything.

A good separation is:

```text
Security Team
     |
     | defines policy
     v
RHACS Policy
     ^
     |
Platform Team
     |
     | operates RHACS
     v
OpenShift/Kubernetes

Application Team
     |
     | fixes workload
     v
Application
```

This provides stronger governance.

For example, the platform team should not silently disable an important security policy just because a deployment is failing.

Instead:

```text
Deployment blocked
       |
       v
Platform investigates
       |
       v
Security + Application consulted
       |
       v
Fix OR formally approve exception
```

---

# 17. RBAC and Access Separation

RHACS should use role-based access control so that users receive only the permissions they require.

A possible model:

```text
Security Administrator
    |
    +--> Security policies
    +--> Risk management
    +--> Compliance
    +--> Investigations

Platform Administrator
    |
    +--> RHACS infrastructure
    +--> Cluster integration
    +--> Sensor
    +--> Collector
    +--> Operational troubleshooting

Application Team
    |
    +--> Application findings
    +--> Vulnerability remediation
    +--> Limited visibility
```

The exact RHACS roles should be designed according to organizational requirements.

---

# 18. Who Should Change RHACS Policies?

A recommended model is:

```text
Security Team
      |
      | defines requirement
      v
Security Policy
      |
      | implementation
      v
Platform Team
      |
      v
RHACS
```

For sensitive production policies, use change management:

```text
Policy change
     |
     v
Review
     |
     v
Approval
     |
     v
Implementation
     |
     v
Testing
     |
     v
Production
```

This prevents accidental weakening of security controls.

# 19. Who Troubleshoots RHACS?

### Platform team handles:

* Pods not running.
* Sensor disconnected.
* Collector failures.
* Central availability.
* Certificate problems.
* Network connectivity.
* Resource exhaustion.
* Operator problems.
* Upgrade failures.
* OpenShift integration problems.

### Security team handles:

* Suspicious behavior.
* Policy violations.
* Risk assessment.
* Threat investigation.
* Compliance issues.
* Security incidents.

### Application team handles:

* Vulnerable dependencies.
* Bad container images.
* Insecure application configuration.
* Kubernetes manifest violations.
* Application-level remediation.

# 21. Practical Rule to Remember

The easiest way to remember the division is:

```text
Security Team
    =
"What security should be enforced?"

Platform Team
    =
"How do we technically operate and enforce it?"

Application Team
    =
"How do we fix our workload when it violates it?"
```

Or:

> **Security owns the security decision. Platform owns the RHACS platform. Application teams own application remediation.**

---

# 22. Interview Answer

A strong interview answer would be:

> "In an enterprise RHACS deployment, I would use a shared-ownership model. The security team owns security policies, vulnerability and risk requirements, compliance, incident investigation, and security exceptions. The platform team owns RHACS installation, upgrades, Central, Sensor, Collector, Admission Controller, cluster integration, availability, networking, and operational troubleshooting. Application teams own remediation of vulnerable images and insecure workload configurations. Security decides what risk is acceptable, while the platform team ensures the controls are technically implemented and reliable. This separation of duties prevents operational teams from weakening security controls without proper approval."

---

# 23. Key Takeaways

1. **Security team owns security policy and risk.**
2. **Platform team owns RHACS infrastructure and operations.**
3. **Application teams own application remediation.**
4. Security should approve security exceptions.
5. Platform should maintain RHACS availability.
6. Security should own compliance and security investigations.
7. Platform should handle cluster/RHACS technical troubleshooting.
8. RHACS RBAC should enforce separation of duties.
9. Production policy changes should follow change management.
10. The best model is **shared responsibility with clear accountability**.

```text
Security
   ↓
Policy + Risk + Compliance + Incident

Platform
   ↓
RHACS + Cluster + Operations

Application
   ↓
Code + Image + Manifest + Remediation
```

**Bottom line:**

> **Security defines the guardrails, platform engineering operates the security platform, and application teams fix what runs inside those guardrails.**
