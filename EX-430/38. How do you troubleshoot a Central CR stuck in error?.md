# How Do You Troubleshoot a Central CR Stuck in Error?

A RHACS `Central` Custom Resource (CR) stuck in an error or unhealthy state means the RHACS Operator has not successfully reconciled the desired Central configuration into a healthy RHACS Central deployment.

The important distinction is:

```text id="p8q7k1"
Central CR error
      |
      +--> Operator problem?
      +--> Central configuration problem?
      +--> Storage problem?
      +--> Scheduling problem?
      +--> Image/registry problem?
      +--> Certificate problem?
      +--> Database problem?
      +--> Network/service problem?
```

Do not immediately delete the `Central` CR or restart Pods. First determine **where reconciliation is failing**.

---

# 1. Understand the Central CR

The RHACS Central CR is the declarative configuration used by the RHACS Operator to deploy and manage Central.

Check it:

```bash id="3wxh6b"
oc get central -n stackrox
```

Example:

```text id="4j6x3a"
NAME       AGE
central    10m
```

A CR existing successfully does **not** mean Central is healthy.

You need to inspect its status.

---

# 2. Describe the Central CR

Start with:

```bash id="qf5r1c"
oc describe central central -n stackrox
```

Look carefully at:

```text id="v5kz6q"
Spec
Status
Conditions
Events
```

The `Status` and `Conditions` sections are especially important.

You may see conditions indicating:

```text id="x9h4y2"
Ready
Degraded
Progressing
Available
Error
```

The exact condition names and messages can vary by RHACS release.

---

# 3. Get the Complete Central YAML

Run:

```bash id="u8xj3n"
oc get central central \
  -n stackrox \
  -o yaml
```

Inspect:

```yaml id="h8j8a7"
spec:
  ...
status:
  ...
```

Compare the desired configuration in:

```text id="7m3d8f"
spec
```

with the observed state in:

```text id="j2u8y6"
status
```

The difference often reveals what the Operator is trying to create or repair.

---

# 4. Check Central Conditions

You can inspect conditions directly:

```bash id="xj0n8s"
oc get central central \
  -n stackrox \
  -o jsonpath='{.status.conditions}'
```

For easier troubleshooting:

```bash id="4z9gq0"
oc get central central \
  -n stackrox \
  -o yaml
```

Look for messages containing:

```text id="jv6h3n"
error
failed
unable
waiting
timeout
forbidden
invalid
```

Do not treat the condition name alone as the root cause.

The condition's message is usually more useful.

---

# 5. Check Central Events

Events are often the fastest way to identify a reconciliation problem.

Run:

```bash id="f4n0tk"
oc get events \
  -n stackrox \
  --sort-by=.lastTimestamp
```

Look for:

```text id="w9d7w5"
Warning
Failed
FailedCreate
FailedMount
FailedScheduling
FailedPull
Unhealthy
BackOff
```

You can also inspect the Central CR events:

```bash id="c2d3j7"
oc describe central central \
  -n stackrox
```

---

# 6. Check the RHACS Operator First

The Central CR is managed by the RHACS Operator.

Therefore, before debugging Central itself, confirm that the Operator is healthy.

Check:

```bash id="2n3x9p"
oc get csv -n rhacs-operator
```

Expected:

```text id="w0s5g3"
PHASE
Succeeded
```

Check the Operator Pod:

```bash id="qj6q3x"
oc get pods -n rhacs-operator
```

Expected:

```text id="xq6q1z"
1/1   Running
```

If the Operator CSV is `Failed`, fix the Operator problem first.

---

# 7. Check Operator Logs

The Operator may report exactly why it cannot reconcile Central.

Run:

```bash id="y5u8nk"
oc logs deployment/rhacs-operator \
  -n rhacs-operator
```

Look for:

```text id="7c9h9e"
reconcile
Central
error
failed
forbidden
invalid
timeout
certificate
secret
storage
```

If logs are very large:

```bash id="6w0l4k"
oc logs deployment/rhacs-operator \
  -n rhacs-operator \
  --since=30m
```

Search for Central-related messages:

```bash id="gqj1w4"
oc logs deployment/rhacs-operator \
  -n rhacs-operator \
  --since=30m | grep -i central
```

---

# 8. Verify the Central Deployment

Check:

```bash id="xj3c7u"
oc get deployment -n stackrox
```

You should normally see a Central Deployment.

For example:

```text id="w4d5z2"
NAME      READY   UP-TO-DATE   AVAILABLE
central   1/1     1            1
```

If it shows:

```text id="y3k6r8"
0/1
```

inspect it:

```bash id="2f9k5d"
oc describe deployment central \
  -n stackrox
```

Check:

* Replica count
* Available replicas
* Conditions
* Pod template
* ServiceAccount
* Container image
* Environment variables
* Volumes
* Events

---

# 9. Check Central Pods

Run:

```bash id="0a2j8p"
oc get pods \
  -n stackrox \
  -o wide
```

Typical problem states include:

```text id="5b7j8w"
Pending
ImagePullBackOff
ErrImagePull
CrashLoopBackOff
CreateContainerConfigError
ContainerCreating
Running but not Ready
```

Each state requires a different troubleshooting path.

---

# 10. If Central Is Pending

Run:

```bash id="u9q3jk"
oc describe pod <central-pod> \
  -n stackrox
```

Check Events.

Common causes:

```text id="d2k4h7"
Insufficient CPU
Insufficient memory
Node selector mismatch
Affinity mismatch
Taint/toleration problem
PVC not available
ResourceQuota
Admission policy
```

Example:

```text id="q2t7r8"
0/3 nodes are available:
Insufficient memory
```

In that case, the Central CR is not necessarily wrong. The cluster cannot schedule the workload.

---

# 11. If Central Has ImagePullBackOff

Inspect:

```bash id="s5z7d4"
oc describe pod <central-pod> \
  -n stackrox
```

Look for:

```text id="x7k9n2"
Failed to pull image
manifest unknown
unauthorized
x509
connection timeout
```

Check the image:

```bash id="g1f5x8"
oc get pod <central-pod> \
  -n stackrox \
  -o jsonpath='{.spec.containers[*].image}'
```

Then verify:

```text id="0z5c2n"
Image exists
Registry reachable
Authentication works
Registry CA is trusted
Mirror configuration is correct
```

---

# 12. Disconnected Registry Troubleshooting

If the cluster is disconnected, verify that all required RHACS images are available in the internal registry.

Conceptually:

```text id="e8m5h2"
Central CR
   |
   v
Operator
   |
   v
Central Deployment
   |
   v
Central image
   |
   v
Internal registry
```

Check for:

```text id="q9j4m1"
manifest unknown
repository does not exist
unauthorized
x509
```

A missing Central image can prevent the Central CR from becoming ready.

---

# 13. Check Registry Authentication

If the error is:

```text id="8x9s2f"
unauthorized
```

check image pull secrets:

```bash id="u1x6q4"
oc get secret -n stackrox
```

Inspect the ServiceAccount:

```bash id="n7q3w8"
oc get serviceaccount \
  -n stackrox
```

Then:

```bash id="5v2m9d"
oc describe serviceaccount <serviceaccount> \
  -n stackrox
```

Confirm that the required registry credentials are available.

---

# 14. Check Registry CA

For a private registry:

```text id="p8r3w6"
registry.example.com
       |
       v
Corporate CA
```

An error such as:

```text id="r5n8c2"
x509: certificate signed by unknown authority
```

usually means the registry CA is not trusted by the relevant OpenShift/container-runtime path.

Inspect the registry certificate:

```bash id="x4k9z1"
openssl s_client \
  -connect registry.example.com:443 \
  -showcerts
```

Check:

* Issuer
* Subject
* SAN
* Validity
* Certificate chain

---

# 15. Check Central Services

Run:

```bash id="k4r7m1"
oc get svc -n stackrox
```

Verify the Central Service exists.

Inspect it:

```bash id="3x6b8j"
oc describe svc central \
  -n stackrox
```

Check:

```text id="q6w2v9"
Selector
Ports
TargetPort
Endpoints
```

---

# 16. Check Central Endpoints

Run:

```bash id="x5k1v7"
oc get endpoints \
  -n stackrox
```

Or:

```bash id="s4d9p3"
oc get endpointslice \
  -n stackrox
```

The Central Service should have endpoints corresponding to ready Central Pods.

If there are no endpoints:

```text id="g8m2n4"
Service
   |
   v
Selector
   |
   v
Pod labels
   |
   v
Pod readiness
```

Check all four.

---

# 17. Check Central Route

If Central is exposed through an OpenShift Route:

```bash id="p2w8h5"
oc get route -n stackrox
```

Inspect:

```bash id="z6k4n1"
oc describe route central \
  -n stackrox
```

Check:

* Hostname
* Service
* Target port
* TLS termination
* Certificate
* Ingress status

---

# 18. Test DNS

From a suitable client:

```bash id="u5r7x2"
dig central-stackrox.apps.example.com
```

or:

```bash id="q8n4v6"
nslookup central-stackrox.apps.example.com
```

If DNS fails:

```text id="w3h9j7"
Central CR
   |
   v
Central Pod
   |
   v
Service
   |
   v
Route
   |
   X
DNS
```

The problem is outside the Central application itself.

---

# 19. Test Central HTTPS

Test the endpoint:

```bash id="z1m7q5"
curl -vk \
  https://central-stackrox.apps.example.com
```

For proper certificate validation:

```bash id="r8c2x6"
curl \
  --cacert corporate-ca.crt \
  https://central-stackrox.apps.example.com
```

A `503 Service Unavailable` response usually means the Route/Ingress reached OpenShift but the backend is not currently serving traffic.

---

# 20. Check Central TLS

Inspect:

```bash id="a7p4y9"
openssl s_client \
  -connect central-stackrox.apps.example.com:443 \
  -servername central-stackrox.apps.example.com
```

Check:

```text id="m6q3t8"
Certificate SAN
Certificate chain
Issuer
Expiration
TLS handshake
```

Common certificate problems:

```text id="j9c2v5"
Wrong hostname
Expired certificate
Missing CA
Incomplete chain
Wrong secret
```

# 21. Check Central Storage

Central may depend on persistent storage depending on the RHACS configuration.

Check PVCs:

```bash id="b3x7k2"
oc get pvc -n stackrox
```

Expected:

```text id="n5j8r1"
STATUS = Bound
```

If a PVC is:

```text id="k2d6v9"
Pending
```

inspect:

```bash id="f8m4q3"
oc describe pvc <pvc-name> \
  -n stackrox
```

Check:

```text id="t7c1w5"
StorageClass
Provisioner
Capacity
Access mode
Events
```

---

# 22. Check StorageClass

Run:

```bash id="x3n7p2"
oc get storageclass
```

Confirm that the expected StorageClass exists.

For example:

```text id="b9m4s7"
lvms-vg1
```

or:

```text id="j6q2c8"
ocs-storagecluster-ceph-rbd
```

The exact StorageClass depends on the OpenShift storage architecture.

---

# 23. Check Central Volumes

Inspect the Central Pod:

```bash id="m2v6q9"
oc describe pod <central-pod> \
  -n stackrox
```

Check:

```text id="f5x8n3"
Volumes
Mounts
VolumeMounts
Mount errors
```

A common error is:

```text id="d7j3k1"
MountVolume.SetUp failed
```

That points toward storage rather than the Central CR itself.

---

# 24. Check Central Logs

Run:

```bash id="r9q5m2"
oc logs <central-pod> \
  -n stackrox
```

If the Pod has multiple containers:

```bash id="n4x7v8"
oc get pod <central-pod> \
  -n stackrox \
  -o jsonpath='{.spec.containers[*].name}'
```

Then:

```bash id="c6m1p9"
oc logs <central-pod> \
  -n stackrox \
  -c <container-name>
```

Look for:

```text id="v2k8s5"
database
certificate
permission
connection refused
timeout
migration
storage
panic
fatal
```

---

# 25. Check Previous Container Logs

If Central is crashing:

```bash id="t4q7n3"
oc logs <central-pod> \
  -n stackrox \
  --previous
```

This is especially useful with:

```text id="w8c5m2"
CrashLoopBackOff
```

because the current container may have very little useful output.

---

# 26. Check Central Readiness Probes

Inspect:

```bash id="z3p7m1"
oc describe pod <central-pod> \
  -n stackrox
```

Look for:

```text id="v9k2x6"
Readiness probe failed
Liveness probe failed
Startup probe failed
```

A Pod can be:

```text id="g4m8q2"
Running
```

while still being:

```text id="j7n3w5"
NotReady
```

This can cause:

```text id="q2s8k4"
Service has no usable endpoints
```

and potentially:

```text id="h5m1v7"
Route returns 503
```

# 31. Check Secrets Referenced by Central

If Central references secrets, verify that they exist.

List Secrets:

```bash id="n6r2w8"
oc get secret -n stackrox
```

Inspect the Central specification:

```bash id="g8m5q1"
oc get central central \
  -n stackrox \
  -o yaml
```

Look for references to:

```text id="x4p7k3"
Secrets
Certificates
Credentials
Registry credentials
TLS configuration
```

A missing Secret can prevent reconciliation or Pod startup.

---

# 32. Check ConfigMaps

List ConfigMaps:

```bash id="v5q2n9"
oc get configmap -n stackrox
```

If the Operator expects a ConfigMap that does not exist or contains invalid configuration, reconciliation may fail.

Do not manually modify Operator-generated ConfigMaps unless the RHACS documentation specifically instructs you to do so.

---

# 33. Check Network Policies

If Central is running but dependent components cannot communicate, inspect NetworkPolicies:

```bash id="c9m4x7"
oc get networkpolicy -n stackrox
```

Then:

```bash id="k2v8p5"
oc describe networkpolicy \
  -n stackrox
```

Check whether traffic between required RHACS components is allowed.

Be especially careful in environments with default-deny policies.

# 34. Check OpenShift Network

If Central is healthy but inaccessible:

```text id="s8n3w5"
DNS
 |
 v
Route
 |
 v
Ingress Controller
 |
 v
Service
 |
 v
Central Pod
```

Test each layer separately.

Check:

```bash id="h4m9q2"
oc get route -n stackrox
oc get svc -n stackrox
```

# 35. Check Operator Reconciliation Continuously

After making a configuration correction, watch the Operator:

```bash id="q6v2m8"
oc logs deployment/rhacs-operator \
  -n rhacs-operator \
  -f
```

In another terminal:

```bash id="z5p9n3"
oc get central central \
  -n stackrox \
  -w
```

And:

```bash id="m8c4x1"
oc get pods \
  -n stackrox \
  -w
```

This helps determine whether the fix is being reconciled successfully.

---

# 36. Do Not Edit the Central Status

Avoid manually changing:

```yaml id="t9w5q3"
status:
```

The Operator owns the status.

Changing status manually does not fix the underlying problem.

Instead, fix:

```text id="v4k8m2"
spec
environment
registry
storage
network
certificates
secrets
RBAC
cluster capacity
```

and allow the Operator to update the status.

---

# 37. Do Not Immediately Delete Central

Avoid:

```bash id="y2n7m5"
oc delete central central -n stackrox
```

unless you have determined that recreation is necessary and understand the consequences.

Deleting Central can affect:

* RHACS configuration
* Persistent data
* Certificates
* Secrets
* Services
* Routes
* Managed resources

First collect:

```text id="k6p3x9"
Central YAML
Operator logs
Central logs
Events
Pod descriptions
PVC status
Service/endpoints
Route status
```

# 38. Common Central CR Failure Patterns

| Symptom                                     | Likely Area                       |
| ------------------------------------------- | --------------------------------- |
| Central CR error immediately after creation | Operator/reconciliation           |
| Central Deployment missing                  | Operator reconciliation           |
| Central Pod Pending                         | Scheduling/resources              |
| ImagePullBackOff                            | Registry/image                    |
| `x509`                                      | Certificate/CA                    |
| `unauthorized`                              | Registry authentication           |
| PVC Pending                                 | Storage                           |
| MountVolume error                           | Storage/Secret                    |
| CrashLoopBackOff                            | Central application/configuration |
| Readiness probe failure                     | Central health/dependency         |
| Service has no endpoints                    | Pod readiness/selector            |
| Route returns 503                           | Service/backend readiness         |
| `forbidden`                                 | RBAC                              |
| DNS failure                                 | DNS/network                       |
| Connection timeout                          | Network/firewall/proxy            |
| Central repeatedly reconciles               | Operator/configuration/dependency |

# 39. L3 Troubleshooting Decision Tree

```text id="m7p4x2"
Central CR = Error
       |
       v
oc describe central
       |
       v
Check Conditions / Events
       |
       v
Is Operator healthy?
       |
       +---- NO ----> Fix Operator/OLM
       |
       +---- YES
              |
              v
       Is Central Deployment created?
              |
              +---- NO ----> Check Operator logs
              |
              +---- YES
                     |
                     v
                Is Pod Ready?
                     |
          +----------+----------+
          |          |          |
        Pending   ImagePull   CrashLoop
          |          |          |
          v          v          v
      Scheduling   Registry    Logs
      Resources    CA/Auth     Config
      Storage      Network     Storage
          |          |          |
          +----------+----------+
                     |
                     v
              Service healthy?
                     |
                     +---- NO ----> Selector/Endpoints
                     |
                     v
                Route healthy?
                     |
                     +---- NO ----> DNS/TLS/Ingress
                     |
                     v
                RHACS UI/API
                     |
                     v
                   READY
```

# 40. Recommended Troubleshooting Sequence

Use this exact order during an L3 incident:

```text id="d4n8s2"
1. Check Central CR
2. Describe Central
3. Check Central conditions
4. Check Central events
5. Check RHACS Operator CSV
6. Check Operator Pod
7. Check Operator logs
8. Check Central Deployment
9. Check Central Pod
10. Check Pod events
11. Check Central logs
12. Check PVC/storage
13. Check Service/endpoints
14. Check Route/DNS/TLS
15. Check registry if images cannot be pulled
16. Check RBAC/SCC if permission errors appear
17. Check network policies/connectivity
18. Fix the first/root failure
19. Allow Operator reconciliation
20. Validate Central again
```

The important rule is:

> **Troubleshoot from the Operator down to the workload and then from the workload outward to storage, services, routes, and clients.**

# 41. Example Troubleshooting Scenario

Suppose:

```bash id="c4m8x1"
oc get central -n stackrox
```

shows Central exists but is unhealthy.

First:

```bash id="p7n2v5"
oc describe central central \
  -n stackrox
```

The condition indicates a reconciliation error.

Check Operator:

```bash id="j9q4w6"
oc get csv -n rhacs-operator
```

CSV:

```text id="r5m7k2"
Succeeded
```

So the Operator is installed.

Check logs:

```bash id="x8c3n6"
oc logs deployment/rhacs-operator \
  -n rhacs-operator \
  --since=30m | grep -i central
```

Suppose the Operator successfully created Central.

Then:

```bash id="f2v9m4"
oc get pods -n stackrox
```

shows:

```text id="w7k5p1"
central-xxxxx   0/1   ImagePullBackOff
```

Describe:

```bash id="q3n8x6"
oc describe pod central-xxxxx \
  -n stackrox
```

Suppose the event says:

```text id="h4m7s2"
manifest unknown
```

The root cause is likely:

```text id="z8p3c5"
Central CR
    |
    v
Operator healthy
    |
    v
Central Deployment created
    |
    v
Central image unavailable
    |
    v
Internal registry missing image
```

The solution is to mirror/publish the correct Central image and allow the Pod to retry.

# 42. Example: Central CR Error Due to Storage

Another scenario:

```text id="x7m2q9"
Central CR
   |
   v
Deployment exists
   |
   v
Central Pod Pending
   |
   v
PVC Pending
   |
   v
StorageClass unavailable
```

Check:

```bash id="m5r8c2"

```

The fix belongs to the storage layer.

Do not modify the Central CR simply because its status reports an error.

# 43. Example: Central CR Error Due to TLS

Suppose Central starts but the Route returns an error.

Check:

```bash id="v8q4m1"
oc get route -n stackrox
oc describe route central -n stackrox
```

Then:

```bash id="j3p6x9"
openssl s_client \
  -connect central-stackrox.apps.example.com:443 \
  -servername central-stackrox.apps.example.com
```

If the certificate is invalid:

```text id="r2m7c5"
Wrong SAN
Expired certificate
Missing CA
Incorrect TLS secret
```

the problem is TLS configuration rather than Central scheduling.

# 44. Corporate/L3 Health Model

For production operations, think of Central as several layers:

```text id="n5x7q2"
Layer 1 - OLM
    |
Layer 2 - RHACS Operator
    |
Layer 3 - Central CR
    |
Layer 4 - Central Deployment
    |
Layer 5 - Central Pod
    |
Layer 6 - Storage
    |
Layer 7 - Service
    |
Layer 8 - Route/Ingress
    |
Layer 9 - DNS/TLS
    |
Layer 10 - User/API
```

A Central error should be mapped to the first unhealthy layer.

This is much more effective than restarting everything.

# 46. Interview Answer

**Question:** How do you troubleshoot a Central CR stuck in error?

**Answer:**

> I first inspect the Central CR using `oc describe central` and check its status conditions and events. Then I verify that the RHACS Operator CSV is `Succeeded` and inspect Operator logs to determine whether reconciliation is failing. If the Central Deployment exists, I check the Central Pod, readiness probes, scheduling, image pulls, storage, Secrets, and logs. I then validate the Service and endpoints, followed by the Route, DNS, and TLS configuration. In disconnected environments I also verify internal registry availability, authentication, image mirroring, and CA trust. I fix the first underlying failure and allow the Operator to reconcile rather than deleting the Central CR or repeatedly restarting Pods.
