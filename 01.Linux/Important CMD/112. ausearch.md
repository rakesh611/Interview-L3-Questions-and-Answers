# 112. ausearch

> **Level:** Linux Corporate/L3 administration and troubleshooting.

## 1. What it is

`ausearch` searches Linux Audit logs and groups related records into audit events. It can filter by time, user, process, executable, system call, key, file, message type, or result.

## 2. Why it matters in production

- Provides a repeatable method to inspect, validate, or control an important Linux subsystem.
- Produces evidence that can be attached to incident, change, problem, audit, and capacity records.
- Helps distinguish configuration, permission, kernel, service, network, storage, security, and application failures.
- Supports before-and-after validation rather than unmeasured configuration changes.

## 4. Core concepts

- One logical event can contain several record types sharing the same audit event ID.
- Real UID, effective UID, login UID, and audit UID have different meanings.
- Rule keys are the most maintainable way to find events generated by a known control.
- Interpreted output resolves numeric identifiers and syscall names but can be slower.
- Audit timestamps and host time must be considered in incident timelines.
- Archived logs can be selected explicitly.

| Command | Purpose | Operational risk |
|---|---|---|
| `sudo ausearch -ts today` | Search events from today. | Read-only |
| `sudo ausearch -ts recent` | Search recent events. | Read-only |
| `sudo ausearch -k identity_changes` | Search by audit rule key. | Read-only |
| `sudo ausearch -ui 1000` | Search by real user ID. | Read-only |
| `sudo ausearch -ua 1000` | Search by audit user/login ID. | Read-only |
| `sudo ausearch -p 1234` | Search by process ID. | Read-only |
| `sudo ausearch -x /usr/bin/passwd` | Search by executable. | Read-only |
| `sudo ausearch -sc openat` | Search by system call. | Read-only |
| `sudo ausearch -f /etc/passwd` | Search records involving a file. | Read-only |

| `sudo ausearch -k root_exec -i` | Interpret numeric values. | Read-only |
| `sudo ausearch --input /var/log/audit/audit.log.1 -ts 07/28/2026 14:00:00` | Search an archived log. | Read-only |

## 7. How to interpret the output

- `type=SYSCALL` contains syscall result, executable, IDs, and process data.
- `type=PATH` contains path, inode, device, ownership, and object context.
- `type=PROCTITLE` contains the encoded process command line.
- `success=yes/no` and the `exit` value describe the kernel result.
- `auid` normally tracks the login identity across privilege changes.

## 8. L3 troubleshooting workflow

1. **Define impact:** Identify the affected service, users, start time, scope, and business symptom.
2. **Preserve evidence:** Capture relevant logs, configuration, counters, timestamps, versions, and current state.
3. **Confirm ownership:** Determine whether systemd, NetworkManager, authselect, firewalld, policy, automation, or another manager owns the configuration.
4. **Use read-only checks first:** Avoid changing state before the failure mode is understood.
5. **Correlate adjacent layers:** Check process, kernel, filesystem, network, DNS, time, identity, audit, and SELinux evidence as appropriate.
6. **Form one hypothesis:** State what evidence supports it and what observation would disprove it.
7. **Make one controlled change:** Use a maintenance window, backup, console path, and rollback command.
8. **Validate service metrics:** Confirm application latency, error rate, authentication, data integrity, and logs—not only command success.
9. **Restore or persist:** Roll back failed experiments and make successful changes through approved configuration management.
10. **Document RCA:** Record root cause, contributing factors, corrective action, prevention, and monitoring.

## 9. Production cautions

- Interpreted names depend on current local identity databases and can differ from historical state.
- Audit logs can contain sensitive command arguments and paths.
- Do not alter original evidence; work from protected copies when investigating.
- A missing event can mean no rule existed, the event was lost, or the action bypassed the expected path.
- Never copy example users, paths, ports, addresses, or devices into production without validation.
- Commands that change credentials, access, labels, firewall rules, packages, audit rules, or services require change control.
- Keep an independent administrative path for SSH, PAM, firewall, DNS, and authentication work.

## 10. Quick practice lab

1. Create a keyed audit rule.
2. Trigger one successful and one denied operation.
3. Search by key, executable, and file.
4. Compare raw and interpreted output.
5. Map all records belonging to one event ID.

## 12. L3 interview review

- Explain what kernel interface, service, database, or configuration source the command uses.
- Distinguish read-only inspection from a runtime or persistent change.
- Explain at least two misleading interpretations of the output.
- State the correct rollback before proposing a production change.
- Describe how automation or a service manager can overwrite a manual setting.
- Identify the security, availability, and data-integrity risks.
