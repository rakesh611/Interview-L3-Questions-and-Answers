# 146. restic

> **Scope:** Corporate/L3 Linux administration, incident troubleshooting, safe change execution, and interview preparation.

## 1. What it is

`restic` is an encrypted, deduplicating backup program supporting local repositories and many remote object or service backends. It provides snapshots, retention, integrity checks, restore, mount, copy, and repository maintenance.

## 2. Production importance

- Provides a repeatable method for diagnosing or controlling the relevant Linux subsystem.
- Produces evidence suitable for incident timelines, change records, problem management, and audit review.
- Encourages before-and-after measurement instead of unverified tuning or repair.
- Separates command success from actual application availability, security, and data integrity.

## 3. Package or kernel interface

- **Primary package/interface:** restic
- Check availability and installed version before relying on an option:

```bash
command -v restic 2>/dev/null || true
rpm -q PACKAGE_NAME 2>/dev/null || true
COMMAND --version 2>/dev/null || COMMAND --help
```

## 4. Core concepts

- Repository encryption protects backup contents, but credentials and repository access still require protection.
- Deduplication occurs at content-defined chunk level.
- A snapshot is a metadata view referencing repository data packs.
- Retention and pruning are different: forgetting removes snapshot references; pruning reclaims unreferenced data.
- Repository checks and restore tests are essential.
- Backups of live databases require application-consistent dumps or snapshots.

## 5. Important commands

| Command | Purpose | Risk |
|---|---|---|
| `restic version` | Display the installed version. | Read-only |
| `export RESTIC_REPOSITORY=/backup/restic` | Set a repository location in the environment. | Read-only |
| `export RESTIC_PASSWORD_FILE=/root/.config/restic/password` | Reference a protected password file. | Read-only |
| `restic init` | Initialize a new encrypted repository. | Backup repository creation |
| `restic backup /etc /home --exclude-file=exclude.txt` | Create a backup snapshot. | Backup creation |
| `restic snapshots` | List snapshots. | Read-only |
| `restic stats latest` | Display statistics for the latest snapshot. | Read-only |
| `restic ls latest` | List files in the latest snapshot. | Read-only |
| `restic check` | Check repository structure and data references. | Repository verification |
| `restic restore latest --target /restore` | Restore the latest snapshot. | File restoration |
| `restic restore SNAPSHOT --target /restore --include /etc/hosts` | Restore a selected path. | File restoration |
| `restic diff SNAPSHOT1 SNAPSHOT2` | Compare two snapshots. | Read-only |
| `restic forget --keep-daily 7 --keep-weekly 5 --keep-monthly 12 --prune` | Apply retention and reclaim data. | Destructive repository maintenance |
| `restic mount /mnt/restic` | Mount snapshots through FUSE. | Temporary backup mount |
| `restic key add` | Add a repository key/password. | Credential change |
| `restic unlock` | Remove stale repository locks only after confirming no active job. | Repository lock change |

## 7. Output interpretation

- A backup summary includes files, directories, added data, processed size, and snapshot ID.
- Low added data after a large scan reflects deduplication.
- `check` validates repository structures but restore testing validates operational recoverability.
- A repository lock protects concurrent maintenance; it should not be removed while a job is active.
- Prune can be I/O-intensive and should be scheduled separately from latency-sensitive workloads.

## 8. Corporate/L3 troubleshooting workflow

1. **Confirm impact:** Record affected applications, users, start time, error rate, latency, and business severity.
2. **Identify scope:** Determine whether the issue is host-wide, process-specific, filesystem-specific, network-path-specific, or limited to one namespace.
3. **Preserve evidence:** Save logs, configuration, counters, command output, package versions, and timestamps before changing state.
4. **Establish ownership:** Identify whether systemd, NetworkManager, firewalld, TuneD, udev, a backup scheduler, configuration management, or the application owns the setting.
5. **Use read-only inspection first:** Confirm the hypothesis with at least two independent evidence sources.
6. **Control the test:** Make only one bounded change and define the rollback command in advance.
7. **Measure service behavior:** Validate latency, throughput, errors, data consistency, authentication, and client experience.
8. **Persist correctly:** Apply successful changes through the supported configuration source rather than an ad hoc runtime command.
9. **Close the incident:** Document root cause, contributing conditions, corrective action, monitoring, and prevention.

## 9. Production cautions

- Protect the repository password and backend credentials outside shell history.
- Test restores on a regular schedule.
- Review retention output before pruning.
- Use immutable/off-site controls because repository credentials can otherwise permit deletion.
- Quiesce applications or back up their supported dump/snapshot formats.
- Replace all example users, paths, devices, addresses, ports, repositories, and services only after validation.
- Keep console or out-of-band access for firewall, bootloader, storage, authentication, and network changes.
- Back up data and configuration before destructive, recursive, or boot-critical commands.
