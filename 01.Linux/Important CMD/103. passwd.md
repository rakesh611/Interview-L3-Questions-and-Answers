# 103. passwd

> **Level:** Linux Corporate/L3 administration and troubleshooting.

## 1. What it is

`passwd` changes passwords and manages selected local password-state attributes such as lock, unlock, expiry, and status. It normally updates `/etc/shadow` for local accounts and invokes the configured PAM password stack.

## 2. Why it matters in production

- Provides a repeatable method to inspect, validate, or control an important Linux subsystem.
- Produces evidence that can be attached to incident, change, problem, audit, and capacity records.
- Helps distinguish configuration, permission, kernel, service, network, storage, security, and application failures.
- Supports before-and-after validation rather than unmeasured configuration changes.

## 4. Core concepts

- A password lock does not necessarily disable every authentication method; SSH keys, certificates, or tokens can still work.
- The PAM stack can enforce complexity, history, dictionary, and identity-provider policies.
- `passwd -l` commonly places a lock marker in the password hash field rather than expiring the account.
- An account with no password is different from a locked account.
- Password changes can fail because of PAM policy, read-only filesystems, SELinux labels, file permissions, or directory-provider state.
- Service accounts should normally use non-interactive authentication rather than rotating human passwords manually.

## 5. Important commands

| Command | Purpose | Operational risk |
|---|---|---|
| `passwd` | Change the current user's password. | Credential change |
| `sudo passwd appuser` | Set or reset another local user's password. | Credential change |
| `sudo passwd -S appuser` | Display password status. | Read-only |
| `sudo passwd -l appuser` | Lock the local password hash. | Access change |
| `sudo passwd -u appuser` | Unlock the local password hash when safe. | Access change |
| `sudo passwd -e appuser` | Expire the password immediately. | Access change |
| `sudo passwd -d appuser` | Delete the password hash, potentially permitting passwordless use depending on PAM. | High-risk access change |
| `sudo passwd -n 1 -x 90 -w 14 -i 7 appuser` | Set minimum age, maximum age, warning, and inactivity values. | Configuration change |
| `sudo chage -l appuser` | Display detailed ageing information. | Read-only |
| `sudo getent shadow appuser` | Inspect the shadow entry when permitted; protect the output. | Read-only |

## 7. How to interpret the output

- `PS` in `passwd -S` commonly means a usable password exists.
- `LK` commonly means the password is locked.
- `NP` commonly means no password is set.
- The status line can include last-change date and ageing parameters.
- A successful password update should be followed by a controlled authentication test.

## 8. L3 troubleshooting workflow

1. **Define impact:** Identify the affected service, users, start time, scope, and business symptom.
2. **Preserve evidence:** Capture relevant logs, configuration, counters, timestamps, versions, and current state.
3. **Confirm ownership:** Determine whether systemd, NetworkManager, authselect, firewalld, policy, automation, or another manager owns the configuration.
4. **Use read-only checks first:** Avoid changing state before the failure mode is understood.
5. **Correlate adjacent layers:** Check process, kernel, filesystem, network, DNS, time, identity, audit, and SELinux evidence as appropriate.
6. **Form one hypothesis:** State what evidence supports it and what observation would disprove it.
7. **Make one controlled change:** Use a maintenance window, backup, console path, and rollback command.
8. **Validate service metrics:** Confirm application latency, error rate, authentication, data integrity, and logs—not only command success.
9. **Restore or persist:** Roll back failed experiments and make successful changes through approved configuration management.
10. **Document RCA:** Record root cause, contributing factors, corrective action, prevention, and monitoring.

## 9. Production cautions

- Never place a password directly on the command line.
- Do not use `passwd -d` on production accounts without understanding PAM `nullok` behavior.
- Locking a password does not revoke SSH keys, active sessions, Kerberos tickets, API tokens, or sudo credentials.
- Preserve emergency administrative access before changing PAM or root credentials.
- Never copy example users, paths, ports, addresses, or devices into production without validation.
- Commands that change credentials, access, labels, firewall rules, packages, audit rules, or services require change control.
- Keep an independent administrative path for SSH, PAM, firewall, DNS, and authentication work.

## 10. Quick practice lab

1. Create a test user.
2. Check status with `passwd -S`.
3. Set a password interactively.
4. Lock and unlock the password while testing console and SSH behavior.
5. Compare the result with `chage -l`.
