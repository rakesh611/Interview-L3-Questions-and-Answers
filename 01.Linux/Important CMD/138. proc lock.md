# 138. /proc/locks (requested as /proc/lock)

> **Scope:** Corporate/L3 Linux administration, incident troubleshooting, safe change execution, and interview preparation.

## 1. What it is

`/proc/locks` lists current advisory file locks and leases known to the kernel. The singular `/proc/lock` is not the standard interface; this guide preserves the requested filename while documenting `/proc/locks`.

## 2. Production importance

- Provides a repeatable method for diagnosing or controlling the relevant Linux subsystem.
- Produces evidence suitable for incident timelines, change records, problem management, and audit review.
- Encourages before-and-after measurement instead of unverified tuning or repair.
- Separates command success from actual application availability, security, and data integrity.

- **Primary package/interface:** Kernel procfs interface

## 4. Core concepts

- The table includes POSIX record locks, BSD `flock` locks, open-file-description locks, and leases when present.
- Locks can be advisory or mandatory depending on type and filesystem behavior.
- Read and write locks cover byte ranges, which may extend to EOF.
- A lock can block another request without preventing ordinary I/O from applications that ignore advisory locking.
- The device and inode fields identify the locked file but are not a pathname.
- Network filesystems can have additional lock-manager and server-state considerations.

## 5. Important commands

| Command | Purpose | Risk |
|---|---|---|
| `cat /proc/locks` | Display all current kernel file locks. | Read-only |
| `sudo cat /proc/locks \| less` | Inspect the complete table. | Read-only |
| `grep ' 1234 ' /proc/locks` | Find entries for PID 1234. | Read-only |
| `awk '{print $2,$4,$5,$6,$7,$8}' /proc/locks \| column -t` | Display selected fields. | Read-only |
| `lslocks` | Show a human-readable lock table. | Read-only |
| `lslocks -p 1234` | Show locks associated with one PID. | Read-only |
| `stat -c 'device=%D inode=%i path=%n' /path/file` | Obtain a file's device and inode. | Read-only |
| `find /mount -xdev -inum 12345 -print` | Resolve an inode to a path within a filesystem. | Read-only |
| `lsof -p 1234` | Correlate a lock holder with open files. | Read-only |
| `strace -e trace=flock,fcntl command` | Observe lock-related system calls. | Read-only |
| `cat /proc/1234/fdinfo/5` | Inspect descriptor lock information where exposed. | Read-only |
| `nfsstat -c; rpcinfo -p nfsserver` | Add NFS evidence when the locked file is remote. | Read-only |

## 7. Output interpretation

- The lock type can be POSIX, FLOCK, OFDLCK, or LEASE depending on kernel support.
- The mode is commonly READ or WRITE.
- The PID identifies the owning process for applicable lock types.
- The `major:minor:inode` tuple identifies the filesystem object.
- Range values show the first and last locked byte; `EOF` means through end of file.
- A leading arrow in some representations can indicate a blocked lock waiting behind another lock.

## 8. Corporate/L3 troubleshooting workflow

1. **Confirm impact:** Record affected applications, users, start time, error rate, latency, and business severity.
2. **Identify scope:** Determine whether the issue is host-wide, process-specific, filesystem-specific, network-path-specific, or limited to one namespace.
3. **Preserve evidence:** Save logs, configuration, counters, command output, package versions, and timestamps before changing state.
4. **Establish ownership:** Identify whether systemd, NetworkManager, firewalld, TuneD, udev, a backup scheduler, configuration management, or the application owns the setting.
5. **Use read-only inspection first:** Confirm the hypothesis with at least two independent evidence sources.
6. **Control the test:** Make only one bounded change and define the rollback command in advance.
7. **Measure service behavior:** Validate latency, throughput, errors, data consistency, authentication, and client experience.
8. **Persist correctly:** Apply successful changes through the supported configuration source rather than an ad hoc runtime command.
9. **Close the incident:** Document root cause, contributing conditions, corrective action, monitoring, and prevention.

## 9. Production cautions

- Do not kill a lock holder until application transaction and recovery behavior are known.
- Advisory locks can be intentional and long-lived.
- Path resolution by inode must stay on the correct filesystem.
- Capture the table quickly because locks can appear and disappear rapidly.
- Replace all example users, paths, devices, addresses, ports, repositories, and services only after validation.
- Keep console or out-of-band access for firewall, bootloader, storage, authentication, and network changes.
- Back up data and configuration before destructive, recursive, or boot-critical commands.

## 10. Practice lab
