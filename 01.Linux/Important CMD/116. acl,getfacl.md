# 116. ACL, getfacl, and setfacl

> **Level:** Linux Corporate/L3 administration and troubleshooting.

## 1. What it is

POSIX Access Control Lists provide permissions beyond the traditional owner/group/other mode bits. `getfacl` displays ACLs and `setfacl` creates, modifies, removes, copies, or restores them.

## 2. Why it matters in production

- Provides a repeatable method to inspect, validate, or control an important Linux subsystem.
- Produces evidence that can be attached to incident, change, problem, audit, and capacity records.
- Helps distinguish configuration, permission, kernel, service, network, storage, security, and application failures.
- Supports before-and-after validation rather than unmeasured configuration changes.

## 4. Core concepts

- Access ACLs apply to an existing file or directory.
- Default ACLs on a directory are inherited by newly created children.
- The ACL mask limits the effective rights of named users, named groups, and the owning group.
- Traditional mode bits and ACL entries are synchronized in specific ways.
- ACL inheritance is not retroactive.
- Filesystem and mount support must be available, though modern enterprise filesystems generally support ACLs.

## 5. Important commands

| Command | Purpose | Operational risk |
|---|---|---|
| `getfacl /data/project` | Display the ACL. | Read-only |
| `getfacl -p /data/project` | Preserve absolute path names in output. | Read-only |
| `getfacl -e /data/project` | Show effective rights. | Read-only |
| `setfacl -m u:appuser:rwx /data/project` | Grant a named user permissions. | Permission change |
| `setfacl -m g:developers:r-x /data/project` | Grant a named group permissions. | Permission change |
| `setfacl -m m:rwx /data/project` | Set the ACL mask. | Permission change |
| `setfacl -d -m u:appuser:rwx,g:developers:r-x,m:rwx /data/project` | Set default inherited ACL entries. | Permission change |
| `setfacl -x u:appuser /data/project` | Remove one named-user entry. | Permission change |
| `setfacl -b /data/project` | Remove extended access ACL entries. | Broad permission change |
| `setfacl -k /data/project` | Remove the default ACL. | Permission change |
| `getfacl -R -p /data/project > /root/project.acl` | Back up ACLs. | Read-only |
| `setfacl --restore=/root/project.acl` | Restore ACLs from a backup. | Bulk permission change |

## 7. How to interpret the output

- A line ending with `#effective:` shows rights reduced by the mask.
- `default:` entries exist only on directories and govern future children.
- A `+` in `ls -l` output commonly indicates an extended ACL or other extended metadata.
- The group mode bits often display the ACL mask rather than only the owning-group entry.
- A user can gain access through several matching group entries, constrained by the mask.

## 8. L3 troubleshooting workflow

1. **Define impact:** Identify the affected service, users, start time, scope, and business symptom.
2. **Preserve evidence:** Capture relevant logs, configuration, counters, timestamps, versions, and current state.
3. **Confirm ownership:** Determine whether systemd, NetworkManager, authselect, firewalld, policy, automation, or another manager owns the configuration.
4. **Use read-only checks first:** Avoid changing state before the failure mode is understood.
5. **Correlate adjacent layers:** Check process, kernel, filesystem, network, DNS, time, identity, audit, and SELinux evidence as appropriate.
6. **Form one hypothesis:** State what evidence supports it and what observation would disprove it.
7. **Make one controlled change:** Use a maintenance window, backup, console path, and rollback command.
8. **Validate service metrics:** Confirm application latency, error rate, authentication, data integrity, and logs—not only command success.
9. **Restore or persist:** Roll back failed experiments and make successful changes through approved configuration management.
10. **Document RCA:** Record root cause, contributing factors, corrective action, prevention, and monitoring.

## 9. Production cautions

- Do not recursively add ACLs without understanding inheritance and application ownership.
- Back up ACLs before bulk changes.
- ACLs do not override SELinux denials or read-only mount state.
- Use groups and default ACLs instead of many one-off user entries where possible.
- Never copy example users, paths, ports, addresses, or devices into production without validation.
- Commands that change credentials, access, labels, firewall rules, packages, audit rules, or services require change control.
- Keep an independent administrative path for SSH, PAM, firewall, DNS, and authentication work.

## 10. Quick practice lab

1. Create a group-shared directory.
2. Set an access ACL and default ACL.
3. Create files as two users.
4. Change the mask and inspect effective rights.
5. Back up and restore the ACL tree.
