# `kdumpctl` Command Guide for Linux

> **Focus:** RHEL 8/9, CentOS Stream, Rocky Linux, AlmaLinux, and other RPM-based systems using `kexec-tools`  
> **Audience:** Linux administrators, production support engineers, RHCSA/RHCE/RH442 learners  
> **Primary package:** `kexec-tools`

---

## 1. What is `kdumpctl`?

`kdumpctl` is the command-line control and diagnostic utility for the Linux
`kdump` crash-dump mechanism.

It is used to:

- Check whether `kdump` is operational.
- Load or unload the crash-capture kernel.
- Rebuild the special kdump initramfs.
- Display reserved crash-kernel memory.
- Estimate the required `crashkernel` memory.
- Configure the recommended `crashkernel` value.
- Configure SSH key authentication for a remote dump target.
- Test whether a real kernel crash produces a valid `vmcore`.

Basic syntax:

```bash
kdumpctl COMMAND
```

Examples:

```bash
sudo kdumpctl status
sudo kdumpctl showmem
sudo kdumpctl estimate
```

`kdumpctl` is supplied by the `kexec-tools` package.

```bash
rpm -qf "$(command -v kdumpctl)"
```

Example output:

```text
kexec-tools-2.0.x-xx.el9.x86_64
```

---

## 2. What is `kdump`?

`kdump` is the Linux kernel crash-dump mechanism.

When the production kernel crashes:

1. The active kernel panics.
2. The system uses `kexec` to boot a small crash-capture kernel.
3. The capture kernel accesses the failed kernel's reserved memory.
4. `makedumpfile` copies selected memory pages into a `vmcore`.
5. The dump is stored locally or transferred to an NFS/SSH target.
6. The system performs the configured final action, normally a reboot.

The main result is usually:

```text
/var/crash/<host-or-address>-<date-time>/vmcore
```

Other useful files can include:

```text
vmcore-dmesg.txt
```

The `vmcore` can be analyzed with the `crash` utility and the matching
uncompressed kernel debug image.

---

## 3. Why a second kernel is required

The original kernel cannot reliably write its own memory after a serious panic.
For that reason, `kdump` reserves memory at boot for a second kernel known as
the **capture kernel** or **crash kernel**.

The memory is reserved with the kernel parameter:

```text
crashkernel=<size>
```

Example:

```text
crashkernel=512M
```

Verify the current boot command line:

```bash
cat /proc/cmdline
```

Display only the `crashkernel` parameter:

```bash
tr ' ' '\n' </proc/cmdline | grep '^crashkernel='
```

Example output:

```text
crashkernel=512M
```

No memory can be reserved after the normal kernel has already booted. Therefore,
changing `crashkernel=` normally requires a reboot.

## 4. `kdumpctl` versus `systemctl`

Use `systemctl` for normal systemd service management:

```bash
sudo systemctl enable --now kdump.service
sudo systemctl restart kdump.service
sudo systemctl stop kdump.service
sudo systemctl status kdump.service
```

Use `kdumpctl` when you need kdump-specific validation or maintenance:

```bash
sudo kdumpctl status
sudo kdumpctl showmem
sudo kdumpctl estimate
sudo kdumpctl rebuild
sudo kdumpctl reset-crashkernel --kernel=ALL
```

Important difference:

- `systemctl status kdump` shows the systemd unit state.
- `kdumpctl status` checks whether the crash-capture configuration is actually
  operational.

A service may be enabled in systemd but still fail because no crash-kernel
memory is reserved, the dump target is unavailable, or the kdump initramfs
cannot be built.

## 5. Important files and directories

| Path | Purpose |
|---|---|
| `/usr/bin/kdumpctl` | Main control utility |
| `/etc/kdump.conf` | Dump target, collector and failure-action configuration |
| `/etc/sysconfig/kdump` | Capture-kernel command-line configuration |
| `/proc/cmdline` | Command line used by the currently running kernel |
| `/sys/kernel/kexec_crash_loaded` | Indicates whether a crash kernel is loaded |
| `/sys/kernel/kexec_crash_size` | Reserved crash-kernel memory size in bytes |
| `/boot/initramfs-$(uname -r)kdump.img` | Common kdump initramfs filename |
| `/var/crash/` | Default local crash-dump location |
| `/var/lib/kdump/` | Runtime or generated kdump data on some releases |
| `/usr/share/doc/kexec-tools/` | Package documentation, depending on release |

Check whether the expected kdump initramfs exists:

```bash
ls -lh /boot/initramfs-"$(uname -r)"kdump.img
```

Check the crash-kernel load flag:

```bash
cat /sys/kernel/kexec_crash_loaded
```

Interpretation:

```text
1 = crash kernel is loaded
0 = crash kernel is not loaded
```

Display the reserved size in MiB:

```bash
awk '{printf "%.0f MiB\n", $1/1024/1024}' /sys/kernel/kexec_crash_size
```

# 7. Important `kdumpctl` commands

## 7.1 `kdumpctl status`

### Purpose

Checks whether `kdump` is operational.

```bash
sudo kdumpctl status
```

Healthy example:

```text
kdump: Kdump is operational
```

A failure may show messages such as:

```text
kdump: No memory reserved for crash kernel
```

or:

```text
kdump: Kdump is not operational
```

### Script-friendly use

`kdumpctl status` returns a non-zero exit code when kdump is not operational.

```bash
if sudo kdumpctl status; then
    echo "PASS: kdump is operational"
else
    echo "FAIL: kdump is not operational"
fi
```

Display the return code:

```bash
sudo kdumpctl status
echo $?
```

Typical interpretation:

```text
0     command succeeded; kdump is operational
non-0 kdump validation failed
```

### Production health check

```bash
sudo kdumpctl status &&
cat /sys/kernel/kexec_crash_loaded &&
sudo systemctl is-enabled kdump.service
```

---

## 7.2 `kdumpctl start`

### Purpose

Loads the configured crash kernel and prepares kdump.

```bash
sudo kdumpctl start
```

For routine systemd service management, prefer:

```bash
sudo systemctl start kdump.service
```

Use `kdumpctl start` mainly when you want its kdump-specific output during
troubleshooting.

Verify:

```bash
sudo kdumpctl status
cat /sys/kernel/kexec_crash_loaded
```

---

## 7.3 `kdumpctl stop`

### Purpose

Unloads or disarms the crash-capture kernel for the current boot.

```bash
sudo kdumpctl stop
```

Preferred service form:

```bash
sudo systemctl stop kdump.service
```

Verify:

```bash
cat /sys/kernel/kexec_crash_loaded
```

Expected after stopping:

```text
0
```

Stopping kdump means a subsequent kernel panic might not produce a crash dump.

---

## 7.4 `kdumpctl restart`

### Purpose

Stops and starts kdump again.

```bash
sudo kdumpctl restart
```

Use this command after changing:

```text
/etc/kdump.conf
/etc/sysconfig/kdump
```

Example workflow:

```bash
sudo vi /etc/kdump.conf
sudo kdumpctl restart
sudo kdumpctl status
```

The systemd equivalent is:

```bash
sudo systemctl restart kdump.service
```

A restart can rebuild or reload required kdump components depending on the
package version and configuration state.

---

## 7.5 `kdumpctl reload`

### Purpose

Reloads the crash-kernel image and kdump initramfs without intentionally
triggering a rebuild.

```bash
sudo kdumpctl reload
```

Use it when:

- The existing kdump initramfs is valid.
- You only need to reload the crash kernel.
- You want to avoid the time required for a full rebuild.

Verify afterward:

```bash
sudo kdumpctl status
cat /sys/kernel/kexec_crash_loaded
```

### Reload versus rebuild

```text
reload  -> load existing kdump kernel/initramfs again
rebuild -> regenerate the kdump initramfs
```

---

## 7.6 `kdumpctl rebuild`

### Purpose

Rebuilds the special kdump initramfs.

```bash
sudo kdumpctl rebuild
```

Use it after changes that affect capture-kernel contents, such as:

- Storage drivers.
- Network drivers for NFS or SSH dumping.
- Multipath configuration.
- LUKS configuration.
- Driver-blacklist configuration.
- `/etc/kdump.conf` changes.
- `/etc/sysconfig/kdump` changes.
- Kernel or `kexec-tools` updates.

Example workflow:

```bash
sudo kdumpctl rebuild
sudo kdumpctl reload
sudo kdumpctl status
```

Review the generated image:

```bash
ls -lh /boot/initramfs-"$(uname -r)"kdump.img
```

Inspect its contents:

```bash
lsinitrd /boot/initramfs-"$(uname -r)"kdump.img | less
```

Troubleshoot rebuild errors:

```bash
sudo journalctl -u kdump.service -b --no-pager
sudo kdumpctl rebuild
```

---

## 7.7 `kdumpctl showmem`

### Purpose

Displays the amount of memory reserved for the crash kernel.

```bash
sudo kdumpctl showmem
```

Example output:

```text
512M
```

Cross-check the boot parameter:

```bash
tr ' ' '\n' </proc/cmdline | grep '^crashkernel='
```

Cross-check the kernel interface:

```bash
cat /sys/kernel/kexec_crash_size
```

If `showmem` reports zero or no reserved memory:

1. Verify `crashkernel=` in `/proc/cmdline`.
2. Configure the parameter for the required kernels.
3. Reboot.
4. Run `kdumpctl showmem` again.

---

## 7.8 `kdumpctl estimate`

### Purpose

Estimates an appropriate `crashkernel` reservation for the current system.

```bash
sudo kdumpctl estimate
```

The estimate can consider items such as:

- Kernel image size.
- Required kernel modules.
- Kdump initramfs size.
- Runtime reservation.
- Encrypted dump-target requirements.
- Large modules.

Example-style output:

```text
Reserved crashkernel:    256M
Recommended crashkernel: 512M
Kernel image size:        45M
Kernel modules size:      20M
Initramfs size:           30M
Runtime reservation:      64M
```

Important:

- The result is a best-effort recommendation.
- Complex SAN, multipath, LUKS, network or large-memory systems may need more.
- A recommendation must still be validated with an actual controlled crash test.

Run before changing memory:

```bash
sudo kdumpctl showmem
sudo kdumpctl estimate
```

---

## 7.9 `kdumpctl get-default-crashkernel`

### Purpose

Displays the default `crashkernel` value recommended by the installed
`kexec-tools` package.

```bash
sudo kdumpctl get-default-crashkernel
```

This is different from `estimate`:

```text
get-default-crashkernel -> package-provided default recommendation
estimate                 -> machine/configuration-specific best-effort estimate
showmem                  -> memory currently reserved by the running kernel
```

Useful comparison:

```bash
echo "Reserved:"
sudo kdumpctl showmem

echo "Estimated:"
sudo kdumpctl estimate

echo "Package default:"
sudo kdumpctl get-default-crashkernel
```

Availability and exact output can vary with the installed `kexec-tools`
version.

---

## 7.10 `kdumpctl reset-crashkernel`

### Purpose

Sets the `crashkernel` parameter to the default value recommended by the
installed `kexec-tools` package.

For the running/default target kernel:

```bash
sudo kdumpctl reset-crashkernel
```

For all installed kernels:

```bash
sudo kdumpctl reset-crashkernel --kernel=ALL
```

For the default boot kernel:

```bash
sudo kdumpctl reset-crashkernel --kernel=DEFAULT
```

For one kernel image:

```bash
sudo kdumpctl reset-crashkernel \
  --kernel=/boot/vmlinuz-$(uname -r)
```

After changing the kernel command line:

```bash
sudo reboot
```

After reboot:

```bash
cat /proc/cmdline
sudo kdumpctl showmem
sudo kdumpctl restart
sudo kdumpctl status
```

### RHEL 9 note

Do not depend on:

```text
crashkernel=auto
```

RHEL 9 and later use explicit or package-recommended crash-kernel values rather
than the older `crashkernel=auto` behavior.

### Verify boot entries

```bash
sudo grubby --info=ALL | grep -E '^(index|kernel|args)='
```

---

## 7.11 `kdumpctl propagate`

### Purpose

Helps configure SSH public-key authentication for a remote SSH dump target.

During a crash, interactive password authentication is not available.
Therefore, the capture kernel must use a preconfigured key.

Example `/etc/kdump.conf`:

```text
ssh kdumpuser@192.0.2.50
sshkey /root/.ssh/kdump_id_rsa
path /var/crash
```

Run:

```bash
sudo kdumpctl propagate
```

Then rebuild and restart:

```bash
sudo kdumpctl rebuild
sudo kdumpctl restart
sudo kdumpctl status
```

Manually test SSH authentication before relying on it:

```bash
sudo ssh -i /root/.ssh/kdump_id_rsa \
  kdumpuser@192.0.2.50 \
  'hostname; test -w /var/crash && echo writable'
```

Also verify:

- DNS or IP reachability.
- Routing in the capture kernel.
- Required NIC driver in the kdump initramfs.
- Correct server host key handling.
- Remote directory permissions.
- SELinux and firewall policy.
- Sufficient remote disk space.

---

## 7.12 `kdumpctl test`

### Purpose

Performs a real end-to-end kdump test by deliberately crashing the kernel and
checking whether a `vmcore` is produced.

```bash
sudo kdumpctl test
```

Some versions also provide:

```bash
sudo kdumpctl test --force
```

`--force` can remove the interactive confirmation and is especially dangerous.

> **DANGER:** This command intentionally crashes the system. It can cause
> service interruption, incomplete writes and data loss. Never run it on an
> active production system. Use an approved maintenance window, confirmed
> backups, console access and a rollback/recovery plan.

After the machine reboots:

```bash
sudo kdumpctl status
sudo find /var/crash -maxdepth 3 -type f \
  \( -name vmcore -o -name vmcore-dmesg.txt \) -ls
```

The exact availability of `kdumpctl test` depends on the installed
`kexec-tools` version. Check locally:

```bash
man kdumpctl
kdumpctl 2>&1 | less
```

---

## 7.13 `kdumpctl setup-crypttab`

### Purpose

Helps configure `/etc/crypttab` so kdump can save a `vmcore` to a
LUKS-encrypted volume without interactive passphrase entry.

```bash
sudo kdumpctl setup-crypttab
```

This command is relevant only on supported architectures and package versions.

Run it when:

- The dump target is LUKS encrypted.
- `kdumpctl restart` requests an unlock passphrase.
- The capture kernel cannot unlock the dump target automatically.

Recommended workflow:

```bash
sudo kdumpctl estimate
sudo kdumpctl setup-crypttab
sudo kdumpctl rebuild
sudo kdumpctl restart
sudo kdumpctl status
```

Encrypted targets often require additional crash-kernel memory.

# 9. Basic RHEL 9 setup example

## Step 1: Install required packages

```bash
sudo dnf install -y kexec-tools
```

Optionally install analysis tools:

```bash
sudo dnf install -y crash
```

Kernel debuginfo packages may require enabling the appropriate debug
repositories.

## Step 2: Check current reservation

```bash
sudo kdumpctl showmem
cat /proc/cmdline
```

## Step 3: Estimate required memory

```bash
sudo kdumpctl estimate
sudo kdumpctl get-default-crashkernel
```

## Step 4: Configure all installed kernels

```bash
sudo kdumpctl reset-crashkernel --kernel=ALL
```

Alternative manual example:

```bash
sudo grubby --update-kernel=ALL --args="crashkernel=512M"
```

Use an appropriately validated size rather than copying `512M` blindly.

## Step 5: Reboot

```bash
sudo reboot
```

## Step 6: Validate after reboot

```bash
tr ' ' '\n' </proc/cmdline | grep '^crashkernel='
sudo kdumpctl showmem
```

## Step 7: Configure the dump target

Edit:

```bash
sudo vi /etc/kdump.conf
```

Simple local example:

```text
path /var/crash
core_collector makedumpfile -l --message-level 1 -d 31
failure_action reboot
final_action reboot
```

Ensure the directory exists:

```bash
sudo install -d -m 0700 /var/crash
sudo restorecon -Rv /var/crash
```

## Step 8: Enable and start kdump

```bash
sudo systemctl enable --now kdump.service
```

## Step 9: Validate

```bash
sudo kdumpctl status
cat /sys/kernel/kexec_crash_loaded
sudo systemctl status kdump.service --no-pager
```

## Step 10: Schedule a controlled crash test

Only during an approved maintenance window:

```bash
sudo kdumpctl test
```

On older setups, administrators may use:

```bash
echo c | sudo tee /proc/sysrq-trigger
```

This also deliberately crashes the kernel and carries the same data-loss and
outage risk.

# 10. Example `/etc/kdump.conf`

## 10.1 Local filesystem target

```text
path /var/crash
core_collector makedumpfile -l --message-level 1 -d 31
failure_action reboot
final_action reboot
```

Apply:

```bash
sudo install -d -m 0700 /var/crash
sudo restorecon -Rv /var/crash
sudo kdumpctl restart
sudo kdumpctl status
```

## 10.2 Dedicated filesystem target

Example:

```text
xfs UUID=11111111-2222-3333-4444-555555555555
path /kdump
core_collector makedumpfile -l --message-level 1 -d 31
failure_action shell
final_action reboot
```

Important: when a filesystem target is specified, `path` is relative to that
target. Avoid accidentally producing a duplicated path such as:

```text
/var/crash/var/crash
```

Prefer stable device identifiers:

```bash
lsblk -f
blkid
```

Use `UUID=` or `LABEL=` rather than an unstable name such as `/dev/sdb1`.

## 10.3 NFS target

```text
nfs 192.0.2.60:/exports/kdump
path /
core_collector makedumpfile -l --message-level 1 -d 31
failure_action reboot
```

Apply:

```bash
sudo kdumpctl rebuild
sudo kdumpctl restart
sudo kdumpctl status
```

## 10.4 SSH target

```text
ssh kdumpuser@192.0.2.50
sshkey /root/.ssh/kdump_id_rsa
path /var/crash
core_collector makedumpfile -l --message-level 1 -d 31
failure_action reboot
```

Apply:

```bash
sudo kdumpctl propagate
sudo kdumpctl rebuild
sudo kdumpctl restart
sudo kdumpctl status
```

# 11. Example `/etc/sysconfig/kdump`

This file controls the command line used by the capture kernel.

Example:

```bash
KDUMP_COMMANDLINE_REMOVE="hugepages hugepagesz quiet"
KDUMP_COMMANDLINE_APPEND="irqpoll nr_cpus=1 reset_devices cgroup_disable=memory"
```

To blacklist problematic drivers in the capture kernel:

```bash
KDUMP_COMMANDLINE_APPEND="rd.driver.blacklist=example_driver modprobe.blacklist=example_driver"
```

After editing:

```bash
sudo kdumpctl rebuild
sudo kdumpctl restart
sudo kdumpctl status
```

Do not copy tuning parameters without a specific reason. Removing a storage or
network driver required by the dump target can prevent the `vmcore` from being
saved.

# 13. Troubleshooting `kdumpctl`

## 13.1 Error: No memory reserved for crash kernel

Check:

```bash
cat /proc/cmdline
sudo kdumpctl showmem
```

Fix:

```bash
sudo kdumpctl reset-crashkernel --kernel=ALL
sudo reboot
```

After reboot:

```bash
sudo kdumpctl restart
sudo kdumpctl status
```

---

## 13.2 `crashkernel` configured but `showmem` is zero

Possible causes:

- The edited boot entry is not the entry that booted.
- The system has not been rebooted since the change.
- The value cannot be reserved because of memory layout constraints.
- The syntax is invalid.
- Secure Boot or UKI-based boot configuration uses a different update method.
- The bootloader configuration did not update correctly.

Check:

```bash
uname -r
cat /proc/cmdline
sudo grubby --default-kernel
sudo grubby --info=ALL
dmesg | grep -i crash
```

---

## 13.3 `kdumpctl status` says kdump is not operational

Collect:

```bash
sudo kdumpctl status
sudo systemctl status kdump.service --no-pager -l
sudo journalctl -u kdump.service -b --no-pager
sudo journalctl -k -b | grep -iE 'kdump|kexec|crashkernel'
```

Then verify:

```bash
sudo kdumpctl showmem
cat /sys/kernel/kexec_crash_loaded
df -hT /var/crash
```

---

## 13.4 Kdump initramfs rebuild fails

Run:

```bash
sudo kdumpctl rebuild
```

Inspect logs:

```bash
sudo journalctl -u kdump.service -b -n 200 --no-pager
```

Check `/boot` capacity:

```bash
df -hT /boot /boot/efi
df -i /boot /boot/efi
```

Inspect existing images:

```bash
ls -lh /boot/initramfs-*kdump.img
```

Common causes:

- `/boot` is full.
- Required driver or dracut module is missing.
- Incorrect NFS/SSH target configuration.
- Broken multipath or LUKS configuration.
- Invalid line in `/etc/kdump.conf`.
- Permission or SELinux denial.
- Unsupported or third-party kernel modules.

---

## 13.5 Dump target directory does not exist

On RHEL 9, create a configured local path before starting kdump.

```bash
sudo install -d -m 0700 /var/crash
sudo restorecon -Rv /var/crash
sudo kdumpctl restart
```

For a custom path:

```bash
sudo install -d -m 0700 /srv/kdump
sudo semanage fcontext -a -t var_crash_t '/srv/kdump(/.*)?'
sudo restorecon -Rv /srv/kdump
```

The exact SELinux type and policy requirement should be validated for your
release and target design.

---

## 13.6 Not enough disk space for `vmcore`

Check:

```bash
df -hT /var/crash
du -sh /var/crash/*
```

Estimate memory size:

```bash
free -h
grep MemTotal /proc/meminfo
```

A raw dump can approach the amount of physical RAM, although `makedumpfile`
filtering and compression usually reduce the stored size.

Review the collector:

```bash
grep -E '^[[:space:]]*core_collector' /etc/kdump.conf
```

Example compressed collector:

```text
core_collector makedumpfile -l --message-level 1 -d 31
```

---

## 13.7 SSH dump fails

Check normal SSH access:

```bash
sudo ssh -i /root/.ssh/kdump_id_rsa \
  kdumpuser@192.0.2.50 \
  'id; df -h; test -w /var/crash && echo writable'
```

Verify configuration:

```bash
grep -E '^[[:space:]]*(ssh|sshkey|path)' /etc/kdump.conf
```

Re-run:

```bash
sudo kdumpctl propagate
sudo kdumpctl rebuild
sudo kdumpctl restart
```

Inspect whether the NIC driver exists in the image:

```bash
lsinitrd /boot/initramfs-"$(uname -r)"kdump.img | \
grep -iE 'network|<driver-name>'
```

---

## 13.8 NFS dump fails

Check NFS from the normal kernel:

```bash
showmount -e 192.0.2.60
sudo mount -t nfs 192.0.2.60:/exports/kdump /mnt
touch /mnt/kdump-write-test
rm -f /mnt/kdump-write-test
sudo umount /mnt
```

Verify the capture initramfs contains required network and NFS components:

```bash
lsinitrd /boot/initramfs-"$(uname -r)"kdump.img | \
grep -iE 'nfs|network'
```

---

## 13.9 SELinux blocks kdump

Look for denials:

```bash
sudo ausearch -m AVC,USER_AVC -ts boot
sudo journalctl -t setroubleshoot --since today
```

Check labels:

```bash
ls -Zd /var/crash
```

Restore standard labels:

```bash
sudo restorecon -Rv /var/crash
```

Do not disable SELinux as the first troubleshooting step.

## 13.10 `/proc/kcore` or KASLR-related loading problem

Check:

```bash
sysctl kernel.kptr_restrict
```

Common RHEL recommendation:

```text
kernel.kptr_restrict = 1
```

Apply through a persistent sysctl file only after validating organizational
security standards:

```bash
echo 'kernel.kptr_restrict = 1' | \
sudo tee /etc/sysctl.d/90-kdump.conf

sudo sysctl --system
sudo kdumpctl restart
```

## 13.11 `kdumpctl start` takes a long time

Investigate:

```bash
sudo journalctl -fu kdump.service
```

Check target latency:

```bash
time stat /var/crash
time df -h /var/crash
```

For NFS/SSH, check DNS, routing and connection timeout:

```bash
getent hosts <dump-server>
ip route get <dump-server-ip>
```

Also inspect:

- Slow or unavailable dump target.
- DNS timeout.
- Multipath path failure.
- LUKS unlock or cryptsetup delay.
- Very large kdump initramfs.
- Storage discovery timeout.

# 14. Safe controlled testing procedure

A crash test is the only complete proof that the design can generate a usable
`vmcore`, but it is disruptive.

## Before the test

- Obtain an approved maintenance window.
- Stop or drain applications.
- Confirm backups.
- Confirm out-of-band console access.
- Confirm storage and filesystem health.
- Confirm `kdumpctl status`.
- Record the expected dump path.
- Ensure monitoring teams know the outage is planned.
- Confirm the system will boot automatically.
- Ensure clustering or fencing will not create an unintended incident.

Commands:

```bash
date
hostnamectl
uptime
sudo kdumpctl status
sudo kdumpctl showmem
cat /sys/kernel/kexec_crash_loaded
df -hT /var/crash
```

## Trigger

Preferred when available:

```bash
sudo kdumpctl test
```

Traditional manual trigger:

```bash
echo c | sudo tee /proc/sysrq-trigger
```

## After reboot

```bash
sudo kdumpctl status
last -x | head -20
sudo find /var/crash -maxdepth 3 -type f -printf '%TY-%Tm-%Td %TT %s %p\n'
```

Check:

```bash
sudo ls -lh /var/crash/*/vmcore
sudo head -100 /var/crash/*/vmcore-dmesg.txt
```

# 15. Basic `vmcore` analysis example

Install the crash utility:

```bash
sudo dnf install -y crash
```

You need:

- The generated `vmcore`.
- A matching uncompressed kernel debug image, commonly named `vmlinux`.
- Debug symbols for the exact kernel release.

Check the crashed kernel version from `vmcore-dmesg.txt`:

```bash
grep -m1 'Linux version' /var/crash/*/vmcore-dmesg.txt
```

Start analysis:

```bash
sudo crash \
  /usr/lib/debug/lib/modules/<kernel-version>/vmlinux \
  /var/crash/<dump-directory>/vmcore
```

Useful commands inside `crash`:

```text
sys
log
bt
ps
ps -m
kmem -i
files
mount
mod
dev
foreach bt
```

Exit:

```text
quit
```

Never analyze with a `vmlinux` that does not match the crashed kernel.

# 17. Complete diagnostic collection script

Save as:

```text
kdump-health-check.sh
```

Script:

```bash
#!/usr/bin/env bash

set -u

section() {
    printf '\n===== %s =====\n' "$1"
}

section "Date"
date --iso-8601=seconds

section "Host"
hostnamectl 2>&1 || hostname

section "Kernel"
uname -a

section "Packages"
rpm -q kexec-tools kernel-core 2>&1

section "Command location"
command -v kdumpctl 2>&1

section "Current boot command line"
cat /proc/cmdline 2>&1

section "crashkernel parameter"
tr ' ' '\n' </proc/cmdline | grep '^crashkernel=' || \
    echo "No crashkernel parameter found"

section "Reserved memory"
sudo -n kdumpctl showmem 2>&1 || true

section "Estimated memory"
sudo -n kdumpctl estimate 2>&1 || true

section "Crash kernel loaded"
cat /sys/kernel/kexec_crash_loaded 2>&1 || true

section "Crash kernel size"
cat /sys/kernel/kexec_crash_size 2>&1 || true

section "kdumpctl status"
sudo -n kdumpctl status 2>&1 || true

section "systemd unit"
systemctl status kdump.service --no-pager -l 2>&1 || true

section "Enabled and active state"
systemctl is-enabled kdump.service 2>&1 || true
systemctl is-active kdump.service 2>&1 || true

section "Configuration"
sudo -n grep -vE '^[[:space:]]*(#|$)' /etc/kdump.conf 2>&1 || true

section "Sysconfig"
sudo -n grep -vE '^[[:space:]]*(#|$)' /etc/sysconfig/kdump 2>&1 || true

section "Kdump image"
ls -lh /boot/initramfs-*kdump.img 2>&1 || true

section "Dump target capacity"
df -hT /var/crash 2>&1 || true
df -i /var/crash 2>&1 || true

section "Recent crash files"
sudo -n find /var/crash -maxdepth 3 -type f \
    -printf '%TY-%Tm-%Td %TT %s %p\n' 2>&1 | tail -50 || true

section "Kdump journal"
sudo -n journalctl -u kdump.service -b -n 200 --no-pager 2>&1 || true

section "Kernel messages"
sudo -n journalctl -k -b --no-pager 2>&1 | \
    grep -iE 'kdump|kexec|crashkernel' || true
```

Make executable:

```bash
chmod +x kdump-health-check.sh
```

Run:

```bash
sudo ./kdump-health-check.sh | tee kdump-health-"$(hostname)"-$(date +%F).txt
```

# 18. Common interview questions

## What does `kdumpctl status` verify?

It checks the operational state of the kdump setup and returns a failure exit
status when kdump is not operational.

## Why is `crashkernel` memory required?

It reserves memory that remains available for the capture kernel after the
primary kernel panics.

## Why is a reboot required after changing `crashkernel=`?

Kernel memory reservation happens during boot, before normal memory allocation.

## What is the difference between `kdumpctl rebuild` and `reload`?

- `rebuild` regenerates the kdump initramfs.
- `reload` reloads the existing crash kernel and initramfs without a deliberate
  rebuild.

## Where is the dump stored?

The target is configured in `/etc/kdump.conf`. The common default is
`/var/crash`.

## What creates the compressed dump?

On RHEL-family systems, `makedumpfile` is normally the default collector.

## Why can `kdumpctl status` fail even when the service is enabled?

The unit can be enabled while the operational configuration fails because of
missing memory reservation, an inaccessible target, a bad initramfs, insufficient
space, or another runtime problem.

## How do you fully validate kdump?

A successful controlled crash test that generates a readable `vmcore` is the
strongest end-to-end validation.

# 19. Command cheat sheet

```bash
# Install
sudo dnf install -y kexec-tools

# Version/package
rpm -q kexec-tools
command -v kdumpctl

# Current status
sudo kdumpctl status

# Configure recommended value for all kernels

sudo kdumpctl start
sudo kdumpctl stop
sudo kdumpctl restart

# Preferred systemd lifecycle
sudo systemctl enable --now kdump.service
sudo systemctl restart kdump.service

# Rebuild or reload
sudo kdumpctl rebuild
sudo kdumpctl reload

# SSH target setup
sudo kdumpctl propagate

# LUKS target helper
sudo kdumpctl setup-crypttab

# Dangerous real crash test
sudo kdumpctl test

# Logs
sudo journalctl -u kdump.service -b
sudo journalctl -k -b | grep -iE 'kdump|kexec|crashkernel'

# Dump files
sudo find /var/crash -type f \
  \( -name vmcore -o -name vmcore-dmesg.txt \) -ls
```

# 20. Important safety notes

1. `kdumpctl test` and `/proc/sysrq-trigger` deliberately crash the machine.
2. Do not test on a live production server.
3. Reserve an approved maintenance window.
4. Confirm console or out-of-band access.
5. Confirm application and filesystem quiescence.
6. Confirm the dump target has adequate capacity.
7. Test again after major kernel, firmware, storage or networking changes.
8. Protect `vmcore` files because they can contain sensitive memory contents.
9. Limit access to `/var/crash` and remote dump repositories.
10. Retain dumps according to incident-response and data-retention policy.

## Final summary

`kdumpctl` is the main kdump-specific administration and validation tool. The
most important commands for daily Linux administration are:

```bash
kdumpctl status
kdumpctl showmem
kdumpctl estimate
kdumpctl restart
kdumpctl rebuild
kdumpctl reset-crashkernel --kernel=ALL
```

For normal service enabling and lifecycle operations, use:

```bash
systemctl enable --now kdump.service
systemctl restart kdump.service
```

For a production-ready configuration, do not stop at a successful service
status. Confirm the reserved memory, capture-kernel load state, dump-target
capacity, kdump initramfs, and the result of a controlled crash test.
