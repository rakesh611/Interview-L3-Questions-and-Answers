# 120. matchpathcon

> **Level:** Linux Corporate/L3 administration and troubleshooting.

## 1. What it is

`matchpathcon` queries the SELinux file-context policy and reports the default context expected for a pathname. It does not normally change the file; use `restorecon` to apply the policy-defined label.

## 2. Why it matters in production

- Provides a repeatable method to inspect, validate, or control an important Linux subsystem.
- Produces evidence that can be attached to incident, change, problem, audit, and capacity records.
- Helps distinguish configuration, permission, kernel, service, network, storage, security, and application failures.
- Supports before-and-after validation rather than unmeasured configuration changes.

## 4. Core concepts

- The expected label comes from SELinux file-context configuration, not from the file's current xattr.
- Path regex order and local customizations affect the selected context.
- `semanage fcontext` creates persistent local path mappings.
- `chcon` changes the current label but is usually not persistent against relabel or restorecon.
- A correct expected context does not guarantee an application is allowed; SELinux type enforcement still applies.
- Use absolute paths for reliable policy matching.

## 5. Important commands

| Command | Purpose | Operational risk |
|---|---|---|
| `matchpathcon /var/www/html/index.html` | Show the expected context for a path. | Read-only |
| `matchpathcon -V /var/www/html/index.html` | Verify the current context against policy. | Read-only |
| `matchpathcon -n /var/www/html/index.html` | Print only the expected context. | Read-only |
| `matchpathcon -m file /var/www/html/index.html` | Specify a file mode/type for matching where supported. | Read-only |
| `ls -Z /var/www/html/index.html` | Display the current SELinux context. | Read-only |
| `semanage fcontext -l \| grep '/var/www'` | Review persistent path mappings. | Read-only |
| `sudo semanage fcontext -a -t httpd_sys_content_t '/srv/web(/.*)?'` | Add a persistent custom mapping. | SELinux policy configuration change |
| `sudo restorecon -Rv /srv/web` | Apply the policy-defined labels. | Filesystem label change |
| `sudo restorecon -nRv /srv/web` | Preview relabel changes. | Read-only |
| `ausearch -m AVC -ts recent -i` | Review recent SELinux denials. | Read-only |

## 7. How to interpret the output

- Output normally contains a pathname and expected SELinux context.
- Verification reports a mismatch when the current xattr differs from policy.
- A custom `semanage fcontext` rule should appear before relying on `restorecon`.
- The type component, such as `httpd_sys_content_t`, is usually the most operationally important field.
- Context mismatches can result from move operations, archive restore, manual `chcon`, or unsupported copy methods.

## 8. L3 troubleshooting workflow

1. **Define impact:** Identify the affected service, users, start time, scope, and business symptom.
2. **Preserve evidence:** Capture relevant logs, configuration, counters, timestamps, versions, and current state.
3. **Confirm ownership:** Determine whether systemd, NetworkManager, authselect, firewalld, policy, automation, or another manager owns the configuration.
4. **Use read-only checks first:** Avoid changing state before the failure mode is understood.
5. **Correlate adjacent layers:** Check process, kernel, filesystem, network, DNS, time, identity, audit, and SELinux evidence as appropriate.
6. **Form one hypothesis:** State what evidence supports it and what observation would disprove it.
7. **Make one controlled change:** Use a maintenance window, backup, console path, and rollback command.
8. **Validate service metrics:** Confirm application latency, error rate, authentication, data integrity, and logs—not only command success.
9. **Restore or persist:** Roll back failed experiments and make successful changes through approved configuration management.
10. **Document RCA:** Record root cause, contributing factors, corrective action, prevention, and monitoring.

## 9. Production cautions

- Do not disable SELinux to solve a labeling problem.
- Use `restorecon -n` to preview broad recursive changes.
- Avoid broad regular expressions that relabel unrelated paths.
- Validate AVC cause before adding policy exceptions.
- Never copy example users, paths, ports, addresses, or devices into production without validation.
- Commands that change credentials, access, labels, firewall rules, packages, audit rules, or services require change control.
- Keep an independent administrative path for SSH, PAM, firewall, DNS, and authentication work.
