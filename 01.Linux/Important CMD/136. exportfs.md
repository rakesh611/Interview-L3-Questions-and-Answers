# 136. exportfs

> **Scope:** Corporate/L3 Linux administration, incident troubleshooting, safe change execution, and interview preparation.

## 1. What it is

`exportfs` manages the NFS server export table. It reads `/etc/exports` and files under `/etc/exports.d/`, updates the kernel or NFS server state, lists active exports, and unexports paths.

## 2. Production importance

- Provides a repeatable method for diagnosing or controlling the relevant Linux subsystem.
- Produces evidence suitable for incident timelines, change records, problem management, and audit review.
- Encourages before-and-after measurement instead of unverified tuning or repair.
- Separates command success from actual application availability, security, and data integrity.

## 3. Package or kernel interface

- **Primary package/interface:** nfs-utils
- Check availability and installed version before relying on an option:

```bash
command -v exportfs 2>/dev/null || true
rpm -q PACKAGE_NAME 2>/dev/null || true
COMMAND --version 2>/dev/null || COMMAND --help
```

## 4. Core concepts

- The configured export files and the currently active export table are different states.
- Client matching can use hosts, networks, netgroups, DNS names, or wildcards with different security implications.
- Options such as `rw`, `ro`, `root_squash`, `sync`, and `subtree_check` affect security and data behavior.
- NFSv4 uses a pseudo-filesystem namespace and can differ from NFSv3 mount discovery.
- DNS changes can influence hostname-based client matching.
- Exporting a parent and child path with inconsistent options can create surprises.

## 5. Important commands

| Command | Purpose | Risk |
|---|---|---|
| `sudo exportfs -v` | Display active exports and options. | Read-only |
| `sudo exportfs -s` | Display active exports in a concise format. | Read-only |
| `sudo exportfs -r` | Re-synchronize active exports with configuration. | NFS export reload |
| `sudo exportfs -rav` | Reload all configured exports verbosely. | NFS export reload |
| `sudo exportfs -a` | Export all configured filesystems. | NFS export change |
| `sudo exportfs -u client.example.com:/srv/share` | Unexport one client/path pair. | NFS access removal |
| `sudo exportfs -ua` | Unexport all filesystems. | Broad NFS outage |
| `sudo exportfs -i -o ro,sync 192.0.2.10:/srv/share` | Create an export while ignoring config files. | Temporary NFS export change |
| `cat /etc/exports; find /etc/exports.d -type f -maxdepth 1 -print -exec cat {} \;` | Review persistent configuration. | Read-only |
| `nfsconf --dump 2>/dev/null \|\| true` | Inspect effective NFS configuration where available. | Read-only |
| `showmount -e localhost` | Check NFSv3-style export visibility. | Read-only |
| `journalctl -u nfs-server -b` | Review server logs. | Read-only |

## 7. Output interpretation

- The verbose list shows the client selector followed by effective options.
- An export present in configuration but absent from `exportfs -v` was not activated successfully.
- A client can mount and still receive permission errors because filesystem DAC, ACL, SELinux, or root squashing applies.
- NFSv4 clients may not rely on `showmount` results.
- Warnings about unmatched hostnames, missing paths, or conflicting options require correction before reload.

## 8. Corporate/L3 troubleshooting workflow

1. **Confirm impact:** Record affected applications, users, start time, error rate, latency, and business severity.
2. **Identify scope:** Determine whether the issue is host-wide, process-specific, filesystem-specific, network-path-specific, or limited to one namespace.
3. **Preserve evidence:** Save logs, configuration, counters, command output, package versions, and timestamps before changing state.
4. **Establish ownership:** Identify whether systemd, NetworkManager, firewalld, TuneD, udev, a backup scheduler, configuration management, or the application owns the setting.
5. **Use read-only inspection first:** Confirm the hypothesis with at least two independent evidence sources.
6. **Control the test:** Make only one bounded change and define the rollback command in advance.
7. **Measure service behavior:** Validate latency, throughput, errors, data consistency, authentication, and client experience.
8. **Persist correctly:** Apply successful changes through the supported configuration source rather than an ad hoc runtime command.
9. **Close the incident:** Document root cause, contributing conditions, corrective action, monitoring, and prevention.

## 9. Production cautions

- Validate syntax and active client use before unexporting or reloading.
- Do not use `no_root_squash` without a strong, documented requirement.
- Prefer IP networks or controlled DNS for access matching.
- Coordinate exports with firewall, SELinux booleans/labels, and filesystem permissions.
- Replace all example users, paths, devices, addresses, ports, repositories, and services only after validation.
- Keep console or out-of-band access for firewall, bootloader, storage, authentication, and network changes.
- Back up data and configuration before destructive, recursive, or boot-critical commands.
