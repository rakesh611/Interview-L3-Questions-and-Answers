# 131. bpftrace

> **Scope:** Corporate/L3 Linux administration, incident troubleshooting, safe change execution, and interview preparation.

## 1. What it is

`bpftrace` is a high-level tracing language for eBPF. It attaches probes to kernel functions, tracepoints, user functions, USDT probes, and performance events to aggregate live production behavior.

## 2. Production importance

- Provides a repeatable method for diagnosing or controlling the relevant Linux subsystem.
- Produces evidence suitable for incident timelines, change records, problem management, and audit review.
- Encourages before-and-after measurement instead of unverified tuning or repair.
- Separates command success from actual application availability, security, and data integrity.

## 3. Package or kernel interface

- **Primary package/interface:** bpftrace plus kernel BTF/debug information as required
- Check availability and installed version before relying on an option:

```bash
command -v bpftrace 2>/dev/null || true
rpm -q PACKAGE_NAME 2>/dev/null || true
COMMAND --version 2>/dev/null || COMMAND --help
```

## 4. Core concepts

- Tracepoints are generally more stable than kernel function names.
- kprobes depend on kernel symbols and implementation details.
- uprobes require the correct binary path, symbol, architecture, and namespace.
- Maps aggregate counts, histograms, sums, averages, and stacks in kernel-assisted tracing.
- BTF improves type awareness and portability.
- A badly designed probe can create high event volume, CPU overhead, or memory pressure.

## 5. Important commands

| Command | Purpose | Risk |
|---|---|---|
| `sudo bpftrace -l 'tracepoint:syscalls:sys_enter_*' \| head` | List matching tracepoints. | Read-only |
| `sudo bpftrace -l 'kprobe:vfs_*' \| head` | List matching kprobe targets. | Read-only |
| `sudo bpftrace -e 'BEGIN { printf("hello\n"); exit(); }'` | Run a minimal one-liner. | Read-only |
| `sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); } interval:s:10 { exit(); }'` | Count open calls by command for ten seconds. | Read-only |
| `sudo bpftrace -e 'tracepoint:sched:sched_switch { @[kstack] = count(); } interval:s:5 { exit(); }'` | Collect kernel stack counts during scheduling. | Read-only |
| `sudo bpftrace -e 'tracepoint:block:block_rq_complete { @us[args->dev] = hist(args->nr_sector); } interval:s:10 { exit(); }'` | Build a block-completion size histogram; fields vary by kernel. | Read-only |
| `sudo bpftrace -p 1234 script.bt` | Attach a script to a process lifetime. | Read-only |
| `sudo bpftrace -c 'curl -s http://127.0.0.1/' script.bt` | Run a command under a tracing script. | Read-only |
| `sudo bpftrace --info` | Display kernel and build capabilities. | Read-only |
| `sudo bpftrace -d script.bt` | Dry-run and inspect generated program without attaching. | Read-only |
| `bpftool prog show` | List loaded BPF programs. | Read-only |

## 7. Output interpretation

- Counts and histograms are often safer and more useful than printing every event.
- Probe-not-found errors commonly reflect kernel-version differences or missing symbols.
- Lost events indicate the collection path cannot keep up.
- Stack resolution requires symbols and permissions.
- Always relate trace events to application timestamps and service-level symptoms.

## 8. Corporate/L3 troubleshooting workflow

1. **Confirm impact:** Record affected applications, users, start time, error rate, latency, and business severity.
2. **Identify scope:** Determine whether the issue is host-wide, process-specific, filesystem-specific, network-path-specific, or limited to one namespace.
3. **Preserve evidence:** Save logs, configuration, counters, command output, package versions, and timestamps before changing state.
4. **Establish ownership:** Identify whether systemd, NetworkManager, firewalld, TuneD, udev, a backup scheduler, configuration management, or the application owns the setting.
5. **Use read-only inspection first:** Confirm the hypothesis with at least two independent evidence sources.
6. **Control the test:** Make only one bounded change and define the rollback command in advance.
7. **Measure service behavior:** Validate latency, throughput, errors, data consistency, authentication, and client experience.
8. **Persist correctly:** Apply successful changes through the supported configuration source rather than an ad hoc runtime command.
9. **Close the incident:** Document root cause, contributing conditions, corrective action, monitoring, and prevention.

## 9. Production cautions

- Use bounded duration and filtered probes in production.
- Prefer tracepoints and aggregation before broad kprobes with per-event output.
- Tracing can expose sensitive paths, commands, addresses, and data.
- Test scripts against the exact kernel version and maintain a stop mechanism.
- Replace all example users, paths, devices, addresses, ports, repositories, and services only after validation.
- Keep console or out-of-band access for firewall, bootloader, storage, authentication, and network changes.
- Back up data and configuration before destructive, recursive, or boot-critical commands.
