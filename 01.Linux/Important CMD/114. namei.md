# 114. namei

> **Level:** Linux Corporate/L3 administration and troubleshooting.

## 1. What it is

`namei` follows a pathname component by component and displays the object type, ownership, and permissions. It is especially useful for diagnosing `Permission denied`, symlink, mount-path, and service-access problems.

## 2. Why it matters in production

- Provides a repeatable method to inspect, validate, or control an important Linux subsystem.
- Produces evidence that can be attached to incident, change, problem, audit, and capacity records.
- Helps distinguish configuration, permission, kernel, service, network, storage, security, and application failures.
- Supports before-and-after validation rather than unmeasured configuration changes.

## 4. Core concepts

- A process needs search/execute permission on every directory component in a path.
- The final file's permissions are not enough if a parent directory blocks traversal.
- Symlinks can redirect into a path with different ownership or policy.
- DAC permissions, ACLs, SELinux, capabilities, mount options, and namespaces can all affect access.
- A service user can have different groups from the administrator's shell.
- Parent directory ownership is critical for SSH keys, web roots, sockets, and application secrets.

## 5. Important commands

| Command | Purpose | Operational risk |
|---|---|---|
| `namei /var/www/html/index.html` | Show path components and object types. | Read-only |
| `namei -l /var/www/html/index.html` | Show long permissions and ownership. | Read-only |
| `namei -m /var/www/html/index.html` | Show mode bits for each component. | Read-only |
| `namei -o /var/www/html/index.html` | Show owner names. | Read-only |
| `namei -om /var/www/html/index.html` | Show owners and modes. | Read-only |
| `namei -l ~/.ssh/authorized_keys` | Check an SSH key path. | Read-only |
| `sudo -u apache namei -l /srv/app/static/file.css` | Evaluate path visibility for a service user. | Read-only |
| `readlink -f /path/to/link` | Resolve the final canonical path. | Read-only |
| `getfacl -p /var /var/www /var/www/html /var/www/html/index.html` | Inspect ACLs on path components. | Read-only |
| `ls -Zd /var /var/www /var/www/html /var/www/html/index.html` | Inspect SELinux contexts. | Read-only |

## 7. How to interpret the output

- `d` is a directory, `-` a regular file, and `l` a symbolic link.
- A missing `x` bit on a directory can block traversal even if the file is readable.
- An unexpected owner or group on one parent commonly explains service failures.
- A symlink component should be followed to its target and all target parents checked.
- Correct DAC output does not eliminate ACL or SELinux denial.

## 8. L3 troubleshooting workflow

1. **Define impact:** Identify the affected service, users, start time, scope, and business symptom.
2. **Preserve evidence:** Capture relevant logs, configuration, counters, timestamps, versions, and current state.
3. **Confirm ownership:** Determine whether systemd, NetworkManager, authselect, firewalld, policy, automation, or another manager owns the configuration.
4. **Use read-only checks first:** Avoid changing state before the failure mode is understood.
5. **Correlate adjacent layers:** Check process, kernel, filesystem, network, DNS, time, identity, audit, and SELinux evidence as appropriate.
6. **Form one hypothesis:** State what evidence supports it and what observation would disprove it.
7. **Make one controlled change:** Use a maintenance window, backup, console path, and rollback command.
8. **Validate service metrics:** Confirm application latency, error rate, authentication, data integrity, and logs—not only command success.
9. **Restore or persist:** Roll back failed experiments and make successful changes through approved configuration management.
10. **Document RCA:** Record root cause, contributing factors, corrective action, prevention, and monitoring.

## 9. Production cautions

- Do not fix access failures with broad `chmod -R 777`.
- Check the service's effective identity and namespace.
- Preserve intended least privilege while correcting one failing component.
- Use `restorecon` rather than arbitrary `chcon` for policy-defined SELinux labels.
- Never copy example users, paths, ports, addresses, or devices into production without validation.
- Commands that change credentials, access, labels, firewall rules, packages, audit rules, or services require change control.
- Keep an independent administrative path for SSH, PAM, firewall, DNS, and authentication work.

## 10. Quick practice lab

1. Create a nested directory path.
2. Remove search permission from one parent.
3. Use `namei -om` to identify the break.
4. Add a scoped group or ACL fix.
5. Verify from the intended service user.
