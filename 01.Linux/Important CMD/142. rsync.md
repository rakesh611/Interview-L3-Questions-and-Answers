# 142. rsync

> **Scope:** Corporate/L3 Linux administration, incident troubleshooting, safe change execution, and interview preparation.

## 1. What it is

`rsync` synchronizes files locally or over a remote shell using size/time checks or checksums, efficient delta transfer, metadata preservation, include/exclude rules, deletion, partial transfers, and hard-link-based snapshot techniques.

## 2. Production importance

- Provides a repeatable method for diagnosing or controlling the relevant Linux subsystem.
- Produces evidence suitable for incident timelines, change records, problem management, and audit review.
- Encourages before-and-after measurement instead of unverified tuning or repair.
- Separates command success from actual application availability, security, and data integrity.

## 3. Package or kernel interface

- **Primary package/interface:** rsync
- Check availability and installed version before relying on an option:

```bash
command -v rsync 2>/dev/null || true
rpm -q PACKAGE_NAME 2>/dev/null || true
COMMAND --version 2>/dev/null || COMMAND --help
```

## 4. Core concepts

- A trailing slash on the source changes whether the directory itself or only its contents are copied.
- `-a` preserves common metadata but does not include ACLs, xattrs, or hard links by itself.
- `--delete` makes the destination mirror source absence and is destructive.
- Checksums increase CPU and read I/O and are not normally required for every transfer.
- Open or changing files can produce an inconsistent backup.
- Remote-shell and daemon modes have different configuration and security models.

## 5. Important commands

| Command | Purpose | Risk |
|---|---|---|
| `rsync -av /source/ /destination/` | Synchronize source contents locally. | File synchronization |
| `rsync -av /source /destination/` | Copy the source directory itself into the destination. | File synchronization |
| `rsync -aHAX --numeric-ids /source/ /destination/` | Preserve hard links, ACLs, xattrs, and numeric IDs. | Metadata-preserving synchronization |
| `rsync -aHAXnvi --delete /source/ /destination/` | Dry-run a mirror and itemize changes. | Read-only |
| `rsync -aHAX --delete --backup --backup-dir=/backup/deleted-$(date +%F) /source/ /destination/` | Mirror while retaining deleted/replaced files. | Destructive synchronization with recovery copy |
| `rsync -av --partial --partial-dir=.rsync-partial /source/ host:/destination/` | Retain partial transfer data. | Network synchronization |
| `rsync -av -e 'ssh -p 2222' /source/ user@host:/destination/` | Use SSH on a custom port. | Network synchronization |
| `rsync -av --bwlimit=50m /source/ host:/destination/` | Limit transfer bandwidth. | Network synchronization |
| `rsync -av --exclude-from=exclude.txt /source/ /destination/` | Apply exclusion rules. | Read-only |
| `rsync -a --link-dest=/snapshots/previous /source/ /snapshots/current/` | Create a hard-link snapshot tree. | Backup creation |
| `rsync -avc /source/ /destination/` | Use content checksums instead of normal quick checks. | High-I/O synchronization |
| `rsync --version` | Display version and compiled capabilities. | Read-only |

## 7. Output interpretation

- Itemized output characters identify file type and which attributes changed.
- `sending incremental file list` refers to list construction, not incremental backup semantics by itself.
- A vanished-file warning can be normal on an active source but means the result may not be consistent.
- Exit codes distinguish syntax, I/O, protocol, partial transfer, timeout, and vanished-source conditions.
- A successful rsync process does not prove an application-consistent database backup.

## 8. Corporate/L3 troubleshooting workflow

1. **Confirm impact:** Record affected applications, users, start time, error rate, latency, and business severity.
2. **Identify scope:** Determine whether the issue is host-wide, process-specific, filesystem-specific, network-path-specific, or limited to one namespace.
3. **Preserve evidence:** Save logs, configuration, counters, command output, package versions, and timestamps before changing state.
4. **Establish ownership:** Identify whether systemd, NetworkManager, firewalld, TuneD, udev, a backup scheduler, configuration management, or the application owns the setting.
5. **Use read-only inspection first:** Confirm the hypothesis with at least two independent evidence sources.
6. **Control the test:** Make only one bounded change and define the rollback command in advance.
7. **Measure service behavior:** Validate latency, throughput, errors, data consistency, authentication, and client experience.
8. **Persist correctly:** Apply successful changes through the supported configuration source rather than an ad hoc runtime command.
9. **Close the incident:** Document root cause, contributing conditions, corrective action, monitoring, and prevention.

## 9. Production cautions

- Always dry-run `--delete` with the exact source slash and destination.
- Do not synchronize live database files without vendor-supported quiescing or snapshot procedures.
- Use `--numeric-ids` carefully across systems with different UID/GID design.
- Protect SSH keys and remote destination permissions.
- Replace all example users, paths, devices, addresses, ports, repositories, and services only after validation.
- Keep console or out-of-band access for firewall, bootloader, storage, authentication, and network changes.
- Back up data and configuration before destructive, recursive, or boot-critical commands.
