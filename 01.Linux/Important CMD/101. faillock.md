# 101. faillock

> **Audience:** Linux L2/L3 administrators, performance engineers, and production support teams.

## 1. Overview

Displays and resets authentication-failure records maintained by pam_faillock.

## 2. Package and availability

- **Package/interface:** `pam`
- Verify with `command -v COMMAND`, `rpm -q PACKAGE`, or the distribution equivalent.
- Use `man COMMAND` and `COMMAND --help` on the target host because options can vary by release.

## 3. Important concepts

- Local faillock is separate from AD or LDAP lockout.
- PAM module order affects counting and denial.
- Policy can treat root differently.

## 4. Important commands

| Command | Purpose |
|---|---|
| `faillock` | Show users with failures |
| `faillock --user appuser` | Show one user |
| `sudo faillock --user appuser --reset` | Reset one user |
| `sudo faillock --reset` | Reset all local records |
| `grep -vE "^\s*(#\|$)" /etc/security/faillock.conf` | Show policy |
| `authselect current` | Check feature enablement |
| `grep -R "pam_faillock" /etc/pam.d /etc/authselect 2>/dev/null` | Inspect integration |
| `journalctl --since "-15 min" \| grep -iE "faillock\|authentication failure"` | Review logs |
| `sudo pamtester login appuser authenticate` | Test with a controlled account |

## 6. Output interpretation checklist

- Confirm that the command targeted the intended PID, device, interface, filesystem, user, service, or namespace.
- Distinguish cumulative counters from interval rates and point-in-time snapshots.
- Compare the result with a known baseline and with application symptoms.
- Correlate with `journalctl`, kernel logs, service logs, and neighboring subsystem tools.
- Treat missing output as a possible permission, namespace, package, or version issue before concluding that no problem exists.

## 7. Production troubleshooting workflow

1. Record the incident time, hostname, kernel version, and affected service.
2. Run read-only inventory and status commands first.
3. For changing metrics, collect at least five interval samples.
4. Identify the narrowest affected object and avoid host-wide changes where possible.
5. Form one hypothesis and choose one measurable corrective action.
6. Capture the original value or configuration and prepare rollback.
7. Apply the change through the owning manager, such as systemd, NetworkManager, LVM, or the service configuration.
8. Repeat the same measurements and compare application latency, errors, throughput, and saturation.
9. Roll back if the intended service metric does not improve.
10. Document root cause, evidence, corrective action, and prevention.

## 8. Production cautions

- Verify identity and approval before unlock.
- Preserve evidence during security investigations.
- Test policy with a nonprivileged account and console access.
- Commands that resize, repair, create, remove, flush, signal, reload, or reconfigure can cause outage or data loss.
- Replace example names and addresses only after validating ownership and dependencies.
- Use change control, verified backups, console access, and a rollback plan for storage, network, time, scheduler, and authentication changes.

## 9. Quick lab

1. Run the first three inspection commands on a non-production host.
2. Save the output and explain every major field.
3. Trigger one safe, controlled state change if the tool supports it.
4. Re-run the inspection and compare the output.
5. Restore the original state and document the rollback.

## 10. L3 interview review

- Explain what kernel or service interface the command reads or changes.
- Identify whether the output is a snapshot, cumulative counter, or interval rate.
- Name two misleading interpretations and the additional evidence needed.
- Explain persistence, configuration ownership, and rollback.
- Describe the safest escalation evidence bundle for vendor support.
