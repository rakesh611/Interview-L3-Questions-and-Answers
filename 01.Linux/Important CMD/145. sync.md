# 145. sync

> **Scope:** Corporate/L3 Linux administration, incident troubleshooting, safe change execution, and interview preparation.

## 1. What it is

`sync` asks the kernel to flush pending filesystem writes and metadata toward persistent storage. It can operate system-wide or on selected files/filesystems depending on implementation and options.

## 2. Production importance

- Provides a repeatable method for diagnosing or controlling the relevant Linux subsystem.
- Produces evidence suitable for incident timelines, change records, problem management, and audit review.
- Encourages before-and-after measurement instead of unverified tuning or repair.
- Separates command success from actual application availability, security, and data integrity.

## 3. Package or kernel interface

- **Primary package/interface:** coreutils
- Check availability and installed version before relying on an option:

```bash
command -v sync 2>/dev/null || true
rpm -q PACKAGE_NAME 2>/dev/null || true
COMMAND --version 2>/dev/null || COMMAND --help
```

## 4. Core concepts

- Linux buffers writes in memory and performs asynchronous writeback.
- A completed `sync` improves crash consistency but is not an application transaction or backup.
- Storage controllers, devices, hypervisors, and network filesystems can have additional cache and durability semantics.
- `sync -f FILE` targets the filesystem containing a file.
- `sync -d FILE` requests data-only synchronization where supported.
- Frequent broad sync operations can cause latency spikes and write bursts.

## 5. Important commands

| Command | Purpose | Risk |
|---|---|---|
| `sync` | Flush pending writes across filesystems. | System-wide writeback |
| `sync /path/file` | Synchronize selected files where supported. | Targeted writeback |
| `sync -d /path/file` | Synchronize file data but not unnecessary metadata where supported. | Targeted writeback |
| `sync -f /data/file` | Synchronize the filesystem containing a file. | Filesystem writeback |
| `time sync` | Measure how long pending writeback takes. | System-wide writeback |
| `grep -E 'Dirty\|Writeback' /proc/meminfo` | Inspect dirty and writeback memory. | Read-only |
| `vmstat 1` | Observe block output and CPU wait. | Read-only |
| `iostat -xz 1` | Observe device latency and queueing. | Read-only |
| `cat /proc/sys/vm/dirty_background_bytes /proc/sys/vm/dirty_bytes 2>/dev/null` | Inspect writeback thresholds. | Read-only |
| `journalctl -k --since '-10 min' \| grep -iE 'I/O error\|reset\|timeout\|filesystem'` | Search for persistence-path errors. | Read-only |
| `fsync /path/file 2>/dev/null \|\| true` | Use a dedicated fsync utility only if installed; applications normally call the syscall. | Read-only |

## 7. Output interpretation

- A long-running sync indicates substantial dirty data, slow storage, blocked paths, or filesystem issues.
- A return from sync does not validate the resulting file's application-level integrity.
- Dirty memory should generally fall as writeback completes.
- Remote filesystem semantics depend on protocol and mount behavior.
- A zero exit status cannot overcome a storage device that falsely reports flush completion.

## 8. Corporate/L3 troubleshooting workflow

1. **Confirm impact:** Record affected applications, users, start time, error rate, latency, and business severity.
2. **Identify scope:** Determine whether the issue is host-wide, process-specific, filesystem-specific, network-path-specific, or limited to one namespace.
3. **Preserve evidence:** Save logs, configuration, counters, command output, package versions, and timestamps before changing state.
4. **Establish ownership:** Identify whether systemd, NetworkManager, firewalld, TuneD, udev, a backup scheduler, configuration management, or the application owns the setting.
5. **Use read-only inspection first:** Confirm the hypothesis with at least two independent evidence sources.
6. **Control the test:** Make only one bounded change and define the rollback command in advance.
7. **Measure service behavior:** Validate latency, throughput, errors, data consistency, authentication, and client experience.
8. **Persist correctly:** Apply successful changes through the supported configuration source rather than an ad hoc runtime command.
9. **Close the incident:** Document root cause, contributing conditions, corrective action, monitoring, and prevention.

## 9. Production cautions

- Avoid repeated global sync loops on busy production hosts.
- Do not use sync as a substitute for database checkpoints or clean shutdown.
- Investigate storage errors rather than assuming flush success.
- Coordinate sync with freeze and snapshot procedures to minimize stall time.
- Replace all example users, paths, devices, addresses, ports, repositories, and services only after validation.
- Keep console or out-of-band access for firewall, bootloader, storage, authentication, and network changes.
- Back up data and configuration before destructive, recursive, or boot-critical commands.
