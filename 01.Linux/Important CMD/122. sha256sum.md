# 122. sha256sum

> **Level:** Linux Corporate/L3 administration and troubleshooting.

## 1. What it is

`sha256sum` computes or verifies SHA-256 cryptographic hashes. It is used for integrity checks, download verification, evidence inventories, duplicate detection, and deployment validation.

## 2. Why it matters in production

- Provides a repeatable method to inspect, validate, or control an important Linux subsystem.
- Produces evidence that can be attached to incident, change, problem, audit, and capacity records.
- Helps distinguish configuration, permission, kernel, service, network, storage, security, and application failures.
- Supports before-and-after validation rather than unmeasured configuration changes.

## 4. Core concepts

- A hash proves byte-for-byte equality with the expected digest, not that the source is trustworthy.
- The expected hash must come from an authenticated or trusted channel.
- Changing one byte changes the resulting digest with overwhelming probability.
- Metadata such as owner, mode, ACL, xattr, and timestamps is not included.
- Text and binary marker behavior is platform dependent; on Linux it normally does not alter bytes read.
- For authenticity, use a digital signature in addition to a hash.

## 5. Important commands

| Command | Purpose | Operational risk |
|---|---|---|
| `sha256sum image.iso` | Compute a file's SHA-256 digest. | Read-only |
| `sha256sum file1 file2` | Hash multiple files. | Read-only |
| `sha256sum image.iso > image.iso.sha256` | Create a checksum file. | Read-only |
| `sha256sum -c image.iso.sha256` | Verify a checksum file. | Read-only |
| `sha256sum -c --quiet checksums.txt` | Report only failures. | Read-only |
| `sha256sum -c --status checksums.txt` | Return status without normal output. | Read-only |
| `sha256sum -c --ignore-missing checksums.txt` | Check only files that exist. | Read-only |
| `find /data -type f -print0 \| sort -z \| xargs -0 sha256sum > data.sha256` | Create a pathname-safe tree inventory. | Read-only |
| `printf '%s' 'exact text' \| sha256sum` | Hash bytes without an added newline. | Read-only |
| `echo 'exact text' \| sha256sum` | Hash text including the newline added by `echo`. | Read-only |
| `sha256sum file; stat -c '%s %y %n' file` | Capture hash, size, and modification time. | Read-only |
| `gpg --verify image.iso.sig image.iso` | Verify a publisher signature when available. | Read-only |

## 7. How to interpret the output

- Verification prints `OK` when the current bytes match.
- `FAILED` means content differs, the wrong file was checked, or corruption occurred.
- A missing file and a mismatched hash are different failure conditions.
- The two spaces or mode marker between digest and filename are part of checksum-file format.
- A stable hash across systems confirms content equality but not filesystem metadata equality.

## 8. L3 troubleshooting workflow

1. **Define impact:** Identify the affected service, users, start time, scope, and business symptom.
2. **Preserve evidence:** Capture relevant logs, configuration, counters, timestamps, versions, and current state.
3. **Confirm ownership:** Determine whether systemd, NetworkManager, authselect, firewalld, policy, automation, or another manager owns the configuration.
4. **Use read-only checks first:** Avoid changing state before the failure mode is understood.
5. **Correlate adjacent layers:** Check process, kernel, filesystem, network, DNS, time, identity, audit, and SELinux evidence as appropriate.
6. **Form one hypothesis:** State what evidence supports it and what observation would disprove it.
7. **Make one controlled change:** Use a maintenance window, backup, console path, and rollback command.
8. **Validate service metrics:** Confirm application latency, error rate, authentication, data integrity, and logs—not only command success.
9. **Restore or persist:** Roll back failed experiments and make successful changes through approved configuration management.
10. **Document RCA:** Record root cause, contributing factors, corrective action, prevention, and monitoring.

## 9. Production cautions

- Do not trust a checksum downloaded from the same compromised channel as the file.
- Quote and safely handle filenames containing whitespace, newlines, or leading dashes.
- Hashing large files consumes I/O and CPU.
- Preserve original evidence read-only during forensic hashing.
- Never copy example users, paths, ports, addresses, or devices into production without validation.
- Commands that change credentials, access, labels, firewall rules, packages, audit rules, or services require change control.
- Keep an independent administrative path for SSH, PAM, firewall, DNS, and authentication work.

## 10. Quick practice lab

1. Hash a file.
2. Change one byte and verify the mismatch.
3. Restore the file and verify again.
4. Compare `printf` and `echo` hashes.
5. Verify a signed checksum manifest if available.
