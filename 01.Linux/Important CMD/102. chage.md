# 102. chage

> **Level:** Linux Corporate/L3 administration and troubleshooting.

## 1. What it is

`chage` displays and changes password-ageing information stored for a local account. It controls the last password-change date, minimum and maximum password age, warning period, inactivity period, and account-expiration date.

## 2. Why it matters in production

- Provides a repeatable method to inspect, validate, or control an important Linux subsystem.
- Produces evidence that can be attached to incident, change, problem, audit, and capacity records.
- Helps distinguish configuration, permission, kernel, service, network, storage, security, and application failures.
- Supports before-and-after validation rather than unmeasured configuration changes.

## 4. Core concepts

- Password ageing is different from an immediate account lock.
- The settings are normally stored in `/etc/shadow` for local users.
- Directory users such as AD or LDAP accounts are usually governed by the directory, not by local `chage` values.
- A maximum age of `-1` commonly disables password expiration; verify the installed implementation.
- Account expiration and password expiration are separate controls.
- Use ISO dates in change records to avoid locale ambiguity.

## 5. Important commands

| Command | Purpose | Operational risk |
|---|---|---|
| `sudo chage -l appuser` | Display all password-ageing information for `appuser`. | Read-only |
| `sudo chage -M 90 appuser` | Set the maximum password age to 90 days. | Configuration change |
| `sudo chage -m 1 appuser` | Require at least one day between password changes. | Configuration change |
| `sudo chage -W 14 appuser` | Begin password-expiration warnings 14 days before expiry. | Configuration change |
| `sudo chage -I 7 appuser` | Disable the account seven days after an expired password remains unchanged. | Configuration change |
| `sudo chage -E 2026-12-31 appuser` | Set an account-expiration date. | Configuration change |
| `sudo chage -E -1 appuser` | Remove the account-expiration date. | Configuration change |
| `sudo chage -d 0 appuser` | Force a password change at the next login. | Configuration change |
| `sudo chage -d 2026-07-28 appuser` | Set the recorded last-password-change date. | Configuration change |
| `sudo passwd -S appuser` | Cross-check password status and ageing summary. | Read-only |

## 7. How to interpret the output

- `Last password change` identifies the date from which ageing is calculated.
- `Password expires` is derived from the last-change date plus maximum age.
- `Password inactive` is the date after which an expired password leads to account disablement.
- `Account expires` can disable login even when the password itself is valid.
- A value such as `never` normally means that specific expiry control is disabled.

## 8. L3 troubleshooting workflow

1. **Define impact:** Identify the affected service, users, start time, scope, and business symptom.
2. **Preserve evidence:** Capture relevant logs, configuration, counters, timestamps, versions, and current state.
3. **Confirm ownership:** Determine whether systemd, NetworkManager, authselect, firewalld, policy, automation, or another manager owns the configuration.
4. **Use read-only checks first:** Avoid changing state before the failure mode is understood.
5. **Correlate adjacent layers:** Check process, kernel, filesystem, network, DNS, time, identity, audit, and SELinux evidence as appropriate.
6. **Form one hypothesis:** State what evidence supports it and what observation would disprove it.
7. **Make one controlled change:** Use a maintenance window, backup, console path, and rollback command.
8. **Validate service metrics:** Confirm application latency, error rate, authentication, data integrity, and logs—not only command success.
9. **Restore or persist:** Roll back failed experiments and make successful changes through approved configuration management.
10. **Document RCA:** Record root cause, contributing factors, corrective action, prevention, and monitoring.

## 9. Production cautions

- Confirm whether the account is local before making a change.
- Forcing expiry on service accounts can cause unattended jobs to fail.
- Test PAM, SSH, console, and application-login behavior because not every service handles expired-password prompts identically.
- Keep a root recovery session available when changing privileged administrator accounts.
- Never copy example users, paths, ports, addresses, or devices into production without validation.
- Commands that change credentials, access, labels, firewall rules, packages, audit rules, or services require change control.
- Keep an independent administrative path for SSH, PAM, firewall, DNS, and authentication work.

## 10. Quick practice lab

1. Create a non-production local user.
2. Record `chage -l` output.
3. Set a short warning and maximum age.
4. Force a password change with `-d 0` and test through a safe login path.
5. Restore the original settings.

- Explain what kernel interface, service, database, or configuration source the command uses.
- Distinguish read-only inspection from a runtime or persistent change.

- State the correct rollback before proposing a production change.
- Describe how automation or a service manager can overwrite a manual setting.
