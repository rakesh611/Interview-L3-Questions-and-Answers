# 133. strace

> **Scope:** Corporate/L3 Linux administration, incident troubleshooting, safe change execution, and interview preparation.

## 1. What it is

`strace` records system calls and signals made by a process. It reveals file searches, permission failures, network connection attempts, blocking waits, process creation, signal delivery, and kernel return codes.

## 2. Production importance

- Provides a repeatable method for diagnosing or controlling the relevant Linux subsystem.
- Produces evidence suitable for incident timelines, change records, problem management, and audit review.
- Encourages before-and-after measurement instead of unverified tuning or repair.
- Separates command success from actual application availability, security, and data integrity.

## 3. Package or kernel interface

- **Primary package/interface:** strace
- Check availability and installed version before relying on an option:

```bash
command -v strace 2>/dev/null || true
rpm -q PACKAGE_NAME 2>/dev/null || true
COMMAND --version 2>/dev/null || COMMAND --help
```

## 4. Core concepts

- System-call tracing does not show CPU-only user-space work between system calls.
- Attaching changes timing and can increase latency.
- `-f` follows children and threads; `-ff` separates output files.
- Filters are essential for reducing production overhead and sensitive data exposure.
- Timestamps and syscall durations help distinguish repeated fast failures from genuine blocking.
- Return values and errno names are often more important than the function arguments.

## 5. Important commands

| Command | Purpose | Risk |
|---|---|---|
| `strace -o /tmp/trace.log command` | Trace a command to a file. | Read-only |
| `sudo strace -p 1234` | Attach to a running process. | Live process tracing |
| `sudo strace -ff -tt -T -p 1234 -o /tmp/app.trace` | Trace threads with timestamps and durations. | Live process tracing |
| `strace -f -e trace=%file command` | Trace file-related system calls. | Read-only |
| `strace -f -e trace=%network command` | Trace network system calls. | Read-only |
| `strace -e trace=openat,statx,access command` | Trace selected path-resolution calls. | Read-only |
| `strace -e trace=connect,sendto,recvfrom,poll,epoll_wait command` | Trace selected network and wait calls. | Read-only |
| `strace -c command` | Summarize counts, errors, and time. | Read-only |
| `strace -S time -c command` | Sort summary by total time. | Read-only |
| `strace -s 256 -yy -e trace=%network command` | Expand strings and decode descriptor paths. | Read-only |
| `strace -e status=failed command` | Show only failed calls where supported. | Read-only |
| `timeout 30 sudo strace -tt -T -p 1234 -o /tmp/trace.log` | Bound an attach trace to 30 seconds. | Live process tracing |

## 7. Output interpretation

- `ENOENT` can be normal during search paths; identify the final required file that fails.
- `EACCES` means a discretionary, ACL, policy, or path permission problem.
- `ECONNREFUSED` differs from `ETIMEDOUT` and points to a different network failure layer.
- Long `futex`, `poll`, `epoll_wait`, or `read` calls can represent normal waiting or a hang depending on workload state.
- `unfinished` and `resumed` lines occur when calls overlap across traced tasks.

## 8. Corporate/L3 troubleshooting workflow

1. **Confirm impact:** Record affected applications, users, start time, error rate, latency, and business severity.
2. **Identify scope:** Determine whether the issue is host-wide, process-specific, filesystem-specific, network-path-specific, or limited to one namespace.
3. **Preserve evidence:** Save logs, configuration, counters, command output, package versions, and timestamps before changing state.
4. **Establish ownership:** Identify whether systemd, NetworkManager, firewalld, TuneD, udev, a backup scheduler, configuration management, or the application owns the setting.
5. **Use read-only inspection first:** Confirm the hypothesis with at least two independent evidence sources.
6. **Control the test:** Make only one bounded change and define the rollback command in advance.
7. **Measure service behavior:** Validate latency, throughput, errors, data consistency, authentication, and client experience.
8. **Persist correctly:** Apply successful changes through the supported configuration source rather than an ad hoc runtime command.
9. **Close the incident:** Document root cause, contributing conditions, corrective action, monitoring, and prevention.

## 9. Production cautions

- Trace files can contain credentials, data, filenames, and network details.
- Use a short duration and narrow syscall filters on production systems.
- Do not attach to highly latency-sensitive processes without approval.
- Store traces with restrictive permissions and delete them according to evidence-retention policy.
- Replace all example users, paths, devices, addresses, ports, repositories, and services only after validation.
- Keep console or out-of-band access for firewall, bootloader, storage, authentication, and network changes.
- Back up data and configuration before destructive, recursive, or boot-critical commands.

## 10. Practice lab

1. Trace a missing file.
2. Trace a refused TCP connection.
3. Compare full and filtered traces.
4. Use summary mode.
5. Identify the slowest syscall and explain whether it is a cause or expected wait.

## 12. L3 interview questions

- What kernel interface, service, or data source does the tool use?
- Which commands are read-only, runtime-changing, persistent, destructive, or security-sensitive?
- What common output can be misinterpreted?
- Which adjacent tools confirm the same hypothesis?
- How would you perform the change remotely without losing access?
- What is the rollback and how would you validate it?
