# 1. What is the `crash` utility?

The Linux **`crash` utility** is an interactive kernel-debugging tool used to inspect:

- A kernel crash dump such as a `vmcore` generated by `kdump`
- The memory and state of a currently running Linux kernel
- Kernel processes and kernel threads
- Kernel stack traces
- Kernel log messages
- CPU run queues
- Kernel memory and slab caches
- Virtual-memory mappings
- Open files and sockets
- Loaded kernel modules
- Interrupt data
- Block-device I/O state
- Kernel data structures and symbols

The tool combines kernel-aware commands with GNU Debugger (`gdb`) capabilities.

The most common production use is:

```text
Kernel panic or server hang
        |
        v
kdump capture kernel saves /var/crash/.../vmcore
        |
        v
Install matching kernel-debuginfo
        |
        v
Open vmcore with crash
        |
        v
Inspect log, panic backtrace, tasks, memory, I/O, locks, and modules
```

## Important distinction

`crash` normally analyzes a **kernel dump**, not an ordinary application core dump.

For application crashes, tools such as these are normally used:

```bash
coredumpctl
gdb
eu-stack
```

For kernel crashes, the normal tools are:

```bash
kdump
kdumpctl
makedumpfile
vmcore-dmesg
crash
```

# 2. `crash` vs `kdump` vs `kdumpctl` vs `coredumpctl`

| Component | Main purpose |
|---|---|
| `kdump` | Kernel crash-dump mechanism |
| `kexec` | Boots the capture kernel without a normal firmware reboot |
| `kdumpctl` | Configures, starts, tests, and checks the `kdump` service |
| `vmcore` | Memory dump captured from the failed kernel |
| `vmlinux` | Uncompressed kernel image containing debugging symbols |
| `crash` | Interactively analyzes the `vmcore` |
| `makedumpfile` | Filters, compresses, or transforms a kernel dump |
| `vmcore-dmesg` | Extracts the kernel message buffer from a `vmcore` |
| `coredumpctl` | Manages user-space application core dumps collected by systemd |

## Example workflow

```bash
# Check whether kdump is ready before an incident
sudo kdumpctl status

# After a crash, locate the dump
sudo find /var/crash -name vmcore -type f

# Determine the kernel release recorded in the dump
crash --osrelease /var/crash/<directory>/vmcore

# Open the dump with the matching vmlinux file
sudo crash \
  /usr/lib/debug/lib/modules/<kernel-release>/vmlinux \
  /var/crash/<directory>/vmcore
```

# 3. How kernel crash dump analysis works

A typical `kdump` configuration reserves memory using the kernel command-line parameter:

```text
crashkernel=...
```

When the production kernel panics:

1. The failed kernel transfers control through `kexec`.
2. A small capture kernel boots from reserved memory.
3. The capture kernel writes the failed kernel's memory to a `vmcore`.
4. The server normally reboots.
5. An administrator analyzes the `vmcore` using `crash`.

## Verify the reserved crash-kernel memory

```bash
cat /proc/cmdline
```

Example:

```text
BOOT_IMAGE=(hd0,gpt2)/vmlinuz-5.14.0-... crashkernel=1G-4G:192M,4G-64G:256M,64G-:512M
```

Check the reservation in the current kernel log:

```bash
dmesg | grep -i crash
```

Example:

```text
crashkernel reserved: 0x00000000a0000000 - 0x00000000b0000000
```

Check the service:

```bash
sudo kdumpctl status
systemctl status kdump
```

# 4. Required files

For reliable offline analysis, `crash` normally requires two matching files.

## 4.1 The `vmcore`

Example:

```text
/var/crash/127.0.0.1-2026-07-28-11:45:30/vmcore
```

This contains memory from the failed kernel.

## 4.2 The matching `vmlinux`

Example:

```text
/usr/lib/debug/lib/modules/5.14.0-503.35.1.el9_5.x86_64/vmlinux
```

This is **not** the same as:

```text
/boot/vmlinuz-5.14.0-503.35.1.el9_5.x86_64
```

The file in `/boot` is usually a compressed bootable kernel image. Kernel dump analysis normally needs the debug-symbol-enabled `vmlinux` supplied by a matching `kernel-debuginfo` package.

## Exact-match rule

The `vmlinux` release should match the release of the kernel that generated the dump.

Example:

```text
vmcore kernel:  5.14.0-503.35.1.el9_5.x86_64
vmlinux kernel: 5.14.0-503.35.1.el9_5.x86_64
```

Do not substitute a newer or older kernel's `vmlinux`.

# 5. Installing `crash` and kernel debuginfo

## 5.1 RHEL, Rocky Linux, AlmaLinux, and CentOS Stream

Install `crash`:

```bash
sudo dnf install crash
```

Check the installed version:

```bash
crash --version
rpm -q crash
```

Install the debuginfo package matching a particular kernel:

```bash
sudo dnf install kernel-debuginfo-<kernel-release>
```

Example:

```bash
sudo dnf install \
  kernel-debuginfo-5.14.0-503.35.1.el9_5.x86_64
```

Depending on the distribution, an additional common debuginfo package may be required:

```bash
sudo dnf install \
  kernel-debuginfo-common-x86_64-5.14.0-503.35.1.el9_5.x86_64
```

List available matching packages:

```bash
dnf list --showduplicates kernel-debuginfo
dnf repoquery "kernel-debuginfo*"
```

Check whether the debug repository is enabled:

```bash
dnf repolist | grep -i debug
```

On subscription-managed RHEL, enable the debug RPM repository appropriate for the installed RHEL major version and architecture.

Example pattern:

```bash
sudo subscription-manager repos --list | grep -i debug
```

Then enable the required repository shown by the command.

## 5.2 Fedora

```bash
sudo dnf install crash
sudo dnf debuginfo-install kernel-core-$(uname -r)
```

## 5.3 Debian or Ubuntu

```bash
sudo apt update
sudo apt install crash
```

The matching kernel debug-symbol package may use a distribution-specific name such as:

```text
linux-image-<kernel-release>-dbgsym
```

The debug-symbol repository may need to be enabled first.

## 5.4 Verify the `vmlinux` file

```bash
ls -lh /usr/lib/debug/lib/modules/<kernel-release>/vmlinux
file /usr/lib/debug/lib/modules/<kernel-release>/vmlinux
```

Example:

```bash
file /usr/lib/debug/lib/modules/5.14.0-503.35.1.el9_5.x86_64/vmlinux
```

Expected characteristics include an ELF image with debugging information.

# 6. Finding and validating a `vmcore`

## 6.1 Find crash directories

```bash
sudo find /var/crash -maxdepth 3 -type f -printf '%TY-%Tm-%Td %TH:%TM %10s %p\n' | sort
```

Find only `vmcore` files:

```bash
sudo find /var/crash -type f -name vmcore -ls
```

Check the dump size:

```bash
du -h /var/crash/<crash-directory>/vmcore
ls -lh /var/crash/<crash-directory>/vmcore
```

A filtered dump may be much smaller than installed RAM.

## 6.2 Examine companion files

A crash directory may contain files such as:

```text
vmcore
vmcore-dmesg.txt
kexec-dmesg.log
```

List them:

```bash
ls -lah /var/crash/<crash-directory>/
```

Read the extracted message log first:

```bash
less /var/crash/<crash-directory>/vmcore-dmesg.txt
```

Search for critical text:

```bash
grep -Ein \
'panic|BUG:|Oops:|Call Trace|watchdog|soft lockup|hard LOCKUP|blocked for more than|Out of memory|NMI|I/O error|XFS|EXT4|hung task' \
/var/crash/<crash-directory>/vmcore-dmesg.txt
```

## 6.3 Determine the kernel release in the dump

```bash
crash --osrelease /var/crash/<crash-directory>/vmcore
```

Example:

```text
5.14.0-503.35.1.el9_5.x86_64
```

Save it in a shell variable:

```bash
VMCORE=/var/crash/<crash-directory>/vmcore
KREL=$(crash --osrelease "$VMCORE")
echo "$KREL"
```

Build the expected `vmlinux` path:

```bash
VMLINUX=/usr/lib/debug/lib/modules/"$KREL"/vmlinux
ls -lh "$VMLINUX"
```

## 6.4 Check dump file type

```bash
file "$VMCORE"
```

Do not edit, move, recompress, or delete the original evidence until it has been copied and checksummed.

## 6.5 Preserve evidence

```bash
sha256sum "$VMCORE" | tee vmcore.sha256
sha256sum "$VMLINUX" | tee vmlinux.sha256
```

Copy to an analysis host when required:

```bash
rsync -avP \
  /var/crash/<crash-directory>/ \
  analysis-host:/data/incidents/<incident-id>/
```

# 7. Starting a `crash` session

## 7.1 Analyze a `vmcore`

```bash
sudo crash \
  /usr/lib/debug/lib/modules/<kernel-release>/vmlinux \
  /var/crash/<crash-directory>/vmcore
```

Example:

```bash
sudo crash \
  /usr/lib/debug/lib/modules/5.14.0-503.35.1.el9_5.x86_64/vmlinux \
  /var/crash/127.0.0.1-2026-07-28-11:45:30/vmcore
```

A successful startup displays a summary similar to:

```text
KERNEL: /usr/lib/debug/lib/modules/.../vmlinux
DUMPFILE: /var/crash/.../vmcore
CPUS: 16
DATE: Tue Jul 28 ...
UPTIME: 42 days, 03:18:27
LOAD AVERAGE: 37.44, 31.20, 20.11
TASKS: 2254
NODENAME: server01
RELEASE: 5.14.0-...
MACHINE: x86_64
MEMORY: 62.7 GB
PANIC: "Kernel panic - not syncing: ..."
PID: ...
COMMAND: "..."
CPU: ...
STATE: TASK_RUNNING (PANIC)
```

## 7.2 Start live-system analysis

```bash
sudo crash
```

Or specify `vmlinux` explicitly:

```bash
sudo crash /usr/lib/debug/lib/modules/$(uname -r)/vmlinux
```

Live analysis should be treated carefully. Avoid commands that write to kernel memory or intentionally panic the system.

## 7.3 Exit

Inside the prompt:

```text
crash> q
```

or:

```text
crash> exit
```

# 8. Important startup options

## 8.1 Display command-line help

```bash
crash --help
```

Display help for a particular interactive command without opening a dump:

```bash
crash --help bt
crash --help ps
crash --help kmem
```

## 8.2 Determine dump kernel release

```bash
crash --osrelease /path/to/vmcore
```

## 8.3 Read commands from an input file

```bash
crash -i commands.txt "$VMLINUX" "$VMCORE"
```

Example `commands.txt`:

```text
set scroll off
sys
sys -t
log
ps -S
ps -m
bt -p
bt -a
foreach UN bt
kmem -i
kmem -s
dev -D
mount
mod
q
```

## 8.4 Select line-editing mode

```bash
crash -e vi "$VMLINUX" "$VMCORE"
```

or:

```bash
crash -e emacs "$VMLINUX" "$VMCORE"
```

## 8.5 Use a command file and redirect results

```bash
crash -i commands.txt "$VMLINUX" "$VMCORE" > crash-report.txt 2>&1
```

# 9. Recommended first-response workflow

The following order gives a fast high-level view before deep kernel-structure analysis.

```text
1. sys
2. sys -t
3. log
4. bt -p
5. bt -a
6. ps -S
7. ps -m
8. foreach UN bt
9. runq
10. kmem -i
11. kmem -s
12. swap
13. dev -D
14. mount
15. mod
16. irq -s
```

## Why this order?

- `sys` confirms release, panic text, uptime, CPU count, and system identity.
- `sys -t` checks whether the kernel was tainted.
- `log` shows the kernel messages immediately before the failure.
- `bt -p` follows the panic task's call stack.
- `bt -a` shows what was executing on every CPU.
- `ps -S` summarizes task states.
- `ps -m` helps find tasks that have not run for a long period.
- `foreach UN bt` finds uninterruptible tasks and their wait locations.
- `runq` checks CPU scheduling congestion.
- `kmem` checks memory exhaustion and slab growth.
- `dev -D` helps identify in-flight storage I/O.
- `mod` identifies loaded third-party or suspect drivers.
- `irq -s` checks abnormal interrupt distribution.

# 10. Important interactive commands

---

## 10.1 `help` — display available commands

### Purpose

Displays the command menu or detailed help for one command.

### Syntax

```text
crash> help
crash> help <command>
```

### Examples

```text
crash> help
crash> help bt
crash> help ps
crash> help kmem
crash> help input
crash> help output
```

### When to use

Use it whenever command syntax differs between installed `crash` versions.

---

## 10.2 `sys` — display system and panic information

### Purpose

Displays key system data similar to the startup banner.

### Basic example

```text
crash> sys
```

Typical fields:

```text
KERNEL
DUMPFILE
CPUS
DATE
UPTIME
LOAD AVERAGE
TASKS
NODENAME
RELEASE
VERSION
MACHINE
MEMORY
PANIC
PID
COMMAND
TASK
CPU
STATE
```

### Check kernel taint

```text
crash> sys -t
```

Kernel taint may indicate conditions such as:

- Proprietary module loaded
- Out-of-tree module loaded
- Forced module load/unload
- Previous warning
- Machine-check event
- Unsigned module

Always record the taint status in the incident report.

### Show embedded kernel configuration

```text
crash> sys config
```

This works when the kernel contains in-kernel configuration data.

### System-call table query

```text
crash> sys -c
crash> sys -c open
crash> sys -c 0
```

### Dangerous option

Do **not** run this on a production live system:

```text
crash> sys -panic
```

It intentionally panics a live system.

---

## 10.3 `log` — display the kernel message buffer

### Purpose

Displays the kernel `printk` message buffer in chronological order.

### Basic example

```text
crash> log
```

### Human-readable timestamp

```text
crash> log -T
```

The converted wall-clock time can be inaccurate, so correlate it with other evidence.

### Hide timestamps

```text
crash> log -t
```

### Display log level

```text
crash> log -m
```

### Search important failure strings

The `crash` prompt supports pipes to external commands:

```text
crash> log | grep -Ei "panic|BUG:|Oops|Call Trace"
```

```text
crash> log | grep -Ei "watchdog|soft lockup|hard LOCKUP"
```

```text
crash> log | grep -Ei "blocked for more than|hung task"
```

```text
crash> log | grep -Ei "Out of memory|oom-killer|Killed process"
```

```text
crash> log | grep -Ei "I/O error|blk_update_request|XFS|EXT4|nvme|scsi"
```

### What to capture

Look for:

- First warning, Oops, or BUG line
- Panic text
- Faulting instruction pointer
- Call trace
- Module list
- CPU and PID involved
- Lockup messages
- OOM victim
- Storage timeout or path failure
- Machine-check or hardware-error messages

Do not focus only on the final panic line. The root trigger may appear hundreds of lines earlier.

## 10.4 `bt` — display kernel stack backtraces

### Purpose

Displays the kernel stack trace for the current context or a selected task.

### Current task

```text
crash> bt
```

### Panic task only

```text
crash> bt -p
```

This is normally one of the most important commands.

### Active task on every CPU

```text
crash> bt -a
```

Filter idle tasks on supported architectures:

```text
crash> bt -a -n idle
```

### Selected CPU

```text
crash> bt -c 0
crash> bt -c 0,1,4-7
```

### Selected PID

```text
crash> bt 1234
```

### Selected `task_struct` address

```text
crash> bt ffff9a2b01234000
```

### Include source file and line data

```text
crash> bt -l
```

This depends on sufficient debuginfo.

### Include symbolic offsets

```text
crash> bt -s
```

### Search possible exception frames

```text
crash> bt -e
```

### Display stack frame contents

```text
crash> bt -f 1234
```

### Fallback when normal unwinding is incomplete

```text
crash> bt -t 1234
crash> bt -T 1234
```

### Interpretation example

```text
#0 machine_kexec
#1 __crash_kexec
#2 panic
#3 watchdog
#4 kthread
```

Possible interpretation:

- A watchdog detected a lockup or hung condition.
- `panic()` initiated the crash.
- `__crash_kexec()` transferred control to the kdump capture kernel.

The root cause is generally below the generic panic/kexec frames or in messages preceding the panic.

## 10.5 `ps` — display process and kernel-thread status

### Purpose

Displays task state, CPU, memory, PID, parent PID, and command.

### All tasks

```text
crash> ps
```

Important task states commonly seen:

| State | Meaning |
|---|---|
| `RU` | Running or runnable |
| `IN` | Interruptible sleep |
| `UN` | Uninterruptible sleep |
| `ZO` | Zombie |
| `ST` | Stopped |
| `DE` | Dead |
| `ID` | Idle |

### Task-state summary

```text
crash> ps -S
```

This is a fast way to see whether hundreds of tasks are stuck in `UN`.

### Tasks by time since last scheduled

```text
crash> ps -m
```

Very large elapsed times can indicate stalled tasks or CPUs.

### Kernel threads only

```text
crash> ps -k
```

### User tasks only

```text
crash> ps -u
```

### Active task on each CPU

```text
crash> ps -A
```

### Specific PID

```text
crash> ps 1234
```

### Command-name match

```text
crash> ps java
crash> ps kworker
```

### Scheduling policy filtering

```text
crash> ps -y FIFO
crash> ps -y RR
crash> ps -y DEADLINE
```

### Display command-line and environment data

```text
crash> ps -a 1234
```

Be careful: environment strings may contain credentials or other secrets.

## 10.6 `set` — show or change task context

### Purpose

Many commands operate on the current task context. `set` displays or changes it.

### Display current context

```text
crash> set
```

### Change to a PID

```text
crash> set 1234
```

Then context-sensitive commands use that task:

```text
crash> bt
crash> files
crash> vm
crash> net -s
```

### Change to a `task_struct` address

```text
crash> set ffff9a2b01234000
```

### Return to panic task

```text
crash> set -p
```

### Set context to active task on CPU 7

```text
crash> set -c 7
```

### Disable paging

Useful for scripts and redirection:

```text
crash> set scroll off
```

### Set hexadecimal output

```text
crash> set radix 16
```

Return to decimal:

```text
crash> set radix 10
```

### Show internal settings

```text
crash> set -v
```

## 10.7 `foreach` — run a task command across many tasks

### Purpose

Runs commands such as `bt`, `files`, `vm`, `task`, or `net` for selected tasks.

### Backtrace all tasks

```text
crash> foreach bt
```

This can produce very large output.

### Backtrace all uninterruptible tasks

```text
crash> foreach UN bt
```

This is one of the most useful hang-analysis commands.

### Backtrace all running/runnable tasks

```text
crash> foreach RU bt
```

### Backtrace all active tasks

```text
crash> foreach active bt
```

### Inspect all tasks with a command name

```text
crash> foreach java bt
```

### Use a regular expression

```text
crash> foreach 'kworker.*' bt
```

### Display open files for all tasks

```text
crash> foreach files
```

### Search tasks referencing a file

```text
crash> foreach files -R "/var/lib/app/data.db"
```

### Display selected `task_struct` members

```text
crash> foreach UN task -R state,pid,comm
```

## 10.8 `runq` — display CPU run queues

### Purpose

Displays tasks queued to run on each CPU.

### All CPU run queues

```text
crash> runq
```

### Selected CPUs

```text
crash> runq -c 0
crash> runq -c 0-7
```

### Time the active task has been running

```text
crash> runq -m
```

### Compare CPU run-queue time lag

```text
crash> runq -T
```

### Show task-group hierarchy and throttling

```text
crash> runq -g
```

### Investigative value

Look for:

- A very large runnable queue on one CPU
- Severe imbalance between CPUs
- One active task running for an abnormal duration
- A throttled task group
- Many real-time tasks
- CPU affinity that concentrates work on too few CPUs

## 10.9 `kmem` — inspect kernel memory

### Purpose

Displays general memory use, slab caches, zones, NUMA data, vmalloc allocations, and page information.

### General memory usage

```text
crash> kmem -i
```

Inspect:

- Total memory
- Free memory
- Used memory
- Cached memory
- Slab usage
- Huge pages
- Swap information

### Slab cache summary

```text
crash> kmem -s
```

Look for unusually large caches, for example:

```text
dentry
inode_cache
kmalloc-*
buffer_head
xfs_inode
ext4_inode_cache
nf_conntrack
task_struct
```

A large cache is not automatically a leak. Compare object count, cache purpose, workload, and historical baseline.

### Inspect a particular slab cache

```text
crash> kmem -s dentry
crash> kmem -s kmalloc-4096
```

### Zone statistics

```text
crash> kmem -z
```

Useful for:

- Free-page shortage
- Zone imbalance
- High-order allocation failure
- DMA or DMA32 exhaustion
- Fragmentation-related analysis

### VM statistics

```text
crash> kmem -V
```

### NUMA and memory-node information

```text
crash> kmem -n
```

### `vmalloc` regions

```text
crash> kmem -v
```

### Huge-page state

```text
crash> kmem -h
```

### Resolve an address to memory type

```text
crash> kmem ffff9a2b01234000
```

Depending on the address, this may identify a slab object, page, vmalloc area, or other memory type.

## 10.10 `vm` — display a task's virtual-memory mappings

### Purpose

Displays the task's `mm_struct`, RSS, virtual size, VMA ranges, flags, and mapped files.

### Current context

```text
crash> vm
```

### Specific PID

```text
crash> vm 1234
```

### Dump the `mm_struct`

```text
crash> vm -m 1234
```

### Dump all VMA structures

```text
crash> vm -v 1234
```

### Translate virtual pages to physical pages

```text
crash> vm -p 1234
```

This can produce large output.

### Search a task's mappings for a file

```text
crash> vm -R libjvm.so 1234
```

### Use cases

- Examine process address-space size
- Determine whether a file was memory mapped
- Inspect large anonymous mappings
- Analyze a process involved in an OOM event
- Check whether memory pages were resident, swapped, or file backed

## 10.11 `files` — display open files

### Purpose

Shows root directory, current working directory, open descriptors, file structures, dentries, inodes, file type, and pathname.

### Current context

```text
crash> files
```

### Specific PID

```text
crash> files 1234
```

### Search for a referenced path

```text
crash> files -R "/var/log/messages" 1234
```

### Show page-cache information for open files

```text
crash> files -c 1234
```

### Inspect a dentry address


## 11.5 Example incident collection script

```bash
#!/usr/bin/env bash
set -euo pipefail

VMCORE=${1:?Usage: $0 /path/to/vmcore}
OUTDIR=${2:-crash-analysis-$(date +%Y%m%d-%H%M%S)}

mkdir -p "$OUTDIR"

KREL=$(crash --osrelease "$VMCORE")
VMLINUX="/usr/lib/debug/lib/modules/${KREL}/vmlinux"

if [[ ! -r "$VMCORE" ]]; then
    echo "ERROR: Cannot read vmcore: $VMCORE" >&2
    exit 1
fi

if [[ ! -r "$VMLINUX" ]]; then
    echo "ERROR: Matching vmlinux not found: $VMLINUX" >&2
    echo "Install the matching kernel-debuginfo package." >&2
    exit 1
fi

cat > "$OUTDIR/commands.txt" <<'EOF'
set scroll off
sys
sys -t
log
bt -p
bt -a
ps -S
ps -m
runq
foreach UN bt
kmem -i
kmem -s
kmem -z
swap
dev -D
mount
mod
irq -s
q
EOF

sha256sum "$VMCORE" > "$OUTDIR/vmcore.sha256"
sha256sum "$VMLINUX" > "$OUTDIR/vmlinux.sha256"
printf '%s\n' "$KREL" > "$OUTDIR/kernel-release.txt"

crash -i "$OUTDIR/commands.txt" "$VMLINUX" "$VMCORE" \
    > "$OUTDIR/crash-report.txt" 2>&1

echo "Report created in: $OUTDIR"
```

Make it executable:

```bash
chmod +x collect-crash-report.sh
```

Run it:

```bash
sudo ./collect-crash-report.sh \
  /var/crash/<crash-directory>/vmcore \
  incident-INC001234
```

# 12. Common crash-analysis scenarios

## 12.1 Kernel panic

Start with:

```text
crash> sys
crash> log
crash> bt -p
crash> bt -a
crash> mod
```

Questions:

- What is the exact panic string?
- Which task and CPU panicked?
- What is the first non-generic function in the panic stack?
- Is a module shown in brackets?
- Was the kernel tainted?
- Did a warning or Oops occur earlier?

---

## 12.2 Hung server with blocked tasks

Run:

```text
crash> ps -S
crash> ps -m
crash> foreach UN bt
crash> dev -D
crash> mount
crash> log | grep -Ei "blocked for more than|hung task|I/O error|timeout"
```

Common stack families:

```text
io_schedule
wait_on_page_bit
blk_mq_get_tag
submit_bio
xfs_log_force
jbd2_log_wait_commit
nfs_wait_bit_killable
mutex_lock
rwsem_down
```

Interpretation must consider the whole stack and subsystem, not one function name.

---

## 12.3 Out-of-memory event

Run:

```text
crash> log | grep -Ei "Out of memory|oom-killer|Killed process"
crash> kmem -i
crash> kmem -s
crash> swap
crash> ps
crash> ps -S
```

Investigate:

- User-process RSS
- Kernel slab growth
- Page-cache use
- Swap exhaustion
- NUMA zone shortage
- Memory cgroup OOM versus global OOM
- High-order allocation failure
- Huge-page reservation

Do not conclude that the process selected by the OOM killer caused the leak. It may only be the chosen victim.

---

## 12.4 Soft lockup or hard lockup

Run:

```text
crash> log | grep -Ei "soft lockup|hard LOCKUP|watchdog|NMI"
crash> bt -a
crash> runq -m
crash> irq -s
crash> ps -m
```

Look for:

- CPU spinning in one function
- Interrupt-disabled loops
- Lock contention
- Driver interrupt handling
- Real-time task starvation
- Run-queue timestamp lag
- Virtualization scheduling delays

---

## 12.5 Storage I/O hang

Run:

```text
crash> foreach UN bt
crash> dev -D
crash> mount
crash> files <blocked-pid>
crash> log | grep -Ei "I/O error|timeout|reset|abort|nvme|scsi|multipath|XFS|EXT4"
crash> mod
```

Correlate:

```text
Blocked task
   -> filesystem function
   -> block layer
   -> device-mapper or multipath
   -> SCSI/NVMe driver
   -> specific device/path
```

---

## 12.6 Network-related hang

Run:

```text
crash> net
crash> net -s <pid>
crash> files <pid>
crash> bt <pid>
crash> log | grep -Ei "NETDEV WATCHDOG|transmit queue|link down|reset|timeout"
crash> irq -s
crash> mod
```

Investigate:

- Socket state
- Network namespace
- Driver/module in stack
- IRQ concentration
- Transmit timeout
- Connection tracking pressure
- Softirq-related CPU saturation

---

## 12.7 Suspected kernel memory leak

Run:

```text
crash> kmem -i
crash> kmem -s
crash> kmem -V
crash> kmem -v
crash> kmem -n
```

A single dump provides only a point-in-time view. Strong leak analysis usually needs:

- Historical monitoring
- Multiple dumps over time
- Slab object growth trend
- Workload correlation
- Object ownership analysis
- Vendor/kernel-source review

---

## 12.8 Third-party module suspected

Run:

```text
crash> sys -t
crash> mod
crash> bt -p
crash> bt -a
crash> sym <fault-address>
```

Collect:

```bash
rpm -qa | sort
modinfo <module>
uname -a
```

From the original system or matching build environment, also preserve the exact module binary and its debuginfo when available.

# 13. Common errors and fixes

## Error 1: `cannot find booted kernel`

### Cause

`crash` cannot locate a suitable `vmlinux`.

### Fix

Specify it explicitly:

```bash
crash \
  /usr/lib/debug/lib/modules/<kernel-release>/vmlinux \
  /path/to/vmcore
```

---

## Error 2: `vmlinux and vmcore do not match`

### Cause

The installed debuginfo belongs to a different kernel build.

### Fix

Check the dump release:

```bash
crash --osrelease /path/to/vmcore
```

Install that exact release's debuginfo and use its `vmlinux`.

---

## Error 3: Missing debuginfo package

### Check

```bash
ls -l /usr/lib/debug/lib/modules/<kernel-release>/vmlinux
```

### Fix

Enable the distribution's debug repository and install:

```bash
sudo dnf install kernel-debuginfo-<kernel-release>
```

---

## Error 4: Permission denied reading `vmcore`

### Fix

```bash
sudo crash "$VMLINUX" "$VMCORE"
```

Or copy the dump to a secured analysis location with appropriate ownership and permissions.

Do not make the dump world-readable.

---

## Error 5: `cannot read excluded page`

### Cause

`makedumpfile` may have excluded unnecessary pages to reduce dump size, or the dump may be incomplete.

### Investigation

```text
crash> set zero_excluded on
```

This makes missing or excluded pages read as zero for some operations, but it can hide the fact that real data is absent. Record when this setting is used.

---

## Error 6: Module functions appear only as raw addresses

### Cause

Module symbols or module debuginfo are missing.

### Fix

Install matching module debuginfo or load an appropriate symbol file:

```text
crash> mod -s <module> <object-file>
```

---

## Error 7: Backtrace looks incomplete or incorrect

Try:

```text
crash> bt -t <pid>
crash> bt -T <pid>
crash> bt -e <pid>
crash> bt -f <pid>
```

Also verify:

- Correct `vmlinux`
- Correct architecture
- Complete dump
- Supported kernel and `crash` version
- Module symbols

---

## Error 8: Command not available

### Cause

The installed `crash` version may be older, the command may be an extension, or architecture/kernel support may differ.

### Check

```text
crash> help
crash> help <command>
```

Also check:

```bash
crash --version
```

---

## Error 9: Very large output or terminal paging

Disable paging:

```text
crash> set scroll off
```

Filter or redirect:

```text
crash> foreach UN bt > blocked.txt
crash> log | grep -Ei "panic|BUG|Oops"
```

# 14. Safety guidelines

## 14.1 Treat the dump as sensitive data

A `vmcore` can contain:

- Passwords
- Tokens
- Private keys
- Customer data
- Database pages
- Application memory
- Network payload fragments
- File contents

Recommended controls:

```bash
chmod 600 vmcore
chown root:root vmcore
```

Store it only in approved encrypted incident storage.

## 14.2 Preserve the original

Create and record a checksum:

```bash
sha256sum vmcore
```

Analyze a controlled copy when possible.

## 14.3 Avoid write operations

The `wr` command writes memory and is particularly dangerous on a live system.

Do not use:

```text
crash> wr ...
```

unless you are in an isolated lab and fully understand the consequences.

## 14.4 Never intentionally panic production

Do not run:

```text
crash> sys -panic
```

on a production live system.

## 14.5 Minimize unnecessary output

Raw memory and process environments can expose secrets. Collect only what is required for the incident.

## Final production reminder

A useful `crash` investigation should answer five questions:

1. **What exact event caused the panic or hang?**
2. **Which task, CPU, module, lock, memory object, or device was involved?**
3. **What evidence appears before the generic panic frames?**
4. **Is the failure caused by the kernel, hardware, a third-party module, or an external dependency?**
5. **What evidence supports the conclusion, and what remains uncertain?**

Never declare a root cause from one command alone. Correlate the panic text, kernel log, stack traces, task states, memory state, device state, module list, and operating history.
