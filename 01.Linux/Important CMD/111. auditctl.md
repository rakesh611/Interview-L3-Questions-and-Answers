# 111. auditctl

> **Level:** Linux Corporate/L3 administration and troubleshooting.

## 1. What it is

`auditctl` displays and changes the Linux Audit subsystem's runtime rules and parameters. It can watch files, filter system calls, tune backlog behavior, and report current audit status.

## 2. Why it matters in production

- Provides a repeatable method to inspect, validate, or control an important Linux subsystem.
- Produces evidence that can be attached to incident, change, problem, audit, and capacity records.
- Helps distinguish configuration, permission, kernel, service, network, storage, security, and application failures.
- Supports before-and-after validation rather than unmeasured configuration changes.

## 4. Core concepts

- Runtime rules disappear after reboot unless loaded from persistent rule files.
- Modern persistent rules are commonly stored under `/etc/audit/rules.d/` and compiled with `augenrules`.
- File watches are convenient, while syscall/path filters can be more precise and scalable.
- Audit rules operate in the kernel and can add overhead when too broad.
- The audit daemon must keep up with event rate to avoid backlog loss or failure actions.
- Immutable mode prevents further rule changes until reboot.

## 5. Important commands

| Command | Purpose | Operational risk |
|---|---|---|
| `sudo auditctl -s` | Display audit subsystem status. | Read-only |
| `sudo auditctl -l` | List loaded rules. | Read-only |
| `sudo auditctl -w /etc/passwd -p wa -k identity_changes` | Watch writes and attribute changes. | Runtime audit change |
| `sudo auditctl -W /etc/passwd -k identity_changes` | Remove a matching watch. | Runtime audit change |
| `sudo auditctl -a always,exit -F arch=b64 -S openat -F dir=/etc -F perm=wa -k etc_changes` | Audit selected file access through a syscall rule. | Runtime audit change |
| `sudo auditctl -a always,exit -F arch=b64 -S execve -F euid=0 -k root_exec` | Audit commands executed with effective UID 0. | Runtime audit change |
| `sudo auditctl -b 16384` | Set the kernel audit backlog limit. | Runtime kernel change |
| `sudo auditctl -r 1000` | Set an audit message rate limit. | Runtime kernel change |
| `sudo auditctl -e 1` | Enable auditing. | Runtime audit change |
| `sudo auditctl -e 2` | Enable immutable rule mode until reboot. | High-impact irreversible-until-reboot change |
| `sudo augenrules --check` | Check whether persistent rules need rebuilding. | Read-only |
| `sudo augenrules --load` | Load persistent rules. | Audit rules reload |

## 7. How to interpret the output

- `enabled 1` means auditing is enabled; `2` normally means immutable mode.
- `lost` should remain zero; increases indicate audit records were dropped.
- `backlog` shows queued records and must be compared with `backlog_limit`.
- Rule keys such as `identity_changes` make later searches easier.
- Architecture-specific syscall rules may require both `b32` and `b64` on 64-bit systems.

## 8. L3 troubleshooting workflow

1. **Define impact:** Identify the affected service, users, start time, scope, and business symptom.
2. **Preserve evidence:** Capture relevant logs, configuration, counters, timestamps, versions, and current state.
3. **Confirm ownership:** Determine whether systemd, NetworkManager, authselect, firewalld, policy, automation, or another manager owns the configuration.
4. **Use read-only checks first:** Avoid changing state before the failure mode is understood.
5. **Correlate adjacent layers:** Check process, kernel, filesystem, network, DNS, time, identity, audit, and SELinux evidence as appropriate.
6. **Form one hypothesis:** State what evidence supports it and what observation would disprove it.
7. **Make one controlled change:** Use a maintenance window, backup, console path, and rollback command.
8. **Validate service metrics:** Confirm application latency, error rate, authentication, data integrity, and logs—not only command success.
9. **Restore or persist:** Roll back failed experiments and make successful changes through approved configuration management.
10. **Document RCA:** Record root cause, contributing factors, corrective action, prevention, and monitoring.

## 9. Production cautions

- Do not enable immutable mode until the full rule set is validated.
- Broad `execve` or directory rules can generate very high volume.
- Audit failures can trigger configured system actions; review `auditd.conf`.
- Treat audit logs as security evidence and preserve chain of custody.
- Never copy example users, paths, ports, addresses, or devices into production without validation.
- Commands that change credentials, access, labels, firewall rules, packages, audit rules, or services require change control.
- Keep an independent administrative path for SSH, PAM, firewall, DNS, and authentication work.
