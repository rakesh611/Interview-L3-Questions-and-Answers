# 1. Kernel module overview

A **Linux kernel module** is a piece of code that can be loaded into or removed from the running kernel.

Kernel modules commonly provide:

- Hardware device drivers
- File-system support
- Network protocol support
- Virtualization drivers
- Storage drivers
- Encryption and security functionality
- Netfilter and firewall functionality

Examples:

| Module | Purpose |
|---|---|
| `virtio_net` | VirtIO network driver used by virtual machines |
| `virtio_blk` | VirtIO block-storage driver |
| `xfs` | XFS file-system support |
| `nf_conntrack` | Network connection tracking |
| `br_netfilter` | Bridge traffic integration with Netfilter |
| `bonding` | Network interface bonding |
| `8021q` | IEEE 802.1Q VLAN support |
| `kvm` | Kernel-based virtualization framework |
| `kvm_intel` | Intel KVM processor support |
| `kvm_amd` | AMD KVM processor support |
| `nvme` | NVMe storage driver |
| `loop` | Loopback block devices |

Kernel module files are usually stored below:

```bash
/lib/modules/$(uname -r)/
```

Example:

```bash
find /lib/modules/"$(uname -r)" -type f -name '*.ko*' | head
```

Depending on the distribution, modules may be:

```text
.ko
.ko.xz
.ko.zst
.ko.gz
```

Do not normally include `.ko`, `.ko.xz`, or `.ko.zst` when using `modprobe` or `modinfo`.

Correct:

```bash
sudo modprobe bonding
modinfo bonding
```

Normally avoid:

```bash
sudo modprobe bonding.ko.xz
```

## Kernel module versus built-in driver

A kernel feature can be compiled in one of two main ways:

1. **Built directly into the kernel**
2. **Built as a loadable module**

A built-in driver does not need to be loaded with `modprobe` and normally does not appear in `lsmod`.

Check the kernel configuration when available:

```bash
grep CONFIG_XFS_FS /boot/config-"$(uname -r)"
```

Possible results:

```text
CONFIG_XFS_FS=y
```

Meaning: built into the kernel.

```text
CONFIG_XFS_FS=m
```

Meaning: built as a module.

```text
# CONFIG_XFS_FS is not set
```

Meaning: not enabled in this kernel build.

# 2. How the four commands work together

The four commands solve different parts of kernel module administration.

| Command | Primary function |
|---|---|
| `lsmod` | Shows modules currently loaded in the running kernel |
| `modinfo` | Shows metadata, parameters, aliases, dependencies, firmware, and file location |
| `modprobe` | Loads or removes a module and handles dependencies |
| `depmod` | Scans installed module files and generates dependency and alias databases |

Typical workflow:

```text
1. lsmod
   Check whether a module is already loaded.

2. modinfo
   Inspect the module, its parameters, dependencies, aliases, and file.

3. modprobe
   Load or remove the module.

4. depmod
   Rebuild module indexes after manually installing, replacing, or deleting a module.
```

Example:

```bash
lsmod | grep '^bonding'
modinfo bonding
sudo modprobe bonding
lsmod | grep '^bonding'
```

If a new third-party module was copied into the module tree:

```bash
sudo cp example.ko.xz /lib/modules/"$(uname -r)"/extra/
sudo depmod -a
sudo modprobe example
```

# 3. `lsmod` — list loaded kernel modules

## 3.1 What is `lsmod`?

`lsmod` displays the kernel modules that are currently loaded.

It formats information obtained from:

```bash
/proc/modules
```

Basic command:

```bash
lsmod
```

Example output:

```text
Module                  Size  Used by
bonding               245760  0
8021q                   40960  0
garp                    16384  1 8021q
mrp                     20480  1 8021q
stp                     12288  1 bridge
llc                     16384  2 bridge,stp
```

## 3.2 Understanding the output

### `Module`

The module name.

Example:

```text
bonding
```

### `Size`

The memory size associated with the loaded module, in bytes.

Example:

```text
245760
```

This value is not necessarily the exact total physical memory consumed by all module-related allocations.

### `Used by`

Shows the module reference count and, when available, modules that depend on it.

Example:

```text
llc  16384  2 bridge,stp
```

Meaning:

- The `llc` module has a usage count of `2`.
- `bridge` and `stp` use it.

A usage count of `0` does not always guarantee that unloading the module is safe. A driver may still be associated with hardware, network interfaces, file systems, or active kernel objects.

---

## 3.3 Important `lsmod` commands

### List all loaded modules

```bash
lsmod
```

### Search for a particular module

```bash
lsmod | grep '^bonding'
```

The `^` anchors the search to the start of the line.

Another example:

```bash
lsmod | grep '^br_netfilter'
```

### Perform a case-insensitive search

```bash
lsmod | grep -i 'virtio'
```

### Show only module names

```bash
lsmod | awk 'NR > 1 {print $1}'
```

### Count loaded modules

```bash
lsmod | awk 'NR > 1' | wc -l
```

### Sort modules by size

```bash
lsmod | sort -k2 -nr
```

Preserve the heading:

```bash
{
    lsmod | head -n 1
    lsmod | tail -n +2 | sort -k2 -nr
}
```

### Display the ten largest loaded modules

```bash
lsmod | tail -n +2 | sort -k2 -nr | head -n 10
```

### Find modules with zero displayed users

```bash
lsmod | awk 'NR > 1 && $3 == 0 {print}'
```

Do not automatically unload every module shown with zero users.

### View the original `/proc/modules` data

```bash
cat /proc/modules
```

Example:

```text
bonding 245760 0 - Live 0xffffffffc0a00000
```

`lsmod` is easier for routine administration, while `/proc/modules` can provide extra low-level fields.

### Continuously watch module changes

```bash
watch -n 1 lsmod
```

Search for one module:

```bash
watch -n 1 "lsmod | grep -E '^Module|^bonding'"
```

### Record currently loaded modules

```bash
lsmod > /tmp/lsmod-before.txt
```

After a change:

```bash
lsmod > /tmp/lsmod-after.txt
diff -u /tmp/lsmod-before.txt /tmp/lsmod-after.txt
```

### Check the `lsmod` version

```bash
lsmod --version
```

### Display help

```bash
lsmod --help
```

---

## 3.4 Practical examples

### Verify that KVM modules are loaded

For Intel:

```bash
lsmod | grep -E '^kvm|^kvm_intel'
```

For AMD:

```bash
lsmod | grep -E '^kvm|^kvm_amd'
```

### Verify VirtIO modules

```bash
lsmod | grep virtio
```

### Verify Linux bridge and bridge Netfilter modules

```bash
lsmod | grep -E '^bridge|^br_netfilter'
```

### Verify network bonding

```bash
lsmod | grep '^bonding'
```

### Verify VLAN support

```bash
lsmod | grep '^8021q'
```

### Check loaded Netfilter modules

```bash
lsmod | grep -E '^nf_|^nft_|^xt_'
```

---

## 3.5 Limitations of `lsmod`

`lsmod` only shows **currently loaded loadable modules**.

It does not directly show:

- Modules available but not loaded
- Drivers compiled directly into the kernel
- Detailed module parameters
- Module aliases
- Module license
- Module firmware requirements
- Module configuration from `/etc/modprobe.d/`
- Whether a module should load automatically during boot

Use `modinfo`, `modprobe -c`, `/sys/module`, kernel configuration files, and boot logs for those tasks.

# 4. `modinfo` — display module information

## 4.1 What is `modinfo`?

`modinfo` displays information embedded in a kernel module.

Basic command:

```bash
modinfo MODULE_NAME
```

Example:

```bash
modinfo bonding
```

Typical fields may include:

```text
filename:       /lib/modules/5.14.0-xxx.el9.x86_64/kernel/drivers/net/bonding/bonding.ko.xz
author:         Thomas Davis, tadavis@lbl.gov and many others
description:    Ethernet Channel Bonding Driver
license:        GPL
alias:          rtnl-link-bond
depends:
retpoline:      Y
intree:         Y
name:           bonding
vermagic:       5.14.0-xxx.el9.x86_64 SMP mod_unload modversions
sig_id:         PKCS#7
signer:         Red Hat Enterprise Linux kernel signing key
parm:           max_bonds:Max number of bonded devices (int)
```

The exact output depends on the kernel and distribution.

---

## 4.2 Important fields

| Field | Meaning |
|---|---|
| `filename` | Module file location |
| `name` | Module name |
| `description` | Human-readable purpose |
| `author` | Module author information |
| `license` | Module license |
| `alias` | Hardware or software aliases that can trigger module loading |
| `depends` | Direct module dependencies |
| `firmware` | Firmware files the module may require |
| `parm` | Supported module parameters |
| `vermagic` | Kernel build/version compatibility string |
| `intree` | Whether it was built as part of the kernel source tree |
| `retpoline` | Retpoline build information when applicable |
| `sig_id` | Signature format |
| `signer` | Certificate or key used to sign the module |
| `sig_key` | Signing key identifier |
| `signature` | Module signature data |

---

## 4.3 Important `modinfo` commands

### Display all available information

```bash
modinfo bonding
```

### Show the module file path

```bash
modinfo -n bonding
```

Equivalent:

```bash
modinfo -F filename bonding
```

Example output:

```text
/lib/modules/5.14.0-xxx.el9.x86_64/kernel/drivers/net/bonding/bonding.ko.xz
```

### Show the description

```bash
modinfo -d bonding
```

Equivalent:

```bash
modinfo -F description bonding
```

### Show the license

```bash
modinfo -l bonding
```

Equivalent:

```bash
modinfo -F license bonding
```

### Show the author

```bash
modinfo -a bonding
```

### Show supported parameters

```bash
modinfo -p bonding
```

Equivalent:

```bash
modinfo -F parm bonding
```

Example:

```text
max_bonds:Max number of bonded devices (int)
```

### Show dependencies

```bash
modinfo -F depends bonding
```

Another example:

```bash
modinfo -F depends virtio_net
```

### Show aliases

```bash
modinfo -F alias e1000e
```

Aliases help automatic hardware-driver selection.

### Show required firmware

```bash
modinfo -F firmware iwlwifi
```

This is useful when a wireless or storage adapter fails because firmware is missing.

### Show kernel version compatibility information

```bash
modinfo -F vermagic bonding
```

Compare with:

```bash
uname -r
```

A mismatch may cause:

```text
Invalid module format
```

### Show module signature information

```bash
modinfo bonding | grep -E '^(sig_id|signer|sig_key|signature):'
```

A compact command:

```bash
modinfo -F signer bonding
```

This is important on Secure Boot systems.

### Query a module by file path

```bash
modinfo /lib/modules/"$(uname -r)"/kernel/drivers/net/bonding/bonding.ko.xz
```

### Query a module for another installed kernel

List installed module trees:

```bash
ls -1 /lib/modules/
```

Then query:

```bash
modinfo -k 5.14.0-XXX.el9.x86_64 bonding
```

This is useful before booting a newly installed kernel.

### Print only one field for scripting

```bash
modinfo -F filename xfs
modinfo -F description xfs
modinfo -F depends xfs
modinfo -F firmware iwlwifi
```

### Print null-separated output

```bash
modinfo -0 -F alias e1000e
```

This is useful in scripts when values could contain newline characters.

### Check the version

```bash
modinfo --version
```

### Display help

```bash
modinfo --help
```

## 4.4 Inspecting runtime parameters

`modinfo -p` shows parameters that may be accepted when loading a module.

```bash
modinfo -p MODULE_NAME
```

Example:

```bash
modinfo -p loop
```

After a module is loaded, parameter values may be exposed under:

```bash
/sys/module/MODULE_NAME/parameters/
```

Example:

```bash
ls -l /sys/module/loop/parameters/
```

Read a parameter:

```bash
cat /sys/module/loop/parameters/max_loop
```

List all readable parameters:

```bash
for file in /sys/module/loop/parameters/*; do
    printf '%-50s = ' "$file"
    cat "$file"
done
```

Some parameters are read-only after module loading. Others may be writable, depending on the driver's implementation and file permissions.

---

## 4.5 Check whether a module exists

```bash
modinfo MODULE_NAME
```

Example:

```bash
modinfo bonding
```

If it exists, the command returns module information.

If it does not exist for the selected kernel:

```text
modinfo: ERROR: Module bonding not found.
```

Use the command status in a script:

```bash
if modinfo bonding >/dev/null 2>&1; then
    echo "bonding module is available"
else
    echo "bonding module is not available"
fi
```

---

## 4.6 Find the package that owns a module

### RHEL-family systems

```bash
rpm -qf "$(modinfo -n bonding)"
```

### Debian-family systems

```bash
dpkg -S "$(modinfo -n bonding)"
```

This is useful when checking whether a driver came from the distribution kernel or a third-party package.

## 4.7 `modinfo` production use cases

### Investigate an `Invalid module format` error

```bash
uname -r
modinfo -F vermagic MODULE_NAME
journalctl -k -b | tail -n 100
```

### Investigate missing firmware

```bash
modinfo -F firmware MODULE_NAME
journalctl -k -b | grep -i firmware
```

### Check whether Secure Boot may reject a module

```bash
modinfo MODULE_NAME | grep -E '^(signer|sig_id|sig_key):'
mokutil --sb-state
journalctl -k -b | grep -Ei 'module|signature|secure boot'
```

### Find module dependencies

```bash
modinfo -F depends MODULE_NAME
modprobe --show-depends MODULE_NAME
```

`modprobe --show-depends` is usually more operationally useful because it processes aliases and configuration rules.

# 5. `modprobe` — load and remove modules

## 5.1 What is `modprobe`?

`modprobe` loads or removes kernel modules.

Unlike `insmod`, `modprobe` understands:

- Module dependencies
- Module aliases
- `/etc/modprobe.d/*.conf`
- Blacklists
- Module parameters
- Install and remove rules
- Dependency indexes generated by `depmod`

Basic load command:

```bash
sudo modprobe MODULE_NAME
```

Basic remove command:

```bash
sudo modprobe -r MODULE_NAME
```

Use `modprobe` instead of `insmod` for normal administration.

---

## 5.2 Load a module

```bash
sudo modprobe bonding
```

Verify:

```bash
lsmod | grep '^bonding'
```

Check kernel messages:

```bash
journalctl -k -b --no-pager | tail -n 50
```

or:

```bash
dmesg | tail -n 50
```

---

## 5.3 Load a module with parameters

General syntax:

```bash
sudo modprobe MODULE_NAME parameter=value
```

Example:

```bash
sudo modprobe loop max_loop=16
```

Verify when exposed:

```bash
cat /sys/module/loop/parameters/max_loop
```

Before using a parameter, confirm it:

```bash
modinfo -p loop
```

Important:

- Parameter names and allowed values are driver-specific.
- A wrong value may cause module loading to fail.
- Loading with a parameter is usually temporary until reboot.
- Parameters should be made persistent through `/etc/modprobe.d/*.conf`.

---

## 5.4 Remove a module

```bash
sudo modprobe -r bonding
```

Verify:

```bash
lsmod | grep '^bonding'
```

No output normally means it is no longer loaded.

Warning: Do not remove a module used by:

- The root file system
- Active storage
- Active network interfaces
- Mounted file systems
- Production applications
- The system console
- Virtual machine storage or network devices
- Required cryptographic or firewall functions

---

## 5.5 Important `modprobe` commands

### Load a module

```bash
sudo modprobe MODULE_NAME
```

Example:

```bash
sudo modprobe 8021q
```

### Remove a module

```bash
sudo modprobe -r MODULE_NAME
```

Example:

```bash
sudo modprobe -r 8021q
```

### Load multiple modules

```bash
sudo modprobe -a bonding 8021q br_netfilter
```

### Display verbose actions

```bash
sudo modprobe -v bonding
```

### Perform a dry run

```bash
modprobe -n -v bonding
```

This shows what would be done without loading the module.

This should be one of the first commands used during troubleshooting.

### Show module dependencies

```bash
modprobe --show-depends virtio_net
```

Example output may resemble:

```text
insmod /lib/modules/.../net_failover.ko.xz
insmod /lib/modules/.../virtio_net.ko.xz
```

### Display effective modprobe configuration

```bash
modprobe -c
```

Search configuration for a module:

```bash
modprobe -c | grep -E '(^|[[:space:]])bonding([[:space:]]|$)'
```

Show blacklist entries:

```bash
modprobe -c | grep '^blacklist'
```

Show module option entries:

```bash
modprobe -c | grep '^options'
```

### Resolve a module alias

```bash
modprobe -R 'pci:v00008086d*'
```

A practical hardware alias is normally obtained from:

```bash
modinfo -F alias DRIVER_NAME
```

or:

```bash
lspci -nnk
```

### Use blacklist rules during a manual probe

```bash
sudo modprobe -b MODULE_NAME
```

`-b` tells `modprobe` to apply configured blacklist commands to the module name.

### Check whether an operation would make a real change

```bash
sudo modprobe --first-time MODULE_NAME
```

If the module is already loaded, this command fails instead of succeeding silently.

For removal:

```bash
sudo modprobe --first-time -r MODULE_NAME
```

### Wait while attempting to remove a busy module

```bash
sudo modprobe -r --wait 5000 MODULE_NAME
```

The timeout is in milliseconds.

This does not make an unsafe removal safe. It only retries while the module remains busy.

### Use a module tree for another kernel

```bash
sudo modprobe -S 5.14.0-XXX.el9.x86_64 --show-depends bonding
```

This selects another kernel version's module directory.

### Show exported symbols

```bash
modprobe --show-exports "$(modinfo -n MODULE_NAME)"
```

This is mainly for advanced driver and dependency investigation.

### Show required module symbol versions

```bash
modprobe --show-modversions "$(modinfo -n MODULE_NAME)"
```

This is mainly used in packaging and compatibility investigation.

### Check version

```bash
modprobe --version
```

### Display help

```bash
modprobe --help
```

## 5.6 Find what currently uses a module

Start with:

```bash
lsmod | grep '^MODULE_NAME'
```

Check reverse module dependencies:

```bash
lsmod | awk '$1 == "MODULE_NAME" {print}'
```

Inspect holders:

```bash
ls -l /sys/module/MODULE_NAME/holders/
```

Example:

```bash
ls -l /sys/module/llc/holders/
```

Inspect related devices:

```bash
find /sys/module/MODULE_NAME -maxdepth 3 -type l -o -type d
```

For a network driver:

```bash
ethtool -i INTERFACE
ip -br link
```

For storage:

```bash
lsblk -o NAME,TYPE,FSTYPE,MOUNTPOINTS
lspci -nnk
```

For mounted file systems:

```bash
findmnt
```

## 5.7 Why `modprobe -r` reports “Module is in use”

Example error:

```text
modprobe: FATAL: Module MODULE_NAME is in use.
```

Possible reasons:

- Another module depends on it.
- A network interface uses the driver.
- A file system is mounted.
- A block device is open.
- A process has the device open.
- A kernel subsystem holds a reference.
- The driver does not support unloading.
- The kernel was built without module unloading support.

Investigation:

```bash
lsmod | grep '^MODULE_NAME'
ls -l /sys/module/MODULE_NAME/holders/
lsof /dev/DEVICE
fuser -vm /mount/point
journalctl -k -b --no-pager | tail -n 100
```

Never force module removal on a production system merely to bypass “in use.”

---

## 5.8 `modprobe` versus `insmod`

### `insmod`

```bash
sudo insmod /path/to/module.ko
```

Characteristics:

- Requires a module file path
- Does not automatically resolve normal dependencies
- Bypasses most alias-based selection
- Mainly useful for driver development and controlled testing

### `modprobe`

```bash
sudo modprobe module_name
```

Characteristics:

- Searches the module tree
- Resolves dependencies
- Reads configuration
- Understands aliases
- Is preferred for normal administration

Recommended:

```bash
sudo modprobe MODULE_NAME
```

# 6. `depmod` — build the module dependency database

## 6.1 What is `depmod`?

`depmod` scans module files for a kernel version and generates files used by `modprobe` and other `kmod` tools.

The most important generated files include:

```text
modules.dep
modules.dep.bin
modules.alias
modules.alias.bin
modules.symbols
modules.symbols.bin
modules.devname
```

Location:

```bash
/lib/modules/$(uname -r)/
```

Basic command:

```bash
sudo depmod -a
```

`-a` means scan all modules. It is also the default when no module filenames are supplied.

---

## 6.2 Why is `depmod` required?

Assume a third-party module is manually installed:

```bash
sudo install -D -m 0644 mydriver.ko \
    /lib/modules/"$(uname -r)"/extra/mydriver.ko
```

The module file exists, but `modprobe` may not know about it until the indexes are updated.

Run:

```bash
sudo depmod -a
```

Then:

```bash
sudo modprobe mydriver
```

Without a current dependency database, `modprobe` can report:

```text
modprobe: FATAL: Module mydriver not found in directory /lib/modules/...
```

even though a module file was recently copied into the tree.

---

## 6.3 Important `depmod` commands

### Rebuild all dependency information for the running kernel

```bash
sudo depmod -a
```

### Rebuild dependency information for a specific installed kernel

```bash
sudo depmod -a 5.14.0-XXX.el9.x86_64
```

List available kernel versions:

```bash
ls -1 /lib/modules/
```

### Quick update

```bash
sudo depmod -A
```

`-A` checks whether modules are newer than the existing dependency file. If nothing changed, it exits without regenerating everything.

### Verbose mode

```bash
sudo depmod -v
```

This can produce substantial output.

Filter for one module:

```bash
sudo depmod -v 2>&1 | grep -i mydriver
```

### Dry run: print generated data without writing it

```bash
depmod -n
```

This can be very large.

Filter it:

```bash
depmod -n | grep 'mydriver'
```

### Warn about duplicates and related issues

```bash
sudo depmod -w
```

### Check unresolved symbols with `System.map`

```bash
sudo depmod -e -F /boot/System.map-"$(uname -r)"
```

This is useful when investigating third-party or incorrectly built modules.

### Check symbol versions using `Module.symvers`

When a suitable `Module.symvers` file is available:

```bash
sudo depmod -e -E /path/to/Module.symvers
```

`-E` and `-F` are mutually exclusive.

### Use a staging root

```bash
depmod -b /tmp/staging-root
```

Expected input layout:

```text
/tmp/staging-root/lib/modules/KERNEL_VERSION/
```

This is mainly useful for package creation, image building, chroots, and initramfs preparation.

### Specify a different output root

```bash
depmod -o /tmp/output-root
```

This is an advanced packaging/build option.

### Show version

```bash
depmod --version
```

### Display help

```bash
depmod --help
```

## 6.4 Inspect the generated dependency database

### Human-readable dependencies

```bash
less /lib/modules/"$(uname -r)"/modules.dep
```

Search for a module:

```bash
grep '/virtio_net\.ko' /lib/modules/"$(uname -r)"/modules.dep
```

Example structure:

```text
kernel/drivers/net/virtio_net.ko.xz: kernel/net/core/net_failover.ko.xz
```

Meaning: `virtio_net` depends on `net_failover`.

### Search aliases

```bash
grep -i 'bond' /lib/modules/"$(uname -r)"/modules.alias | head
```

### Search built-in modules

```bash
grep -i '/xfs\.ko' /lib/modules/"$(uname -r)"/modules.builtin
```

The exact built-in metadata files depend on the kernel and distribution.

## 6.5 When should an administrator run `depmod` manually?

Normally package-management scripts run `depmod` automatically after a kernel or module package is installed.

Manual execution is appropriate after:

- Copying a custom module into `/lib/modules/...`
- Removing a module manually
- Replacing a third-party driver
- Restoring the module tree from backup
- Repairing missing or corrupted dependency files
- Preparing modules in a chroot or offline image
- Testing an out-of-tree kernel module
- Investigating `modprobe` dependency-resolution failures

Typical sequence:

```bash
sudo install -D -m 0644 mydriver.ko \
    /lib/modules/"$(uname -r)"/extra/mydriver.ko

sudo depmod -a
modinfo mydriver
sudo modprobe -n -v mydriver
sudo modprobe mydriver
lsmod | grep '^mydriver'
journalctl -k -b --no-pager | tail -n 100
```

# 7. Persistent module loading

A module loaded with:

```bash
sudo modprobe MODULE_NAME
```

is loaded only into the current running kernel. It may not remain loaded after reboot unless hardware discovery or configuration loads it again.

For explicit boot-time loading, create a file in:

```text
/etc/modules-load.d/
```

Example:

```bash
echo 'br_netfilter' | sudo tee /etc/modules-load.d/br_netfilter.conf
```

Load it now:

```bash
sudo modprobe br_netfilter
```

Verify:

```bash
lsmod | grep '^br_netfilter'
```

A file can contain multiple module names:

```bash
sudo tee /etc/modules-load.d/network-modules.conf >/dev/null <<'EOF'
bonding
8021q
br_netfilter
EOF
```

Apply without reboot by loading them manually:

```bash
sudo modprobe bonding
sudo modprobe 8021q
sudo modprobe br_netfilter
```

Check configuration files:

```bash
grep -R --line-number --no-messages \
    -E '^[[:space:]]*[[:alnum:]_-]+' \
    /etc/modules-load.d /usr/lib/modules-load.d /run/modules-load.d
```

On systemd systems, the relevant service is:

```bash
systemctl status systemd-modules-load.service
```

Logs:

```bash
journalctl -u systemd-modules-load.service -b
```

---

# 8. Persistent module parameters

To configure module parameters persistently, create a file under:

```text
/etc/modprobe.d/
```

Syntax:

```text
options MODULE_NAME parameter=value
```

Example:

```bash
sudo tee /etc/modprobe.d/loop.conf >/dev/null <<'EOF'
options loop max_loop=16
EOF
```

Check effective configuration:

```bash
modprobe -c | grep -E '^options loop '
```

Reload only when safe:

```bash
sudo modprobe -r loop
sudo modprobe loop
```

Verify:

```bash
cat /sys/module/loop/parameters/max_loop
```

If the module is required during early boot, the initramfs may also need rebuilding.

### RHEL-family systems

```bash
sudo dracut -f
```

### Debian/Ubuntu systems

```bash
sudo update-initramfs -u
```

Do not rebuild the initramfs casually on a damaged boot configuration. Confirm free space in `/boot` and retain a known-good boot entry.

# 9. Blacklisting a module

Blacklisting tells automatic module-loading mechanisms not to select a module in normal alias-based probing.

Create:

```bash
sudo tee /etc/modprobe.d/blacklist-example.conf >/dev/null <<'EOF'
blacklist MODULE_NAME
EOF
```

Example:

```bash
sudo tee /etc/modprobe.d/blacklist-nouveau.conf >/dev/null <<'EOF'
blacklist nouveau
EOF
```

Important: This is only an example. Do not blacklist a graphics, storage, network, or security module without confirming the impact.

Verify effective configuration:

```bash
modprobe -c | grep -E '^blacklist nouveau$'
```

Test a blacklisted-aware probe:

```bash
modprobe -n -v -b nouveau
```

## Stronger disable rule

A blacklist may not prevent every explicit load path. A stronger rule is sometimes used:

```text
install MODULE_NAME /bin/false
```

Example:

```bash
sudo tee /etc/modprobe.d/disable-example.conf >/dev/null <<'EOF'
blacklist MODULE_NAME
install MODULE_NAME /bin/false
EOF
```

Inspect:

```bash
modprobe -c | grep -E '^(blacklist|install) MODULE_NAME'
```

## Early-boot modules

If the module exists in the initramfs, update the initramfs after changing its configuration.

### RHEL-family systems

```bash
sudo dracut -f
```

### Debian/Ubuntu systems

```bash
sudo update-initramfs -u
```

On RHEL, a temporary kernel-command-line blacklist can also involve parameters such as:

```text
rd.driver.blacklist=MODULE_NAME
modprobe.blacklist=MODULE_NAME
```

Boot-loader changes should be performed through the distribution-supported tool and tested with rollback access.

# 10. Production troubleshooting workflow

Use this sequence when a device, file system, virtual function, or kernel feature is not working.

## Step 1: Record the running kernel

```bash
uname -r
uname -a
```

## Step 2: Check whether the module is loaded

```bash
lsmod | grep '^MODULE_NAME'
```

## Step 3: Check whether the module is available

```bash
modinfo MODULE_NAME
```

## Step 4: Confirm the module file

```bash
modinfo -n MODULE_NAME
ls -l "$(modinfo -n MODULE_NAME)"
```

## Step 5: Inspect dependencies and parameters

```bash
modinfo -F depends MODULE_NAME
modinfo -p MODULE_NAME
modprobe --show-depends MODULE_NAME
```

## Step 6: Inspect modprobe configuration

```bash
modprobe -c | grep -E \
    '^(alias|blacklist|options|install|remove).*MODULE_NAME'
```

Also search source files directly:

```bash
grep -R --line-number --no-messages \
    -E 'MODULE_NAME' \
    /etc/modprobe.d /run/modprobe.d /usr/lib/modprobe.d
```

## Step 7: Perform a dry run

```bash
modprobe -n -v MODULE_NAME
```

For blacklist-aware behavior:

```bash
modprobe -n -v -b MODULE_NAME
```

## Step 8: Load the module

```bash
sudo modprobe -v MODULE_NAME
```

## Step 9: Check kernel logs immediately

```bash
journalctl -k -b --since '-5 minutes' --no-pager
```

or:

```bash
dmesg --ctime | tail -n 100
```

## Step 10: Verify runtime state

```bash
lsmod | grep '^MODULE_NAME'
ls -l /sys/module/MODULE_NAME/
```

For network devices:

```bash
lspci -nnk
ip -br link
ethtool -i INTERFACE
```

For USB devices:

```bash
lsusb
usb-devices
```

For block devices:

```bash
lsblk -o NAME,MAJ:MIN,TYPE,SIZE,FSTYPE,MOUNTPOINTS
lspci -nnk
```

## Step 11: Rebuild dependency metadata when needed

Only if a module was manually added, replaced, or removed:

```bash
sudo depmod -a
```

Then repeat:

```bash
modinfo MODULE_NAME
modprobe -n -v MODULE_NAME
sudo modprobe MODULE_NAME
```

# 11. Common errors and solutions

## 11.1 `Module not found`

Error:

```text
modprobe: FATAL: Module MODULE_NAME not found in directory /lib/modules/KERNEL
```

Check:

```bash
uname -r
ls -ld /lib/modules/"$(uname -r)"
find /lib/modules/"$(uname -r)" -type f -iname '*MODULE_NAME*.ko*'
modinfo MODULE_NAME
```

Possible causes:

- Module package is not installed.
- Running kernel and `/lib/modules` do not match.
- A newly installed module was not indexed.
- The module name is wrong.
- The driver is built into the kernel.
- The distribution kernel does not provide the module.
- `/lib/modules` is incomplete or corrupted.

Possible repair after manually adding a module:

```bash
sudo depmod -a
```

On RHEL-family systems, inspect installed kernel packages:

```bash
rpm -qa | grep '^kernel' | sort
```

Verify installed package files:

```bash
sudo rpm -V kernel-core kernel-modules-core kernel-modules
```

Package names vary by version and installation profile.

---

## 11.2 `Invalid module format`

Error:

```text
modprobe: ERROR: could not insert 'MODULE_NAME': Invalid module format
```

Check:

```bash
uname -r
modinfo -F vermagic MODULE_NAME
journalctl -k -b --no-pager | tail -n 100
```

Likely causes:

- Module built for a different kernel
- Kernel ABI mismatch
- Compiler/build option mismatch
- Corrupted module
- Incorrect third-party driver package

Do not use `modprobe --force` in production as a routine solution. Kernel compatibility checks exist to protect system integrity.

Correct solution:

- Install a module built for the running kernel.
- Rebuild the out-of-tree module against the correct kernel development package.
- Boot the matching kernel.
- Use the vendor-supported driver package.

---

## 11.3 `Required key not available` or signature rejection

Possible error:

```text
modprobe: ERROR: could not insert 'MODULE_NAME': Required key not available
```

Check:

```bash
mokutil --sb-state
modinfo MODULE_NAME | grep -E '^(sig_id|signer|sig_key):'
journalctl -k -b | grep -Ei 'module|signature|verification|secure boot'
```

Likely cause:

- Secure Boot is enabled.
- The module is unsigned.
- The signing certificate is not trusted.
- The module signature is invalid.

Correct solution depends on organizational policy:

- Use a distribution-signed module.
- Use a vendor-signed module.
- Sign the module using an approved key and enroll that key.
- Follow the platform's Secure Boot and MOK procedure.
- Do not disable Secure Boot without authorization and risk review.

---

## 11.4 `Unknown symbol`

Kernel log example:

```text
MODULE_NAME: Unknown symbol some_symbol
```

Check:

```bash
journalctl -k -b --no-pager | tail -n 200
modinfo -F depends MODULE_NAME
modprobe --show-depends MODULE_NAME
sudo depmod -a
```

Advanced check:

```bash
sudo depmod -e -F /boot/System.map-"$(uname -r)"
```

Possible causes:

- Missing dependency
- Stale `modules.dep.bin`
- Version mismatch
- Incorrectly built third-party module
- Incompatible symbol version

---

## 11.5 Module is blacklisted

Dry run:

```bash
modprobe -n -v -b MODULE_NAME
```

Search configuration:

```bash
modprobe -c | grep -E \
    '^(blacklist|install|options|alias).*MODULE_NAME'
```

Search files:

```bash
grep -R --line-number --no-messages \
    'MODULE_NAME' \
    /etc/modprobe.d /run/modprobe.d /usr/lib/modprobe.d
```

Also check the kernel command line:

```bash
cat /proc/cmdline
```

Search for:

```text
modprobe.blacklist=MODULE_NAME
rd.driver.blacklist=MODULE_NAME
```

---

## 11.6 Module loads but the device still does not work

Check device-to-driver binding.

PCI:

```bash
lspci -nnk
```

USB:

```bash
lsusb
usb-devices
```

Network:

```bash
ip -br link
ethtool -i INTERFACE
```

Kernel logs:

```bash
journalctl -k -b --no-pager | grep -Ei \
    'firmware|error|fail|timeout|reset|MODULE_NAME'
```

Firmware:

```bash
modinfo -F firmware MODULE_NAME
```

Possible causes:

- Missing firmware
- Hardware not detected
- Wrong driver bound
- Driver loaded but initialization failed
- Device disabled in BIOS/UEFI
- IOMMU/VFIO binding
- PCI resource conflict
- Power-management issue
- Secure Boot rejection
- Hardware failure

---

## 11.7 `Module is in use`

Check:

```bash
lsmod | grep '^MODULE_NAME'
ls -l /sys/module/MODULE_NAME/holders/
```

For a device:

```bash
lsof /dev/DEVICE
fuser -v /dev/DEVICE
```

For a mount:

```bash
findmnt
fuser -vm /mount/point
```

For network:

```bash
ip -br link
ethtool -i INTERFACE
```

Safely stop or detach users before removal. Do not force removal of storage, file-system, or active network drivers.

---

## 11.8 Module parameter did not take effect

Check accepted parameters:

```bash
modinfo -p MODULE_NAME
```

Check effective configuration:

```bash
modprobe -c | grep -E '^options MODULE_NAME '
```

Check current runtime value:

```bash
ls -l /sys/module/MODULE_NAME/parameters/
cat /sys/module/MODULE_NAME/parameters/PARAMETER
```

Possible reasons:

- Parameter name is wrong.
- Value is invalid.
- Module was already loaded before configuration changed.
- Parameter is only read during module initialization.
- Another configuration file overrides it.
- The module is built into the kernel.
- The driver is loaded from the initramfs.
- Kernel command-line settings override or supplement it.

|---|---|
| `/proc/modules` | Modules currently loaded in the running kernel |

| `/sys/module/MODULE/parameters/` | Runtime module parameters |
| `/sys/module/MODULE/holders/` | Modules that depend on the selected module |

| `/lib/modules/$(uname -r)/updates/` | Common location for updated modules |
| `/lib/modules/$(uname -r)/modules.dep` | Text module dependency map |
| `/lib/modules/$(uname -r)/modules.dep.bin` | Binary dependency index |
| `/lib/modules/$(uname -r)/modules.alias` | Module alias map |
| `/lib/modules/$(uname -r)/modules.alias.bin` | Binary alias index |
| `/lib/modules/$(uname -r)/modules.builtin` | Modules built into the kernel |
| `/etc/modprobe.d/*.conf` | Local module options, aliases, blacklists, install/remove rules |
| `/usr/lib/modprobe.d/*.conf` | Vendor-supplied modprobe configuration |
| `/run/modprobe.d/*.conf` | Runtime-generated modprobe configuration |
| `/etc/modules-load.d/*.conf` | Local boot-time module loading list |

| `/run/modules-load.d/*.conf` | Runtime boot-time loading configuration |


# 15. Safety and production notes

1. Kernel modules run in kernel space and have very high privilege.
2. A defective or incompatible module can crash, hang, or corrupt a system.
3. Never load an untrusted module.
4. Avoid `modprobe --force`, `--force-vermagic`, and `--force-modversion`.
5. Do not unload active storage, root-file-system, network, virtualization, or security drivers.
6. Record the existing state before making changes.
7. Keep console, out-of-band management, or hypervisor access available.
8. Test persistent changes on a non-production system first.
9. Confirm that `/boot` has sufficient free space before rebuilding initramfs.
10. Keep a rollback plan for changes to initramfs or boot-loader parameters.
11. Use vendor-supported kernel modules on enterprise systems.
12. Investigate kernel messages immediately after module operations.

Recommended pre-change evidence:

```bash
date -Is
uname -a
lsmod > /var/tmp/lsmod-before.txt
modprobe -c > /var/tmp/modprobe-config-before.txt
journalctl -k -b --no-pager > /var/tmp/kernel-log-before.txt
```

Recommended verification:

```bash
lsmod | grep '^MODULE_NAME'
modinfo MODULE_NAME
journalctl -k -b --since '-10 minutes' --no-pager
```
