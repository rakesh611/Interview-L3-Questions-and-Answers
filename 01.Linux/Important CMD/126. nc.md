# 126. nc / ncat / netcat

> **Scope:** Corporate/L3 Linux administration, incident troubleshooting, safe change execution, and interview preparation.

## 1. What it is

`nc` (netcat) creates simple TCP, UDP, and Unix-domain socket clients or listeners. Administrators use it to test port reachability, application banners, bidirectional data flow, basic proxies, and network paths.

## 2. Production importance

- Provides a repeatable method for diagnosing or controlling the relevant Linux subsystem.
- Produces evidence suitable for incident timelines, change records, problem management, and audit review.
- Encourages before-and-after measurement instead of unverified tuning or repair.
- Separates command success from actual application availability, security, and data integrity.

## 3. Package or kernel interface

- **Primary package/interface:** nmap-ncat on RHEL; netcat-openbsd or netcat-traditional on other distributions
- Check availability and installed version before relying on an option:

```bash
command -v nc 2>/dev/null || true
rpm -q PACKAGE_NAME 2>/dev/null || true
COMMAND --version 2>/dev/null || COMMAND --help
```

## 4. Core concepts

- Several incompatible netcat implementations exist; always check `nc --help` or `ncat --help`.
- A successful TCP connection proves a listener and transport path are available, not that the application is healthy.
- UDP is connectionless, so a successful command does not necessarily prove the remote application received the datagram.
- Listening mode can expose a service to the network and must be tightly scoped.
- TLS support is normally provided by Nmap Ncat, not every `nc` implementation.
- Netcat transmits data without application-level protection unless TLS is explicitly used.

## 5. Important commands

| Command | Purpose | Risk |
|---|---|---|
| `nc -vz server.example.com 22` | Test a TCP port without sending application data. | Read-only |
| `nc -vz -w 3 192.0.2.20 443` | Test TCP reachability with a three-second timeout. | Read-only |
| `printf 'HEAD / HTTP/1.0\r\nHost: example.com\r\n\r\n' \| nc example.com 80` | Send a minimal HTTP request. | Read-only |
| `nc -l 8080` | Start a TCP listener on port 8080. | Temporary network listener |
| `printf 'test message\n' \| nc 192.0.2.20 8080` | Send data to a test listener. | Network test |
| `nc -u -vz -w 3 192.0.2.53 53` | Perform a basic UDP-port test; result is not definitive. | Read-only |
| `nc -U /run/myapp.sock` | Connect to a Unix-domain socket when supported. | Read-only |
| `ncat --ssl server.example.com 443` | Open a TLS-capable connection with Nmap Ncat. | Read-only |
| `ncat --ssl --ssl-verify --ssl-trustfile ca.pem server.example.com 443` | Verify a TLS peer with Nmap Ncat. | Read-only |
| `ss -lntup` | Confirm listeners and owning processes. | Read-only |
| `sudo tcpdump -ni any 'host 192.0.2.20 and port 8080'` | Observe the network test. | Read-only |

## 7. Output interpretation

- `succeeded` or an open connection normally confirms the TCP handshake.
- `Connection refused` indicates an active rejection, commonly no listener or a reject rule.
- `timed out` suggests filtering, routing failure, silent drops, or an unresponsive path.
- A received banner helps identify the application but should not be treated as secure identity.
- For UDP, packet capture and server logs provide stronger evidence than client exit status.

## 8. Corporate/L3 troubleshooting workflow

1. **Confirm impact:** Record affected applications, users, start time, error rate, latency, and business severity.
2. **Identify scope:** Determine whether the issue is host-wide, process-specific, filesystem-specific, network-path-specific, or limited to one namespace.
3. **Preserve evidence:** Save logs, configuration, counters, command output, package versions, and timestamps before changing state.
4. **Establish ownership:** Identify whether systemd, NetworkManager, firewalld, TuneD, udev, a backup scheduler, configuration management, or the application owns the setting.
5. **Use read-only inspection first:** Confirm the hypothesis with at least two independent evidence sources.
6. **Control the test:** Make only one bounded change and define the rollback command in advance.
7. **Measure service behavior:** Validate latency, throughput, errors, data consistency, authentication, and client experience.
8. **Persist correctly:** Apply successful changes through the supported configuration source rather than an ad hoc runtime command.
9. **Close the incident:** Document root cause, contributing conditions, corrective action, monitoring, and prevention.

## 9. Production cautions

- Never use a broadly bound listener on an untrusted network.
- Do not use netcat to transfer secrets in clear text.
- Avoid shell-execution options such as `-e`; implementations may omit them because of severe security risk.
- Coordinate scans and listeners with network-security policy.
- Replace all example users, paths, devices, addresses, ports, repositories, and services only after validation.
- Keep console or out-of-band access for firewall, bootloader, storage, authentication, and network changes.
- Back up data and configuration before destructive, recursive, or boot-critical commands.

## 10. Practice lab

3. Capture the TCP handshake.
4. Repeat with a closed port.

## 12. L3 interview questions

- What kernel interface, service, or data source does the tool use?
- Which commands are read-only, runtime-changing, persistent, destructive, or security-sensitive?
- What common output can be misinterpreted?
- Which adjacent tools confirm the same hypothesis?
- How would you perform the change remotely without losing access?
- What is the rollback and how would you validate it?
