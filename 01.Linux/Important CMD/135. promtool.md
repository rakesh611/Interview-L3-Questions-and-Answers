# 135. promtool

> **Scope:** Corporate/L3 Linux administration, incident troubleshooting, safe change execution, and interview preparation.

## 1. What it is

`promtool` validates Prometheus configuration and rules, runs rule unit tests, executes PromQL queries, analyzes TSDB data, and collects selected debugging information depending on the installed Prometheus version.

## 2. Production importance

- Provides a repeatable method for diagnosing or controlling the relevant Linux subsystem.
- Produces evidence suitable for incident timelines, change records, problem management, and audit review.
- Encourages before-and-after measurement instead of unverified tuning or repair.
- Separates command success from actual application availability, security, and data integrity.

## 3. Package or kernel interface

- **Primary package/interface:** Prometheus
- Check availability and installed version before relying on an option:

```bash
command -v promtool 2>/dev/null || true
rpm -q PACKAGE_NAME 2>/dev/null || true
COMMAND --version 2>/dev/null || COMMAND --help
```

## 4. Core concepts

- Configuration syntax validation does not prove targets are reachable or credentials are valid.
- Rule checking validates expressions and files; unit tests validate expected alert and recording-rule results against synthetic series.
- PromQL behavior depends on label sets, staleness, lookback, evaluation time, and data availability.
- TSDB tools should be used carefully against active storage.
- Subcommands and flags can change between Prometheus releases.
- Validation should be part of CI before a production reload.

## 5. Important commands

| Command | Purpose | Risk |
|---|---|---|
| `promtool --version` | Display the installed version. | Read-only |
| `promtool check config /etc/prometheus/prometheus.yml` | Validate Prometheus configuration and referenced rule files. | Read-only |
| `promtool check rules /etc/prometheus/rules/*.yml` | Validate rule files. | Read-only |
| `promtool test rules tests.yml` | Run recording-rule and alert-rule unit tests. | Read-only |
| `promtool query instant http://localhost:9090 'up == 0'` | Run an instant PromQL query. | Read-only |
| `promtool query range http://localhost:9090 'rate(node_cpu_seconds_total[5m])' --start='2026-07-28T10:00:00Z' --end='2026-07-28T11:00:00Z' --step=30s` | Run a range query; options depend on version. | Read-only |
| `promtool query series http://localhost:9090 --match='up'` | List matching series where supported. | Read-only |
| `promtool tsdb analyze /var/lib/prometheus` | Analyze TSDB cardinality and block data. | TSDB analysis |
| `promtool tsdb list /var/lib/prometheus` | List TSDB blocks where supported. | Read-only |
| `promtool tsdb dump /var/lib/prometheus` | Dump TSDB samples; can produce large output. | High-volume data read |
| `promtool debug all http://localhost:9090` | Collect a Prometheus debug bundle where supported. | Diagnostic collection |
| `curl -X POST http://localhost:9090/-/reload` | Reload after validation only when lifecycle reload is enabled. | Prometheus configuration reload |

## 7. Output interpretation

- A configuration check can report referenced rule-file failures.
- Rule-unit-test output identifies evaluation time, expected labels, annotations, and actual results.
- High-cardinality labels often appear in TSDB analysis as many series or large postings.
- An empty query result differs from a query parsing or server error.
- Always record Prometheus version because CLI behavior and feature support vary.

## 8. Corporate/L3 troubleshooting workflow

1. **Confirm impact:** Record affected applications, users, start time, error rate, latency, and business severity.
2. **Identify scope:** Determine whether the issue is host-wide, process-specific, filesystem-specific, network-path-specific, or limited to one namespace.
3. **Preserve evidence:** Save logs, configuration, counters, command output, package versions, and timestamps before changing state.
4. **Establish ownership:** Identify whether systemd, NetworkManager, firewalld, TuneD, udev, a backup scheduler, configuration management, or the application owns the setting.
5. **Use read-only inspection first:** Confirm the hypothesis with at least two independent evidence sources.
6. **Control the test:** Make only one bounded change and define the rollback command in advance.
7. **Measure service behavior:** Validate latency, throughput, errors, data consistency, authentication, and client experience.
8. **Persist correctly:** Apply successful changes through the supported configuration source rather than an ad hoc runtime command.
9. **Close the incident:** Document root cause, contributing conditions, corrective action, monitoring, and prevention.

## 9. Production cautions

- Do not run large TSDB dumps on a busy server without estimating I/O and output size.
- Protect debug bundles because they can contain configuration, endpoints, and runtime details.
- Validate secrets and endpoint access separately; syntax checks do not contact every target.
- Use CI rule tests and controlled reload rather than editing live configuration blindly.
- Replace all example users, paths, devices, addresses, ports, repositories, and services only after validation.
- Keep console or out-of-band access for firewall, bootloader, storage, authentication, and network changes.
- Back up data and configuration before destructive, recursive, or boot-critical commands.
