# dmesg in Linux — Important Commands with Examples

## 1. What is `dmesg`?

`dmesg` means **diagnostic message**.

It is a Linux command used to display messages generated by the **Linux kernel** and stored in the kernel ring buffer.

The kernel records messages related to:

- System boot
- CPU initialization
- RAM and memory errors
- Storage devices
- Filesystems
- USB devices
- Network interfaces
- Device drivers
- Kernel modules
- Hardware failures
- Out-of-memory events
- I/O errors
- SELinux and security-related kernel events
- Kernel warnings and crashes

Basic command:

```bash
dmesg
```

Example:

```bash
[root@server ~]# dmesg
[    0.000000] Linux version 5.14.0-427.el9.x86_64
[    0.524811] x86/cpu: VMX supported
[    1.983726] systemd[1]: System initialization started
[    3.214821] sd 2:0:0:0: [sda] 209715200 512-byte logical blocks
[    5.948287] XFS (sda2): Mounting V5 Filesystem
```

The value inside brackets is normally the time in seconds since the system booted.

---

## 2. Kernel Ring Buffer

Linux stores kernel messages in an in-memory area called the **kernel ring buffer**.

Important characteristics:

- It has limited size.
- New messages can overwrite old messages.
- It is recreated after every reboot.
- It mainly contains kernel-generated events.
- On systemd systems, persistent kernel logs may also be available through `journalctl`.

Check kernel logs from the journal:

```bash
journalctl -k
```

Check kernel logs from the current boot:

```bash
journalctl -k -b
```

---

## 3. Permission Requirements

On some systems, a normal user may receive:

```text
dmesg: read kernel buffer failed: Operation not permitted
```

Run it with root privileges:

```bash
sudo dmesg
```

Check the kernel restriction:

```bash
sysctl kernel.dmesg_restrict
```

Example:

```text
kernel.dmesg_restrict = 1
```

A value of `1` means unprivileged users are not allowed to read the kernel ring buffer.

# Important `dmesg` Commands

## 4. Display All Kernel Messages

```bash
dmesg
```

Example:

```bash
sudo dmesg
```

Use this when you want to review all currently available kernel messages.

---

## 5. Display Human-Readable Timestamps

```bash
dmesg -T
```

Example:

```bash
sudo dmesg -T
```

Sample output:

```text
[Tue Jul 28 09:22:18 2026] usb 2-1: new high-speed USB device
[Tue Jul 28 09:22:19 2026] usb-storage 2-1:1.0: USB Mass Storage device detected
```

### Important Note

`dmesg -T` converts boot-relative timestamps into wall-clock time. The converted time may be inaccurate if the system clock changed after boot because of NTP synchronization or manual time changes.

---

## 6. Display ISO-8601 Timestamps

```bash
dmesg --time-format=iso
```

Example:

```bash
sudo dmesg --time-format=iso
```

Sample output:

```text
2026-07-28T09:22:18,403221+05:30 usb 2-1: new high-speed USB device
```

This format is useful for incident reports and log correlation.

---

## 7. Display Only the Latest Messages

```bash
dmesg | tail
```

Example:

```bash
sudo dmesg | tail -n 20
```

This displays the last 20 kernel messages.

Use it immediately after:

- Connecting a USB device
- Adding a disk
- Loading a module
- Creating a network interface
- Experiencing an application or hardware failure

---

## 8. Follow New Kernel Messages in Real Time

```bash
dmesg --follow
```

Short option:

```bash
dmesg -w
```

Example:

```bash
sudo dmesg -w
```

The command waits and displays new kernel messages as they are generated.

Stop it with:

```text
Ctrl+C
```

Practical example:

```bash
sudo dmesg -w
```

Then connect a USB drive in another terminal or physically attach it. New device events will appear immediately.

---

## 9. Follow Messages with Human-Readable Time

```bash
dmesg -wT
```

Example:

```bash
sudo dmesg -wT
```

This is useful during live troubleshooting.

---

## 10. Display Only New Messages

```bash
dmesg --follow-new
```

Short option:

```bash
dmesg -W
```

Example:

```bash
sudo dmesg -W
```

Difference:

- `dmesg -w` first shows existing messages and then follows new messages.
- `dmesg -W` waits only for messages generated after the command starts.

---

## 11. Display Human-Readable Values

```bash
dmesg -H
```

Example:

```bash
sudo dmesg -H
```

`-H` enables human-readable output and normally pipes the result through a pager.

Navigation keys:

- `Space`: next page
- `b`: previous page
- `/text`: search
- `q`: quit

---

## 12. Prevent Output from Opening in a Pager

```bash
dmesg --nopager
```

Example:

```bash
sudo dmesg -H --nopager
```

This is useful inside scripts.

---

## 13. Display Raw Kernel Messages

```bash
dmesg --raw
```

Short option:

```bash
dmesg -r
```

Example:

```bash
sudo dmesg -r
```

Sample output:

```text
<6>[    4.824123] e1000e: Intel(R) PRO/1000 Network Driver
<3>[  812.293112] sd 3:0:0:0: I/O error
```

The number inside angle brackets represents the encoded kernel facility and priority.

---

## 14. Decode Facility and Priority

```bash
dmesg --decode
```

Short option:

```bash
dmesg -x
```

Example:

```bash
sudo dmesg -x
```

Sample output:

```text
kern  :info  : Linux version 5.14.0-427.el9.x86_64
kern  :err   : sd 3:0:0:0: I/O error
```

This makes severity analysis easier.

## 23. Kernel Message Priority Levels

| Level | Name | Meaning |
|---:|---|---|
| 0 | emerg | System is unusable |
| 1 | alert | Immediate action is required |
| 2 | crit | Critical condition |
| 3 | err | Error condition |
| 4 | warn | Warning condition |
| 5 | notice | Normal but important condition |
| 6 | info | Informational message |
| 7 | debug | Debug-level message |

# Searching Kernel Messages

## 26. Search Messages with `grep`

Syntax:

```bash
dmesg | grep -i "keyword"
```

The `-i` option performs a case-insensitive search.

---

## 27. Search for Errors

```bash
sudo dmesg -T | grep -i error
```

Better search:

```bash
sudo dmesg -T | grep -Ei "error|failed|failure|critical"
```

---

## 28. Search for Warnings

```bash
sudo dmesg -T | grep -i warning
```

Combined search:

```bash
sudo dmesg -T | grep -Ei "warn|error|fail|critical"
```

---

## 29. Search for Out-of-Memory Events

```bash
sudo dmesg -T | grep -Ei "oom|out of memory|killed process"
```

Example output:

```text
Out of memory: Killed process 5821 (java) total-vm:8245120kB
oom_reaper: reaped process 5821 (java)
```

Interpretation:

- The system encountered memory pressure.
- The kernel OOM killer selected and terminated a process.
- The affected process was `java` with PID `5821`.

---

# Saving and Exporting Output

## 55. Save `dmesg` Output to a File

```bash
sudo dmesg -T > /tmp/dmesg-output.txt
```

Verify:

```bash
ls -lh /tmp/dmesg-output.txt
```

Read it:

```bash
less /tmp/dmesg-output.txt
```

---

## 56. Save Only Errors and Warnings

```bash
sudo dmesg -T --level=err,warn > /tmp/dmesg-errors-warnings.txt
```

---

## 57. Append New Messages to a File

```bash
sudo dmesg -wT >> /var/tmp/dmesg-live.log
```

Stop with `Ctrl+C`.

For continuous production logging, prefer a properly configured logging service rather than leaving an interactive `dmesg` command running indefinitely.

---

## 58. Save Raw Output for Technical Analysis

```bash
sudo dmesg --raw > /tmp/dmesg-raw.log
```

# Clearing the Kernel Ring Buffer

## 59. Clear All Kernel Ring Buffer Messages

```bash
sudo dmesg --clear
```

Short option:

```bash
sudo dmesg -C
```

### Warning

This clears the current in-memory kernel message buffer. It does not necessarily remove messages already saved by `journald`, `rsyslog`, or another logging system.

Do not clear `dmesg` during an incident before collecting evidence.

---

## 60. Read and Then Clear the Buffer

```bash
sudo dmesg --read-clear
```

Short option:

```bash
sudo dmesg -c
```

Example:

```bash
sudo dmesg -c > /tmp/dmesg-before-clear.txt
```

This saves the current messages and then clears the kernel ring buffer.

Use it carefully.

---

# Kernel Console Log Level

## 61. Display Current Console Log Level

```bash
cat /proc/sys/kernel/printk
```

Example output:

```text
4 4 1 7
```

The first value represents the current console log level.

---

## 62. Set Console Log Level with `dmesg`

```bash
sudo dmesg --console-level warn
```

Short form:

```bash
sudo dmesg -n warn
```

Numeric example:

```bash
sudo dmesg -n 4
```

This controls which kernel messages are printed to the system console. It does not control which messages are stored in the ring buffer.

Use caution on production systems.

---

# Common Production Troubleshooting Examples

## 65. Disk Attached but Not Visible

Step 1: Check block devices:

```bash
lsblk
```

Step 2: Check recent kernel messages:

```bash
sudo dmesg -T | tail -n 50
```

Step 3: Search storage-related events:

```bash
sudo dmesg -T | grep -Ei "sd[a-z]|scsi|nvme|attached|capacity"
```

Step 4: Check errors:

```bash
sudo dmesg -T --level=err,warn
```

Possible output:

```text
sd 4:0:0:0: [sdb] Attached SCSI disk
```

---

## 66. USB Drive Not Detected

Run:

```bash
sudo dmesg -wT
```

Connect the USB device and observe the output.

Focused command:

```bash
sudo dmesg -wT | grep -Ei "usb|storage|sd[a-z]"
```

Possible issues:

- Insufficient power
- USB port failure
- Unsupported device
- Driver problem
- Device reset
- I/O error

---

## 67. Network Interface Goes Down

```bash
sudo dmesg -T | grep -Ei "link is down|link is up|nic|enp|ens|eth"
```

For a specific interface:

```bash
sudo dmesg -T | grep -i enp1s0
```

Also check:

```bash
ip -s link show enp1s0
ethtool enp1s0
journalctl -u NetworkManager
```

---

## 68. Server Rebooted Unexpectedly

Current `dmesg` only contains messages from the current boot, so it may not reveal the exact cause of the previous reboot.

Check current boot messages:

```bash
sudo dmesg -T --level=err,warn
```

Check boot history:

```bash
last -x | head -n 20
```

Check previous boot kernel logs:

```bash
sudo journalctl -k -b -1
```

Check previous boot errors:

```bash
sudo journalctl -b -1 -p err
```

Check for panic or watchdog events:

```bash
sudo journalctl -b -1 | grep -Ei "panic|watchdog|soft lockup|hard lockup|oom|thermal"
```

---

## 69. Process Was Killed Suddenly

Check OOM events:

```bash
sudo dmesg -T | grep -Ei "out of memory|oom-kill|killed process"
```

Also use:

```bash
sudo journalctl -k | grep -Ei "out of memory|oom-kill|killed process"
```

For systemd-managed applications:

```bash
systemctl status application.service
journalctl -u application.service
```

---

## 70. Filesystem Became Read-Only

```bash
sudo dmesg -T | grep -Ei "read-only|remount.*ro|filesystem error|i/o error"
```

Check filesystem-specific messages:

```bash
sudo dmesg -T | grep -Ei "xfs|ext4"
```

Do not immediately remount it read-write without identifying the underlying cause. A failing storage device can cause additional corruption.

---

## 71. High CPU or System Freeze

Search for lockups:

```bash
sudo dmesg -T | grep -Ei "soft lockup|hard lockup|hung task|rcu.*stall"
```

Search for hardware errors:

```bash
sudo dmesg -T | grep -Ei "mce|machine check|hardware error|thermal"
```

Check current resource usage:

```bash
top
vmstat 1
mpstat -P ALL 1
```

---

## 72. Kernel Module Failed to Load

Load the module:

```bash
sudo modprobe example_module
```

Check command status:

```bash
echo $?
```

Check recent messages:

```bash
sudo dmesg -T | tail -n 30
```

Search for the module:

```bash
sudo dmesg -T | grep -i example_module
```

Common causes:

- Module not found
- Symbol version mismatch
- Unsupported hardware
- Secure Boot rejection
- Missing firmware
- Invalid module parameter

---

## 73. Secure Boot Blocked a Module

Search:

```bash
sudo dmesg -T | grep -Ei "secure boot|verification failed|required key|module signature"
```

Possible output:

```text
Lockdown: modprobe: unsigned module loading is restricted
module verification failed: signature and/or required key missing
```

---

## 74. Application Segmentation Fault

```bash
sudo dmesg -T | grep -i segfault
```

Check systemd coredumps:

```bash
coredumpctl list
```

Inspect a specific coredump:

```bash
coredumpctl info PID
```

`dmesg` provides only limited crash information. Use `coredumpctl`, application logs, and a debugger for deeper analysis.

---

## 75. Storage Timeout or Reset

```bash
sudo dmesg -T | grep -Ei "timeout|reset|abort|i/o error|failed command"
```

For SAN or multipath environments:

```bash
sudo dmesg -T | grep -Ei "scsi|multipath|path.*down|timed out"
multipath -ll
```

```bash
sudo dmesg -T | grep -Ei "xfs.*error|ext4.*error|filesystem.*error|corrupt|read-only"
```

# `dmesg` Versus `journalctl`

| Requirement | Recommended command |
|---|---|
| Current kernel ring buffer | `dmesg` |
| Follow current kernel events | `dmesg -wT` |
| Current boot kernel logs | `journalctl -k -b` |
| Previous boot kernel logs | `journalctl -k -b -1` |
| Persistent and searchable logs | `journalctl` |
| Filter kernel errors by priority | `journalctl -k -p err` |
| Incident time-window analysis | `journalctl -k --since ... --until ...` |

Examples:

```bash
sudo journalctl -k
```

```bash
sudo journalctl -k -b
```

```bash
sudo journalctl -k -b -1
```

```bash
sudo journalctl -k -p err
```

```bash
sudo journalctl -k \
  --since "2026-07-28 09:00:00" \
  --until "2026-07-28 10:00:00"
```

### Main Difference

`dmesg` reads the current kernel ring buffer.

`journalctl -k` reads kernel messages collected by `systemd-journald`, which can be persistent when persistent journal storage is enabled.

Do not immediately:

- Clear the `dmesg` buffer

- Replace kernel parameters
- Reload drivers
- Reset storage paths

First collect evidence and establish the probable cause.

# Important Limitations of `dmesg`

1. The ring buffer has limited capacity.
2. Old messages can be overwritten.
3. Messages are normally lost after reboot.
4. `dmesg -T` timestamps can become inaccurate if system time changes.
5. It does not replace application logs.
6. It does not always provide full hardware health information.
7. Root privileges may be required.
8. Some messages are informational and do not indicate a real fault.
9. A kernel warning should be correlated with workload impact and other logs.
10. Previous-boot analysis usually requires `journalctl`, kdump, pstore, or external monitoring.

---

# Safety and Operational Best Practices

- Preserve the output before making changes.
- Use exact incident timestamps.
- Filter by severity, but also review surrounding context.
- Do not assume every line containing `error` is a production incident.
- Correlate kernel events with application, service, storage, and network logs.
- Use persistent journaling on production systems.
- Configure kdump for kernel-crash analysis.
- Do not clear the ring buffer during incident investigation.
- Avoid exposing complete logs publicly because they may contain hostnames, device details, memory addresses, or infrastructure information.

# Interview Questions

## What is `dmesg`?

`dmesg` displays messages stored in the Linux kernel ring buffer. It is mainly used to investigate boot, hardware, driver, storage, network, memory, and kernel-level events.

## Why can old messages disappear from `dmesg`?

The kernel ring buffer has limited capacity. When it becomes full, new kernel messages overwrite older entries.

## What is the difference between `dmesg` and `journalctl -k`?

`dmesg` reads the current in-memory kernel ring buffer. `journalctl -k` reads kernel messages collected by `systemd-journald` and can include persistent logs from previous boots.

## How do you monitor kernel messages in real time?

```bash
sudo dmesg -wT
```

## How do you find OOM-killer activity?

```bash
sudo dmesg -T | grep -Ei "oom|out of memory|killed process"
```

## How do you check previous-boot kernel messages?

```bash
sudo journalctl -k -b -1
```

## Why should `dmesg -C` be used carefully?

It clears the current kernel ring buffer and may destroy volatile evidence required for troubleshooting.
