# 127. logrotate

> **Scope:** Corporate/L3 Linux administration, incident troubleshooting, safe change execution, and interview preparation.

## 1. What it is

`logrotate` rotates, compresses, removes, mails, and post-processes log files according to policy. It is commonly started by a systemd timer or scheduled job.

## 2. Production importance

- Provides a repeatable method for diagnosing or controlling the relevant Linux subsystem.
- Produces evidence suitable for incident timelines, change records, problem management, and audit review.
- Encourages before-and-after measurement instead of unverified tuning or repair.
- Separates command success from actual application availability, security, and data integrity.

## 3. Package or kernel interface

- **Primary package/interface:** logrotate
- Check availability and installed version before relying on an option:

```bash
command -v logrotate 2>/dev/null || true
rpm -q PACKAGE_NAME 2>/dev/null || true
COMMAND --version 2>/dev/null || COMMAND --help
```

## 4. Core concepts

- Rotation policy can be size-based, time-based, or both depending on directives.
- The state file records the last rotation and prevents unintended repeated time-based rotations.
- `create` creates a new file after renaming the old file.
- `copytruncate` copies and truncates an open log but has a race window and should be avoided when the application can reopen logs.
- `postrotate` commonly signals or reloads the writer after renaming.
- Compression, retention, permissions, ownership, SELinux labels, and disk headroom must be planned together.

## 5. Important commands

| Command | Purpose | Risk |
|---|---|---|
| `logrotate --version` | Display the installed version. | Read-only |
| `sudo logrotate -d /etc/logrotate.conf` | Debug policy without rotating. | Read-only |
| `sudo logrotate -v /etc/logrotate.conf` | Run verbosely according to normal eligibility. | Log-maintenance operation |
| `sudo logrotate -f /etc/logrotate.conf` | Force all eligible definitions to rotate. | Broad forced rotation |
| `sudo logrotate -d /etc/logrotate.d/myapp` | Debug one application policy. | Read-only |
| `sudo logrotate -f -v /etc/logrotate.d/myapp` | Force one application policy. | Forced rotation |
| `sudo logrotate -s /tmp/logrotate.status /etc/logrotate.d/myapp` | Use an alternate state file for testing. | Test rotation |
| `systemctl status logrotate.timer` | Check timer state. | Read-only |
| `systemctl list-timers logrotate.timer` | Show the next and previous runs. | Read-only |
| `journalctl -u logrotate.service` | Review service-run logs. | Read-only |
| `lsof /var/log/myapp.log` | Identify the writer before choosing rotation behavior. | Read-only |
| `ls -lZ /var/log/myapp*` | Verify ownership, mode, and SELinux context after rotation. | Read-only |

## 7. Output interpretation

- Debug output explains whether a file needs rotation and which rule matched.
- A log can remain large because the state file says it rotated recently, the size threshold was not reached, or the path does not match.
- Disk usage may not fall if the application keeps a deleted rotated inode open.
- A failed `postrotate` can leave the application writing to the old inode.
- A missing new file often reflects an absent or incorrect `create` directive.

## 8. Corporate/L3 troubleshooting workflow

1. **Confirm impact:** Record affected applications, users, start time, error rate, latency, and business severity.
2. **Identify scope:** Determine whether the issue is host-wide, process-specific, filesystem-specific, network-path-specific, or limited to one namespace.
3. **Preserve evidence:** Save logs, configuration, counters, command output, package versions, and timestamps before changing state.
4. **Establish ownership:** Identify whether systemd, NetworkManager, firewalld, TuneD, udev, a backup scheduler, configuration management, or the application owns the setting.
5. **Use read-only inspection first:** Confirm the hypothesis with at least two independent evidence sources.
6. **Control the test:** Make only one bounded change and define the rollback command in advance.
7. **Measure service behavior:** Validate latency, throughput, errors, data consistency, authentication, and client experience.
8. **Persist correctly:** Apply successful changes through the supported configuration source rather than an ad hoc runtime command.
9. **Close the incident:** Document root cause, contributing conditions, corrective action, monitoring, and prevention.

## 9. Production cautions

- Use debug mode before forcing rotation.
- Do not use `copytruncate` for high-rate or audit-critical logs without accepting possible loss.
- Validate scripts in `prerotate` and `postrotate`; they run with elevated privilege in many deployments.
- Confirm free space because compression temporarily needs additional capacity.
- Replace all example users, paths, devices, addresses, ports, repositories, and services only after validation.
- Keep console or out-of-band access for firewall, bootloader, storage, authentication, and network changes.
- Back up data and configuration before destructive, recursive, or boot-critical commands.
