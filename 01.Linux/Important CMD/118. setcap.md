# 118. setcap

> **Level:** Linux Corporate/L3 administration and troubleshooting.

## 1. What it is

`setcap` assigns or removes file capabilities. It is used to grant specific privileged operations to an executable while avoiding full setuid-root privilege, but incorrect use can create a direct privilege-escalation path.

## 2. Why it matters in production

- Provides a repeatable method to inspect, validate, or control an important Linux subsystem.
- Produces evidence that can be attached to incident, change, problem, audit, and capacity records.
- Helps distinguish configuration, permission, kernel, service, network, storage, security, and application failures.
- Supports before-and-after validation rather than unmeasured configuration changes.

## 3. Package and availability

- **Primary package/interface:** libcap
- Check command availability:

```

- Read the installed manual because options vary by distribution and release:

```

## 4. Core concepts

- Only regular executable files on a supporting filesystem can use file capabilities as intended.
- The most common assignment form is `cap_name=ep`.
- Multiple capabilities are comma-separated.
- An empty capability string removes assigned capabilities.
- Package upgrades or file replacement can remove custom capabilities.
- systemd service capabilities are often better controlled with unit directives than by modifying application files.

## 5. Important commands

| Command | Purpose | Operational risk |
|---|---|---|
| `sudo setcap cap_net_bind_service=ep /opt/myapp/bin/server` | Allow binding privileged ports. | Security-sensitive permission change |
| `sudo setcap cap_net_raw=ep /opt/lab/pinglike` | Grant raw-socket capability in a lab. | Security-sensitive permission change |
| `sudo setcap 'cap_chown,cap_dac_override=ep' /opt/lab/tool` | Assign multiple capabilities. | High-risk permission change |
| `sudo setcap -r /opt/myapp/bin/server` | Remove all file capabilities. | Permission change |
| `sudo setcap '' /opt/myapp/bin/server` | Clear file capabilities using an empty set. | Permission change |
| `sudo setcap -v cap_net_bind_service=ep /opt/myapp/bin/server` | Verify that a capability assignment matches. | Read-only |
| `getcap -v /opt/myapp/bin/server` | Display the resulting capability. | Read-only |
| `sudo getcap -r /opt /usr/local 2>/dev/null` | Audit custom software trees. | Read-only |
| `systemctl show myapp -p CapabilityBoundingSet -p AmbientCapabilities -p NoNewPrivileges` | Inspect systemd capability controls. | Read-only |
| `sudo setcap cap_setuid=ep /path/to/file` | Example of a dangerously powerful assignment; do not use in production. | Critical-risk example |

## 7. How to interpret the output

- A successful command can still be ineffective if a process bounding set excludes the capability.
- Capabilities such as `CAP_SYS_ADMIN`, `CAP_SYS_PTRACE`, `CAP_DAC_OVERRIDE`, `CAP_SETUID`, and `CAP_SYS_MODULE` are highly sensitive.
- File replacement changes the inode and normally removes the prior xattr.
- The owning filesystem must preserve the `security.capability` attribute.
- Check the executed path, because wrappers or symlinks can cause a different file to run.

## 8. L3 troubleshooting workflow

1. **Define impact:** Identify the affected service, users, start time, scope, and business symptom.
2. **Preserve evidence:** Capture relevant logs, configuration, counters, timestamps, versions, and current state.
3. **Confirm ownership:** Determine whether systemd, NetworkManager, authselect, firewalld, policy, automation, or another manager owns the configuration.
4. **Use read-only checks first:** Avoid changing state before the failure mode is understood.
5. **Correlate adjacent layers:** Check process, kernel, filesystem, network, DNS, time, identity, audit, and SELinux evidence as appropriate.
6. **Form one hypothesis:** State what evidence supports it and what observation would disprove it.
7. **Make one controlled change:** Use a maintenance window, backup, console path, and rollback command.
8. **Validate service metrics:** Confirm application latency, error rate, authentication, data integrity, and logs—not only command success.
9. **Restore or persist:** Roll back failed experiments and make successful changes through approved configuration management.
10. **Document RCA:** Record root cause, contributing factors, corrective action, prevention, and monitoring.

## 9. Production cautions

- Never assign capabilities to user-writable executables.
- Avoid `CAP_SYS_ADMIN` unless the application is effectively trusted as root.
- Document capabilities in deployment automation so upgrades do not silently change behavior.
- Prefer systemd sandboxing, dedicated ports, reverse proxies, and least-privilege service design.
- Never copy example users, paths, ports, addresses, or devices into production without validation.
- Commands that change credentials, access, labels, firewall rules, packages, audit rules, or services require change control.
- Keep an independent administrative path for SSH, PAM, firewall, DNS, and authentication work.

## 10. Quick practice lab

1. Compile or use a harmless lab executable.
2. Assign `cap_net_bind_service`.
3. Test binding a low port as a non-root user.
4. Inspect process capability masks.
5. Remove the capability and confirm the operation fails.
